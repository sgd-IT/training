# 代码注释规范（自然口语风格）

核心原则：**注释是写给"人"看的，不是写给"机器"看的。** 用跟同事口头解释的语气写——不端着、不堆术语、不重复代码。

使用本 skill 时，输出开头标注【项目名·code-comment-style】，项目名取当前工作区根目录名（如 hc-standard、remote-monitor）。

## 何时使用

- 写任何新代码并附带注释时（行内、方法头、类头、SQL、脚本都算）
- 补充、修改、重构既有注释时
- 检查注释质量、统一注释风格时

## 六个做法

### 1. 解释"为什么"，不解释"是什么"

代码本身能看出来的东西不复述，注释只补代码看不出的意图和业务原因。

```java
// 反例：方法名已经说了，注释纯复述
// 获取用户列表
List<User> users = userMapper.selectAll();

// 正例：补的是代码看不出的业务原因
// 这里必须全量查，因为下游推送需要比对增量，不能漏人
List<User> users = userMapper.selectAll();
```

### 2. 长逻辑提前剧透

复杂方法开头用一句话概括整体流程（如"校验 → 扣库存 → 发通知"），让读者先拿到地图再读细节。

```java
// 整体流程：校验 → 扣库存 → 发通知
// 通知失败不回滚订单，交给重试任务兜底
public void placeOrder(OrderReq req) {
```

```js
// 流程：拉告警列表 → 按设备分组 → 未读置顶
async function loadAlerts() {
```

### 3. 标记坑位带点情绪

历史遗留、临时方案、反直觉写法，直接用大白话写清楚"别动"和原因，比冷冰冰的 WARNING 更有效。

```java
// 别动！这里 sleep 500ms 是等上游缓存过期，删了会偶发读到旧价格
Thread.sleep(500);

// 临时方案：设备 SDK 有内存泄漏，等上游修复后换官方重连（预计 2026-11）
scheduledRestart();
```

要点：**带上原因和期限**，否则后人会把它当垃圾代码"顺手优化"掉。

### 4. 复杂计算分步解说

多步公式、链式调用，在上方用自然语言拆解每一步在算什么。

```java
// 积分 = 基础分 × 倍率 + 签到奖励，其中：
// 1. 基础分：每消费 1 元记 1 分，单日封顶 500
// 2. 倍率：会员日 2 倍，其余 1 倍
// 3. 签到奖励：连续 7 天 +50，封顶 +200
int points = base * rate + bonus;
```

### 5. TODO 具体可追溯

只写"TODO: 优化"等于没写。格式：**改什么 + 为什么现在没改 + 什么条件/时间改**。

```java
// 反例
// TODO: 优化

// 正例
// TODO(设备 SDK 升到 v2.3 后)：改用批量查询接口。
// 现在逐条查是因为 SDK 批量模式有丢包 bug，暂时用缓存顶着（见 ALERT-231）
```

### 6. 控制密度

不是每行都要注释，只在"不看注释容易误解"的地方写。判断标准：**删掉这条注释，读者会不会误解这段代码？**

```java
// 反例：全是复述
int a = 1; // a 等于 1
a++;       // a 自增

// 正例：只在反直觉处写一行
cache.put(key, EMPTY); // 缓存空值防穿透，TTL 在上一行单独设置
```

## 用户风格硬约束（优先级高于上面六条）

用户的个人风格是**极简短行**。与上面六条通用写法冲突时，以本节为准。

- **常量 / 字段 Javadoc 一律单行**：`/** 统计缓存新鲜期：盖住值守大屏 60 秒的轮询周期 */`，不写 `<p>` 分段。
- **方法 Javadoc 一两句收住**：最多「做什么 + 一条关键结论」，要参数就补 `@param`；不展开流程推演、不写 `<p>` 段落。
- **已有的单行 Javadoc 不允许扩写成多行**。改写只在原行内动字，不得把一行拆成带 `<p>` 的多行块。这是用户明确问责过的点（原话“不符合我的风格”）。
- **行内注释 15 字以内**：用「取当前时间戳」「清掉窗口外成员」「逐个预热」这类口语短句，同一动作全链路用同一措辞。
- **类头一句功能**，最多再加一行关键结论，仅此而已。

风格样本：`FireSpaceServiceImpl.createFireSpace`、`RemoteControlCodeServiceImpl`、`FireDashboardServiceImpl` 的常量区。

例外：只有用户字面要求「详细说明 / 写清背景」时才展开多行；不能以「这块逻辑复杂所以多写点」为理由自行加长。

## 写注释前自问三句

1. 删掉这条注释，读者会不会误解这段代码？不会 → 别写。
2. 我是在复述代码，还是在解释原因？复述 → 删掉或改成"为什么"。
3. 半年后新同事看到这条，能明白当初为什么这么做吗？不能 → 补上业务背景或坑位原因。

## 检查 / 改写既有注释

1. 通读目标文件：先看方法级注释，再看行内注释。
2. 逐条对照上面六个做法，标记问题类型：废话复述 / 缺"为什么" / 坑位未预警 / TODO 模糊 / 密度过高。
3. 批量改写时只动注释、不动代码逻辑。
4. 按下方格式输出改写建议：

```markdown
## 注释检查：<文件路径>
- L42：废话复述｜现：`// 获取用户列表`｜建议：改为解释"必须全量查"的业务原因
- L88：坑位未预警｜现：无注释｜建议：标注 sleep 500ms 的原因和删除后果
```

## 语言与格式约定

- 注释语言跟随文件既有注释习惯（本项目群默认中文，英文代码库混写时跟随周边）。
- 单行注释说清一件事就收，硬上限一行；确实要分步就用「1. 2. 3.」编号短句，不写散文式长段。
- 结构化注释（`[决策点]`、`[决策锚点]` 等）按对应 skill 或项目模板的格式写，本规范管其余日常注释的语言风格。
