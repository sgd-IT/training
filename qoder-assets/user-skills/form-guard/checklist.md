# 六层检查清单

每项给判定口径与默认分级。判定顺序：B → C → D → F → E（先看有没有人拦，再看拦得住看不懂，最后看留不留脏数据）。

## A. UI 标识层

| 检查项 | 判定口径 | 默认分级 |
|---|---|---|
| 必填字段有红星 | `el-form-item` 的 `prop` 命中 rules 里 `required: true`（两处要同时成立） | P1 |
| placeholder 说清"填什么" | "请填写停用原因，如：装置检修"这类，不是"请输入原因" | P1 |
| 选填字段标"选填" | 选了不填也允许的字段要标出来，不留空 | P2 |
| 格式约束写在字段附近 | 长度、格式说明在字段下方或 placeholder，不只写在弹窗标题 | P2 |
| 校验失败红字落在字段下方 | 报错位置 = 出错的输入框 | P1 |
| prop 与 rules key 对得上 | key 对不上规则静默失效，属于 B 层问题，UI 上表现为"填了没反应" | P0 |

## B. 前端校验层

| 检查项 | 判定口径 | 默认分级 |
|---|---|---|
| 每个必填字段在 rules 中有规则 | rules 里能找到该 `prop`，且含 `required: true` 与 `trigger` | P0 |
| 提交方法真的调用了 validate | 提交方法内有 `this.$refs.xxx.validate(...)` 且不通过直接 return | P0 |
| 多个表单不共用一份 rules | 主表单与弹窗字段不同就必须拆开，否则校验互相串味 | P1 |
| 校验失败聚焦首个错误字段 | 提交后滚动/聚焦到第一个错误项 | P2 |
| 提交按钮有 loading 与防重复提交 | 提交中置灰 | P2 |

## C. 后端拦截层

| 检查项 | 判定口径 | 默认分级 |
|---|---|---|
| Service 入口做必填校验 | 方法开头就有空值判断，且在所有写操作之前 | P0 |
| App/OpenAPI 同样校验 | 绕过页面的入口也拦得住 | P0 |
| 校验文案是业务语言 | 见 SKILL.md 文案口径表 | P0 |
| 抛业务异常而非运行时异常 | `ServiceException`；`RuntimeException` 会被全局处理器原样外泄 `e.getMessage()` | P0 |
| 参数注解带中文 message | `@NotBlank(message="请填写停用原因")`；不写 message 会弹 Spring 英文 | P0 |
| 校验不依赖前端 | 删掉前端规则，后端仍拦得住 | P0 |

## D. 错误文案层

| 检查项 | 判定口径 | 默认分级 |
|---|---|---|
| 无字段英文名/表名/类名 | 文案里不出现 `reason`、`stopTime`、`base_risk_unit_log` | P0 |
| 无 SQL、堆栈、框架异常原文 | 不出现 `SQLException`、`DataIntegrityViolation`、`null` | P0 |
| 外部平台报文已转译 | 返回给用户的是中文业务话术，原始报文另存运维字段 | P0 |
| 移动端接口异常是中文 | App 端对非中文消息统一弹"数据异常"，用户看不到真实原因 | P0 |
| 同一约束两种文案分开 | 人看的一版、运维看的一版，不要用同一句对付两种人 | P1 |
| 有可操作建议 | 告诉用户改成什么样 | P1 |
| 一句话，长度可控 | 能在 Toast/MessageBox 里一眼看完 | P2 |

## E. 反馈闭环层

| 检查项 | 判定口径 | 默认分级 |
|---|---|---|
| 成功提示 = 业务真成功 | 外部同步失败时不提示"操作成功" | P0 |
| 同步失败有独立提示 | 区分"已保存但同步失败"与"保存失败" | P1 |
| 提示贴着触发操作 | 失败提示出现在弹窗/表格附近，不是无关联的全局 Toast | P1 |
| 部分成功有中间态 | 批量操作区分全成功与部分失败 | P1 |
| 同步状态与结果落库正确 | 失败分支落 `sync_status`/`sync_result`，且失败码判定覆盖全部失败码（不能只判 500） | P1 |

## F. 副作用与事务层

| 检查项 | 判定口径 | 默认分级 |
|---|---|---|
| 校验先于写库/推送/改状态 | 校验代码位置在副作用之前 | P0 |
| 多步写操作在同一事务内 | 关键步骤有 `@Transactional` | P0 |
| 不出现"状态改了记录没存" | 失败后数据处于半改状态即违规 | P0 |
| 抛异常前确认事务边界 | 抛异常会回滚时，先想清楚记录到底该不该留 | P1 |
| 外部调用失败不吞异常 | 失败结果必须落到状态字段或抛出 | P1 |

## 快速判定路径

1. 用户说"没告诉我不能填" → 查 A + B。
2. 用户说"报一堆看不懂的" → 查 D（文案），再看是谁抛的（C）。
3. 用户说"提示成功了其实没成功" → 查 E。
4. 用户说"数据乱了" → 查 F。
5. 用户说"填了没反应" → 先查 B 里的 prop/rules key 是否对得上。
