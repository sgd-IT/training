# 表单守卫（校验、文案与反馈闭环）

使用本 skill 时，输出开头标注【项目名·form-guard】，项目名取当前工作区根目录名（如 hc-standard、remote-monitor）。

分工边界：操作摆放与可点性走 `frontend-interaction-design`；代码冗余走 `code-conciseness-check`；设计决策留痕走 `decision-driven-coding`；配色与视觉精度走 `frontend-design` / `frontend-visual-craft`。本 skill 只管三件事：**输入约束落在哪一层、错误长什么样、结果有没有闭环**。

> 为什么三件事合一个 skill：用户的一句抱怨（"报一堆看不懂的，也没说不能为空"）天然同时包含文案与必填标识两类缺陷，拆成两个 skill 会导致体检时只查一半、还容易重复输出。校验、文案、闭环共用同一条链路（视图表单 → 前端 API → Controller → Service → 外部调用）和同一份输出模板，拆开没有收益。

## 内核

"用户看不懂"不是文案写得丑，是**约束没落到用户面前**，于是错误由最后碰到的组件抛出——通常是外部平台、数据库或框架异常，技术报文被直接甩给用户。

按顺序判三件事，缺一件就会复发：

1. **可预防性**：必填在用户点提交之前就告诉他了吗？
2. **拦截点**：错误由业务代码抛，还是由外部依赖抛？外部抛 = 文案不可控。
3. **副作用顺序**：校验通过之前状态改了吗？改了 = 半成品数据。

## 两种模式

| 你在做什么 | 走哪条 | 产出 |
|---|---|---|
| 写/改表单、接口、加必填项 | 模式 A：落地 | 按落点顺序直接改代码 |
| 用户投诉"不人性化/看不懂/没提示必填/提示成功了其实没成功" | 模式 B：审查 | 分级问题清单 + 前后端分区落点 |

### 模式 A：落地顺序

1. **先定约束**：哪些必填、哪些选填、格式与取值范围，落到字段旁的文案里，别只存在代码里。
2. **UI 标识**：必填 label 出红星（Element UI/Plus：`el-form-item` 的 `prop` 命中 rules 里的 `required: true` 才自动出星），placeholder 写清"填什么"，选填字段标"选填"。
3. **前端规则**：`rules` 与表单一一对应，多个表单不要共用一份；提交前必须 `this.$refs.xxx.validate()`，不通过就不发请求。`prop` 与 rules 的 key 不一致会**静默失效**，规则写了等于没写。
4. **后端拦截**：Service 方法**第一段**做必填校验，抛业务异常，文案用业务语言。前端校验是体验，后端校验才是契约——App/OpenAPI 直接调后端，前端规则拦不住。
5. **写文案**：同一条约束，UI 上写给人看（"请填写停用原因"），日志/同步结果列写给运维看（原始报文），两者分开，别用同一句话对付两种人。
6. **副作用顺序**：写库、推外部、改状态全部放在校验通过之后；多步写操作放同一事务，失败回滚。
7. **反馈闭环**：成功提示必须等于业务真成功。外部同步失败要分开表达"已保存，同步失败"，不能一律报成功。

### 模式 B：审查流程

1. **先读全链路**：视图表单 → 前端 API → Controller → Service → 外部调用。只看一处必然下错结论。
2. **按 [checklist.md](checklist.md) 六层逐项过**，每项都有判定口径。
3. **分级**：
   - P0 阻断：必填无任何约束、报错是原始技术报文、失败已产生副作用、外部调用失败却提示成功。
   - P1 明显摩擦：只有后端拦或只有前端拦、placeholder 不说清填什么、同步结果不落库、提示不贴着出错操作。
   - P2 打磨：文案啰嗦、缺"选填"标识、校验失败不聚焦首错字段。
4. **输出报告**按下面模板，一条一行说清"哪里、什么问题、怎么改"，不写理论科普。
5. **不硬凑**：没违反就不报，同一问题只报一次。

## 四条红线

违反这些先改，别谈优化：

- **必填三层不一致**：UI 标识、前端规则、后端拦截，缺一层就是体验漏洞（后端那层不能少）。
- **外部依赖抛错给用户**：平台报文、SQL、框架异常、字段英文名，一律转译成业务语言再返回。
- **校验在副作用之后**：状态先改、记录后存，失败留下半成品。
- **假成功**：外部同步失败、批量部分失败，仍提示"操作成功"。

## 文案口径

| 场景 | 别写 | 写成 |
|---|---|---|
| 必填为空 | `reason 不能为空` / `「原因」不能为空` | `请填写停用原因` |
| 格式错 | `手机号格式错误` | `电话格式有误，应为11位手机号(如13800138000)` |
| 时间先后 | `activationTime must after stopTime` | `启用时间必须晚于停用时间` |
| 外部失败 | 平台原始报文、SQL 报错、堆栈 | `保存失败，数据同步未完成，请稍后重试` |
| 状态冲突 | `状态不匹配` | `该单元已停用，无需重复操作` |
| 选中项为空 | `操作失败` | `请先选择要处理的记录` |

三条规则：说人话、说清怎么改、不出现字段英文名/表名/类名。

## 本项目技术栈落点（RuoYi / Element UI）

先记这几条，否则文案改了也不生效：

- **Spring 参数校验**：`@Valid` + `@NotBlank(message="请填写停用原因")`。RuoYi 的 `GlobalExceptionHandler` 对 `BindException` / `MethodArgumentNotValidException` 取 `getDefaultMessage()`，所以**不写 message 就会把 Spring 英文（`must not be null`）直接弹给用户**。
- **运行时异常**：`RuntimeException` / `Exception` 分支是 `AjaxResult.error(e.getMessage())`，异常原文会原样外泄——业务代码里 `throw new RuntimeException(sqlMsg)` 等于把 SQL 甩到页面上。业务异常统一抛 `ServiceException`。
- **Element 静默失效**：`el-form-item` 的 `prop` 与 rules 的 key 对不上，规则不触发也不报错；`required` 若写在 `el-form-item` 上但 `rules` 里没有 `required: true`，红星和校验可能不一致。判定时两处都要看。
- **移动端兜底**：App 端对服务端返回的非中文错误消息统一弹"数据异常"，真实原因只在服务端日志里。所以移动端接口的异常**必须**是中文业务异常，否则用户看到的就是"数据异常"四个字。
- **同步状态**：外部推送结果要落 `sync_status`（0未同步/1已同步/2同步失败）与 `sync_result`，失败判定要覆盖全部失败码，不要只判某一个码。

## 自查线索（先 grep 再下结论）

```bash
# 前端：字段配了 required 但提交方法里没有 validate → 规则形同虚设
grep -rn "required: true" <视图目录>
grep -rn "\.validate(" <视图目录>
grep -rn "el-form-item" <视图目录>          # 看哪些字段没标 required
grep -rn "prop=" <视图目录>                 # prop 与 rules key 是否对得上

# 后端：Service 入口有没有必填校验
grep -rn "StringUtils.isBlank\|StringUtils.isEmpty" <service目录>
grep -rn "throw new ServiceException" <service目录>
grep -rn "throw new RuntimeException" <service目录>   # 会把原文外泄

# 原始报文透传风险
grep -rn "getStr(\"msg\")" <service目录>
```

命中不等于有问题，要读上下文确认再下判断。
