# SQL 守卫（MySQL 规范落地与审查）

使用本 skill 时，输出开头标注【项目名·sql-standards】，项目名取当前工作区根目录名。

分工边界：运行时性能归因（耗时占比、profiling、实测复现）属于诊断，本 skill 只给判定口径与改法；代码重复与冗余走 `code-conciseness-check`；跨模块重构取舍走 `decision-driven-coding`；DDL 的**执行**走项目的数据库工具/工单流程，本 skill 不代你动生产库。

## 内核

规范不是背条文，是保证三件事：**可读**（别人看得懂字段含义）、**可控**（不会拖垮数据库）、**可演进**（以后改得动）。

落到判定上只有三个问题：

1. 这条 SQL 会读多少行？（`rows` 与 `Handler_read_next`，不是看有没有 `key`）
2. 这次变更会锁多少行、锁多久？（能否低峰、能否在线 DDL）
3. 三个月后要加字段、加索引、改语义，现在这个结构挡不挡路？

## 第 0 步：先探测项目现状（不能跳）

规范是通用的，**列名和写法不是**。任何建表、加列、写查询之前，先把下面四件事查清，否则会产出"改不了的建议"。

1. **照抄同库既有表**：挑 2~3 张同业务域的表看 `SHOW CREATE TABLE`，现有风格就是本项目的约定。
2. **确认六个口径**：逻辑删除列、创建/更新时间列、审计字段（创建人/更新人）、多租户列、索引命名、字符集与排序规则。
3. **确认数据库版本**：5.7 还是 8.0，决定能不能用 CTE、窗口函数、`INSTANT` 加列、`EXPLAIN ANALYZE`。
4. **确认迁移脚本位置与命名**：仓库里已有迁移文件怎么放、怎么编号，就是约定（常见 `V20260101__desc.sql`、`migration/`、`db/changelog/` 等）。

```sql
-- 六口径一次查全（把 <表名> 换成同业务域的既有表）
SELECT COLUMN_NAME, COLUMN_TYPE, IS_NULLABLE, COLUMN_DEFAULT, COLUMN_COMMENT
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = '<表名>'
  AND COLUMN_NAME IN ('deleted', 'is_deleted', 'create_time', 'update_time',
                      'created_at', 'updated_at', 'creator', 'updater', 'tenant_id');

SELECT VERSION();

-- 索引命名习惯
SELECT DISTINCT INDEX_NAME FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = '<表名>';
```

三条判定规则（比后面所有条文都优先）：

- **新表 / 新列 / 新索引**：跟同库现有口径走。库里已经是 `deleted` 就继续写 `deleted`，不要新开 `is_deleted`——一致性优先于"更符合规约"。
- **存量列名与类型**：不为了"对齐规约"去改。改名会三层同时失配（实体映射与注解、手写 SQL、前端字段/导出列），收益为零。只在"这张表本来就要动"时顺带纠正。
- **评审报告**：存量遗留口径只写一句现状说明，**不计入问题项**；只有本次改动新引入的才算分。

## 两种模式

| 你在做什么 | 走哪条 | 产出 |
|---|---|---|
| 写建表脚本、加字段、加索引、写查询 | 模式 A：落地 | 按顺序直接给出 SQL 与迁移脚本 |
| review SQL / DDL / 排查"索引没生效、分页慢" | 模式 B：审查 | 分级问题清单 + 改法 |

### 模式 A：落地顺序

1. **先定查询再定表**：哪些列进 WHERE、ORDER BY、GROUP BY / 统计，先写出来。索引从查询倒推，不要先建完表再补索引。
2. **定字段**：最小可用类型（状态用 `TINYINT`、布尔用 `TINYINT`、金额用 `DECIMAL`），能 `NOT NULL` 就 `NOT NULL` 并给默认值，每列必须有 COMMENT 说清单位与取值。
3. **定主键**：`id BIGINT` 自增（确有分布需求才上雪花），不用 UUID 做聚簇主键。关联列命名 `xxx_id`，**自己建索引**，不建物理外键。
4. **定索引**：单表 ≤5 个；联合索引等值列在前、区分度高的在前、范围列最后；唯一业务约束必须 `uk_` 兜住，不能只靠代码判重。
5. **写查询**：只列需要的列；条件列不包函数、不做运算、不隐式转换；深分页走游标；`IN` ≤1000；`JOIN` ≤3 张表。
6. **写迁移**：按第 0 步探到的目录与命名落文件，必须可重复执行，末尾带验证 SQL；与对应代码同批提交。
7. **上线前把关**：EXPLAIN 看 `type / rows / Extra`；大表加列加索引先评估锁表风险与执行窗口。

### 模式 B：审查流程

1. **先分清对象**：建表脚本 / 迁移脚本 / Mapper XML / `@Select` 注解 / Wrapper 链式条件。对象不同能查的问题不同（Wrapper 看不到执行计划，先看条件形态）。
2. 按 [checklist.md](checklist.md) 五层逐项过，每项都有判定口径。
3. **分级**：
   - P0 阻断：线上全表扫描、无 LIMIT 的全表更新/删除、索引完全失效、DDL 会锁表、SQL 拼接。
   - P1 明显风险：深分页、`COUNT(*)` 无覆盖索引、低区分度单列索引、`SELECT *`、隐式类型转换。
   - P2 打磨：命名不规范、缺 COMMENT、类型过宽、多余索引。
4. 按下面模板输出，一条一行说清"哪里、什么现象、为什么、怎么改"，不写理论科普。
5. **不硬凑**：没违反就不报，同一问题只报一次，存量遗留口径不算问题。

## 规范速查（通用基线，新代码默认按此写）

### 一、命名

| 对象 | 规则 | 例 |
|---|---|---|
| 表名 | 小写 + 下划线，单数，有业务含义；禁驼峰、禁拼音、禁 `test1`/`tmp_` 进生产 | `user_order` |
| 普通字段 | 小写 + 下划线 | `handle_status` |
| 主键 / 外键 | `id` / `xxx_id` | `device_id` |
| 布尔 | 全库统一一套：`is_xxx` 或项目既有的逻辑删除列；**不混用两套** | `is_deleted` |
| 状态 | `status`，取值含义写进 COMMENT | `status TINYINT` |
| 时间 | 全库统一一套：`create_time/update_time` 或 `created_at/updated_at`，不混用 | `create_time` |
| 索引 | `idx_字段` / `uk_字段`，主键不命名；命名风格跟项目既有索引 | `uk_tenant_space` |

### 二、建表与字段

- 引擎 `InnoDB`；字符集 `utf8mb4`；排序规则与同库既有表一致（跨表 JOIN 时 collation 不一致会触发隐式转换、索引失效）。
- 每表必须有主键；不用 UUID 做聚簇索引主键（页分裂、写入放大）。
- 字段尽量 `NOT NULL` + 默认值。NULL 会让 `COUNT`、比较、索引统计和 `IS NULL` 兜底全部变复杂。
- 金额 `DECIMAL`，禁 `FLOAT/DOUBLE`；枚举状态 `TINYINT`；时间 `DATETIME`。
- 业务表带逻辑删除列 + 创建/更新时间列 + 审计人列（列名按第 0 步探测结果）。
- 单表字段 ≤30~50，过宽就垂直拆；`TEXT/BLOB` 慎用，必须用就拆扩展表。
- 行数预期破 500 万~1000 万先规划分区或分表，别等慢了再想。

### 三、索引

- 不是越多越好：单表 ≤5 个，每个索引都加重写开销。
- 最左前缀：`(a,b,c)` 跳过 `a` 直接失效；等值在前、排序中间、范围最后。
- 低区分度列（性别、省份、`status`）不单独建索引，放联合索引尾部才有意义。
- 索引列上禁函数、禁隐式转换（`varchar` 不加引号、字符集/collation 不一致都会失效）。
- 用不到的老索引定期清（慢日志 + `performance_schema.table_io_waits_summary_by_index_usage` 找零使用率）。

**新增索引前必须过一遍「写侧成本」**：写频繁不取消索引资格，只是把"近似免费"变成"要算账"。

| 判据 | 偏向加 | 偏不加 |
|---|---|---|
| 读写比 | 读 ≫ 写 | 写 ≫ 读，且读侧没有热查询 |
| 写操作类型 | 顺序 INSERT 追加 | 高频 UPDATE 命中索引列 |
| 列可变性 | 写一次不再变（编码、key） | 状态列频繁翻转（`handle_status`） |
| 索引数量边际 | 表上只有 PK + 0~1 个 | 已有 5 个以上还要加第 6 个 |
| 能否复用/覆盖 | 能并入现有索引最左前缀，或做覆盖索引 | 只能单独立一条低区分度索引 |
| 能否替代 | 无法用缓存、冗余字段解决 | 配置类数据可缓存，名称类可冗余 |

三条容易漏的反向事实：

- **写频繁的表反而更需要索引管住锁粒度**：`UPDATE ... WHERE x = ?` 无索引 → 全表扫 → 行锁退化成大范围锁，并发写直接互相阻塞。索引不只是加速读。
- **贵的是随机，不是频次**：自增主键 + 顺序 INSERT 的索引维护是顺序追加；UUID 主键、无序二级索引才是页分裂的来源。
- **唯一约束类索引不能用性能理由砍掉**，那是数据正确性问题。

写频繁但确实不该硬加索引时，按顺序试替代：合并进现有索引列序 → 覆盖索引一条顶多条 → 索引建在读库 → 冗余字段换 JOIN → 配置类数据走进程内缓存。

口诀：**"写频繁"降低的是索引性价比，不取消索引资格；能一票否决的只有「低区分度 + 写密集 + 读侧无热查询」三条同时成立。**

### 四、SQL 编写

- 禁 `SELECT *`：减少回表与传输，也避免加字段后破坏缓存/序列化契约。
- 深分页改游标：`LIMIT 100000,20` → `WHERE id > #{lastId} ORDER BY id LIMIT 20`（前端要跳页则不能改，改建覆盖索引 + 精简 COUNT）。
- 条件列不做运算/函数：`DATE(create_time)='2026-01-01'` → `create_time >= '2026-01-01' AND create_time < '2026-01-02'`。
- 时间范围一律左闭右开，不用 `BETWEEN '... 00:00:00' AND '... 23:59:59'`（丢毫秒尾巴）。
- `IN` ≤1000；大批量走临时表或分批，不要一条 SQL 塞几万值。
- 批量 `INSERT` 多值一次提交，单次控制在 1~5MB。
- `JOIN` ≤3 张表，驱动表要小；能应用层聚合就少 JOIN，用冗余字段换 JOIN。
- `OR` 改写 `UNION ALL`；`!=`、`NOT IN`、`LIKE '%abc'` 前导模糊基本等于全表扫。
- 线上禁 `ORDER BY RAND()`，禁不带 `LIMIT` 的全表查询/更新/删除。
- 一律参数化，禁字符串拼 SQL。

### 五、变更与安全

- DDL 放低峰；大表加列加索引用在线工具或 8.0 `INSTANT`（先用第 0 步的版本结论确认）。
- 上线前必须 EXPLAIN，盯 `type`（`ALL`/`index` 要能解释）、`rows`、`Extra`（`Using filesort`、`Using temporary`、无 `Using index` 即回表）。
- 事务短小：事务里不调远程接口、不发短信、不做重计算；显式提交，避免长事务撑爆 undo log。
- 敏感字段（手机号、身份证）加密或脱敏；应用账号不用 `root`，权限按最小原则。
- 慢 SQL 阈值 1s（核心链路 500ms），接监控 + 定期治理慢日志。

## 六条红线

违反先改，别谈优化：

- **无 `LIMIT` 的全表 `UPDATE`/`DELETE`**：一次误操作锁全表。
- **SQL 拼接**：注入风险 + 执行计划无法复用。
- **多租户表的手写 SQL 漏租户条件**：这是数据泄漏，不是性能问题（拦截器只兜得住标准链式查询，原生 SQL / 手写 UNION / 白名单表都要自己写）。
- **索引列上套函数/隐式转换**：索引白建，且不报错。
- **DDL 无锁表评估直接上生产**：大表加列加索引可能长时间阻塞写入。
- **唯一约束只靠代码判重**：并发下必然产生脏数据。

## 反例速查

| 现象 | 原因 | 改法 |
|---|---|---|
| 索引建了却不生效 | 类型不匹配隐式转换、字符集/collation 不一致、函数包字段 | 对齐类型与 collation，条件改区间 |
| `COUNT(*)` 很慢 | 无覆盖索引，走聚簇索引全表 | 建覆盖索引，或改增量计数/缓存 |
| 更新量不大却锁全表 | 条件未命中索引，行级锁退化为表锁 | 条件列建索引 |
| 分页越翻越慢 | 深分页回表成本高 | 游标分页 `WHERE id > lastId` |
| EXPLAIN 有 key 但接口仍秒级 | 分页的 `COUNT` 在回表 + `filesort` | 列表与 COUNT 分开计时，补覆盖索引 |
| 脚本查不到数据也不报错 | 布尔/删除列字面量与列类型不匹配（`0` vs `b'0'`） | 先 `SHOW COLUMNS` 再写字面量 |
| 跨表 JOIN 突然不走索引 | 两表 collation 或字段类型不一致 | 统一字符集/排序规则与字段类型 |
| 写频繁的表索性不建索引 | 更新/删除条件无索引 → 行锁退化成大范围锁，写并发被自己拖死 | 按写侧判据核算，保留命中写条件的索引 |
| 小表关联列没索引却不痛不痒 | 被驱动表退化成 Block Nested Loop，把驱动表的 `ORDER BY … LIMIT` 索引顺序打掉 | 关联列建索引，或改「先定页再关联」 |

## 自查线索（先 grep 再下结论）

```bash
# 危险语句
grep -rn "SELECT \*" <mapper目录|迁移脚本目录>
grep -rn "UPDATE .*SET" <迁移脚本目录>          # 看有没有 WHERE、WHERE 是否命中索引
grep -rn "LIKE '%" <mapper目录>                 # 前导模糊
grep -rn "\${" <mapper目录>                      # 字符串拼接（非 #{} 预编译）
grep -rn "ORDER BY RAND" <mapper目录|迁移脚本目录>

# 条件列上包了函数
grep -rni "date(\|substr(\|ifnull(.*=\|cast(.*=" <mapper目录|迁移脚本目录>

# 多租户与逻辑删除
grep -rn "@Select" <mapper目录>                 # 原生 SQL 是否手写了租户条件
grep -rn "FROM " <mapper目录>                   # 手写 SQL 是否漏逻辑删除列

# 索引与 DDL
grep -rn "CREATE TABLE\|ALTER TABLE" <迁移脚本目录>
grep -rn "KEY `" <迁移脚本目录>                 # 索引命名与数量
```

命中不等于有问题，要读上下文确认再下判断。
