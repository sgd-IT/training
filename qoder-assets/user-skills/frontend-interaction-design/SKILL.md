# 前端交互布局（设计与审查）

使用本 skill 时，输出开头标注【项目名·frontend-interaction-design】，项目名取当前工作区根目录名（如 remote-monitor、hc-standard）。

分工：整体风格方向走 `frontend-design`；视觉精度（明度阶梯、暗色字重、文字动效、数字排版、动效阻尼）走 `frontend-visual-craft`；本 skill 只管操作摆放与可点性。位置没定就别进来打磨精度，顺序是位置 → 风格 → 精度。

## 内核

用户对按钮位置的预判 80% 来自肌肉记忆，不是你的视觉引导。顺序永远是：**先守平台惯例 → 再按频次和风险排位置 → 最后用尺寸、间距、样式兜住可点性**。反着来的方案再好看，也只是把学习成本转嫁给了用户。

给建议时用具体位置词（下半屏底部、右上角、行尾、键盘上方），不要写"放到合适的位置"这种没用的结论。

## 先判断模式

| 你在做什么 | 走哪个流程 | 产出 |
|---|---|---|
| 写或改页面、弹窗、表单、列表 | 模式 A：摆位决策 | 直接落代码 |
| 被要求"看下这个页面交互有没有问题"，给了截图或文件路径 | 模式 B：审查 | 分级问题清单 |

## 模式 A：摆位决策顺序

按顺序过，前两步定位置，后五步定可用性。任何一步过不了就地改，别留到"后续优化"。

### 1. 这个操作作用于什么？（就近原则，按钮跟着它作用的对象）

| 作用对象 | 放到哪 |
|---|---|
| 单个条目 | 行内：卡片右下角、行尾图标、左滑菜单、长按菜单 |
| 整个列表或页面 | 顶部栏（低频）或底部栏（高频） |
| 当前选择集 | 选中后才出现（底部升起批量栏），空选时隐藏或置灰 |
| 弹窗或 Sheet 的内容 | 紧贴内容底部，不要和内容隔一大段空白 |

### 2. 多高频、多危险？（可达性排优先级）

- 高频主流程 → 下半屏舒适区：底部导航、整宽按钮、sticky 提交栏、悬浮按钮。
- 低频设置类 → 顶部：筛选、排序、更多。这些本来就不该天天点。
- 危险操作 → 离主流程远 + 样式弱：左上角、二级页或红色文字按钮，靠"远 + 弱"双重降温。
- 6.7 寸以上的大屏机，顶部左侧几乎不可达，重要操作必须有底部替代入口。

### 3. 查平台惯例（跨端混用是最大的隐形税）

返回键、页面级操作、弹窗按钮顺序、全局新建、导航范式，四个端各有一套，先查再动手。完整对照表见 [platform-conventions.md](platform-conventions.md)。红线：iOS 页面里放左上角汉堡菜单、Android 里用 iOS 风格的 Sheet 顶部"完成"，用户会迟疑半秒，这半秒就是流失。

### 4. 定主次（位置 + 样式双重编码）

- 一个页面只允许一个主按钮（filled 或品牌色），其余用 outlined 或文字按钮。两个同权重按钮并排，是犹豫和点错的最大来源。
- 顺序即语义：确认在右或在下，取消在左或在上。阅读方向的终点天然被理解为"下一步"。
- 只靠颜色不够稳（色觉障碍用户），位置和样式必须同时表达主次。

### 5. 定尺寸与间距（Fitts 定律的可执行部分）

| 项 | 下限 | 说明 |
|---|---|---|
| 触控目标 | iOS 44×44pt / Android 48×48dp / WCAG 2.2 24×24px | 这是下限，主按钮应明显更大 |
| 相邻可点元素间距 | ≥ 8dp，密集列表 ≥ 12dp | 通道宽度直接决定误触率 |
| 文字按钮 | 给足内边距 | 别让文字本身成为唯一可点区域 |

加大目标比缩短距离更容易见效。贴边贴角的目标等效于"无限大"（手指撞到边缘就停，不会 overshoot），但全面屏时代要和系统手势条、圆角裁切错开。

距离要按真实起点算：从列表项滑过来、从键盘上方伸手过来，起点完全不同。所以操作应靠近上一个动作的落点，而不是几何中心。

### 6. 定位置安全（移动端专属，桌面端跳过）

- 底部安全区：Home Indicator、安卓手势条、圆角裁切内缩，否则主按钮的可点面积会被系统吃掉。
- 键盘弹起：页面上推或按钮吸附键盘上方，绝不能被键盘盖住。
- 长页面：主操作 sticky 在底部（或随滚动渐显），别逼用户滚到底才能提交；但 sticky 栏自身要留足安全区，不遮挡内容。
- 平板、折叠屏、横屏：可达区变成左右下两个扇形，操作栏放两侧或底部，别放顶部居中。

### 7. 校验无障碍与反馈

- 焦点顺序必须和视觉顺序一致（VoiceOver / TalkBack 遍历），这是最常见的交付遗漏。
- 图标按钮要有可读名称；禁用态要说清为什么禁用。
- 点击有反馈（hover-class、按压态），异步操作有 loading 并防重复提交，失败提示要贴着出错的操作。

### 桌面端另算

鼠标没有"够不到"，矛盾变成视线流和移动距离：按 F/Z 型浏览，CTA 放在视线终点（段落末尾、卡片右下、表格最后一列），并且离上一个决策点最近。表格行内操作固定在右侧，超过两个收进"更多"。

## 模式 B：审查流程

1. **先读再评**：有文件路径就完整读模板加样式（Vue/JSX/SCSS），别只看片段下结论；只有截图就先声明"基于截图推断，未验证交互细节"。
2. **按场景扫**：表单、弹窗、列表、空状态、危险操作、移动端底部、导航返回，逐组过 [checklist.md](checklist.md)，每项都要有判定口径。
3. **分级**：
   - P0 阻断：会点错或点不到。危险操作与主操作同权重并排、主按钮被键盘遮挡、触控目标低于下限且紧邻其他可点物、iOS 页面无返回路径。
   - P1 明显摩擦：位置反预期（跨端混用范式）、主操作要额外滚动才够得着、一屏两个主按钮、焦点顺序错乱、空选状态露出无用按钮。
   - P2 打磨：间距不足、无按压反馈、空状态引导按钮不在文案正下方。
4. **输出报告**：按下面的模板，一条一行说清"哪里、什么问题、怎么改"，不写理论科普。
5. **不硬凑**：原则没违反就不报；同一问题只报一次；不改代码，除非用户明确要求。

报告模板：

```markdown
【<项目名>·frontend-interaction-design】交互审查：<页面或组件名>

## P0 阻断
1. `文件:行` 现状一句话 → 违反：<哪条原则> → 改法：<具体动作>

## P1 明显摩擦
1. ...

## P2 打磨
1. ...

已核对无问题：返回路径、主按钮唯一性、触控尺寸、焦点顺序
```

如果连 P1 都没有，就直说"布局符合规范，无需改动"，别为了显得干活而把 P2 凑成 P0。

## 硬红线

违反这些就别谈优化，先改：

- 一屏出现两个同权重主按钮。
- 删除类操作和保存类操作并排且样式相近。
- 移动端主操作落在键盘下方或安全区之外。
- 触控目标小于 24×24px 且与相邻可点物间距 < 8dp。
- 跨端混用导航范式。
- 危险操作没有二次确认，或确认按钮的字眼含糊（"确定"改成"删除"）。

## 常见翻车场景速查

| 场景 | 正确做法 |
|---|---|
| 表单提交 | 紧跟最后一个输入项下方；长表单分步，每步一个主操作；键盘弹起按钮不被挡 |
| 二次确认 | 删除不与保存并排；拉开距离、红色文字按钮、或拆成两步（先标记再确认） |
| 空状态 | 引导按钮在说明文案正下方、水平居中，且是页面唯一可点物 |
| 批量操作 | 选中后才升起底部栏，空选隐藏；批量栏里也要一个主操作 |
| 长列表 | 行内最多两个直出操作，其余进"更多"或左滑；下拉刷新和加载更多不抢位置 |
| 图标按钮 | 必须有文字或 aria-label，纯图标 = 让用户猜 |
