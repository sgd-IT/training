# work-log 工作内容总结

用于持续记录工作内容与经验，最终可翻译成简历素材。核心原则：**每条记录都要能直接翻译成简历上的成果句**——动词 + 对象 + 方法 + 量化结果。

使用本 skill 时，输出开头标注【项目名·work-log】，项目名取当前工作区根目录名（如 hc-standard、remote-monitor）。

## 个人定位（记录的取舍基准）

主定位是**后端**，这是长期定价锚点；**前端**补到能独立交付完整页面；**AI Agent** 是放大器，不是第三根柱子——它得靠后端功底（幂等、重试、状态机、补偿）才立得住。记录和取舍服从这个权重：后端深度 > 前端独立交付 > AI 工程化；简历排序按当前段位（见下）调整。

- **后端（必须有深度证据）**：线上问题排查全过程、带前后对比数字的性能优化、数据一致性与幂等。这三类缺了，就会被打上“什么都会一点，什么都不深”的标签。
- **前端（证据要指向“不是只会套组件库”）**：独立走完路由/状态/表单/权限/接口/部署全流程，以及对长连接、大列表、权限模型、性能指标、前后端契约这些真正难点的处理。
- **AI（必须过工程档门槛，值钱的是环节深度不是项目题材）**：评测、可靠性、成本、真实场景、知道边界——纯“调通 API / 搭个 RAG demo”的记录只进 01，不进 06 和简历池；项目像不像业界 SOTA 不重要，端到端环节真实落地到哪一步才重要（清单见“技术沉淀偏好”AI 条）。
- **项目上限 3 个（1 年段位主推 2 个）**：AI 核心产品（主推）/ 后端深度项目 / 开源或技术沉淀（可选）。宁缺毋滥，两个讲得透的项目远胜五个浅的；06 按项目分组也只留主推分组。
- **时间有限时的投入顺序**：AI 项目做出评测并上线（收益最高、最稀缺）> 前端补到能独立交付（消除最大质疑）> 整理后端故障复盘故事（保住定价锚点）> 其余八股临面再刷。

### 当前段位与目标：1 年经验，目标跳槽

定位不是“资深全栈”，而是“能独立交付完整链路的初中级工程师 + 有真实 AI 落地经验”。据此再收窄：

- **角色不虚标**：1 年经验写“主导架构”会被追问穿；按实际写独立负责/参与，用“这条链路从接口到页面都是我一个人做完的”证明独立性，而不是用头衔。
- **AI 是当前先手，补深度不追题材**：已有 Spring AI 的 RAG + 工具调用 + 工厂模式切模型，是工程档骨架；缺的是评测、成本、可靠性数据，以及开放域环节的真实问题（意图识别、记忆、routing、工具调用纠错）——优先把现有项目补深，不为“像业界项目”去复刻 benchmark，没真实数据的复刻一问就露怯。
- **主推 2 个项目就够**：AI 落地（证明端到端）+ 一次后端故障/性能优化（证明底座）；第三个只在真拿得出手时加。
- **段位决定排序**：1 年段位把 AI 落地项目放最前，后端深度穿插作支撑；不按时间顺序罗列。

## 数据目录

按优先级定位，找到即用：

1. 当前工作区根目录下的 `work-log/`（多仓库工作区用根目录，不进子仓库）；
2. 不存在时用主目录 `d:\code\remote-monitor\work-log\`（跨项目共用、简历素材统一汇总）；
3. 两处都没有：在当前工作区根目录初始化（骨架见 [reference.md](reference.md) 第九节），并告知用户实际落盘位置。

```text
work-log/
├── 00-履历总表.md        # 一行一条总索引：日期｜项目｜角色｜关键词｜核心成果
├── 01-项目/              # 详细记录：一个项目/模块一个文件，追加式
├── 02-专题/              # 跨项目专题汇总：性能优化.md、线上故障复盘.md、技术选型.md 等
├── 03-踩坑手册.md        # 纯结论，按技术栈分区
├── 04-简历素材池.md      # 打磨好的成果句，按能力主题分组
├── 05-技能清单.md        # 技能母表：领域｜技能｜熟练度｜佐证
└── 06-面试素材.md        # 每条工作压成可讲要点，写简历/备面试时直接从这取材
```

- 日期一律用 `YYYY-MM-DD`，取当前系统时间，不猜。
- 详细记录、总表、坑手册、面试素材四者由本 skill 维护，其余文件按需更新。
- 落盘提示：数据目录在项目外，文件可能带透明加密；不要用 PowerShell 追加或读改写（它读到的可能是密文）。正确做法：用 Write 在工作区生成完整临时文件，再 Copy-Item 整文件覆盖，写后 Read 回读校验。

## 技术沉淀偏好

记录与提炼时技术深度优先于业务描述。一条工作是否值得记，按以下四条主线判断（顺序即权重）：

1. **后端深度（定价锚点）**：
   - 线上问题排查全过程：CPU 飙高、慢 SQL、内存泄漏、MQ 积压——工具链 + 推理路径，这是证明“真干过”的最硬素材；
   - 性能优化必须带前后对比数字；
   - 数据一致性与幂等（重试、状态机、补偿），这条是任何方向的底线。
2. **AI Agent 工程化（放大器，按工程档判据入库）**：五项判据——评测、可靠性、成本、真实场景、边界；其中“评测 / 可靠性 / 成本”至少占两项且有真实场景，否则按玩具档处理，只记 01。
   - **题材观**：不刻意找“和业界对齐”的项目，不复刻 benchmark 的 SOTA——没有真实数据，参数和指标都是编的，追问两层就露怯。值钱的是在开放域真实场景里把 agent 端到端做扎实，哪怕只是一个客服/工单场景；筛简历的人不看项目题材，只看深度。
   - **开放域 Agent 深度检查清单**（记录 AI 工作前逐项自查；真实做过的环节写清做到哪一步，没做过的不写）：
     1. **意图识别**：开放域输入怎么分流（规则 / 分类模型 / LLM 判别的取舍）、置信度阈值与兜底、多意图与含糊输入怎么处理；
     2. **MCP / 工具建设**：工具粒度怎么切（万能工具 vs 细粒度）、schema 与参数校验、工具描述怎么写才能让模型选对、写操作幂等与失败语义；
     3. **多轮记忆**：短期上下文怎么管（窗口 / 摘要压缩 / 裁剪策略）、长期记忆（事实抽取、用户画像、存储与召回）、记忆冲突与过期、记忆带来的成本与延迟怎么权衡；
     4. **多 Agent routing**：路由判据（意图分类 / 置信度 / 成本）、错路由的兜底与回退、各子 agent 职责边界；
     5. **在线监控（monitor agent）**：线上 bad case 怎么回收、失败分类、线上指标看板（成功率 / 时延 / 成本）、怎么用线上表现反哺评测集与提示词；
     6. **工具调用纠错**：检索不全 / 召回不好怎么定位与优化（query 改写、召回扩量、重排、chunk 切分、混合检索）、工具选错 / 参数错怎么纠（重试、向用户澄清、降级兜底）。
   - **评测**：黄金测试集（50–100 条）、准确率/召回/忠实度指标、改一版方案后的前后对比、bad case 分类与尚未解决的类型；开放域 agent 以端到端任务完成率为主指标，不能只评单步；
   - **可靠性**：工具调用失败率、超时与重试、人工兜底与回滚、多步任务中间状态持久化——直接复用后端的幂等与状态机功底，记录时要点明这层复用；
   - **成本**：单次调用成本、token 消耗、上下文压缩/提示词缓存/小模型路由/结果缓存等降本手段、月省多少；
   - **真实场景**：有真实使用量与反馈，内部工具也算，只跑过 demo 不算；
   - **边界**：能说清“这个场景用 RAG / Agent 不行，因为……最后改成了 XX”。
   - **Spring AI 项目的记录要点**：模型抽象（ChatClient / ChatModel）、RAG 链路（切分/召回/重排/引用）、工具调用（参数校验、失败兜底、幂等）、工厂模式切模型的判据（按任务/成本/可用性）。这些是“做过”的证据；配上评测/成本/可靠性才够工程档，缺哪项就补哪项，不重复搭 demo。
3. **前端独立交付（消除“只会套组件库”的质疑）**：完整走完路由、状态管理、表单、权限、接口对接、部署上线；真正的难点是——首屏与 LCP 等性能指标、分包懒加载、虚拟列表、WebSocket/SSE 长连接与断线重连、路由级+按钮级+数据级权限、前后端契约（OpenAPI 类型生成、BFF、缓存分层）。
4. **通用深度（后端主线下的细项）**：
   - 物联网设备对接：协议帧结构、设备在线状态判定、上报周期与超时阈值、平台回调（AEP / EMQX）、设备注册模型；
   - 并发与多线程：竞态窗口、原子操作与 CAS、线程模型（回调线程 / 事件循环 / 线程池）、幂等、内存态与持久态一致性；
   - 设计模式：策略、工厂、门面、注册表、规则链、模板方法——写清解决什么问题、新增一类时改哪里；
   - 逻辑设计：算法（取模基准、锚点、轮换）、状态机、口径统一（Java 与 SQL 同源）、边界（跨天 / 跨月 / 空值）。

落到模板上：
- 01 的【方案】必须写清上述至少一条主线的具体取舍；
- AI 类记录必须在【结果】给出评测或成本数据，并至少落一条 bad case 或边界否定结论；涉及多轮对话 / 编排的，【Agent 链路】至少写清 2 个环节的做法与坑，只写环节名不算；
- 06 的“追问与答案”至少 2 组，答不上来的技术点不写进 06；AI 条目必须含一组边界/失败追问。

| "总结今天/这周"、"写个周报/日报" | B 汇总 |

## 模式 A：记录一条工作内容

1. **收集素材**：用户描述为主；必要时看本会话改动的文件和相关 git 提交（只读 `git log` / `git diff`，不执行任何 add/commit）。
2. **查重**：落盘前先在 `01-项目/<项目名>.md` 里搜"同日期 + 同模块"的已有条目（Grep 日期或模块名）。命中则合并更新——保留原结论、补新内容；未命中才追加。`00-履历总表.md` 同理：已有同日同模块的行就改那一行，不新增。
3. **按模板整理**（见下方"单条记录模板"），缺关键信息时一次问全：
   - 结果有没有量化数据？没有精确数字就用量级对比（如"P99 从 ~800ms 降到 ~120ms"）。
   - 角色是独立负责 / 主导 / 参与？负责的具体是哪部分？
   - 有没有踩坑和可复用结论？
   - 涉及 AI / Agent 的：黄金集规模、核心指标与 bad case 分类、工具调用失败与兜底、单次成本或 token；再对照“开放域 Agent 深度检查清单”问命中的环节——意图识别 / 记忆 / routing / 在线监控 / 检索纠错各做到哪一步、踩过什么坑；评测/可靠性/成本一项都问不出来的，按玩具档只记 01，不进 06 和简历池。
4. **落盘（四处联动）**：
   - 追加或合并到 `01-项目/<项目名>.md`（不存在则创建）；
   - 值得写进简历的工作，同步写一条压缩版到 `06-面试素材.md`（格式见模式 C）；日常小改动只记 01；
   - 在 `00-履历总表.md` 表尾加一行索引（或更新已有行）；
   - 遇到特别/疑难问题（含可复用的坑）时，同步追加到 `03-踩坑手册.md` 对应技术栈分区（写入标准见"落盘规则"；跨项目同样适用）。
5. 把写入的完整条目贴回给用户过目。

## 模式 B：按时间段汇总工作内容（日报/周报口径）

1. **定时间范围**（按用户口径，默认"最近 7 天"）：

   | 用户说法 | 时间范围 |
   |---|---|
   | 今天 | `today 00:00` |
   | 这周 / 本周 | 本周一 00:00 至今 |
   | 最近 N 天 | 滚动 N 天 |
   | 明确区间 | 按给出的起止日期 |

2. **发现仓库**：当前工作区下含 `.git` 的子目录即工作仓库，先探测；探测不到再用显式路径。

   ```powershell
   Get-ChildItem -Path "<工作区根>" -Directory |
     ForEach-Object { if (Test-Path (Join-Path $_.FullName ".git")) { $_.Name } }
   ```

   - 排除第三方克隆目录（如 ponytail）与工具仓库，只统计自己维护的仓库。
   - 本主工作区现有三个：后端（Java / Spring Boot）、PC 前端（Vue3）、移动端（UniApp）。

3. **拉代码侧素材**（只读）。每个仓库拉三样，已提交与未提交分开看：

   ```powershell
   git -C <repo> log --since="<范围>" --date=short --pretty="%ad %s"
   git -C <repo> status --short
   git -C <repo> diff --stat
   ```

   - 需要改动细节时对 log 加 `--stat`。
   - 工作区未提交的改动单列"未提交"，不要和已提交混在一起，也不要当成没发生。

4. **合并记录侧素材**：`00-履历总表.md` 与 `01-项目/` 中该时间段的条目。
5. **去重合并**，按"项目/模块"分组输出。默认用**汇报口径**：大白话，讲完成什么、解决什么问题、带来什么价值；用户要"技术口径"时再补模块、文件与关键决策。涉及 AI 项目的，注明本周评测指标、bad case、成本的变化，以及开放域环节的推进（如记忆改成摘要压缩、召回加了重排）；没有新数据就写"无新数据"，不虚报。
6. 默认只在对话输出、不落盘；用户说"存档"时写入 `02-专题/` 或用户指定文件。
7. **周报定稿格式（用户既定偏好）**：正文用"通俗分类名：大白话说明"，一行一条、不加编号与表格、每条 15–20 字；口径、N+1、字典化、锚点、码流、去重等术语全部换成业务说法，目标是老板与非技术同事能看懂一半；跨端联动细节与量化指标在本档删除，需要时另出详版。

## 模式 C：提炼简历与面试素材

触发："更新简历素材"、"提炼成简历句"、"整理面试素材"、"这个项目面试怎么讲"。

**C1 面试素材（写简历的原料）**：

1. 优先读 `06-面试素材.md` 里已有的条目；缺哪个专项的条目，再回 `01-项目/` 取细节补写。
2. 每条按"面试素材格式"压缩，只留可讲的东西，不抄技术流水。
3. 在 `06-面试素材.md` 开头维护一句自我介绍定位句（模板：后端为主，工作中主动补前端并落地过 AI 能力，能独立从 0 交付一个带 AI 功能的产品；优势不是前端做得多漂亮，而是能把前后端和 AI 整条链路扛下来；1 年经验不写“资深/主导架构”）。不写"精通前后端 AI"这类空话。

**C2 简历成果句**：

1. 读指定时间段的面试素材（默认最近一个月）。
2. 挑 3–5 条最有价值的（有规模、有数字、有决策的优先）。
3. 按公式改写：**动词 + 做了什么 + 用什么技术/方法 + 解决什么规模的问题 + 量化结果**。
4. 写入 `04-简历素材池.md` 对应能力主题分区，遵守"落盘规则"里的条数上限。
5. 提醒用户：投不同岗位时用同一母池按 JD 裁剪重排，最相关的放最前，不一份简历通投。
6. 排序服从段位：1 年经验、目标跳槽时，"能独立交付的 AI 落地项目"放最前（端到端 + AI 先手），后端深度（排查/性能/一致性）作为底座证据穿插；3 年以上再反过来把后端深度放最前。不按时间顺序堆项目，也不前后端平均分配篇幅。
7. 主推项目要能撑起三个 8–10 分钟故事：性能/故障（后端深度）、架构取舍（为什么这么设计）、AI 落地（有评测、有 bad case、有成本）。每个按"背景 → 我的决策 → 踩的坑 → 数字结果 → 复盘"组织；1 年段位至少做到两个完整（AI 落地 + 一次后端故障/性能排查），架构取舍讲清一个取舍即可；哪个故事讲不完整，先回 06 补，不急着改简历。

## 模式 D：维护技能清单

1. 更新 `05-技能清单.md`：新技能标熟练度，"佐证"列必填（连回工作记录）。
2. 熟练度分级与"精通最多 2–3 个"的约束见 reference.md。
3. 月度同步：新学→加"了解"；常用→升级并补佐证；一年没碰→降级或删。

## 模式 E：检索回查

触发："查一下以前……"、"Redis 的坑都有哪些"、"面试前过一遍 MySQL"、"按标签找记录"。

1. 只读检索：先查 `00-履历总表.md` 定位，再进 `01-项目/` 取完整记录；踩坑类直接查 `03-踩坑手册.md`，技能佐证查 `05-技能清单.md`。
2. 支持按关键词（模块/技术/业务域）、标签、时间范围三种入口组合过滤。
3. 输出命中清单：`日期｜模块｜一句话结论｜文件位置`，按时间倒序；用户要求展开某条时再贴全文。
4. 不改任何文件；用户说"汇总成专题"时才写入 `02-专题/`。

## 单条记录模板

```markdown
## <记录/模块名> · <日期范围>
> 项目：<所属项目名>
### 【类型】
功能开发 | 性能优化 | 故障排查 | 技术债 | 架构 | 协作 | 数据迁移 | AI 应用
### 【背景】
为什么做，业务痛点
### 【方案】
关键技术决策 + 选型理由（为什么不用另一方案）
### 【我的角色】
独立负责 | 主导 | 参与（写明具体负责部分）
### 【结果】
量化数据；无精确数据用量级对比
### 【Agent 链路】（仅多轮对话 / Agent 编排记录）
只写真实做过的环节，一行一个：做法 → 遇到的问题 → 怎么优化 → 效果；环节从意图识别 / MCP 工具 / 多轮记忆 / routing / 在线监控 / 工具调用纠错里挑，没做过的不写
### 【评测与成本】（仅 AI 记录）
黄金集规模、核心指标及前后对比、bad case 分类与未解决项、单次成本/token、降本手段
### 【踩坑 & 根因】
现象 → 定位过程 → 根本原因
### 【可复用结论】
一句话原则，下次可直接复用
### 【关联】
Git commit / MR / 文档路径
### 【标签】
见"打标签维度"，一般 2–3 个
```

【施工】【待办】等模板外字段按需插入（一般紧跟【方案】或【结果】），编号风格与相邻块保持一致。

AI 类记录在【结果】后插入【评测与成本】块（黄金集规模、核心指标及前后对比、bad case 分类与未解决项、单次成本/token、降本手段）；涉及多轮对话或 agent 编排的，再加一个【Agent 链路】块，其余记录不写。

### 面试素材格式（06-面试素材.md）

一条工作一条，H2 标题 + 引用行 + 7 个列表项（AI 条目 8 个），全文控制在 12 行内（AI 条目 14 行），写简历时直接抄改：

```markdown
## <项目/专项> · <日期>
> 项目：<所属项目名>｜角色：<独立负责 / 主导 / 参与>
- **技术维度**：后端深度（排查/性能/一致性）/ AI 工程（评测/可靠性/成本）/ 前端交付（长连接/性能/权限）/ 并发 / 设计模式 / 逻辑设计（选 1–2 个）
- **场景与规模**：什么业务场景，系统多大（数据量/用户量/设备量）
- **我做了什么**：动词开头，含技术方案与选型理由
- **难点与解决**：最有技术含量的一点，现象 → 根因 → 做法
- **结果**：量化对比，没有数字就写量级
- **评测与成本**（仅 AI 条目）：黄金集规模、指标前后对比、bad case 分类与未解决项、单次成本与降本手段
- **追问与答案**：2–3 组高频追问 → 一句话答案，答不上来的不写；AI 条目必须含一组边界否定题
- **技能**：对应 05-技能清单里的技能项
```

只写能讲清楚、经得起追问的内容；讲不明白的技术不写进来；追问与答案要能接住“为什么不用另一种方案”。

AI 条目还必须再配一组边界否定题（“这个场景为什么不用 RAG / 为什么不用 Agent，最后改成了什么”）和至少一组环节深浅题（如“召回不全除了换嵌入模型你还试过什么”“多轮对话里用户前后改口怎么记”）；答不出来就按玩具档处理，不写进 06。

写完每组追问，假扮面试官再追一层（为什么不用另一种方案？边界在哪？线上出问题怎么发现？）。答不上来说明这个点还没吃透，先别入库，回 01 或代码补，补不出来就删掉这条追问。

## 版式与层级规范

数据文件首行用 H1 做**文件级标题**（`# 履历总表`、`# 项目名`）。H1 只给文件标题，不用于记录。记录及各层级：

1. 条目标题 H2：`## <记录/模块名> · <日期范围>`（如 `## 消防告警分级响应系统 · 2026-10-08 ~ 10-09`，日期承载于标题）；
2. 标题下紧贴一行项目名小标注：`> 项目：<所属项目名>`；
3. 字段名作为 H3 小标题：`### 【类型】`，内容紧跟其下一行，不与正文同级；
4. 各块之间不插空行、整体紧凑；更深层级按 H2→H3→H4 顺延、保持不跳级；
5. 存量旧格式（`### 日期 · 标题` + `【】` 平铺）已于 2026-10-19 全量迁移，之后新写一律用本规范。

## 落盘规则

- **01 去重**：同一日期同一模块只保留一条记录，重复时合并更新（见模式 A 第 2 步）。
- **03 踩坑手册**：分区固定为 后端（Java / Spring）、前端（Vue / UniApp）、数据库（MySQL / Redis）、基础设施 / 部署、AI 应用（LLM / Agent）、其他；条目用 H3，正文四行——问题 / 根因 / 触发条件 / 做法。触发条件写“什么现象一出现就该想到这个坑”（如“设备长期离线但日志有上报 = 先查超时阈值与上报周期是否匹配”）。遇到特别/疑难问题（含会再犯的坑）即记，一次性环境问题（密码错了、服务没启动）不记；此规则对所有使用本 skill 的项目生效。
- **02 专题**：同一主题跨项目或跨月累计 ≥3 条时才汇总成专题，否则不建。
- **04 简历素材池**：一个能力主题保留 3–5 条，按时间倒序；新条目进正式区，旧的挪到"备选"或删除，不无限堆积。"AI 应用与 Agent 工程"分区只收工程档条目（带评测指标或成本数据），玩具档不上架。
- **06 面试素材**：按项目分组、时间倒序；一条工作一条，不合并不同专项；优先记技术维度（后端深度/AI 工程/前端交付）占比高的条目，纯业务配置类不写；每条至少 2 组追问与答案；AI 条目必须过工程档门槛（评测/可靠性/成本至少占两项 + 真实场景），否则不改写；按项目分组最多保留 3 个主推项目，其余挪进 `02-专题/` 归档。

## 维护节奏

- **当天记**：每天下班前 5 分钟，哪怕只写三行；周五补周一的细节已丢一半。
- **月度回顾（每月最后一个周日，15 分钟）**：扫一遍 `00-履历总表.md`，做四件事：
  1. **合并专项**：同主题的零散条目并成一条可讲的专项，01 合并记录、06 提炼成一条；
  2. **补追问**：把 06 里答不上来或写不下去的追问补上，补不出来就删掉；
  3. **校准技能**：`05-技能清单.md` 过一遍——新学加“了解”，常用升级并补佐证，一年没碰降级或删；
  4. **对齐定位**：确认 06 里后端深度条目没被前端/AI 挤掉，主推项目仍不超过 3 个；AI 项目补当月评测指标、bad case 与成本变化。
- 投不同岗位时用同一母表裁剪重排，不一份通投。

## 打标签维度

每条记录挂 2–3 个标签组合：

- **层级**：前端 / 后端 / 数据库 / 缓存 / 消息队列 / 基础设施 / 监控告警 / AI 应用
- **技术栈**：Vue3 / Java / Spring Boot / MySQL / Redis / WebSocket / UniApp / LangChain / Spring AI / Dify / OpenAI 兼容 API 等
- **前端深水区**：首屏性能 / 长连接 / 虚拟列表 / 权限模型 / 前后端契约
- **AI 专项**：评测 / RAG / Agent 编排 / 意图识别 / MCP 工具 / 多轮记忆 / routing / 在线监控 / 检索纠错 / 成本优化 / 可靠性兜底
- **动作类型**：从0到1 / 重构 / 性能优化 / 线上故障 / 技术选型 / 降本 / 带人 / AI 落地
- **业务域**：告警 / 设备 / 值守 / 报表 / 权限 等

改简历时按"动作类型 + 技术栈"检索，可一次拉出所有同类战绩。

## 写作硬性规范

- 动词开头，动作 + 对象 + 方法 + 结果；禁止"负责 XX 开发"式名词堆砌。
- 结果优先量化；写不出数字就写量级和对比（"构建 12 分钟 → 3 分钟"）。
- 每条记录脱离上下文能独立读懂，不写只有当天才懂的缩写。
- 只记事实，不记流水账；同一天零散小事合并为一条。
- 当天记，不攒到周末补——细节会丢一半。
