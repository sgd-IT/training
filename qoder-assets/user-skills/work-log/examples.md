# 填写示例

本文件是 [SKILL.md](SKILL.md) 的补充资料，展示各类记录的填写范式。所有示例均为 2026-10-19 定版格式：文件标题 H1，记录 H2，字段 H3。

## 示例 1：完整单条记录（模板填法示范）

```markdown
## 订单中心 · 超时未支付自动关单 · 2026-09-21
> 项目：电商交易平台
### 【类型】
性能优化 / 重构
### 【背景】
原方案每分钟全表扫描未支付订单，日约 300 万次无效查询，订单表 CPU 峰值 78%，大促前存在漏单风险
### 【方案】
用 Redis ZSET 延迟队列替代轮询：下单时写入带到期时间戳的 ZSET，消费者按到期扫描关单；选 ZSET 而非 MQ 延迟消息的原因：需要支持取消订单时移除任务（ZREM）
### 【我的角色】
主导：方案设计 + 核心编码 + 灰度上线
### 【结果】
消除每日约 300 万次无效查询；订单表 CPU 峰值 78% → 22%；支撑日均 40 万单无漏单
### 【踩坑 & 根因】
现象：灰度期间偶发"已支付订单被关单" → 定位：支付回调与关单消费者并发竞争 → 根因：关单前未二次校验订单状态，且未加分布式锁
### 【可复用结论】
延迟队列消费端必须"取任务后二次校验业务状态"，不要假设任务取出时条件仍成立
### 【关联】
commit a1b2c3d；MR #128
### 【标签】
后端 / Redis / 性能优化 / 订单
```

## 示例 3：本项目真实工作改写（消防远程值守系统）

> 基于大屏告警弹窗去重工作；结果数字用占位符，记录时应补真实值。

```markdown
## 值守大屏 · 报警弹窗去重 · 2026-09-29
> 项目：消防远程值守系统
### 【类型】
故障排查
### 【背景】
大屏告警弹窗同一告警反复弹出，干扰值守人员处置
### 【方案】
梳理告警推送链路，确认轮询与推送两条路径各自触发弹窗；在弹窗队列入口按告警唯一标识去重，保留最新一条
### 【我的角色】
独立负责：根因定位 + 方案设计 + 前后端落地
### 【结果】
重复弹窗消除（补真实数据：弹窗量从日均 A 次降至 B 次）
### 【踩坑 & 根因】
现象：同一告警短时间弹多次 → 定位：多个触发源各自入队 → 根因：弹窗队列缺幂等去重，且上游无法保证只推一次
### 【可复用结论】
任何"实时弹出/提醒"类需求，先定唯一键并在消费端幂等去重，不能依赖上游只推一次
### 【关联】
对应 commit 链接（补真实值）
### 【标签】
前端 / WebSocket / 线上故障 / 告警
```

## 示例 4：履历总表与踩坑手册的条目形态

履历总表一行：

```markdown
| 2026-09-21 | 订单中心/超时关单 | 主导 | Redis ZSET、延迟队列、性能优化 | CPU 78%→22%，日均 40 万单无漏单 | 01-项目/订单中心.md |
```

踩坑手册（文件 H1、分区 H2、坑条目 H3）：

```markdown
## 数据库（MySQL / Redis）

### Redis 延迟队列

- 问题：消费端取出任务后直接关单，灰度期间误关已支付订单。
- 根因：支付回调与关单消费者并发竞争，任务取出时业务条件已不成立。
- 触发条件：关单量与支付回调量同时上来 + 偶发“已支付被关单” = 先查消费端有没有二次校验。
- 做法：消费端取任务后二次校验业务状态，关键动作加分布式锁。
```

## 示例 7：面试素材条目（06-面试素材.md）

```markdown
## 告警字段语义统一 · 2026-10-08 ~ 10-09
> 项目：消防远程值守系统｜角色：独立负责
- **技术维度**：逻辑设计 / 数据迁移
- **场景与规模**：消防远程值守平台告警链路，存量告警 31,563 条，覆盖 PC / 大屏 / 移动端三端
- **我做了什么**：将四套并行语义（数字编码实为类型、英文级别、前端风险级、来源码）收敛为类型/等级/来源/档位四维模型，新增 alarm_kind 字段，读侧双读 + 写侧单一判据，读侧先于写侧原子切换
- **难点与解决**：按类型字段估算的迁移分布严重失真 → 同一事件存在两条写入链路两种编码 → 改为按事件名称逐项映射，实测 31,150/295/118（原估 29,797/92/1,674）
- **结果**：31,563 条存量零歧义切换、全程可回退；等级判据从散落 5+ 处收敛为单点；542 文件 clean 编译通过，烟感真机双通道实测闭环
- **追问与答案**：① 为什么不能直接改 level 的取值？→ 存量数据的 level 同时承载“类型”和“等级”两种语义，直接改会把历史类型映射错；② 为什么读侧先于写侧？→ 旧数据仍靠 level 解释，先改读侧可以随时回退；③ 怎么保证中途不停机？→ 行级判据（alarm_kind IS NULL = 旧语义），新旧共存
- **技能**：Java / Spring Boot / MySQL / 数据迁移 / 架构设计
```

## 示例 8：技术型条目（并发竞态，重点看“追问与答案”）

```markdown
## 告警去重时间戳竞态 · 2026-10-14
> 项目：消防远程值守系统｜角色：独立负责
- **技术维度**：并发 / 缓存
- **场景与规模**：告警入库按 deviceId:alarmType:sourceType 做 5 分钟窗口去重，单日告警量万级，多来源并发写入
- **我做了什么**：用 ConcurrentHashMap.putIfAbsent 原子占位，非重复时才用三参 replace(key, old, new) CAS 刷新时间戳；删除基于 get+remove 的重复判断死方法
- **难点与解决**：时间戳刷新与“是否重复”判定分在两处 → 窗口边界易被提前刷新/漏判 → 把刷新收敛进非重复分支，判定只留一套
- **结果**：单文件 +2/-18，去重逻辑从两套收敛为一套
- **追问与答案**：① 为什么不用 get 判断再 put？→ 两步之间存在竞态，putIfAbsent 才能原子占位；② replace 的返回值不校验会怎样？→ 两线程同时通过窗口检查时 CAS 只有一个成功，另一个仍会落库，去重是尽力而为；③ 要做强一致怎么办？→ 以 DB 唯一索引或分布式锁兜底，内存缓存只做第一层
- **技能**：Java / 并发编程 / 缓存设计
```

反向验证：写完上面三组，假扮面试官再追一层“那你的去重能保证不重复落库吗”。答得上（不能，只是降低概率，强一致靠唯一索引）才保留；答不上就把这条追问补进 01 再回来。

## 示例 9：AI Agent 类记录（工程档写法）

```markdown
## 工单 AI 分派 Agent · 2026-10-12 ~ 10-16
> 项目：智能工单系统
### 【类型】
AI 应用
### 【背景】
一线工单日均 600+ 全靠人工分派，错分率约 18%，平均流转 40 分钟
### 【方案】
RAG 召回历史工单与制度文档 + 工具调用落单：Agent 调 create_assign 工具写库；选工具调用而非让模型直接给结论，原因是分派动作要幂等可回滚（复用后端状态机 + 补偿）
### 【我的角色】
主导：评测集建设 + Agent 编排 + 后端接口改造
### 【结果】
人工分派量下降约 70%，错分率 18% → 6%
### 【Agent 链路】
- 意图识别：分类模型先判专业域，置信度低于阈值转人工；含糊工单（“这个问题处理一下”）先澄清提问，不硬分
- MCP 工具：查询、写库拆成细粒度工具并做 schema 校验，写操作带幂等键；工具描述写明适用与禁用场景，减少模型误选
- 工具调用纠错：跨专业工单召回候选不足时，先扩大候选池再让模型重排；「文档缺失」类需求明确转人工，不硬答
### 【评测与成本】
黄金集 80 条，分派准确率 71% → 89%；bad case 收敛为「跨专业工单」「文档缺失」两类，后者未解决；单次成本 ¥0.12 → ¥0.04（提示词缓存 + 小模型路由）；工具调用失败率 2.3%，重试后 0.4%
### 【踩坑 & 根因】
现象：上线后同一工单偶发重复分派 → 定位：模型超时重试叠加前端重复提交 → 根因：写操作工具没带幂等键，重试不判重
### 【可复用结论】
Agent 的写操作工具必须带幂等键，重试与人工兜底共用一套状态机，不能假设模型只调一次
### 【关联】
commit xxxx；评测集 eval/golden_80.jsonl
### 【标签】
AI 应用 / Agent / 评测 / 降本 / 工单
```

同一件事的简历句对比：

❌ 基于 LangChain 实现智能问答与工单分派功能

✅ 主导工单 AI 分派 Agent（RAG + 工具调用），自建 80 条黄金评测集把分派准确率从 71% 提升到 89%，bad case 收敛至两类；对写操作工具做幂等改造，调用失败率 2.3% → 0.4%，单次成本 ¥0.12 → ¥0.04

差距在于：前者只说了“做了什么”，后者给出了评测、bad case、可靠性、成本四组证据——这就是玩具档和工程档的分水岭。

还有一种反面写法是“复刻了某公开 benchmark，分数刷到 SOTA”：没有业务数据、没有自己的 bad case，面试官追一句“换到真实开放域输入会怎样”就答不上。深度不看题目，看环节。

已有 Spring AI 的 RAG + 工具调用 + 工厂切模型项目，不用另起炉灶，也不为了“像业界项目”去复刻 benchmark：对照 SKILL.md 的“开放域 Agent 深度检查清单”把现有链路补深——意图识别、多轮记忆、routing、工具调用纠错里哪些环节真实踩过坑，把坑、优化过程和前后数字补进【Agent 链路】与【评测与成本】，就是工程档。复刻来的项目没有自己的坏数据和踩坑记录，追问两层就露怯。
