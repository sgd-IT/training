Bug class: 报警记录与音频关联问题的误诊（把结构性一对多配对误判为文件覆盖bug）
Root cause: 嘉果漏铝链路中 /lyxl/push 每次status=0都生成独立msgId并新建一条报警记录（约3~5秒一次），而设备端一次物理报警只上传一个15秒音频；服务端Hash池按field=time就近匹配后hdel消费，故一批N条记录中仅最新一条能拿到音频。历史上确有一次真实覆盖问题——旧版用String单key存msgId，后续push把前一次的msgId顶掉（commit d986dd2已改为Hash池修复），但被覆盖的对象始终是Redis中的msgId引用，OSS上的音频文件本身从不被覆盖。
Fix pattern: 先用 git log -S 与 git show 定位历史相关修复commit确认旧bug是否已修，再用数据规律验证当前假设（若现象呈"每批仅最新一条命中"则指向就近匹配的预期行为，而非覆盖），并通过grep服务端日志"接收到音频文件"统计每批实际上传次数来区分"设备只传一次"与"多次上传仅一次成功"。
Reusable lesson: 不要因为列表中存在大量无音频记录就断定是覆盖bug而去改存储层，因为真正原因可能是上报次数与音频次数的一对多结构错配，改存储无效；应先做历史修复核查+数据规律+设备行为日志三重验证再定根因。适用于排查跨接口异步关联（状态推送与文件上传分离）的数据缺失类问题；不适用于同一请求内直接写入的文件冲突场景。
