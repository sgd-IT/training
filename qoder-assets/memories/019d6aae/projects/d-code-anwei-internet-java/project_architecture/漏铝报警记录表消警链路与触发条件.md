漏铝报警表 mon_aluminum_leakage_alarm_record 的消警机制（经全库调用点排查验证）：

- 消警本质是单条 UPDATE：action_status 0→1、processing_status 0→1、eliminate_time 置当前时间；系统中不存在任何人工/前端按钮式消警接口。
- 唯一实际触发路径：前端监控页轮询 GET /monitor/center/todayAlarm → MonitorCenterServiceImpl.getTodayAlarm() → getAlarmPopUpWindow(castWellId)（条件：processing_status=0 + alarm_time 近3小时内 + 按 id 倒序 LIMIT 1）→ 铸造中信号 cdReses==1 时按 alarmType 分流 → alarmType=3（声音漏铝）调 AluminumLeakageAlarmRecordServiceImpl.videoOffAlarm(id, gmtCreate)，且仅当 (now - 创建时间) > 30秒才执行消警。
- 关键不变量与反直觉事实：①每次轮询只消 1 条，效果为逐条滚动消费；②30秒保护期保证弹窗至少展示30秒；③消警强依赖有客户端在轮询——无人开页面时报警永远积压；④非铸造状态（cdReses!=1）既不弹窗也不消警；⑤alarmType=2 且 monLevel=0 时 getAlarmPopUpWindow 直接返回 null；⑥热成像（alarmType=0）分支的 videoOffAlarm 调用已被注释，热成像报警不会自动消警而持续挂起；⑦批量消警方法 offAlarm(castWellId) 所有调用处均被注释（死代码），其内部条件 alarm_time >= 当前时间存在疑点，即使启用也命中不了历史记录。
- 体系隔离：感知数据报警表 alarm_information 的消警是另一套独立体系——阈值恢复正常自动消（AlarmMethod.fireAlarm 链路）、水泵恢复消警（ZzqjMethod）、铸造后期/快速切断阀全清（AlarmEliminationMethod.allClearAlarm，操作 AlarmInformation 维度），与漏铝记录表互不影响，排查时不可混淆。
