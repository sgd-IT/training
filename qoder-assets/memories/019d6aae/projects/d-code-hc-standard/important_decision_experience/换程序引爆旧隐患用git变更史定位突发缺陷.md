Conclusion: 当线上突然报某接口字段缺失/返空、且涉事代码看似"一直如此"时，优先怀疑"最近一次更换程序把积压的旧改动首次带上生产"，用 git 变更史 + 生产数据时间线双轨定位引爆点，而不是急于改动从未出问题的老代码。
Rationale (trade-off): 单纯看当前源码会误判"代码一直这样写为何现在才坏"；结合生产数据(成功记录的最后时间点 vs 报错起始时间)与关键行的引入提交日期，能把"埋雷时间"和"引爆时间"分开，避免错误回滚或改错文件。
Rejected alternatives: ①直接归因于移动端App版本落后——被否，因为实测任何App版本都会中招(服务端返null导致客户端丢参);②重写/回退历史老SQL别名——被否，别名自首次提交即存在且单独无害，真正变量是新加的显式映射行。
Applicable / expiry conditions: 适用于"无明显代码改动却突然爆发"的前后端联调型线上故障复盘；若故障表现为多接口并发超时等网络特征，应先走服务器网络稳定性优先的诊断；当项目改为蓝绿/金丝雀发布或有完整部署审计日志时，可直接读发版记录替代此推断法。
