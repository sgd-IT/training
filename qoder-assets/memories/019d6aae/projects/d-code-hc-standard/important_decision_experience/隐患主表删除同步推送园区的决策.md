## 结论
「隐患信息」页删除（DELETE /base/hiddenTrouble/{id}）同步推园区删除，实现在 BaseHiddenTroubleServiceImpl.pushDeleteToPlatform：只推 sync_status='1' 的记录，推失败仅 log.error 留痕、不阻断本地删除；本次不动公共基类 PlatementBaseApi.sendDelete。

## 理由与权衡
园区 check_info 的主键就是本地 id，删除推送传本地 id 即可定位，无需映射表。历史上主表删除只删本地，导致园区残留一条永远卡在"待治理"的孤儿隐患：本地行删掉后既补不回来（POST /push/hiddenTrouble 只捡库内 status=31 的记录），也无法靠再推关闭态覆盖（buildUploadEntity 需从库里读回 measureId/areaName 才能拼平台实体）。失败不阻断是因为平台接口抖动不该让用户在业务页删不掉隐患，残留可人工兜底。

## 否决方案
- 失败即阻断本地删除：两边强一致，但平台不可用时隐患删不掉，可用性代价过高。
- 失败入队重试（新增待清理表 + 定时任务）：可靠性最好，但要新增表与调度任务，本次不引入。
- 同步修 sendDelete 非 JSON 兜底与全局失败判定：sendDelete 是公共基类方法，风险设备/单元/事件/措施等 6 个删除接口的判定口径都要跟着复核，改动面超出本次范围。

## 适用与失效条件
适用于 base_hidden_trouble 治理主表删除链路。失效场景：sync_status 为 NULL 的历史行（早期环境存在留空数据）实际可能推成功过，本方案按"只有明确成功才推"处理，这类行删除后园区仍可能残留，需人工按 id 在平台侧清理。
