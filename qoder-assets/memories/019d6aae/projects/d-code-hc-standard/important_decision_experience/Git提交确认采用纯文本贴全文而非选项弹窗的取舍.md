Conclusion: 提交类高危操作的确认采用"纯文本贴全文 + 等用户明确回复"的形式：一次列全每个提交的文件清单与提交信息标题加正文全文，并在正文定稿后、以及任何确认之后新发生的文件改动（含登记类文档）都先贴 diff，再重新等确认。

Rationale (trade-off): 交互式选项弹窗虽然点选成本低、界面干净，但把"授权 5 次提交"压缩成一次点击，且屏幕上只能展示 subject 一行，正文说明在确认之后才生成，用户实际未在知情状态下同意；对写仓库状态这类不可轻易撤销的操作，知情完整性优先于交互便利。代价是多一轮往返与更长的输出。

Rejected alternatives: ① 保留选项弹窗但把正文塞进选项描述——受长度限制仍会截断，且"(推荐)"标签构成引导，被否；② 逐条提交逐个询问（5 轮往返）——最严格但过碎，改为一次性贴全所有提交的全文由用户整体确认；③ 只贴文件清单不贴提交信息——正是本次被批评的做法，被否。

Applicable / expiry conditions: 适用于 git add/commit/push 及任何确认后才允许改动仓库或业务文件的场景；当用户主动要求"以后按推荐直接执行"或改用显式指令（如直接说"推送"）时，该轮可视为已获全文级授权，无需重复贴文。回退手段 git reset --soft HEAD~N 只动提交记录不动工作区内容，是此类误授权后的补救选项，但须用户点头才执行。
