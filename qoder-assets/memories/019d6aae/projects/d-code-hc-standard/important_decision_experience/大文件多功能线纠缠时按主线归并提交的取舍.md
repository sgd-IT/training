Conclusion: 当同一个大文件（如作业票主服务实现、其控制器与前端页面）同时承载多条功能线改动时，放弃"一个提交只放一个逻辑单元"的文件级拆分，改为把该文件整体归入其主线功能提交，其余功能线的接口层由该提交带出，并在提交清单里向用户显式说明这一归并与原因。

Rationale (trade-off): git 按文件粒度暂存，单文件内的多主题改动无法在不引入交互式暂存/hunk 拆分的前提下分开提交；强行拆分会导致同一文件被反复部分提交、中间提交不可编译。选择"文件数少但每提交内容真实"优于"提交数好看但内容被切碎"。

Rejected alternatives: ① 用 `git add -p` 按 hunk 拆分——在 PowerShell 非交互 shell 下不可稳定驱动，风险高于收益；② 全部合并成一个巨型提交——彻底丧失可回溯性，被否；③ 先重构拆文件再提交——超出本次"提交"授权范围，被否。

Applicable / expiry conditions: 适用于累积大量改动、单次提交授权下的分批落库场景；当项目引入按 hunk 暂存的可靠工具链，或相关大文件已被拆薄（单文件只服务一条功能线）时，应回到严格的最小单元口径重新评估。

Notes: 后续同类任务（作业票权限改造，11 个已修改文件拆成 5 个提交）再次验证该策略可用：BaseWorkSpecialServiceImpl.java、BaseWorkSpecialMapper.xml、SysUserMapper.java/.xml 与新增 SQL 脚本统一归入 feat(workSpecial) 一个提交，用户在确认清单后未对粒度提出异议。执行要点是清单中每个提交都要列出所属文件全集并写明归并理由，否则用户会误判为违反最小单元口径。注意此归并仅解决"文件归属"问题，与提交前是否取得用户对提交信息全文的确认无关——后者仍需单独满足。
