本平台向园区平台上报人员时有两套并行标识，取值来源不同且不可互换：

- 实时定位上报：LocationTask.java 组装报文时 personId = people.getOutId()（即 base_contractor_people.outid，恒为 UUID），cardId = 定位系统 position.mac；该取值自 2026-03-13 提交起生效，此前无 HTTP/UUID 通道。仅上报 isOnline=true 的记录，人不在厂则园区表不会新增该人。
- 作业票推送：operatorId 来自 APP 选人链路，8 个 Fragment 均执行 bean.setId(personnelListBeans.get(i).getSyncId())，即 base_work_special.operatorId 存的是 sync_id 逗号串。
- outid 由 BaseContractorPeopleServiceImpl 新增/同步时 IdUtils.fastSimpleUUID() 生成；sync_id 在整条定位同步链路中从不写入，唯一写点是 TaskPractitionersPersonMapper.updatePerson(@Param("syncId"), @Param("outerId"))，调用处传 (outerId, outerId) 使 sync_id=outid，而该任务 sys_job 状态为停用且 cron 是每月 1 日。

反直觉结论：园区"人员定位基础信息表"中的人员ID取决于该人第一次被上报时所用的标识，因此库内两代编码并存——历史内部人员 sync_id 为 19 位雪花 ID（base_work_special 中雪花 operatorId 成功 60 条、失败 1 条），2026-03-13 后进园区的人为 UUID（UUID operatorId 成功 2 条）。判定某字段是否"正确"不能只看字段名，必须查具体人员在园区侧的实际ID；新录入人员没有雪花 sync_id 来源，沿用 sync_id 口径必然匹配失败。

注意：本条描述的是两条通道的取数事实；推送时不得把 operatorId 转成定位卡号这一硬约束见"作业票推送operatorId必须传人员定位UUID原值"，口径选型权衡见"作业票operatorId采用逐人兼容而非统一单一ID口径"。
