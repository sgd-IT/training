作业票（base_work_special）向省厅平台的同步是"状态触发式"结构，删除类变更天然不在同步覆盖范围内：
- 推送唯一出口是 PlatementTicketNewApi.startTicket(entity[, validate])，被四条业务路径调用：新增保存(saveWorkSpecial)、开工(startWork)、完工(endWork)、批量补推；此外 GET /base/workSpecial/upload?outerId=xx 是无过滤的人工调试推送口。
- 平台专门的物理删除接口 `/openapi/work/deleteWorkSpecial/` 在 OpenApiConstant 中已被注释停用，平台改为主数据接口的 deleteMark=1 表达删除，因此"删除是否同步"完全取决于本地删除流程是否主动调一次 startTicket。
- 补推的两条候选查询（selectUnsyncedOuterIdsByDateRange / selectAllOuterIdsByDateRange）都带 `deleteMark = 0` 过滤，已删票永远不会被补推通道捞起——即删除推送一旦失败就没有自动重试路径，只有 sync_status='2' 留痕。
- deleteMark 不在 NON_PLATFORM_FIELDS 剔除名单内，每次推送都会带上该字段；列为 varchar(50) DEFAULT '0'，正常票推送时必有值。
- BaseWorkSpecialValidator.validateBaseWorkSpecial 在 startTicket 内是启用状态（其上方"暂未开放使用"的注释已过时），93 项校验会拦截历史脏数据（如 workStatus='1' 缺 checkTime）。

## Notes
- 第 3 条中"已删票永远不会被补推通道捞起、删除推送失败没有自动重试路径"的结论已失效：项目已新增独立接口 POST /push/deletedWorkSpecial（走 selectUnsyncedDeletedOuterIdsByDateRange / selectAllDeletedOuterIdsByDateRange，按 deleteMark=1 + updateTime 范围过滤，onlyUnsynced 默认 true，推送时 validate=false 跳过 93 项预校验），删除推送失败的票可在该接口重推。原有 /push/workSpecial 等接口仍保留 deleteMark=0 过滤，本条其余各点仍然有效。
