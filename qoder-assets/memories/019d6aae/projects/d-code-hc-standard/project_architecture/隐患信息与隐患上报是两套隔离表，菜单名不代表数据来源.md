PC 端「隐患信息」菜单在后端唯一对应 BaseHiddenTroubleController（`@RequestMapping("/base/hiddenTrouble")`、`@Log(title = "隐患信息")`），数据实体是 base_hidden_trouble；「隐患上报」菜单对应 BaseHiddenTroubleUploadController（`/base/hiddenTroubleUpload`），实体是 base_hidden_trouble_upload。两张表在 SQL 层零 JOIN、零同步（BaseHiddenTroubleMapper.xml 的 selectHiddenTroubleList 只 from base_hidden_trouble），任一表新增都不会在另一表生成记录，因此两个菜单看到的隐患条目天然不是同一批。

字段命名口径互斥，可用来反判一条隐患属于哪张表：
- 上报表独有：registrant 登记人、registTime 登记时间、dangerManageType 治理类型、dangerManageDeadline 治理期限、dangerName 隐患名称、dangerDesc 隐患描述、businessState（0待治理/1待验收/2验收不通过/4验收通过）。
- 主表独有：codeNumber 隐患编号、findUserName 发现人、findTime 发现时间、requirementTime 落实要求时间、responsibleName/responsibleUserName 责任单位/责任人、rectificationUserName 整改人、status（0待认领/9已认领/11·20整改中/21待复查/22待延期/30整改驳回/31已关闭）、dataSource/relationKey。

反直觉事实：仓库内 ruoyi-ui 与 Android 工程均不存在标题为"隐患详情"的弹窗组件，若界面上出现以「装置/单元/治理类型/限期时间/排查人/排查时间/隐患内容」为字段的"隐患信息"详情弹窗，则该数据实体实为 base_hidden_trouble_upload（上报表），只是被仓库外的新前端挂在「隐患信息」菜单下展示——菜单名与实际数据来源错位。判断归属不能凭菜单名，须用 F12 看删除请求 URL（/base/hiddenTrouble/{id} 还是 /base/hiddenTroubleUpload/{ids}）或按上述字段口径比对。
