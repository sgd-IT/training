PlatementRiskCheckUnitApi.saveEnable() 是向园区平台推送风险单元状态变更的权威 API 方法；base_risk_unit_log 表用于存储停机记录；DataSyncTask.autoSyncUnitStatus() 及其子方法 autoActivateExpiredUnits() / autoDeactivateActiveUnits() 负责定时自动启停逻辑（仅在每天两个固定时刻 23:30 与 6:00 运行，未来时间的启用最多有约 24 小时延迟）；sync_status='0' 是触发 syncRiskUnit() 将本地状态变更同步至平台的必要数据库标记。

启停时间错位的另两处结构性成因（实测代码取证）：
1. TaskList.java 的"天/月/年"周期分支忽略 base_risk_task.work_start_time 字段，把 create_time/plan_time 硬编码为 '00:00:00'，导致所有任务在凌晨出现。
2. BaseRiskUnitLogServiceImpl.insertBaseRiskUnitLog() 在记录创建时无条件把单元状态置为 '1'（停机），不参照配置的 stopTime，造成提前失效。

## Notes
- 【启停同步只到"任务层"，不到"记录层"（2026-10 实测补充）】本条第 1、2 项描述的是"时刻错位/提前失效"，但停用后排查任务仍持续派送的真正断点在记录层：单元停用时任务 status 已联动置 1、task_next_time 冻结（这一层是同步的），而小时周期分支已在当天 00:10 一次性把全天班次写入 base_risk_task_record，这些已排定的未来班次不会随停用撤销，APP 按 create_time<=NOW() 照常放出。判断"开停是否同步"必须分任务层与记录层两层核对，不能只看 base_risk_task.status。详见「排查任务小时分支一次排完整天导致开停只同步任务层不同步记录层」。
