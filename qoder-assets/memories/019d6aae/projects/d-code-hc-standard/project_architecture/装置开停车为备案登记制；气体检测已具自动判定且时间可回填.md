两处曾被误判为"不可自动化"的结构事实，其中第2点已于本轮代码核查更正：

1. 装置开停车（base/deviceCtrl）是"本地登记 + 上报园区审核"的备案链路，不是控制执行。BaseDeviceCtrlService / DeviceCtrlController 提供 add/sync/getById/page，前端 deviceCtrl/index.vue 维护 startTime/endTime/ctrlMode 并校验 majorHazard 关联单元编码；PlatementDeviceCtrlApi 走 OpenApiConstant.DeviceCtrl.save/detail/page 上报园区。系统内不存在任何下发装置开关指令的通道，也没有开停计划的修改接口（只有新增与同步）。因此"装置按设定时间自动开停车"能实现的准确语义是"到点自动生成开停车记录并上报园区"；若要落地定时执行，可复用 ruoyi-quartz 的 DataSyncTask 模式（@Scheduled + selectUnsync* + sync(ids) 批量补偿），该框架已有 autoSyncUnitStatus 自动启停先例。真实控制物理装置属 DCS/生产范畴，不可按常规功能开发估时兜底。

2. 【已更正】气体检测数据实际上具备程序化合格判定能力，且检测时间可回填。此前判断"standard/result 为自由文本无法自动比对""insertBaseWorkSensor 会把 time 强制设为 DateUtils.getNowDate()"均与现状不符：
   - 系统已内置 com.ruoyi.common.utils.GasJudgeUtil，含 LEL_TABLE（可燃气体按爆炸下限分档，如 ≤0.5%/≤0.2%）、TOXIC_LIMIT_TABLE（毒性阈值）、氧气 19.5%~23.5% 区间，录入后经 GasJudgeUtil.judge 直接返回达标/未达标结论（见 BaseWorkSpecialServiceImpl 按 sensor.type 0有毒/1可燃/2氧气分别调用）。故"结果是否合格"是可自动判定的，不再是纯文本盲区。
   - 检测时间 time 并非服务端强制覆盖：移动端 App（other1 项目 ActivityYasAnalysis）在录入页可手动选择分析时间（默认当前时间，可拉起时间选择器改为真实取样时间，提交补秒），后端 insertBaseWorkSensor 按"前端传了就以前端为准、没传才取当前时间"处理。正因 time 可回填，开工前 30 分钟窗口校验（checkGasDetection 读 base_work_sensor.sensorList）才有实际意义。
   - 仍需注意的边界：平台侧推送契约（ApiSensorDto/PlatementTicketNewApi）仍按文本字段传输，本地自动判定结论不会体现到监管平台；历史自由文本记录只能跳过回溯判定。

3. 录入通道有两条且互不相通，勿混淆：电子票体系 POST /api/special/addWorkSensor → base_work_sensor（App 录入，参与开工 30min 校验）；老纸质票体系 POST /api/ticket/addAnalysis → base_ticket_analysis（PC 端 base/ticket/indexShow.vue 展示，不参与 checkGasDetection）。PC 后台无 addWorkSensor 调用，即 PC 不能录电子票气体数据。
