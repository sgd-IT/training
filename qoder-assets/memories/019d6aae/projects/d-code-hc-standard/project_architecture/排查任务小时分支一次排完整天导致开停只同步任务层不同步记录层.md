风险单元停用后排查任务仍照常派送，根因是派送分两层而只有第一层随开停同步：

① 任务层已同步：单元置停用（status=1）时 updateStatusByUnitId 联动把该单元下任务置 status='1'；TaskList.addRiskTaskRecord（sys_job 104，cron `0 10 0 * * ?`）取数条件为 status=0 AND task_next_time<=NOW()，故停用后不再排下一次班，task_next_time 冻结不漂移。

② 记录层未同步：小时周期分支在每天 00:10 一次性把当天全部班次排完——work_start_time=work_end_time='00:00:00' 被判定为隔天，班次窗口为今日 00:00 至次日 00:00，for 循环 planTimeEnd += cycle 逐班生成，每条 create_time = planTimeEnd - cycle、plan_time = planTimeEnd，收尾把 task_next_time 写成次日 00:00（粗粒度游标，与"下一个班次点"无关）。条数可验算：4 条 1h + 3 条 2h → 4×24+3×12=132 条/天，与库内实测每日 132 条吻合。

后果：排班粒度是"天"、开停粒度是"时刻"，日内任何时刻停用都发生在排班完成之后，已排定的未到点班次无人撤销；APP 待检按 create_time<=NOW() 放行，于是停用后仍持续冒出待检。历史复现非偶发：某单元停机窗口 00:00~11:57，当天仍排满 132 条。

配套约束（改造时必须同时满足）：
- job 105 的逾期 SQL 条件为 check_status=0 AND plan_time<=NOW() 且不含 deleted 判断，若回收记录时只置 deleted=1 而 check_status 仍为 0，会被改成 check_status=4 冒到"逾期"栏，故回收须物理删除。
- task_next_time 在天/月/年分支与小时分支语义不同（前者=下一轮派送日 00:00，后者=下一个班次点），任何按游标的归一逻辑必须按 check_cycle_unit 分开处理。
- 平台推送侧不受影响：getSyncRecordList 要求 check_time 非空，未检查的记录本就不推。
- Quartz 改 sys_job 的 cron_expression 后 trigger 仍持旧表达式，须经 RuoYi 定时任务编辑接口刷新或重启才生效；代码内 @Scheduled 发版即生效。
