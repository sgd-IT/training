hc-standard 中把 base_contractor_people（人员库）与 sys_user（账号库）做身份关联时，稳定的关联键是「姓名」而非「手机号」。实测证据：base_contractor_people.phone = sys_user.phone_number 仅命中 121/161，且存在同人两库手机号不同的硬冲突（胡军 sys_user 侧 18571056077、人员库侧 13469816026；余威同样不一致）；而 base_contractor_people.name = sys_user.nick_name 在测试库命中 140/155。因此任何"由人员身份反查登录账号 user_id"的逻辑（如作业票监护人/操作权限判定）应按 nick_name=name 关联并加 user_type='01' 过滤，不要假定两边手机号一致。

del_flag 过滤口径必须按场景分治，不可一刀切限定 del_flag='0'：
- 新建票时的实时反查（resolveGuardianUserIds / selectUserIdsByNickNames）用 del_flag='0' 是正确的——新票不应把操作权限授给已注销账号。
- 存量票一次性回填则必须放宽为 del_flag IN ('0','2')：正式库有 67 个 del_flag='2' 的历史账号，其中包含仍在历史票上担任监护人的人员（如「刘建飞」user_id 801/865），限定 '0' 会直接漏掉这类监护人使其无法操作自己的历史票。

重名风险按库别差异极大，写关联 SQL 前须在目标库实查：测试库 sys_user 内重名 nick_name 仅 2 个，正式库实测有 13 个（如「刘恒旭」对应 2 个账号、「罗念阳」对应 2 个账号）。因此：
- 回填 applyUserId 不可用 JOIN（一票匹配多行会报错或产生重复行），应改为聚合取值 MIN(u.user_id)。
- 回填 guardianUserIds 应用 GROUP_CONCAT(DISTINCT ... ORDER BY ...) 聚合成逗号串，配合 FIND_IN_SET 匹配多个分隔符形态（半角逗号/全角逗号/分号统一替换为半角逗号）。
副作用：按姓名匹配遇重名会同时命中多个 user_id，判定时任一命中即视为该人；外施队承包商人员在 sys_user 中普遍无账号（如正式库王鹏飞在 base_contractor_people 存在 id=963、contractor_id=1001，但 sys_user 无记录），其身份无法反查到 user_id，据此的登录/操作能力受账号体系现状限制而非代码缺陷。
