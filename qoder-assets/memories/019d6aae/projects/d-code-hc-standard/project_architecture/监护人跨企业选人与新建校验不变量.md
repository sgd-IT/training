hc-standard 移动端 other1 的 8 类票型建票 Fragment（FragmentHotWork / HeightOperations / ConfinedSpaceOperation / Hoisting / Electricity / MovingEarth / OpenCircuit / BlindPlate）复用同一套选人组件 DialogWorkPeopleMultiple（多选，用于监护人/安全交底人/接受交底人）与 DialogWorkPeopleRadio（单选，用于作业人），其数据源均调 getWorkPeopleList(contractorId, deptName, jobPost, name)。改造该链路须知三条结构事实：

1. 部门前置硬门禁：showDialogWorkPeoMultiple 内有 `if (mListDept.size() == 0) { showToast("请选择作业部门"); return; }`，而 mListDept/mListPost 由所选作业单位的 getGroupList(contractorId) 填充——外施队承包商企业名下无部门分组时该弹窗根本打不开；但用户口径确认"最终是本公司内部人员开票、只需能选到外施队的人"，故作业单位仍选内部企业(1001)、部门正常，此门禁不触发，无需放宽。

2. 跨企业选人不变量：getWorkPeopleList 传 contractorId=null 即返回全企业人员（后端 SQL `<if test="contractorId != null">` 条件生效），这是"内外各一"能选出内部人员的必要前提；searchPeople 若继续带 deptName 过滤则只能命中同部门，会漏掉另一侧人员——需按字段决定是否去 deptName。本轮实现用 Fragment 级 guardianMode 标志区分：仅监护人弹框设 true 并在 searchPeople 时不带 deptName（跨企业可选外施队），作业人 showDialogWorkPeopleRadio 保持原部门逻辑不受限。企业类型经 ContractorPeopleBean.companyType → MultiSelectBean.stringB 透传给前端做即时校验展示。

3. 监护人校验落点：validateGuardian 只挂在 BaseWorkSpecialServiceImpl.insertBaseWorkSpecial（新建）首行，编辑(update)/开工(startWork)/完工(endWork) 均不校验，存量票不受影响；jhr 为园区平台必填纯姓名逗号串不可改存储结构，校验只能按姓名反查 base_contractor.company_type(1内部/2承包商)。
