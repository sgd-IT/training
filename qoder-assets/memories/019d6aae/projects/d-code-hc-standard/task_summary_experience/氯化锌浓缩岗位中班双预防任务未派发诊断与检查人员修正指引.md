## Task description
- Core requirement: 排查"氯化锌车间浓缩岗位中班双预防到现在没派发任务"的原因，并给出可转发的修改指引
- Task background: 双重预防排查任务由 ruoyi-quartz 的 TaskList.addRiskTaskRecord（job_id=104，cron `0 10 0 * * ?`）每日凌晨生成 base_risk_task_record；APP 端 /api/risk/getTaskRecordList 按登录人 ID + create_time <= NOW() 过滤待检列表；MCP 只读连接落点为 tgr-gz-vue 库

## Execution process
1. 读 TaskList.java 确认小时周期分支 create_time = planTimeEnd - checkCycle（8 小时任务当日三条分别为 00:00/08:00/16:00），天/月/年分支已改为读取 work_start_time
2. MCP 核对 base_risk_unit：LIKE '%氯化锌%' 命中 3 个同名单元，仅 b24cefde...（status=0、deleted=0）有效，其余两个已删除/停用且无名下任务；确认系统内无独立"浓缩岗位"单元，岗位信息只在 troubleshoot_content 文本中
3. MCP 核对 base_risk_task：该单元 27 条任务全部 status=0/deleted=0，6 条 8 小时任务检查人为"文茂华,全正华,冯中卫"，sync_status=1 已同步平台
4. 误判纠正：MCP 返回 task_next_time="2026-10-10T16:00:00.000Z" 一度被当作未来时刻；用 DATE_FORMAT 取字符串原值后确认为 UTC+8 序列化偏移，真实值为次日 00:00
5. 记录侧验证：6 条中班记录（第3次）create_time=2026-10-10 16:00、check_status=0、deleted=0、check_user_id="830,832,720"，SQL 内比较 create_time <= NOW() 结果为 1，证明数据库层面已按时派发
6. job 侧验证：sys_job_log 显示 job 104 今日 00:10:02 执行成功（耗时 2816ms），job 105（改状态）每 10 分钟正常执行
7. 对照组验证：液氯储罐气化装置为 1-2 小时周期任务，当日 00:00 至 20:11 各轮均正常完成，证明 APP 派发链路整体通畅
8. 操作痕迹佐证：浓缩岗位第1次由冯中卫 02:03 完成、第2次由全正华 09:39 完成，第3次无人操作（create_by 为空）
9. 定位结论：非派发故障，而是任务"检查人员"配置与实际中班在岗人员不一致；给出改法——管理后台"风险管理→排查任务"按检查人员搜索后逐条修改，改动自次日起生效，当日已生成记录不会换人
10. 可见性边界核查：确认移动端仅此一个列表接口且强制按 SecurityUtils.getUserId() 过滤；因 SQL 用 like 包含匹配，"830,832,720" 会误命中 userId=2（系统管理账号），普通员工侧仍只有三人可见

## Notes
- MCP datetime 返回带 Z 后缀属 UTC 序列化，直接心算会把"已派发"误判为"未到时间"，必须用 DATE_FORMAT 或与同会话 NOW() 在 SQL 内比较
- sys_job_log 无 job_id 列，须按 invoke_target 过滤；sys_user 无 phonenumber 列，手机号字段名不同，盲写列名会报错
- 记录表 check_user_id 采用 like 包含匹配存在子串误命中风险（如 ID 2 命中 "720"），严格做法是按逗号切分精确匹配
- 用户口中"没派发"可能指 APP 待检列表、管理后台或园区平台推送三种含义，先用 AskUserQuestion 收敛入口再深挖，避免长时间单向假设

## Notes
- 【步骤 9 根因口径修正（2026-10-14 同单元复诊）】把"检查人员配置与实际在岗人员不一致"当作唯一根因过于绝对。本次同样反馈下实查：任务侧 27 条与记录侧两天各 26 条全部按时生成、应检人即中班三名在岗人员，链路完全正常；真实成因是使用者认知缺口——任务到点静默出现、无任何手机提醒，8 小时任务分 00:00/08:00/16:00 三批，未到点的班次记录在 APP 查不到，容易被说成"没派发"。因此结论应先排除这两类机制性认知缺口，再考虑改人配置。
- 【逾期处置口径补充】plan_time 到期未提交会被 job 105 自动置 check_status=4（TaskHandleMapper.updateRiskTaskRecord：check_status=0 AND plan_time <= NOW()），任务从"待检"移入"逾期"页签；APP 详情页仅在 checkStatus=="0" 时渲染"正常/异常"按钮，故逾期后无法在手机端补做，只能由管理员在后台处理或直接做数据修复。
- 【答复口径】若班组称"没收到所以没做"，可据库内 create_time 说明该批自派发时刻起即可见；完成的记录由 DataSyncTask.syncRiskTaskRecord 按 06:00/23:30 两批推送平台，未到批次不算故障。
