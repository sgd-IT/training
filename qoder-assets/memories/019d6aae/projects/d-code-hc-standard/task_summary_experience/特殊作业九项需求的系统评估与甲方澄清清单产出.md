## Task description
- Core requirement: 对甲方提出的 9 项特殊作业/人员证书/装置管理需求，逐条评估"待明确需求"列在现有系统中的落地口径，并按单人全栈工程师给出估时；后续追问签字流程是否明确、气体检测是否需要合格标准、哪些需求不合理，最终产出可向甲方发出的需求澄清清单。
- Task background: 需求横跨 PC 端(ruoyi-ui)、移动端(other1 Android)、后端(ruoyi-system/ruoyi-admin/ruoyi-quartz)与园区平台对接层(ruoyi-common platement)，原表已给工时（43=3人天、44=2、34=3、35=2、46=2、51=5）需校验合理性。

## Execution process
1. 盘点取证策略：先 LSP documentSymbol + SearchCodebase 并行摸清模块边界，再按"账号体系/选人数据源/状态机/平台契约/打印模板/定时框架"六个维度定向 Grep+Read，避免全文通读超大 Service。
2. 需求43（外施队独立办票）根因定位：APP 登录走 SysLoginService.appLogin/appPwdLogin，要求 sys_user 且 userType="01"；承包商人员仅存 base_contractor_people，无系统账号 → 断点在账号而非建票功能本身。PC 端 workSpecial 页新增/修改按钮自初版即注释，建票只能走 APP。
3. 签字分工可行性判定：base_work_approve_config 含 id/person/point/sort/source_type/wanGong 六列，但 batchWorkApprove 初始化时丢弃 person 字段；updateBaseWorkApprove 不校验签署人身份与顺序，PC 接口 ApiSpecialController.updApprove 同样开放 → "外施队签/公司签"缺"签署方"概念，必须补节点-签署方映射与校验。
4. 需求44（双人监护内外各一人）判定：jhr 为平台必填字段，多人用英文逗号分隔纯姓名串（PlatementTicket/BaseWorkSpecialValidator 证实），库内无来源标识；APP 选人为 DialogWorkPeopleMultiple 多选，数据源 getWorkPeopleList(contractorId,...) 限定"作业单位自己的人员" → **不放开选人范围就选不出"公司1人"，故"全部可选"是必要前提而非优化项**。
5. 需求32（气体多次录入/修改）判定为已基本实现：ActivityYasAnalysis 支持新增与修改，后端 /api/special/addWorkSensor、/updateWorkSensor 齐全，base_work_sensor 一对多按 time 倒序，打印模板循环渲染；剩余缺口为新增时 time 被后端强制覆盖为当前时间、无完工锁定、无作废入口。
6. 需求34（中断/恢复）关键约束：平台 workStatus 枚举固定 0未开始/1已验收/2进行中/3未验收/4已删除，无"中断"值 → 中断只能本地留痕，推平台仍显示进行中；APP 全仓库检索"中断|暂停|pauseWork|resumeWork"零命中，确认完全新建。
7. 需求35（开工前有效检测）方案分层：startWork 现只有安全措施+现场会签两道校验，无气体校验；提出三口径——A 仅控30分钟时间窗(1~1.5人天)、B 加自动合格判定(需结构化录入+阈值配置表，再+2~3人天)、C 人工下拉结论(+0.5~1人天)；并说明 standard/result 均为自由文本导致无法可靠比对。
8. 需求46（打印/PDF）判定：TicketsType.getTemplateByType 提供 8 类票型 docx 模板，printWorkSpecial 在完工时已生成 Word 上传平台，但 PC/APP 均无预览打印入口；PDF 建议浏览器另存（零依赖），后端归档需 LibreOffice 或商用库另计 1~2 人天。
9. 需求51（装置自动开停车）定性：已有 deviceCtrl 模块是"本地登记+上报园区审核"备案流，非控制执行，且上报后无修改接口；quartz DataSyncTask 的 @Scheduled + autoSyncUnitStatus 模式可作为到点自动执行的落点参考；"自动开关物理装置"属 DCS 范畴不可按 5 人天兜底。
10. 输出结构：① 逐条评估（现状+落地方案+估时区间）② 单人总量表（合计 17~24 人天，含变更项最坏约 30，加 15% 缓冲折 4~6 周）③ 关键路径排期（第1周账号体系为一切外施队需求前置）④ 甲方确认清单（阻塞/口径类）。第二轮追问补充《需求澄清清单》四段式：阻塞项→逐条问题→需甲方提供材料→需甲方知悉的平台约束。
