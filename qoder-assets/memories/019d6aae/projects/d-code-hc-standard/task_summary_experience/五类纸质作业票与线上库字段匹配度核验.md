## Task description
- Core requirement: 用户提供公司现行纸质票样（一式三联，共5页：动火/临时用电/高处/吊装/受限空间），询问这5张票"是否可以做"（按票样生成打印模板）以及票面字段是否匹配线上库 tgr-gz-vue。
- Task background: 特殊作业电子票链路为主表 base_work_special + 措施 base_work_step + 气体分析 base_work_sensor + 会签 base_work_approve/_config + 操作证 base_work_certificate + 措施配置 base_ticket_safe_config；需逐票栏目做字段落点核对并给出改造点清单。

## Execution process
1. MCP 可用性判定：全局 mcp.json 中 tgr-gz-vue 已配置但本会话 mcps 缓存目录未注册该服务名，直连调用不可用，改用兜底通道 D:\Tool\mysql-8.0.46-winx64\bin\mysql.exe 只读 SELECT。
2. 中文乱码处置：PowerShell 管道解码口径导致结果集乱码，--result-file 未生成文件、Start-Process 传 -e 参数被空格拆断；最终用 .NET ProcessStartInfo 设 StandardOutputEncoding=UTF8 并以 powershell -File 执行脚本，一次性批量取回正确中文数据。
3. 结构取证：information_schema.COLUMNS 一次取回 6 张表的列名+类型+注释（base_work_prepare 表名不存在，无该行返回）。
4. 关键纠错：首轮样例查询用 ticketsType='11' 返回 0 行；GROUP BY 实查确认 base_work_special.ticketsType 存的是 1~8（1动火88条、6临电56、4高处13、2受限3、5吊装3、7动土2、3盲板2、8断路2，共169条），而 base_work_approve_config.source_type 存 11~18，两套编码不可混用。
5. 措施条数比对：base_ticket_safe_config 按 source_type 分组计数得 11→16、12→15、13→14、14→15、15→20 条，与公司票样 16/14/15/20/15 项完全一致，且每类末条 editable=1 为"其他安全措施"。
6. 会签节点比对：实查 base_work_approve_config 确认动火6栏、临电4栏、高处4栏、吊装4栏与票样对应；受限空间仅"作业负责人意见→所在单位意见→完工验收"，比票样少"安全管理部门意见""班前班长验票"两节点（补 config 行即可，不改表）。
7. 数据质量核查：deptName 全库 0 条有值；workUnit 与 workUnitName 不一致者 136/169，且存在脏值 "0"，故票面"申请单位/作业单位"两栏只能同取 workUnitName。
8. 子表格式核查：operatorInfo 实为"姓名:身份证号,作业类别,证书编号"多人逗号拼接；base_work_certificate 同一人存在 personType=1/2 重复两条需打印去重；sensor 的 standard 为自由文本（"国家标准"/"国标"/"0"/"测试"）无法映射票面合格阈值，result 与 unit/unitShow 分列存储需拼接。
9. 风险辨识字典核查：sys_dict_data 的 b_t_risk_identify 值为 1~21（不补零），而主表 risk 存两位补零串（如 "02,07,09,10"），且字典项与票面14/15项不完全对齐（灼烫 vs 高温烫伤/化学品灼伤、其他爆炸 vs 化学爆炸/物理爆炸）。
10. 输出结论：5 张票均可做，最难的措施与会签配置已齐；列出 7 个待确认/改造点 + 工作量估算 6~10 人天 + 建议实施顺序（动火→临电→高处→吊装→受限）。
