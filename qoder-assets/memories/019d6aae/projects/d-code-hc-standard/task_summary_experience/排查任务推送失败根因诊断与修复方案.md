## Task description
- Core requirement: diagnose why '排查任务' (risk task records) were not pushed to the platform, answering "排查任务推送过去没有"
- Task background: the platform's '运行效果分析' showed '应完成 69 / 已完成 0', indicating a push failure; the local database showed base_risk_task.sync_status='2' with '批量操作超过最大限制'; the task required tracing the push code path to identify the exact root cause.

## Execution process
1. MCP database query: confirmed all 141 base_risk_task rows have sync_status='2' and sync_result='出错了，请联系管理员: 批量操作超过最大限制'
2. Code grep: located PlatementRiskCheckUnitApi.saveTask() and its callers (BaseRiskTaskServiceImpl.sync(), DataSyncTask.syncRiskTask())
3. Analysis of saveTask(): verified it has no internal batching logic, unlike the already-fixed saveTaskResult/saveTaskItemLog methods which use BATCH_SIZE=10
4. Cron job analysis: confirmed DataSyncTask.syncRiskTask() runs daily at 23:30/06:00 and fetches all unsynced IDs (including previously failed ones), leading to a dead loop of 141-item failures
5. Verification: checked selectUnsyncedIds SQL and confirmed it includes sync_status='2', proving the dead loop

## Notes
- The identical error message for base_risk_measure.sync_status='2' confirms PlatementRiskMeasuresApi.save() suffers from the same unbatched issue, requiring the same fix.
- The platform's '应完成 69' is computed independently and does not reflect our pushed tasks, as the task list never arrived.

## Task overview
Successfully diagnosed the root cause of the 排查任务 push failure: the PlatementRiskCheckUnitApi.saveTask() method performs a single, unbatched POST of all 141 tasks, violating the platform's batch size limit and causing a permanent failure loop. The fix is to add internal batching with BATCH_SIZE=10, mirroring the pattern used in saveTaskResult/saveTaskItemLog.
