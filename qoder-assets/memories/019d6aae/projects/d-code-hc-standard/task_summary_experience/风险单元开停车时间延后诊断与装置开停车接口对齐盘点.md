## Task description
- 核心需求一：要求系统输入的风险单元开停车时间与实际开停车时间严格一致，消除现存的"24小时延后指令"现象。
- 任务背景一：停机记录由前端 riskUnit/index.vue 提交 addRiskunitlog 落 base_risk_unit_log；实际状态切换依赖 DataSyncTask 的 autoSyncUnitStatus()（内含 autoActivateExpiredUnits / autoDeactivateActiveUnits）。
- 核心需求二：用户提供园区平台装置开停车接口文档（5.2.10.1 save、5.2.10.3 delete、5.2.10.4 单条、5.2.10.5 page），需盘点本地实现与平台契约的对齐度。

## Execution process
1. 定位延后根因（两处）：BaseRiskUnitLogServiceImpl.insertBaseRiskUnitLog 不判断 stopTime 是否已到，无条件立即把单元置为停用（status='1'）并联动停止排查任务，导致未来时间的停机提前生效。
2. 定位第二处根因：BaseRiskUnitServiceImpl.autoSyncUnitStatus() 只在每天 23:30 与 6:00 两个 @Scheduled 时点执行，activationTime/stopTime 到点后需等待下一个时点，最大延迟约 24 小时。
3. 提出改造方案（待用户确认，未实施）：新增停机记录时先比较 stopTime 与当前时间，仅当 stopTime <= now 才立即停用单元与任务，未来时间交由定时任务到点处理；另新增每分钟执行的纯本地状态切换任务（autoSyncUnitStatus 不涉及平台推送），原 23:30/6:00 的平台同步节奏保持不变。
4. 装置开停车对齐盘点结论：PlatementDeviceCtrlApi 的 save/detail/page 路径、BaseDeviceCtrl.isDeviceSelectionValid() 的装置编号 [0-9]{12} 校验、BaseDeviceCtrlService.normalize() 的重大危险源字段互斥、buildBody() 的 ctrlMode/startTime/endTime/files/unitLists/applicant 字段、AbstractPlatementResourceService 的 add/sync/delete 状态机均已与平台文档对齐。
5. 识别两处本地校验缺口：平台要求的"开车须校验该装置-单元最近一条审核通过记录为停车"的交替校验，以及"装置-单元维度时间段不得重合"的唯一性校验，本地均未实现。
6. 缺口难点结论：approvalStatus（审核通过状态）以园区为准且本地未落库，本地提前拦截需在 sync 成功后回写 approvalStatus，或新增前调平台 page 接口比对历史记录。

## Notes
- 风险单元开停车（base_risk_unit / base_risk_unit_log）与装置开停车（base/deviceCtrl → 园区 deviceCtrl 接口）是两条独立链路，不可混为一谈；用户提出的时间精确对齐只针对前者。
- autoSyncUnitStatus() 只改本地状态、不调平台 API，因此可安全提高执行频率；而 syncRiskUnit() 含平台推送，提频会增加远端调用量，两者应拆分为不同调度。
- 判定"24小时延后"不能只看定时任务频率，还需同时检查新增记录时的即时写入逻辑——本例中即时停用与低频定时恢复是两个叠加成因。
