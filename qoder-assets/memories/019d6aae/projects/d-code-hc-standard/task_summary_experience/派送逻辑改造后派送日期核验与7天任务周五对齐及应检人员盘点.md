## Task description
- Core requirement: 在派送逻辑改造后核实当前各排查任务会几号派送，并把唯一的周六 7 天任务（瞿彬、彭亨清）对齐到周五，随后盘点全库还有哪些人挂有派送任务
- Task background: 上一轮已修复 TaskList.java 递推基准与 updateStatusByUnitId 无条件重置两处漂移根因；用户关心存量锚点与新逻辑的实际生效结果

## Execution process
1. 只读 SQL 按 check_cycle_unit+check_cycle 聚合 status=0 AND deleted=0 的任务，输出 cnt/min_next/max_next/work_start_time，一次看清 68 条启用任务的分层派送现状
2. 明细查询 11 条 7 天任务，用 DAYNAME(task_next_time) 直接取星期名，避免心算跨月日期出错
3. 查 update_time >= 当天的记录判断部署后是否有人工新建/启停（结果为空，说明存量未被重排）
4. 给出单条 UPDATE 方案（同时改 task_next_time 与 task_start_time 为目标周五 00:00:00，WHERE 加周期与状态条件），并列出"明天就派（间隔13天空一期）"与"下周五起（空两期）"两个口径供选择，等用户确认后才动库
5. 用户要求确认后复查：发现该任务 task_next_time 已是 2026-10-23（周五）、task_start_time 同为 10-23，无需再执行 UPDATE；11 条 7 天任务全部对齐周五
6. 交叉核对 base_risk_task_record 历史（最新一条 create=10-17、plan=10-24、check_status=1 已完成），确认新一期 10-23 与上一期 plan=10-24 有一天重叠但不产生逾期或重复待办
7. 按 check_user_name 分组 + LEFT JOIN base_risk_unit 汇总应检人员清单（12 组），得出 7 天任务只有夏翔飞与瞿彬/彭亨清两组、其余为天1/小时/月季半年周期
8. 发现张艳军/文建新/尹超杰组的 check_user_id 存在 5 种排列顺序，按 ID 精确分组会把 7 条任务拆成 5 行造成人数统计偏差

## Notes
- 关键结论：新代码只保证"不再漂"，不会主动把已有的周五/周六锚点拉回周一；要让某天稳定必须单独执行一次数据对齐 UPDATE。
- 全部 68 条任务 work_start_time 均为 00:00:00，派送时刻仍是凌晨，日期对齐与时刻调整是两件事，需分别处理。
- 本环境 MySQL MCP 为只读连接，任何 UPDATE 只能交付 SQL 给用户执行，不得声称已代为改库。
- 该任务 update_time 停留在 2025-04-16，说明锚点是通过直接改库完成的，界面与 MyBatis 更新都会刷新该字段。

## Task overview
完成派送逻辑改造后的效果核验：确认 11 条 7 天任务下次派送统一为 2026-10-23（周五）且之后每周五稳定，输出了单条任务改派送日的可执行 SQL 与两种口径对比，并盘点了全库 12 组应检人员的周期与风险单元分布，同时暴露了 check_user_id 顺序不一致影响按人统计的数据质量问题。全程只读未改库。
