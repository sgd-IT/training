## Task description
- Core requirement: 完善人员定位报警类型处理，确保各类定位报警都能正常识别和推送；同时核查系统是否具备图示「基于定位的人员聚集预警功能」
- Task background: 当前人员定位报警只处理了部分类型（SOS），其他类型（低电量、休眠、反光衣等）被忽略；问题根因在三个接入通道的处理逻辑不一致且存在硬编码缺陷；需全面诊断并提出最小可落地修复方案。图中要求包含：1）覆盖内部员工/承包商/外来人员；2）预警半径≤15m；3）颜色预警模型（3人黄/4-6橙/≥7红）；4）24小时内推送至控制室/值班室；5）现场实时声光报警；6）预警确认与闭环流程；7）处置流程与责任人设置。系统通过WebSocket接入外包平台报警，需验证各环节实现情况。

## Execution process
1. 通过SearchCodebase和Grep定位到核心入口：/sync/addAlarmRecord（alarmCategory==111分支）的硬编码白名单 {"2", "32"}，其余所有类型直接return 0丢弃
2. 发现AlarmType枚举中alarmFix=1（人员定位）仅定义2条，与定位平台实际类型清单（TripAlarmListDto注释：44玩手机/41人员滞留/35人数异常/15睡岗离岗/7低电量/31SOS/13休眠/22反光衣/23安全帽）严重不符
3. 诊断出111分支去重键relationKey=卡id，导致同一张卡的多个报警类型（如SOS+低电量）合并为一条，类型信息丢失
4. 发现卡号查不到时throw ServiceException会整条丢弃报警，无任何记录
5. 确认WebSocket通道（WebsocketServiceImpl.sendMsg）虽不丢弃但硬编码if-else链，未命中类型均标记为"未知报警：X"
6. WebsocketServiceImpl.java：定位报警接收入口，type=5为「聚集报警」，消息字段仅含posX/posY/groupId/mapId/id/type/mac/timestamp，无人数/半径/级别字段
7. BaseAlarmRecord.java：报警记录领域对象，含alarmStatus(未处理/已处理)、confirmUser/confirmTime/solution，但无预警级别/聚集人数/半径字段
8. alarmRecord/index.vue：前端报警台账页面，支持按部门+岗位(postCode=3)分配接收人、确认处理闭环
9. 用户确认：人员定位功能为外包平台实现，本平台仅负责接收、入库、分配、确认闭环；聚集判定（半径/人数分级/声光）均在平台侧完成
