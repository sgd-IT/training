## 备注（本轮取证补充）
- **措施只能用 SQL 建**：后台「管控措施」新增表单只有分析单元/分析事件/一二三级分类/措施描述，**没有 risk_measure_code 字段**；而同步报文取 `CONCAT('GK', risk_measure_code)`，页面新增的记录编码为空会拼出 NULL 被园区拒收。故上文"数据修复（SQL脚本）"必须保留显式给编码的 INSERT，不可改走 UI 新增。
- **顺序硬约束**：必须先建措施 → 触发同步并确认 `base_risk_measure.sync_status='1'` → 再改隐患 measureId → 最后调 `/push/hiddenTrouble`。若先改隐患再同步措施，平台侧仍因措施不存在而挂错。
- **措施同步入口实测清单**：单条/批量用 `GET /base/riskMeasure/sync/{ids}`（权限 `base:riskMeasure:sync`，对应管控措施页勾选后点「同步」按钮）；全量 8 类补推用 `POST /push/riskTask?startDate=&endDate=`；`PushDataServiceImpl.rePushRiskMeasure(startDate,endDate)` 存在但**无独立 `/push/riskMeasure` 入口**，仅被全量补推调用。
- **重推后的状态副作用**：`/push/hiddenTrouble` 固定推 `businessState=4`，已关闭隐患重推后平台显示「验收通过」；要保持「待治理」需另加按 businessState=0 的单条补推接口（属代码改动）。
- **区域→装置单元映射现状核实**：information_schema 无任何 area_unit/unit_area 型映射表；`base_area` 仅有 `equipment_id`（氯化锌车间等均为空），无 risk_unit_id。因此改造前系统对区域与措施的组合**零约束**，任何"某区域归某单元"的表格都只是待企业确认的候选口径，不得当作现状对外表述。
- **执行通道卡点**：当前 MySQL MCP 为只读，INSERT/UPDATE 无法执行；工作区 token 文件为透明加密内容不可用于接口调用，重推需用户提供可写库或可用登录态。
