Bug class: 生产代码里残留"临时调试"拦截块（如 `if (Boolean.TRUE) { log.warn(...); return; }`）静默截断对外推送链路，且容易被误认为历史提交的一部分。

Root cause: 这类块是调试期手工粘贴进文件的、从未 commit 的工作区改动（本次证据：`git log -S "独有字符串" -- <file>` 返回空 + `git diff` 中该行为 `+` 开头 + `(Get-Item $f).LastWriteTime` 指向调试当天）；因缩进不规整（注释带 tab、`if` 顶格），常规 grep 单行匹配难以判定归属。同时本工具沙箱的 Node fallback shell 下 `git checkout -- <file>` 会静默不生效，grep 仍能命中被"删除"的内容，若据此以为已还原则会把拦截代码提交上去。

Fix pattern: 三步闭环——① 用 `git log -S "<块内独有中文串>" -- <file>` 判空确认是否入库；② 未入库时用 SearchReplace 精确删除整块（含其后空行），保留原上下文衔接；③ 以 `git diff --stat -- <file>` 输出为空作为"已与 HEAD 一致"的唯一判据，再用全仓 grep 关键词（拦截/跳过推送/mockSuccess/skipPush）确认零残留。

Reusable lesson: 不要凭 `git checkout` 有执行就认为文件已还原，因为沙箱 fallback shell 会吞掉该操作，必须用 git diff 空输出复核；也不要把"临时调试"块当历史遗留去改写注释，它本就未入库应整块删除。适用于提交前清理工作区调试残留、判断某段代码是否从未 commit；不适用于已入库的历史调试代码（那需 revert 提交而非删工作区）。

## Notes
- 补充第四种形态（三端地址核查会话实测）：`git status` / `git diff` 干净**并不必然**等于"用户没改"，还可能是改动停留在 IDE 编辑器 buffer 而未保存到磁盘。此时文本读取类视图可能呈现未保存内容，而 `git hash-object <文件>` 与 `git rev-parse HEAD:<路径>` 两个 blob sha 完全一致、文件 mtime 仍是数天/数周前。判据须升级为三方交叉：hash-object vs HEAD sha + mtime + 直接读盘取行；三者一致才可真判"无改动"，否则要提示用户先 Ctrl+S，否则会按"已回切"的错误前提继续打包或重启服务。
