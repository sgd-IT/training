按字段名下结论前须按取值形态分组统计推送结果

Bug class: 用单一字段名判定外部平台标识是否合法，导致误判"某种取值必然推送失败"
Root cause: 园区"人员定位基础信息表"中的人员ID取决于该人第一次被上报时所用的标识，同一字段会出现两代编码并存。本项目实测 base_work_special 按 operatorId 形态分组统计得：19 位雪花形态成功 60 条、失败 1 条，UUID 形态成功 2 条；而 LocationTask 上报 personId 取 outid（UUID）自 2026-03-13 起生效（git blame 验证）。仅凭宋鹏那条"作业人员编码错误"就断言雪花不可用，忽略了历史人员是以雪花标识先入园区表的。
Fix pattern: 判定标识类字段是否可用时，先按"取值形态 × 推送结果"分组统计（SELECT CASE WHEN 字段 LIKE '%-%' THEN 'uuid' ELSE 'snowflake' END, sync_status, COUNT(*) ... GROUP BY），再用 git blame 确认各通道取值的生效时间，最后逐人核对目标平台侧的实际ID；不要直接给字段下"某形态必错"的结论。
Reusable lesson: 不要因为存在一条失败样本就断定某种取值形态整体不可用，因为平台侧人员ID按首次上报标识分代存储、两种形态可同时合法；应先做形态×结果的分组统计并核对取值生效时间再定论。适用于改动跨系统人员/设备标识映射（如 operatorId、personId、outerId、sync_id）；不适用于平台明确只接受单一格式且有官方文档约束的字段。

补充同源教训（2026-10 需求台账核对会话）：同一类"以来源标签代替实测"的错误也发生在需求状态判定上——甲方/台账标注为"未完成"的 9 条需求，逐条 grep 后端方法名 + APP 按钮文案 + PC 事件处理函数后实测有 5 条代码层早已完成（中断恢复、开工前气体检测、PDF预览导出、气体多次录入修改、外施队证书企业筛选）。凡判断功能是否已实现，必须落到调用点与 UI 入口取证，既不能采信台账/备注文字，也不能沿用上一轮评估记忆的结论快照。

## 完成度取证编排补充（来自存量功能核验会话）
Step 1: 落点锚定 — SELECT @@hostname + DATABASE() 确认 MCP 所连库别；同名库必须靠 hostname 锚定。
Step 2: 三层调用点取证 — 后端 Service/Controller 方法名 + APP 按钮中文文案与 R.id 控件 + PC 页面事件函数，三类 grep 交叉出命中矩阵；缺一即查 SHOW COLUMNS 核对新列是否在目标库存在。
Step 3: 入口实查 — 菜单按 component/perms LEFT JOIN parent_id 实查 sys_menu，前端路由与注释掉的按钮不代表能力边界。
Step 4: 六类代码卡点反推用例 — ①分支枚举 ②输入变形 ③时序窗口 ④数据前置 ⑤绕过UI直连接口 ⑥并发幂等，产出"改什么→期望什么"成对断言的用例表。
Step 5: 运行态双向取证 — adb 驱动模拟器（每轮重新 dump 取坐标）+ DB/API 记录双查确认终态字段。
Step 6: 免写库递推验证 — 只读递归 SQL 按新规则逐期重算日期（禁用假想初值，先查当前计划字段真实值）。
Step 7: 能力边界实证 — 读 UA 与可见性确认工具可操作范围。
