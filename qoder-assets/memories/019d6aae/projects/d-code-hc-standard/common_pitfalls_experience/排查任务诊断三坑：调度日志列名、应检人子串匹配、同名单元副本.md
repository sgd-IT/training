Bug class: 排查任务诊断中的三处具体踩坑（列名假定 + 人员匹配规则 + 同名副本）

Root cause 1（列名）：RuoYi 的 sys_job_log 表主键是 job_log_id，没有 job_id 列，只有 invoke_target / job_name / status / exception_info / create_time；sys_user 表也没有 phonenumber 列（手机号在本项目另有字段）。按直觉写 `WHERE job_id IN (...)` 或 `SELECT phonenumber` 会直接报 Unknown column 并浪费一轮往返。
Fix pattern 1: 对不确定的表先查 information_schema.COLUMNS 拿列名与注释，再写业务 SQL；查调度执行情况按 invoke_target 模糊匹配而非 job_id。
Reusable lesson 1: Don't 凭 RuoYi 通用版记忆假定扩展库的列名，因为本项目表结构有定制差异会导致查询报错；instead 先取列结构。Applies when 首次在 hc-standard 库查询非核心业务表（调度日志、用户表等）；does not apply to 已在既往任务中核实过列名的核心表（base_risk_task / base_risk_task_record）。

Root cause 2（人员匹配）：BaseRiskTaskRecordMapper.xml 的待检查询用 `check_user_id like concat('%', #{userId}, '%')` 做子串包含匹配，而 check_user_id 存的是逗号分隔 ID 串。短 ID 会命中长串的数字子串——实测 "830,832,720" 除三名应检人外还命中 userId=2。
Fix pattern 2: 判定"某人能否看到某任务"必须按该包含规则实算而非只看名单字面人员；若要收口需改为按逗号切分的精确匹配。
Reusable lesson 2: Don't 用"ID 是否在逗号串里"的心算去回答可见性问题，因为包含匹配会带来额外误命中账号；instead 直接在 SQL 里复现 mapper 的 like 条件反查全部命中账号。Applies when 排查移动端待检列表可见范围或核对任务应检人；does not apply to 管理后台的记录列表（其查询不按登录人过滤）。

Root cause 3（同名副本）：base_risk_unit 存在多个 risk_unit_name 完全相同的历史记录（部分 status=1/deleted=1 或 risk_obj_id 为空），按名称直接取第一条会命中失效副本。
Fix pattern 3: 按名称查出多条时，必须用 deleted=0 AND status=0 过滤出唯一生效单元，必要时再回溯其所属风险对象确认归属。
Reusable lesson 3: Don't 拿同名主体的第一条查询结果继续向下分析，因为失效副本的状态会导出相反结论；instead 先按删除标记与启停状态筛有效记录。Applies when 通过名称定位任何双预防主体（对象/单元/任务）；does not apply to 已有唯一业务编码可精确定位的场景。
