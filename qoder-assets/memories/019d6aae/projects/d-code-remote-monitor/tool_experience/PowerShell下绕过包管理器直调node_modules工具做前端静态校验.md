## Usage Scenario
在 Windows PowerShell 环境用命令行对前端仓库做权威静态校验（ESLint / vue-tsc），或判断一次类型检查失败是否由本次改动引入。典型触发：npx/pnpm 脚本被拦；改完页面需要零告警证据。

## Usage Method
1. 绕过包管理器：`npx eslint` / `npx vue-tsc` 会被 PowerShell 执行策略拒绝（UnauthorizedAccess / PSSecurityException），cmd 包装又被沙箱以"终端为 PowerShell 须用 PowerShell 命令"驳回。先 Set-Location 进入前端仓库，再用 node 直调包内 bin 入口（eslint 与 vue-tsc 各自的 bin js 文件），或直调 `node_modules\.bin\<tool>.cmd`（如 vue-tsc.cmd --noEmit、eslint.cmd），效果与 pnpm run 等价；pnpm 自身报 ERR_PNPM_IGNORED_BUILDS 时同样走直调。
2. 输出捕获：重定向用 `*>` 捕获全部流写入日志文件，随后 `Write-Host $LASTEXITCODE` 打印退出码；后台任务靠读该退出码判结束。
3. 结论判读：ESLint 无输出且退出码 0 即干净。vue-tsc 的退出码与错误总数都不能作为"本次有问题"的判据——本仓库存在数百条存量类型错误。正确判据两步：① 在输出里按改动文件路径过滤只看命中行；② 与 logs 目录下历史 vue-tsc 基线日志逐条比对同文件同错误（删代码会让行号整体漂移，行号不同不构成新增），再辅以 git diff 确认相关符号未被本次触及。

## Notes
- 直接调用 npx 会被 PowerShell 执行策略整段拦截，造成误判为"工具没装"，必须改用 node 直调包内 bin 入口。
- 拿 vue-tsc 非零退出码就断言自己写坏了类型会造成大面积返工与无关修复，必须先按改动文件过滤再与历史基线比对确认无新增。
- 语言服务未就绪时问题检测工具返回"Unable to detect code problems"不可作判据，应转上述命令裁决。
- 在原文件上直接运行格式化器会把仓库历史遗留格式问题一并改写而使本次 diff 失真，格式校验应改用临时隔离副本比对。
