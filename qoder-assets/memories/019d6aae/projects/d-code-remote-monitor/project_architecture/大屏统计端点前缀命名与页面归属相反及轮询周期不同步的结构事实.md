消防大屏统计链路的命名与周期不变量（grep 前端调用点 + 生产 infra_api_access_log 双向核实）：

一、端点前缀与页面归属相反，是改造时最容易误判的切入点。`FireDashboardController` 里 `/eiot/firewatch/dashboard/*` 虽在注释与前缀名上写作"监控中心大屏"，实际是监控中心、报警大屏、值守大屏三块屏的唯一共用总入口；字面更像值守大屏专用的 `/eiot/firewatch/duty-screen/*`（getDutyScreenStatistics）前端零调用，2026-10-30 其接口声明、实现与 Controller 端点已三处一并注释下线。因此任何针对大屏统计的缓存、限流、字段改造只改 dashboard 一套即全覆盖，判断影响面的唯一依据是 grep 前端 .vue 的调用点，不能采信 Controller 注释与前缀名。反向约束：注释掉一个 Service 方法必须同时清点其全部调用点，只注释接口与实现而漏掉 Controller 调用点会直接编译失败（报"找不到符号"）。

二、三块大屏的主轮询周期不同步，缓存新鲜期须按最慢的一档取值。duty-screen/index.vue 为 setInterval(loadData, 60000)，monitoring-center/index.vue 与 alarm-screen/index.vue 为 30000（useVisiblePolling），另有 usePropertyMapData 独立 30 秒轮询 /property/list。线上实测 statistics 稳定约 182 次/小时，恰为 60+120 之和，可用作轮询组数反推校验。故 STATISTICS_FRESH_SECONDS=70 的成立理由是"盖住值守大屏 60 秒整轮"，若按 30 秒假设解释该值则理由错误；同理预热 fixedDelay=60s 必须小于新鲜期这条时序约束，其基准也是值守大屏的 60 秒而非 30 秒。

三、流量权重与鉴权形态的反直觉分布。statistics 单端点占 firewatch 域总耗时约 96%（4442 次 × 平均 1952ms = 8670 秒），而同页链路 realtime-alarms 仅 2.8%、property/list 仅 0.2%，给它们加缓存的收益可忽略。97% 调用的 request_params 为 {"query":null,"body":null}（不带 tenantId、全部 user_id=1 超管两个出口 IP），即绝大多数流量落在 all 全量视角那一份 key 上，定时预热优先刷 all 收益最大；按租户分 key 的边际价值只在超管主动切租户时才兑现。极值 263 秒出现在同一 IP 一分钟内三次请求之间，属连接池排队放大而非单条慢 SQL。
