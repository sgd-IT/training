消防值守告警链路"看起来存在实则不成立"的结构事实（2026-10-22 需求 29/42/34 落地后状态更新）：

1. 【已修复】报警 Excel 导出曾长期是伪实现：FireAlarmOrderController 只有 /statistics 与 /export-pdf，前端 handleExportExcel 请求 /eiot/firewatch/alarm-order/export 得 404 后被 catch 静默兜底调用 exportTableToCSV()，只导当前页（pageSize=20）且格式为 CSV。现已新增 /export 端点 + AlarmOrderExportVO（@ExcelProperty 列：报警编号/所属单位/设备名称/设备类型/报警类型/报警级别/报警时间/处置状态/处置人/处置时间/响应时长），实现复用 pageAlarmOrders 分页链路保证与列表同源，上限 2000 行；前端已删除 CSV 静默兜底，失败明确提示「导出失败，请稍后重试」。项目内通用范式仍是 framework ExcelUtils.write + VO 上 @ExcelProperty（FireHazardController / FirePatrolTaskController 为先例）。

2. 大屏实时告警的状态字段曾被二次覆盖：FireDashboardServiceImpl.convertToRespVO 先用 AlertOrderStatusResolver.resolveOrderStatus(record) 赋 orderStatus，随后又被 readFlg 三元表达式覆盖，使大屏只剩 pending/closed 两态而处置中心有四态——这是"今日警情与火警处置内容不匹配"的直接成因。read_flg 不可作为处置状态判据，handle_status 才是唯一权威。（口径统一批次已消除该二次覆盖。）

3. 【已修复】"实时告警"列表与"待处理"计数曾语义不同源：待处理走 countTodayUnreadAlerts（今日且 handle_status<3），实时告警走 selectLatestAlerts（ORDER BY alert_time DESC LIMIT 10，既不限状态也不限日期），日期过滤靠前端 filterTodayAlarms，badge 取 alarmList.length，故"待处理 0、实时告警 10"是三指标混用的必然结果。现改为 AlertRecordMapper.selectTodayUnclosedAlerts，badge 取 todayAlarm.pendingCount，列表最多显示 10 条；selectLatestAlerts 因无调用方已作死代码删除。

4. 同一指标族的判据与时间范围必须逐出口核对，改一处极易漏其余（浏览器端到端实测取证）：把统计侧计数改为 ORDER_STATUS_CASE_SQL 判据后，实时列表 SQL（selectTodayUnclosedAlerts）仍残留 handle_status < 3，实测出现"待处理 0 / 列表 10 条"（已补改为同一段 CASE IN ('pending','deferred','handling')）；同理大屏"今日警情"是当日范围而处置中心 orderStatus=unclosed 是全量历史，实测点进去显示 262 条与卡片 0 条冲突。alarm-order 链路的数字出口共四类需逐一比对判据+时间范围是否同源：①/dashboard/statistics 计数字段 ②selectTodayUnclosedAlerts 列表 ③/alarm-order/page 的 orderStatus 筛选分支 ④/alarm-order/status-count 顶部徽标。

5. 【已收口，2026-10-23】第④项徽标不再取全量：today=1 场景下徽标改取当前筛选返回的列表 total，与列表同范围，"列表 0 条、徽标 262"消失。同时"今日"的实现方式已变更——不再是前端拼当天 alarmTimeBegin/alarmTimeEnd 字符串，而是新增 AlarmOrderPageReqVO.todayOnly 参数，由 AlertRecordMapper.TODAY_CONDITION_SQL 常量提供 DATE(FROM_UNIXTIME(alert_time / 1000)) = CURDATE() 这一段，统计侧三处查询与列表筛选共用，避免浏览器/JVM/DB 时区各算一次导致整体差一天；用户手动选时间范围时以用户为准且不传 todayOnly。「仅看今日」标签也改为跟随实际 timeRangeFilter 显示，手动选时间后自动隐藏。

6. 【新发现的同类陷阱，2026-10-23】分组查询的 SELECT 别名若与表里真实列同名，MySQL 的 GROUP BY 会优先按真实列分组，导致统计只覆盖该列非空的行。报警统计总数一度显示 263 而明细 33454，根因正是 eiot_alert_record 真实存在 order_status 列（varchar，线上仅 286 条有值且全是 2026-04 遗留），而 CASE 表达式的别名也写作 order_status。修法是把别名改成不与任何列冲突的名字（status_group），并同步所有按该别名取值的 Java 侧读取点（Map.get("status_group")）。凡用 CASE 派生虚拟维度做 GROUP BY，先确认表里没有同名列。

7. 【处置状态分组值现状，2026-10-23】FireAlarmOrderServiceImpl.applyOrderStatusFilter 的 orderStatus 支持的取值集合为：单值 pending / deferred / handling / handled / closed，分组值 unclosed（未闭环 = pending+deferred+handling）与 finished（已闭环 = handled+closed）。分组值存在的必要性在于统计侧字段本身就是多值之和：大屏 handledCount 来自 AlertOrderStatusResolver.sumHandled = handled + closed，若跳转/筛选只用 handled 单值必然漏掉「已关闭」那批，重现"卡片 N 条、点进去 N-1 条"。新增任一分组值时必须三点同步，缺一即失效：①后端 switch 增 case（导出与 PDF 复用同方法故自动支持）②前端 alarm-order 的 ORDER_STATUS_FILTERS 白名单加入该值（否则 URL 带入的值被过滤掉、筛选不生效）③处置中心筛选下拉补对应 el-option（否则用户看不到也无法清除该筛选）。另外该 switch 的 default 分支只 log.warn 不抛错，未知/未生效值会静默退化为"不加状态筛选"（列表变成全量），因此新增分支后必须重启后端才可见效果，不能只看编译通过。
