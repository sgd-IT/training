值守排班域按单位取候选人时，fire_property.name 不能作为定位键：同一条"广东安为安全科技有限公司"在测试库（192.168.250.160/anwei_fire_remote_monitor）存在两条记录——id=1001 的 tenant_id=1（系统租户）、id=1018 的 tenant_id=166；而生产库中 id=1001 的 tenant_id=166。即同一 id 的记录其租户归属在两库不一致，测试库那条指向系统租户属历史改动的脏数据。后果：前端 /system/user/simple-list?tenantId=xxx 的入参完全来自所选物业记录的 tenant_id，选中哪一条就决定拿到的是系统租户人员还是该企业人员，两库表现不同。另核实：system_tenant 中并不存在名为"安为科技有限公司"的租户，只有"安为科技"(165)、"广东安为安全科技有限公司"(166)、"安为园区"(167)；其中租户 167 下 status=0 的用户数为 0，是唯一零候选人的单位。所有按名称匹配单位的排查都必须改用 id + tenant_id 双键核对。适用边界：值守排班/值班人取数的跨环境与跨库比对；不适用：设备、告警等其他 eiot 域的取数逻辑。
