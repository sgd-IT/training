消防值守告警链路的现成底座（2026-09-28 经 MCP 实测 anwei_fire_remote_monitor 库 + framework 全量盘点确认），推翻了三条常见误判：

1. **处置状态机不是从零建**：`eiot_alert_record` 已有 `handle_status`（tinyint，0=待处置/1=稍后处置/2=处置中/3=已处置）与 `order_status`（pending/handling/handled/closed/confirmed/real_fire/false_alarm，含"真实火警/误报"确认语义）双轨；`fire_alarm_handle_record` 表已实现 10 种动作流水（receive/view/confirm/false_alarm/real_fire/reset/mute/call/notify/close + duration 耗时字段）。真正缺失的只是"确认截止时间、时限计时、超时升级链"这一层。

2. **视频覆盖有现成数据源**：`video_camera`（24 路）+ `device_camera_relation`（15 条设备-摄像头关联），判定"有无视频覆盖"不需要新建表。

3. **电话侧已有话务平台对接代码**：`eiot_call_record` + `eiot_duty_phone`（值守座机管理）+ `CallRecordPushController`/`CallRecordPushService`（话单推送接收，含录音归档）；缺的是"系统主动外呼/语音群呼"，属对外呼 API 的对接项而非从零建设。

4. **台账已有三个生长点**：`fire_transmission_device`（传输装置台账，空表）、`fire_facility_category`（15 类设施分类字典）、22 张 `fire_*` 值守业务表群；但防火分区、视频覆盖标记、报警区域三类定级必需字段在全部 120 张表中确实不存在。

5. **framework 侧可复用件**：spring-boot-starter-protection 自带 Idempotent（幂等注解+IdempotentRedisDAO）、RateLimiter（限流）、Lock4j（分布式锁）、ApiSignature（签名）四套组件；operatelog 提供操作日志切面；infra_config（仅 7 行，几乎闲置）+ ConfigApi 是 DB 级参数配置落点；infra_job/infra_job_log 提供 Quartz 任务可视化管理面；module-eiot-task 的 ActionExecutorManager/DeviceActionExecutor 是联动执行编排通道；iot-components 共 18 个协议组件。

6. `fire_alarm_order` 表字段齐全（response_duration/handle_duration/notify_channels）但 0 行——建了未使用，实际工单数据源仍是 eiot_alert_record。

## Notes
- 【定时任务实际覆盖面（2026-10 读 FirewatchScheduledTask.java 全文核实）】该类只承载两类调度：巡检任务超期标记/快照/重置（每天 00:05）与维修工单超期自动催办（每天 9:00）。不含告警超时升级调度、不含基于排班上下班时间的自动签到签退。判断"某条时限类能力是否已实现"应直接核对该文件的方法清单，不能由 PRD 存在即推定已落码。
- 【交接班是真实实现，非演示数据】`FireHandoverRecordMapper`（含 countInRange 等统计方法）为真表访问层，`FireDataCenterServiceImpl` 直接消费其统计数据，与 alarm-assist 接口的演示数据状态不同，勿一并归入"未实现"。
- 【"向监管上报"能力在本底座之外且完全缺失】上述底座均为"接收/内部流转"侧；对属地消防物联网平台/远程监控平台的对外推送接口域在 controller/admin 24 个域中不存在，grep 监管/regulator/上报平台亦零匹配。补此项属新增接口域而非改造既有链路。
- 【重要边界修正（2026-10-23 线上库实测）】本条所有表与行数结论仅代表内网测试库（192.168.250.160）现状，不可当作生产库已具备：生产库（腾讯云 gz-cdb-dnqlqqwx:60477）实测**不存在** `eiot_call_record`、`fire_maintenance_unit`、`fire_duty_record`、`sip_device`、`sip_config`、`sip_device_channel`、`iot_sip_relation`、`media_server` 八张表，其中 `/admin-api/eiot/firewatch/call-record/page` 与 `/admin-api/eiot/firewatch/maintenance-unit/{list,page}` 近 30 天在生产持续返回 500。评估"某底座能力线上是否可用"必须先按生产库单独核对表存在性，不能沿用本条的测试库事实。
- 【fire_duty_record 状态更新（后续任务实测）】上述八张生产缺表中的 `fire_duty_record` 已在开发库 anwei_fire_remote_monitor 通过 MCP 执行 DDL 补建（列对齐 FireDutyRecordDO，索引 tenant_id/property_id/record_time/schedule_id/record_type），对应前端 duty-record 页面路由也已放开；生产库核查当时仍无此表，上线前仍需单独补建。其余七张表的缺表结论不受影响。
