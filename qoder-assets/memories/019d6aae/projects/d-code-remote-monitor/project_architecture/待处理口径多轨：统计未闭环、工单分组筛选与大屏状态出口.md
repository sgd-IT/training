消防值守 PC 端「待处理」这一名称在多条链路上判据不同源，跨链路对齐数字时必须先辨明用的是哪一套：

- 统计侧：FireDashboardServiceImpl.buildTodayAlarm 的 pendingCount 走 AlertRecordMapper.countTodayUnreadAlerts，判据为 `handle_status IS NULL OR handle_status < 3`，即包含 0=待处置、1=稍后处置、2=处置中三种未闭环状态。
- 筛选侧：/eiot/firewatch/alarm-order/page 的入参 AlarmOrderPageReqVO.orderStatus 原本只接受单值等值匹配，语义为「仅 pending」不含 handling，故与大屏卡片数字对不上。口径统一批次已扩展出分组值 unclosed（未闭环）并把 handle_status=1 独立成 deferred（稍后处置），前端下拉现为「未闭环 / 待处理 / 稍后处置 / 处理中 / 已处置 / 已关闭」六项；大屏今日警情整卡跳转传 ?orderStatus=unclosed 而非 pending。核对历史数据或旧分支时仍要确认用的是单值还是分组语义。
- 表达式与别名现状（2026-10-23 实测）：状态解析表达式位于 AlertOrderStatusResolver，其分组查询别名为 status_group，不可写作 order_status —— eiot_alert_record 历史上存在同名真实列，MySQL 的 GROUP BY 会优先按真实列分组，导致统计只覆盖该列非空的行；Java 侧读取点须同步用 Map.get("status_group")。筛选条件收口在 FireAlarmOrderServiceImpl.applyOrderStatusFilter(wrapper, status, logScope)，列表分页与 PDF 导出共用同一个 switch；handled/closed 与 pending/deferred/handling 的聚合分别由 AlertOrderStatusResolver.sumHandled / sumUnclosed 单点提供，两个统计类不再各写一遍。
- 已实证的分叉后果：大屏显示今日 23 总数 / 22 已处置 / 1 待处理，点进去列表 0 条——那条是 id=17202、handle_status=1（稍后处置）、read_flg=1、details 无任何处置动作。统计按 handle_status<3 计入未闭环，而列表若仍用 orderStatus=pending 单值会把它排除，两边天然不等。排查此类"数字有、列表空"要先查该记录的 handle_status 具体取值，不要假定是日期范围问题。
- 实时列表侧：曾走 selectLatestAlerts（LIMIT 10、不限状态不限日期）+ 前端 filterTodayAlarms + badge=alarmList.length，三者语义不同源导致"待处理 0 / 实时告警 10"。现改为 selectTodayUnclosedAlerts（今日且 handle_status < 3），badge 取 todayAlarm.pendingCount，最多显示 10 条，与计数同源。
- 大屏状态出口：FireDashboardServiceImpl.convertToRespVO 曾先用 resolveOrderStatus 赋 orderStatus 又被 readFlg 三元表达式覆盖，使大屏只剩 pending/closed 两态；该二次覆盖已在口径统一批次消除，handle_status 是唯一权威判据。
- 前端遗留死值：mapAlarmToDisplay 里 status 取 item.orderStatus || 'pending'，判断条件仍写作 ['pending','handling','confirming']，其中 confirming 后端 resolver 从不产出。
- 既有 UI 先例：告警记录页（alarm-record/index.vue）的「处置状态」下拉同样以 value="pending" 表示「待处理」、handling 表示「处理中」，即项目惯例把待处理当单值而非未闭环分组；已补上「未闭环」选项与处置中心对齐。
- 跳转契约：duty-screen → alarm-order 统一走 URL query —— 点实时告警条目传 ?id=xxx（openAlarmFromQuery 打开详情弹窗），点今日警情整卡传未闭环分组值 + today=1；alarm-order 侧对 query 值做白名单校验，非法值落空不过滤。
- 「今日」判据必须单点定义：前端曾用浏览器本地时间拼 alarmTimeBegin/alarmTimeEnd 字符串，与后端 DATE(FROM_UNIXTIME(alert_time/1000)) = CURDATE() 各算一次，浏览器/JVM/DB 任一时区偏差就整体差一天。现改为 AlarmOrderPageReqVO.todayOnly 参数，由 AlertRecordMapper.TODAY_CONDITION_SQL 常量统一提供该段 SQL，统计侧查询与列表筛选共用同一段；用户手动选时间范围时以用户为准、不再传 todayOnly。
- 结构性约束：跨链路对账不能靠前端多次请求合并（分页 total 会失真）；前端 pendingCount 亦不可对当前页数据 filter 得出（pageSize=10 时数字随翻页跳动），应由后端 /eiot/firewatch/alarm-order/status-count 一次 group by 返回各状态总数，徽标 = pending + deferred + handling。today=1 场景下徽标改取当前筛选的列表 total，已与列表同范围。

## Notes
- 【状态判据已简化为纯 handle_status 五态（2026-10-23 本批改造落码）】正文所述 ORDER_STATUS_CASE_SQL 曾有的 details 关键词兜底与 read_flg 回退分支**已被整体删除**：现 CASE 只有约 5 行，直接映射 handle_status 0=pending / 1=deferred / 2=handling / 3=handled / 4=closed；resolveOrderStatus 同步简化，lastActionRecord / isClosedAction 等中文串反推方法已删。凡再遇到"状态与 details 文本不一致"类问题，不要再指望 details 参与判定。
- 【新增第 5 态 + order_status 列被 DROP】handle_status 扩为五态（新增 4=已关闭），resolveHandleStatusByAction 把「关闭工单」写 4；eiot_alert_record.order_status 遗留列经迁移脚本回填后 DROP，双轨合并为单轨。注意：CASE 简化会让约 95 条历史数据的状态判定变化（hs=0 且 read_flg=1 的 77 条由"已处置"变"待处置"；hs=1 但 details 有旧动作的 18 条变"稍后处置"），跨版本对账前先确认是否已跑过回填脚本。
- 【别名陷阱的前提已消失但仍需守】原"GROUP BY 别名撞真实列 order_status"的成因（表里有同名真实列）随该列被 DROP 而不再成立；但用 CASE 派生虚拟维度做 GROUP BY 时仍应保持 status_group 这类不与业务列重名的别名，防止后续再加同名列复发。
- 【URL 驱动模式的"可退出性"缺口已修（2026-10-23 实测）】正文跳转契约里的 today=1 是常驻 URL 的参数：从大屏跳进处置中心后，页面内改筛选、翻页、点刷新都不会清掉它，「仅看今日」标签因此永远显示且无取消入口，列表一直被锁在今天；更隐蔽的是 handleResetFilters 只清空筛选控件而不动 query，重置形同无效。修法：给该标签加 closable，点 × 调 clearTodayOnly —— 从 route.query 摘掉 today 后用 router.replace（不是 push，避免后退又回到今日模式）重写 URL，回到第 1 页重查；handleResetFilters 在处于今日模式时一并调用 clearTodayOnly。凡用 URL query 表达"临时视图模式"（仅今日、仅某状态等），必须同时提供退出入口并让重置逻辑覆盖该参数，否则模式不可逆。
- 【装饰性状态标签应删不应对齐】处置中心顶栏「实时刷新」曾是无条件渲染的静态 el-tag，背后既无 WebSocket 也无轮询开关，实际 30 秒轮询隐式运行，易被误读为实时推送；2026-10-23 已直接删除该标签。判据：不带任何状态、不可交互、文案与实际机制不符的展示元素属误导装饰，优先删除而非改写文案。
