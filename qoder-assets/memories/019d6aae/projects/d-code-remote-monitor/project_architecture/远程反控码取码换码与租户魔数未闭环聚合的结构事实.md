消防远程值守"反控码 + 魔数判定 + 未闭环聚合"三处结构事实：

1. RemoteControlCodeServiceImpl（module-eiot-biz service/remote）现状已核实为可用版本：生成分支内含 opsForValue().set(key, code, CODE_TTL_MINUTES, TimeUnit.MINUTES) 写回，接口声明的 verifyCode(String)（读同一 key 比对）在该实现类中已存在。此前记录的"手写半成品：无 set 写回、new Random() 只 import ThreadLocalRandom 因而编译不过、每次请求换码"已不成立，不要再当作现状引用。仍需保留的告警：同一文件在不同读取通道可能返回不同版本（一次 Read 得到 50 行 StringRedisTemplate 无 verifyCode 的版本，ripgrep 与 node 读磁盘得到 70 行 RedisTemplate 含 verifyCode 的版本），改动前务必用第三方通道核实字节。既有惯例：RedisTemplate<String, Object> + opsForValue().set(..., TimeUnit) 是本仓库写法（先例 RemoteConsoleServiceImpl、EiotRedisDAO）；expire 字段语义是绝对过期时刻（毫秒时间戳）而非剩余分钟数，移动端按时间戳消费。

1b. 取码的结构不变量（实测确认）：getRemoteControlCode() 以 RedisKeyConstants.REMOTE_CONTROL_CODE + tenantId 为 key，命中已有值时直接返回旧码，仅 key 不存在或过期才生成新码；set(..., TimeUnit) 只在生成分支执行，因此重复调用 GET /eiot/device/remote/code（AppDeviceInfoController）既不会换码也不会重置有效期。任何"刷新反控码"类前端按钮若只做重新请求，在 5 分钟 TTL 内必然看不到变化，要真正换码必须走 force 语义——Service 侧新增 force 入参、在 if (force || code == null) 分支生成并覆盖写回，控制器用 @RequestParam(defaultValue = "false") boolean force 透传。配套约束：verifyCode 读同一 key 比对，强制换码会立即作废旧码，PC 端 VerifyModal 里操作员已抄录的旧码将校验失败并需重新索取，这是安全上期望的行为而非缺陷。改造落点共四处：RemoteControlCodeService 接口、RemoteControlCodeServiceImpl、AppDeviceInfoController、pages/remote-control-code/index.vue 的 fetchCode(force)。

2. 魔数判定已归一：VideoCameraService.isPublicCamera(VideoCameraDO) 提升为接口静态方法，Impl 私有副本删除、AppVideoCameraController 内联判定改为调用；系统租户判定收口为 FirePropertyTenantSupport.isSystemTenant()（tenantId == null || == 1L），FireDashboardServiceImpl 不再自写 == 1L。PUBLIC_CAMERA_TENANT_ID 仍为 166。新增此类判定时走上述出口，不要再写字面量。

3. 未闭环聚合口径已单点化：AlertOrderStatusResolver 新增静态方法 sumHandled（handled+closed）/ sumUnclosed（pending+deferred+handling），FireDashboardServiceImpl 与 FireAlarmOrderServiceImpl 均改为调用；前端 alarm-order 另有 OPEN_STATUSES + isOpenStatus() 常量函数。新增状态枚举时改 Resolver 与这两处常量即可，不必再逐处同步。

4. 告警状态筛选 SQL 已收成 FireAlarmOrderServiceImpl.applyOrderStatusFilter(wrapper, status, logScope)，列表分页与 PDF 导出共用，签名类型是 LambdaQueryWrapperX<AlertRecordDO>（非 LambdaQueryWrapper）。
