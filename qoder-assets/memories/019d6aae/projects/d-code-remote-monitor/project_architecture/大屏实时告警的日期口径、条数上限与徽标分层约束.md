值守大屏（duty-screen）「实时告警」列表的可见范围由三层不同源的判据共同截断，改任何一层都会让数字对不上：

1. 后端 AlertRecordMapper.selectTodayUnclosedAlerts 的注解 SQL 三条件：`DATE(FROM_UNIXTIME(alert_time/1000)) = CURDATE()`（当天，取**数据库服务器时区**，本项目 time_zone=SYSTEM 即 +08:00）、`handle_status IS NULL OR handle_status < 3`（只含未闭环，已处置/已关闭不出现）、`ORDER BY alert_time DESC LIMIT #{limit}`。alert_time 列是毫秒 bigint。
2. 条数上限按链路不同：FireDashboardServiceImpl.buildRealtimeAlarms(10) 使 statistics 首屏恒为 10 条；只有 statistics 请求失败降级到 /realtime-alarms 时前端传 limit=15。Controller 默认值 10，且该接口**只有 limit、没有 offset**，无法做真正的增量翻页——要加载更多只能放大 limit 重拉后整体替换。
3. 前端 filterTodayAlarms 再按**浏览器本地时区**过滤一遍当天，作为兜底；浏览器与数据库跨日时会出现列表被滤空或只剩部分数据。

不变量：卡片标题右侧红点取 todayAlarm.pendingCount（今日未闭环全量计数，可达上千），列表最多渲染 limit 条，两者设计上必然不等，不是缺陷。列表容器滚动能力来自公共 .card-content 的 overflow-y:auto 且滚动条隐藏，单条约 50px，一屏约 5~6 条，无自动轮播（自动滚动已移除）。

边界：本条适用于 duty-screen 实时告警列表与其计数口径；处置中心分页列表走 alarm-order/page，不受此 LIMIT 约束。
