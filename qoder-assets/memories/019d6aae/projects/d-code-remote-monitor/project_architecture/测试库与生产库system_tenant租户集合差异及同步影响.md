两套数据库的 system_tenant 租户集合不一致（实测）：
- 测试库（192.168.250.160:3306 / anwei_fire_remote_monitor）只有 2 个租户：id=1「安为科技值守中心」（系统租户）、id=166「广东安为安全科技有限公司」。
- 生产库（anwei-fire-remote-monitor-prod）除 1、166 外还有 id=174「东莞南城碧桂园湾区国际」、id=176「粤电花园」、id=178「广州越秀金桥养老院」，状态均为 status=0（正常）、deleted=0。

结构性后果：任何把生产侧业务数据（video_camera 等带 tenant_id 的表）原样搬到测试库的操作，都会让挂在 174/176/178 上的记录成为租户隔离过滤下不可见的孤儿数据——项目多租户机制按 TenantUtils.execute(tenantId) 拼接 tenant_id 条件，租户主表缺记录时常规视图查不到。因此跨环境同步前必须先比对两侧 system_tenant，缺失租户要么一并同步（但租户下无用户与套餐，只能由超管跨租户查看，无法直接登录），要么改写归属到目标库已有租户。

补充口径：video_camera 表的 channel_id 存在两种取值形态——ICC 四段式（如 1000011$1$0$1）与单字符序号（"0"/"1"/"2"...），后者多见于 pull_type=1 的直连/热成像类摄像头；比对或迁移时不能假定 channel_id 一定是四段式格式。

## Notes
- 「测试库只有 2 个租户」并非全环境通用结论：用户 2026-10 明确陈述其远程（线上）环境的公共摄像头是挂在安为（tenant_id=166）名下，即不同远端部署的租户集合各自独立。凡涉及租户集合的判断，必须按当前实际连接的那套库现查 system_tenant，不能沿用本条所列清单。
- 2026-11 一次结构比对实测：information_schema.TABLES 统计测试库约 6 行、生产库约 4 行（TABLE_ROWS 估算值），与本条早期记录的「测试 2 / 生产含 174/176/178」方向一致但绝对数量已变化，说明两侧租户都在持续增删；本条所列具体 id 清单仅为历史快照，只可用作"两侧会不一致"的判据示例，不可作为当前差集结论。
