在执行代码修改任务时，必须严格遵守'只动注释'的原则：仅允许修改、删除或添加代码注释，任何代码逻辑（包括方法签名、控制流、变量赋值等）均不得更改。该原则适用于用户发起的代码清理、风格调整和文档补充类任务。

## 适用边界（重要例外）
- 用户说"把注释写好"/"帮我写一下注释"时，只改注释文本，**不得顺手补全或替换方法体实现**；若原处是留给用户填写的空骨架，必须保持空骨架状态。**例外升级（2026-10-28 实测）**：当用户指令为"检查一下，不对你就注释一下/改一下"这类授权处置时，可直接给出含删行标记（// Deleted:）的成品编辑块 + 精简坑位注释，视为已授权改动该一处；仍不得扩改其他位置。
- 教学/挖空训练场景（hand-typing-training 的出题模式）下本原则升级为硬约束：核心代码一律由学员手敲，AI 只提供注释里的步骤描述，不附可抄代码，也不得覆盖学员已填写的代码段；误覆盖后须先还原再说明。
- **跟敲（文字教程）模式同样受本原则约束**：后端改动只给文件路径 + 行号锚点 + 方法签名 + 分步动作描述 + 坑位提示，**不得给可直接粘贴的完整方法体或完整 if/return 控制流块**。判据是"交付形态按端分，不按新手档统一定"——前端（学员零基础）给可抄小块，后端（学员能读懂、自己写需参考）给文字与签名；把前端口径套到后端等于代写，学员会明确问责。
- 仅当用户明确要求"你直接把实现写完"/"你帮我写"/"你注释一下（授权处置）"时才可写代码，且只动用户指定的那一处，不扩改其他位置。
- 判据来源：用户的字面指令对象（"注释" vs "实现"）与改动所属端（前端 vs 后端），而非"这是教学所以多给代码"的上下文推测。

## 补充判据（本轮 DeviceStateCheckHandler 三轮检查实测）
- 审查双层嵌套条件时，除逐条核对每层真值外，必须做**外层/深层语义一致性检查**：外层门卫条件与内层放行条件若互为取反（如外层"状态没变才进"包着内层"状态变了才写"），整块为死分支，一次都不会执行。此类缺陷编译通过、日志正常、监控指标反而变好，只能靠场景推演表（每种消息类型 × 外层结果 × 内层结果）发现。
- 节流/开关类改造收口前须验证"压住的写是不是目标那条"：确认被包住调用点的下游是否真的产生监控里那条 SQL（如 updateSubDeviceState 内部有 NODE_TYPE_GATEWAY 前置判断，对非网关设备空转，节流装在此处收益为零）。
