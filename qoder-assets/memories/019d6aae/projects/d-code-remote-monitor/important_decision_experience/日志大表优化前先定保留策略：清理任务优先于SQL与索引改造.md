Conclusion: 对 infra_api_access_log 这类高写入日志大表做查询性能改造前，必须先评估保留策略（AccessLogCleanJob 的 14 天清理）是否真的生效；若未生效，优先启用清理任务把表压到 8~9 万行量级，再决定是否投入 SQL/索引优化。本轮最终只交付方案、未落代码，并把"启用清理任务"列为比接口优化更优先的一项。

Rationale (trade-off): 实测该表约 6300 行/天，14 天保留生效后规模仅 8~9 万行，此时 SELECT * 回传大字段、无索引 ORDER BY id DESC 全表扫都只需几十毫秒，字段瘦身与排序对齐的收益被大幅稀释；反之若数据须长期留存（审计用途），接口优化就成为必选项。维度是"改动成本 vs 收益倍数"：开一个任务是配置/注解级改动，改 Mapper+新增详情接口+前端联动是一次强耦合发版。

Rejected alternatives: ①直接加复合索引 (tenant_id, create_time)——本身合理，但用户明确选择暂不动表结构；且索引会拖慢高频写入，日志表上需谨慎。②只做 SQL 优化不管清理——被否，因为在百万行基础上做的优化在清理生效后即失去意义，属重复投入。③用 SHOW TABLE STATUS 近似值替代 COUNT——被否，页码不准体验差，且默认时间范围落地后 COUNT 也走 range，收益不成立。

Applicable / expiry conditions: 适用于写入频繁、有既定保留期但保留期执行链未被验证过的日志/流水类表；一旦清理任务确认稳定运行且表规模降到 10 万行以内，本条中"先清理后优化"的优先级判断即失效，应重新按实际行数评估是否需要索引改造。若业务要求日志长期留存（审计、合规），则清理方案不可用，接口优化与索引成为唯一路径。
