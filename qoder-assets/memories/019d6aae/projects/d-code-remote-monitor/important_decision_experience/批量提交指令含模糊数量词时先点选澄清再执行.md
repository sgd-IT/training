Conclusion: 当用户指令中的数量词/序号对多主题清单存在多种合理解读时（如"提交2笔"既可指最新新增的两笔也可指清单顺序的前两笔），先用 AskUserQuestion 列出候选组合让用户点选，再连续执行全部批次。
Rationale (trade-off): 提交动作会把文件从工作区剥离，错收后需 reset 回退、成本高且有夹带计划外文件风险；一轮澄清的成本远低于返工，且澄清时可同时复核拉取结果与剩余范围。
Rejected alternatives: 按"最近新增"惯例自行推断直接执行（省一轮交互，但可能整批提交错误内容）；把全部批次都提交完再事后调整（违背用户指定的最小提交面）。
Applicable / expiry conditions: 适用于一次给出多主题清单且用户回复含模糊数量词/序号的场景；若用户明确给出文件名或哈希等唯一指代，则无需澄清直接执行。

## Notes

- 适用边界补充：本条只在"多主题清单 + 模糊数量词/序号"两个前提同时成立时生效。用户发出「只提交代码」这类不含数量词的短指令时，其含义是限定动作范围为 commit（不 push、不收配置类文件），并非指代清单中的某几笔，不应据此触发点选澄清，否则属过度提问。
- 另一类不适用情形：指令既无数量词也无清单（如单句"你来设计一下"），此时不存在可点选的候选集合，本条的点选机制无从套用，应改用"默认假设 + 单一待确认问题"的方式推进，不要连续抛多个开放问题。
