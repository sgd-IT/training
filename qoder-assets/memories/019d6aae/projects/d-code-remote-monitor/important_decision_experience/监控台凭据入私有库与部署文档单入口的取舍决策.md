Conclusion: 监控台凭据（deploy/config/frontend/sba.htpasswd、application-prod.yaml 里的 Druid 控制台账号口令）直接提交进私有库；部署文档收敛为 deploy/README.md 唯一入口，不再维护分主题专项说明。

Rationale (trade-off): 私有仓库暴露面可控，换取"clone 完就能构建上线"的最短路径——发版流程从三步砍到两步（构建机 build-push.ps1 → 服务器改 .env 版本号 + pull-images.sh 上线），新人无需理解 htpasswd 生成与环境变量透传两套前置。文档侧的代价是长度增加，但换来读者不必判断先看哪份。

Rejected alternatives: ① .gitignore 忽略 htpasswd + docker-compose 用 ${DRUID_USERNAME}/${DRUID_PASSWORD} 透传注入 —— 更安全但每次新环境要额外生成文件、服务器 .env 必须补两行否则容器拒绝启动，被用户以"不用管那么多了，私有库直接提交也行"否决；② README 作索引 + 保留专项说明文档的分层结构 —— 结构更清晰，但用户明确"不用那么多文档"，且四份文档并存正是本次困惑根源。

Applicable / expiry conditions: 仅在仓库为私有且访问面受控时成立；一旦该库转公开、有外部协作者加入或引入 CI 公开日志，须重新评估回退到环境变量注入方案。口令轮换要注意旧值永久留在 git 历史。文档入口唯一化的约束长期有效：新增部署专项内容应折进 README 而非另开文件。
