Conclusion: 为 eiot_product.product_key 补索引这类小表在线 DDL，采用「测试库先跑一遍验证计划恢复」+「生产库保持未动、待单独授权后用最简 ALTER 语句执行并立刻重跑同一组 EXPLAIN」双轨，而不是把测试库通过当作生产可跳过的依据；同时否决"从分页查询里摘掉 details 大字段来缓解排序落盘"这一优化项。

Rationale (trade-off): 测试库 5.7.38 与生产 5.6.28-cdb2016 优化器行为不同（5.6 对 IS NOT NULL 不生成有界 range、无 EXPLAIN ANALYZE），测试通过不能推断生产必然通过，反之亦然；而该 DDL 是纯增量的、目标表仅 25 行、LOCK=NONE 不阻塞读写、回滚只需一条 DROP INDEX，风险面极小，所以"直接生产执行 + 即时验收"比"依赖跨版本推断"更可靠。details 被否决是因为 Grep 前端确认 alarm-record/index.vue 从 item.details 解析设备名与位置并传入编辑弹窗，摘字段会直接破坏列表功能——收益侧省下的行宽远抵不过功能损坏。

Rejected alternatives: ①仅在测试库验证后即视为修复完成（被否：版本差异使结论不可迁移）；②重建 idx_tenant_alert_time 列序（此前实测已否决，deleted 接近全量不减行）；③建 uk_product_key 唯一索引（逻辑删除下同名 key 重建会被挡，属正确性议题不应混入性能修复）；④调小 pageSize / 给 name 加前导模糊索引（治的是 N+1 与无效索引，非本问题）。

Applicable / expiry conditions: 适用于"目标表行数极小、写侧冷、DDL 纯增量且可单语句回滚、但两套环境 MySQL 主版本不一致"的索引变更场景；一旦两库版本对齐或引入 online schema change 工具，"必须各自独立验收计划"这条约束即失效。同样，若 details 改为冗余出独立的设备名/位置列并被前端切换消费，则"不可裁剪"结论需重新评估。
