结论：Git 提交粒度按**一个逻辑主题/特性一笔**执行。同一特性横跨多个文件属正确做法（例：后端多端登录平台管控把 security 框架配置与服务实现、WebFrameworkUtils、system 模块 DTO/VO/错误码/service 共 9 个文件合为一笔 feat(auth)；2026-10-30 一轮 10 笔提交中，日志保留 90 天把 AccessLogCleanJob/ErrorLogCleanJob/新增 LogRetentionTask 三文件合为 B1，大屏预热把 Controller/Service/Impl/WarmUpTask/RedisKeyConstants 五文件合为 B2，配置 JSON 校验把 ComponentServiceImpl+ErrorCodeConstants 合为 B5，用户均一次授权通过）。同日又一例：duty-screen 跳转目标改造与 device-screen 接收 query 定位两个文件合为一笔 feat(firewatch)，理由是"只改一侧则点了没反应或新能力无入口"，在清单里显式注明合笔理由后获用户认可。

依据（权衡）：判据是"这一笔能否用一句 type(scope): 中文描述讲清一个主题"。若机械按"一个文件一笔"拆分，同一特性会被拆成十余笔无意义提交，历史不可读且回滚困难。

跨仓库边界规则（2026-10-30 补充）：**同一主题的前后端改动不得合并成一笔**——两个物理仓库各自成批（如 ThingComponent 间隔放宽 = 后端 B7，component/index.vue 提示文案改 = 前端 F2，虽语义同源仍分两笔），因为 git 提交无法跨仓库原子生效，合并不仅技术上不可行，还会让两仓历史互相丢失对应关系。此时应在两笔的提交正文里互相点明同口径关系，便于日后单独回滚任一侧时发现问题。

被否决的替代方案：既有规范中"最小单元＝单文件优先"的字面理解——实测会导致过度拆分，且用户对特性级分组无异议，说明该表述偏严而非正确路径。

适用 / 失效条件：适用于日常功能开发与跨仓库分批提交；当某文件改动确属**另一个独立主题**时仍需拆开，不得借"同特性"名义混装。本条仅澄清粒度判据，不改变"提交前展示清单并获确认""停在本地不主动 push"等既有约束；其中 push、stash、fetch+rebase、pull 等改变工作区状态或重写本地提交 sha 的操作均为独立授权动作，须逐项单独征得同意（权威口径以 IMMUTABLE 记忆「Git提交需用户确认、按最小单元且只提交代码文件」为准）。

## Notes

- 【推送前置条件复现】同一口径在多轮双仓提交推送中反复成立：推送前必须 fetch，若 status -sb 显示纯 ahead 无 behind 则直接 push，无需 pull --rebase --autostash；推送结果以 "旧sha..新sha master -> master" 行 + push 后再跑一次 status -sb 确认同步为唯一判据。
- 【提交范围裁剪】清单式呈现的价值在于用户可中途裁剪（曾出现"值班排班先不提交"），因此即使改动很少也要先列清单。注意排除项要逐文件看 diff 判定，不能按文件类型一刀切：application.yaml 里 profiles.active 的环境切换行属本地调试态必须排除，但同仓库的 pom.xml、application-dev/prod.yaml、nginx.conf 若承载功能生效必需的配置则属破例收录项，须向用户申请而非默认排除。SQL 迁移脚本同理属待问项：2026-10-30 本轮 V20261029 索引脚本与 V20261027 UDP 落地脚本均在先询问/说明状态后经用户拍板独立成笔入库（后者从"留工作区"转为"udp的也提交推送"），说明 SQL 脚本的正确处理是明确告知其当前状态并请用户决定，而不是默认排除或默认收录。
- 【同文件混装主题的拆笔判据（2026-10-28 修正）】此前记录的 deploy/config/server/application-prod.yaml 案例应理解为：**同一物理文件里的改动若分属两个可各自一句话描述的独立主题，才需要拆笔**；若各 hunk 都服务于同一个对外主题（如"监控页在 Boot3 下能用"包含 starter 替换、exclude 删除、连接池参数、client.url），整文件成笔是正确的，不必强行拆。拆与不拆的裁决标准始终是"一笔能否一句话说清一个主题"，而非文件内 hunk 数量或配置项差异幅度。
- 【授权收敛的实际形态】用户可能以一句"提交"批量放行已展示的完整清单（本轮后端 3 笔 + 前端 8 笔共 11 笔一次性授权；2026-10-30 再次以"提交git"放行 10 笔），此时按清单原样执行即可，无需逐笔再确认；但清单必须先完整展示过，且 push 仍需单独授权。
- 【推送授权独立性（最新事实，权威口径以 IMMUTABLE 记忆「Git提交需用户确认、按最小单元且只提交代码文件」为准）】上述"纯 ahead 即直接 push"仅指已获推送授权后的技术路径选择，绝不构成免确认推送的理由：用户说"提交"只代表 commit，push 是需要单独授权的独立动作，推送前必须列出待推送提交清单并取得明确同意；stash、fetch+rebase、pull 等改变工作区状态或重写本地提交 sha 的操作同样需单独征得同意。历史上曾出现未经确认直接推送而被用户问责的情况，任何情况下都不得省略推送前的确认环节。
