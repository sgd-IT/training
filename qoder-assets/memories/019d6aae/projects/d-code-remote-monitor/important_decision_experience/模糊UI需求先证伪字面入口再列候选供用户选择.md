Conclusion: 面对"功能图标放到第一个位置"这类无法定位的模糊UI需求，先全仓检索证伪字面入口的存在，再向提出人列出带具体描述的可行动候选（下拉菜单项调序 / 按钮排换序 / 新增独立按钮）由用户选定后实施。
Rationale (trade-off): 直接按猜测实施会重蹈此前该需求"全仓找不到对应改动"的错误并造成返工；纯追问不给选项则把定位成本推回给用户，且用户未必了解代码结构。列出候选既澄清了歧义又给出可执行路径。
Rejected alternatives: 一是直接实现最可能的解释（被否决——同一需求此前已因猜错页面而未验收）；二是只问"您指哪个页面"开放式问题（被否决——提出人无法映射到代码位置）。
Applicable / expiry conditions: 适用于历史核查结论标记"无法定位/需确认所指页面"的UI类需求二次处理；当需求描述已明确指向具体页面与元素时不适用，应直接实施。
Notes:
- 上述"列候选供选择"的前提是能枚举出彼此互斥的具体落点。当需求只给出动作动词而完全缺失作用对象与作用范围（例如仅一句"如何交互你来设计一下"），候选项本身无从推导，此时列候选与开放式追问同样无效；应先确认需求所属的功能模块或交付物载体，再进入候选枚举环节。
- 澄清手段按歧义程度分级：① 有多个合理落点 → 列候选点选；② 指代词有歧义但范围明确（如模糊数量词）→ 就指代本身点选；③ 只有动作、完全没有对象（如"你来设计一下"）→ 不要连续追问多个开放问题，改为"给出一份带默认假设的最小方案 + 一个待确认的核心问题"，让用户在可见产出上纠偏，比在空白上描述需求成本更低。
