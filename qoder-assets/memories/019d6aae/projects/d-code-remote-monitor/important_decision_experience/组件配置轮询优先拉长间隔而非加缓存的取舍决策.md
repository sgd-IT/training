Conclusion: 组件配置轮询（ThingComponent.config() 的 @Scheduled）优先只做最小改动 —— 拉长轮询间隔，不加 @Cacheable 缓存层。

【最新落地事实（2026-10-30 修正，权威以此为准）】最初定稿推荐 `fixedRate=5000 → fixedDelay=30000`（30 秒），但用户最终提交的是 `@Scheduled(fixedRate = 300000)`（5 分钟，未改 fixedDelay）。因此本条里"代价仅配置生效延迟到 30 秒""fixedDelay 自然错峰"两点已不是现状：实际代价是配置/启停变更最长 5 分钟才生效，惊群并发问题也未通过 fixedDelay 解决。评估该轮询压力时须按 5 分钟口径重算，不能再引用 30 秒结论。

Rationale (trade-off): 拉长间隔可立即回滚、不引入任何失效语义。关键判断依据是"轮询间隔只影响配置多久生效，不影响组件重启次数"——只有 status/config 真的变更才会调 stateChange 触发 stopServer/startServer，没变直接 return。配套约束（本轮发现）：该轮询是 DB 配置下发到组件的唯一通道（全仓检索确认 updateComponent 只写库、无任何主动重载路径），所以前端保存配置的提示文案必须与该间隔同口径 —— 已相应把 component/index.vue 的提示由"几秒内重新加载"改为"几分钟内生效"。改这个间隔时必须同步检查所有对它做时长承诺的前端文案/文档。

Rejected alternatives:
（1）给 ComponentApi.getInfo 加 @Cacheable + 写路径 @CacheEvict —— 收益更彻底，但 ComponentServiceImpl 全类目前无任何缓存注解，写路径有四条（updateComponent、createComponent、deleteComponent，以及 ComponentManager.componentDiscover 里的自动建组件），漏任一条就是"配置改了永不生效"这类极难排查的故障；且缓存 key 是 type 而 update/delete 入参是 id，evict 前须先查出 type 才能删对 key。
（2）事件驱动（配置保存时发 MQ/Redis 通知，轮询直接删除）或单任务批量查询后内存分发 —— 能根治，但要同时改 ComponentManager 与组件基类，跨 module-eiot-biz ↔ iot-component-core 模块边界，改动面大一个量级；且只要保持"每组件各自轮询"，成本模型仍是「组件数 × 频率」线性增长。

Applicable / expiry conditions: 适用于"高频轮询低变更数据"且变更由人工偶发触发、延迟可接受的场景；若业务要求配置秒级生效，则不能靠调小间隔解决，须升级到事件驱动，并同步撤销前端"几分钟内生效"的文案。不适用前提是该轮询结果本身参与业务判定而非仅用于变更比对。
