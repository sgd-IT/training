Conclusion: 大屏二三级告警通知匣（AlarmNotice）的条目列表与未读计数只存前端内存，不做 localStorage 持久化，也不向后端回写已读状态；页面刷新即从头计数。

Rationale (trade-off): 通知匣定位是"到达暂存 + 入口"，全量台账已由同页既有实时告警列表承担，重复持久化会引入两套口径的一致性维护成本；大屏长期不刷新的运行特征使刷新丢计数的实际影响很小；忽略按钮只做视觉移除以坚守"轻提示不写处置状态"的安全原则。

Rejected alternatives: localStorage 持久化未读集合（刷新不丢数，但多端一致性、过期清理逻辑复杂，且易被误当作处置状态来源）；点击条目即上报后端标记已读（语义清晰但把轻提示变成有副作用的操作，违背"轻"的目标）。

Applicable / expiry conditions: 在未读语义仅为"本会话内新到未点开"的前提下成立。**已过期（后续会话）**：用户已把 duty-screen 与 monitoring-center 两处「待处置 N」通知匣全部删除，二三级告警现仅通过「待处理」格子的 Toast 提醒，不再有通知匣浮层；AlarmNotice 组件文件因仍导出 isLightAlarmLevel 而保留。本条不得再作为"要重建/继续维护通知匣"的依据；仅当通知匣这类内存态轻提示浮层重新引入时，才回到此决策评估持久化与已读回写取舍。适用于消防值守 PC 大屏的临时通知类浮层；不适用于告警工单等待处置的数据视图。
