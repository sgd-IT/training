## Task description
- Core requirement: 用户要求"看看线上库有哪些字段缺的"，并进一步限定为"缺什么字段会影响系统使用"、"比如最近 git 提交的内容"——即要判定库结构缺失项在生产环境的真实影响面，而非罗列差异。
- Task background: 消防远程值守项目存在两套库（内网测试 192.168.250.160:3306 与腾讯云生产 gz-cdb-dnqlqqwx:60477，均名为 anwei_fire_remote_monitor）；生产库的 MySQL MCP 实例 anwei-fire-remote-monitor-prod 处于 disabled，当前会话仅有另一项目的 MCP 服务可用，故改用本机 mysql.exe 做只读查询兜底。

## Notes
- 单看"库间差异清单"会得出误导结论：生产相对测试**没有任何缺列**，真正的风险全在表级缺失；判断"影响系统使用"必须叠加"是否有 Controller + 前端是否调用 + 线上日志是否已有 500"三层证据，缺一层就会把死代码当故障或把真故障降级。
- infra_api_error_log 检索不到异常记录不等于接口正常，access_log 的 result_code=500 才是权威判据。
- 项目无 Mapper XML、全部走 MyBatis-Plus 注解，因此"扫描 DO 字段"即可近似覆盖代码对库列的全部诉求；但若存在手写 @Select 列名则此法覆盖不到。
- notify_message 表的实际列名是驼峰 messageType（与全库 snake_case 惯例不符），DO 未加 @TableField 时按 message_type 拼 SQL 必报 Unknown column——遇到"库里明明有却报缺列"优先怀疑列名命名风格不一致。
- PowerShell 下 Get-Content 读 UTF-8 中文 SQL 文件会显示乱码，但同文件用 Read 工具或 node fs.readFileSync 读取内容正常，勿据终端显示判定文件损坏。
- 【排除性判据（后续线上排障补充）】result_code=500 **不等于**库结构缺失；本条方法只能证明"是否为缺表所致"，不可当作 500 的万能源头归因。三条区分口径：① infra_api_error_log 的 exception_name/exception_message 为 SQLSyntaxErrorException / "Unknown column" / Table doesn't exist 时才指向库结构缺失；② 若异常是 AsyncRequestNotUsableException + Broken pipe（客户端先断开、后端写响应失败），或堆栈里根本没有 Controller/Service/Mapper 帧，则与库结构无关，属耗时或链路问题；③ 权限不足会立即返回 403，不会表现为长耗时 500。还须交叉核对同一接口在其他来源 IP 的表现——若其他客户端平均 1 秒正常返回，则该接口不存在全局结构或性能缺陷，问题在该客户端链路。
