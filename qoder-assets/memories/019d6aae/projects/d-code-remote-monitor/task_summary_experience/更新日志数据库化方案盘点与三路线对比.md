## Task description
- Core requirement：确认数据库中是否有可存放更新日志（changelog）的表，并给出数据库化方案对比。
- Task background：更新日志此前为前端 data.ts 硬编码常量（CHANGELOG），页面与 App.vue 弹窗同步读取；用户希望改为数据库维护以实现多端共享与免发版更新。

## Execution process
1. 用 MCP 查 information_schema.tables，按 notice/config/version/log/message 模糊匹配筛出候选表：system_notice（通知公告，0 行）、infra_config（参数配置，7 行）、notify_message（iot通知消息，0 行）、system_notify_message（站内信，0 行）；确认库中不存在 changelog 专用表。
2. SHOW CREATE TABLE system_notice：字段为 id / title varchar(50) / content text / type tinyint（1通知 2公告）/ status / creator / create_time / updater / update_time / deleted / tenant_id。
3. Grep 后端确认 module-system 已有 NoticeDO / NoticeMapper / NoticeService / NoticeServiceImpl / NoticeController 全套 CRUD；前端 src/api/system/notice/index.ts 与 views/system/notice 页面已存在。
4. 查 system_menu 确认公告菜单已配置：id=107「通知公告」，按钮权限 1036 system:notice:query、1037 create、1038 update、1039 delete。
5. Grep server/src/main/resources/application.yaml 的 ignore-tables，确认 system_notice 不在租户忽略清单内（受多租户隔离），而 infra_config 在清单内（全系统共享）。
6. SHOW CREATE TABLE infra_config：value 列为 varchar(500)，且 module-infra 的 ConfigApi 只提供按单个 config_key 取值、无列表接口。
7. 读 NoticeForm.vue 确认 content 走富文本编辑器录入，无法保留"新功能/优化/修复"三色标签的结构化条目。
8. 输出三方案对比并推荐 A：A 新建 system_changelog 表（version/release_date/title/items text/status + 加入 ignore-tables + 后端 DO/Mapper/Service/Controller 四文件 + 前端改异步）；B 复用 system_notice（零新表但条目退化纯文本、需加忽略清单与只读接口、将来与公告混表）；C 维持硬编码。

## Notes
- 生产库为 MySQL 5.6，不支持 JSON 字段类型，结构化条目只能用 text 存 JSON 字符串。
- 判断"能否借用现成表"要看三点：字段容量是否够（infra_config value 500 字符上限）、访问接口形态是否匹配（ConfigApi 单 key 取值 vs 需要列表）、隔离语义是否一致（更新日志需全系统共享，公告表默认按租户隔离）。
- 任务止于方案确认，用户尚未选定路线，未落任何代码改动。
