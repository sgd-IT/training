## Task description
- Core requirement: design a programming exercise for patrol task status management service that addresses multiple logical flaws in the existing implementation
- Task background: existing FirewatchScheduledTask has bugs in overdue marking (marks completed tasks), state reset (resets cancelled tasks), and daily task handling (marks '每天' tasks as overdue); the exercise requires fixing these while adding robustness features
- Additional requirement: design new scheduled tasks for duty schedule status management based on shift start/end times

## Execution process
1. Identified core issues: (a) batchRefreshPartolTaskStatus() lacks status filtering, causing completed tasks to be marked overdue; (b) batchResetRoutineTaskStatus() lacks status filtering, causing completed/cancelled tasks to be reset; (c) '每天' tasks (plan_date=NULL) are incorrectly included in overdue marking
2. Designed exercise requirements covering: (a) correct SQL conditions for both mapper methods; (b) proper tenant isolation using @TenantIgnore; (c) comprehensive logging and exception handling; (d) adherence to Java/MyBatis-Plus coding standards
3. Specified four core methods to implement: refreshPatrolOverdueTasks(), snapshotAllTasksToRecord(), batchRefreshPartolTaskStatus(), batchResetRoutineTaskStatus()
4. Provided detailed data model, state transition rules, and test case table for validation
5. Identified three core duty schedule status transition scenarios: automatic check-in at start_time, automatic check-out at end_time, and absent marking after start_time + buffer
6. Designed cron expressions: '0 */5 * * * ?' for frequent scanning of start/end time conditions, '0 0 */1 * * ?' for hourly absent checks
7. Specified SQL update logic for each scenario: status transitions with tenant-aware filtering via @TenantIgnore
8. Proposed mapper method additions: autoCheckIn(), autoCheckOut(), autoMarkAbsent()
9. Confirmed multi-tenant isolation requirements: all methods require @TenantIgnore annotation and proper tenant_id handling
