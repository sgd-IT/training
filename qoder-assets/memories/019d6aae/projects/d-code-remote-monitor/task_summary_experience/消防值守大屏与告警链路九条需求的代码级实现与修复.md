## Notes
- 本条"42 的口径统一已消除待处理0/实时10矛盾"的结论经浏览器端到端实测后不成立：当时只把统计侧 countTodayUncoveredAlerts 改为 ORDER_STATUS_CASE_SQL 判据，实时列表 SQL selectTodayUnclosedAlerts 仍残留 handle_status < 3 旧判据，导致实测出现"待处理 0 / 实时告警仍 10 条"。最新结果：列表 SQL 已改为同一段 CASE IN ('pending','deferred','handling')，与统计同源。
- 另发现原归档未覆盖的口径断层：大屏"今日警情"是当日范围，处置中心 orderStatus=unclosed 是全量历史（实测今日待处理 0 但点进去显示 262 个待处理警情）。最新处理：跳转 query 增加 today=1，处置中心读取后自动补当天 alarmTimeBegin/alarmTimeEnd 并显示「仅看今日」标签，用户手动选时间范围时以用户为准；顶部 pendingCount 徽标仍取全量 status-count，尚未跟随筛选。
- 派生事实：同一指标族的多个出口（计数、列表、跳转目标页、徽标）必须逐点核对判据与时间范围是否同源，只改其中一个出口会留下可见矛盾。
