## 任务描述
- 核心需求：拿用户提供的《智慧消防建设指南》文章（设备联网→数据传输→平台汇聚→业务闭环→监管对接→持续运营六段链条）作为清单，对 anwei-fire-remote-monitor 项目做一次实然 vs 应然的对标体检，输出差距报告。
- 任务背景：纯只读梳理任务，不改动任何代码；需交叉验证 PRD 设计文档与实际代码实现之间的差距，而非只看文档是否存在。

## 执行过程
1. 读文章拆出六段链条与十个章节，把每章转成可验证的能力项（协议接入种类、传输安全、分级/去重/误报抑制、工单闭环、台账导出、开放接口、角色端、合规口径）。
2. SearchCodebase 两路并行摸底：一路查协议组件与部件类型字典（GBT26875 国标 TCP、四信 FF 变体、私有 UDP、大华通用协议 V1/V2 自动检测；GbtConstants 与 DahuaComponentTypeConstants 覆盖剩余电流、测温、故障电弧 case 129、管网压力、液位、消火栓智能帽、水浸、可燃气体、防火门、排烟风机），一路查告警语义（迁移 SQL alarm_kind_tier、字段语义定稿文档）。
3. Bash 列 controller/admin 24 个域与前端 firewatch 模块清单，确认维保（单位/合同/计划/看板）、维修工单、巡检任务、值班排班/记录/电话、远程控制台、SIP(GB28181)、Modbus、视频、数据中心均有真实 Controller/ServiceImpl。
4. Grep 差分验证"设计有、代码无"：交接班为真表实现；TLS/SslContext/Certificate 在 iot-components 内零匹配；监管/regulator/上报平台/119 无任何对外上报实现。
5. Read 定时任务类全文核实覆盖面：仅巡检超期标记/快照/重置（每天 00:05）与维修工单超期催办（每天 9:00），不含告警超时升级调度。
6. 结合记忆库既有事实（三级定级口径、三层去重不一致、弹窗分流、未闭环判据、框架可复用底座）为每条结论标注证据层级：代码级 / DDL级 / PRD级 / 演示数据级。
7. 输出六环节达成度矩阵 + P0/P1/P2 差距清单，并指出远程控制能力超前于"只读采集"口径带来的合规审查点。

## 注意
- 关键结论：①设备联网高、③平台汇聚高（项目最强项）、②数据传输半程（归一化达标但 TLS/设备证书/断点续传全缺）、④业务闭环中高（家底厚但缺最后一环）、⑤监管对接为结构性空白（只有接收侧，无对外上报接口域）、⑥持续运营仅雏形。
- 最重要缺口：PRD-01 已定义完整升级链（30s 复核倒计时、超时升级、三级升级自动通知 119），代码层完全没有调度器实现；短信能力本身存在于 alertconfig 域，属"未接上升级链"而非"从零建设"。
- 第二缺口：移动端页面全部为查看类，无巡检执行（扫码/GPS/拍照）、无维保执行，导致物业与维保角色只有账号没有工具。
- 误报预防只有骨架：辅助判断区依赖的后端 alarm-assist 接口未就绪，前端为演示数据；人工标记误报已可用，即"误报处置有、误报抑制无"。
- "向监管上报"是否需要补取决于有无真实验收要求，不应默认列为必做项。
- 远程控制台能远程操作主机，比"只读采集、不改动原系统联动"的通行口径更激进，落地前需备属地条件说明。
