## Task description
- Core requirement: understand how to identify whether the code runs in development or production environment across the Vue backend, Java backend, and WeChat Mini-Program mobile app.
- Task background: The user was puzzled about environment identification; the investigation revealed three independent, project-specific mechanisms with critical pitfalls for deployment.

## Execution process
1. Vue backend: Identified Vite's `--mode` flag mechanism, where `.env.{mode}` files are loaded based on npm scripts (e.g., `pnpm dev` → `--mode env.local`). Confirmed that `import.meta.env.DEV/PROD` is Vite-built-in, while `VITE_*` variables are custom.
2. Java backend: Identified Spring Boot's profile mechanism, where `application.yaml`'s `spring.profiles.active` defaults to `dev`, and production is activated via `SPRING_PROFILES_ACTIVE=prod` in docker-compose.yml.
3. Mobile app: Identified HBuilderX's compile-time `process.env.NODE_ENV` folding, where `development` maps to an internal IP (`http://192.168.250.130:48080`) and `production` maps to the public domain (`https://fire-remote-admin.anxunwang.cn:18080`).
4. Critical risk analysis: Discovered that uploading the mobile app from the `dev` build directory (which contains the hard-coded IP) would cause all network requests to fail in production due to unreachable IP and strict domain whitelisting requirements.
5. Solution: Defined the correct workflow: use HBuilderX "发行" (not "运行") to generate the `build/mp-weixin` folder, then run a grep self-check to confirm no internal IPs remain, and finally upload from the `build` directory.

## Notes
- The mobile app's `process.env.NODE_ENV` is folded at compile time, so the ternary expression is removed and the URL is hardcoded into the final JS bundle. This makes runtime environment detection impossible.
- The `unpackage/dist/` directory only contained `dev/mp-weixin`, confirming the project had never been built for production before.
