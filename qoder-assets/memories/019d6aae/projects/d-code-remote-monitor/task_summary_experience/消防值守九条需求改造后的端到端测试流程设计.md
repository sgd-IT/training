## Task description
- Core requirement: 用户要求"修改的需求给我测试的流程"，即把上一轮已落地的九条外部需求（17 三色 / 28 今日值班 / 29 Excel 导出 / 36 设备类型 / 42 实时告警 / 34 口径统一）转成可勾选执行的端到端测试流程。
- Task background: 改动横跨后端 FireDashboardServiceImpl / FireAlarmOrderServiceImpl / AlertRecordMapper / AlarmRecordService 与前端 duty-screen / monitoring-center / alarm-order / alarm-record / AlarmPopupDialog；需先重启后端才能生效，且多数断言依赖库内真实状态分布，故流程必须包含 SQL 造数与对账基准。

## Execution process
1. 第 0 节「环境与数据准备」：明确要求先重启后端（改了 Mapper 与 Service）再验证；给出三条基准 SQL —— 今日 handle_status 状态分布（pending/deferred/handling/handled）、当天排班物业分布（status IN ('on_duty','scheduled')）、单条告警的设备类型四级链路 JOIN（alert→device_info→product→category）。
2. 造数手法：用 UPDATE eiot_alert_record SET handle_status = 1, read_flg = 0 WHERE id = ? 在测试库人工制造一条 deferred，用于验证「稍后处置」全链路；并声明只在测试库改状态。
3. 每条需求的断言写成"改动前 vs 改动后"对比项（如三级告警圆点由红变黄、四档 level=4/5/6 不得显示为红色、悬停不再变红），便于回归识别。
4. 28 今日值班补充失败归因路径：企业账号仍为空时先查 fire_duty_schedule.property_id 是否为空（空值会被物业过滤掉）。
5. 29 导出验证以"行数 > 20 且为 xls"为核心判据，并加入停后端后点导出的失败路径断言（提示「导出失败，请稍后重试」且不再生成 CSV），同时要求 PDF 与 Excel 行数一致。
6. 34 核心对账链：大屏今日警情待处理数字 = 处置中心 orderStatus=unclosed 的 total；大屏已处置 = handled + closed 合计；报警记录页总数 = 已处置 + 待处理；PDF status=pending 行数 = 列表 pending total；badge 不随翻页变化；处置失败时状态保持不变不假装成功。
7. 追加「接口级快速校验」：从 F12 取 Authorization 与 tenant-id 直连三个端点 —— /alarm-order/status-count（期望徽标 = pending+deferred+handling）、/alarm-order/page?orderStatus=unclosed（期望 total = 三项之和）、/dashboard/statistics（期望 todayAlarm.totalAlarms = handledCount + pendingCount）。
8. 末尾以「通过标准」表按需求编号逐项给出单一判定条件，作为验收口径。

## Notes
- 跨链路状态类需求（同一张表派生多个数字）的测试流程必须先给"库侧基准 SQL"，否则页面数字无法证伪；对账断言要写成等式而非"看起来对"。
- 前端静默兜底类缺陷必须专门设计失败路径用例（主动停后端/换无权限账号/断网），只走成功路径永远发现不了 catch 里的降级分支。
- alert_time 为毫秒时间戳，SQL 里日期过滤须写 DATE(FROM_UNIXTIME(alert_time/1000)) = CURDATE()，直接比较会全表落空。
- deleted 列存在 NULL 历史行，统计 SQL 须写 (deleted = 0 OR deleted IS NULL)。
