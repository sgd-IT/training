## Task description
- 核心需求：回答"处置中心的标记误报是否存在真实状态记录"，即判断该动作是纯前端态还是有后端持久化。
- 任务背景：处置中心（alarm-order）与消控室监控（monitoring-center）两屏共用 PUT /eiot/firewatch/alarm-order/false-alarm 接口；前端提交成功后把列表项 status 置为 'false_alarm' 展示。

## Execution process
1. 定位后端链路：FireAlarmOrderController.markFalseAlarm → FireAlarmOrderServiceImpl.markFalseAlarm → markReadAndAppend，单次 updateById 只写 read_flg=1、handle_status=3，并把 `[ISO时间] 标记误报：<中文原因>` 追加进 details 文本。
2. 核对 AlertOrderStatusResolver：orderStatus 仅由 handle_status 派生（0/NULL→pending、2→processing、3→handled、其余→confirming），不存在 false_alarm 取值；handle_status 可被后续动作覆盖。
3. 核对 AlertRecordDO 与 _sql/mysql 迁移脚本（含 V20260805_2、V20261008、V20261023）：全库从未新增误报标记列、误报原因码列或处置动作列；确认无 handle_record 类处置流水表（Grep handle_record|handling_record|处置记录表 = 0 命中）。
4. 前端取证：mapAlarmToDisplay 用后端 orderStatus 覆盖本地 status，getAlarmTimeline 的误报条目写入内存 ref timelineRecords，故刷新后统一显示"已处置"、时间线只剩"系统接收到告警"；ORDER_STATUS_FILTERS 无 false_alarm 项。
5. 生产库实测（只读 MCP）：details LIKE '%标记误报%' 共 73 行（handle_status=3 有 67、=2 有 5、=1 有 1；alarm_kind=1 有 38、=3 有 18、NULL 有 16），with_handler=0；抽样末段形如 `2026-10-26T09:16:55.760238706] 标记误报：施工/装修影响`；information_schema 核实 details 为 text、max(CHAR_LENGTH)=323、≥250 仅 3 行，无截断风险；order_status 列线上仍存在（V20261023 的 DROP 未执行）。
6. 缺陷定位：confirmAlarm 有 SecurityFrameworkUtils.getLoginUserNickname() 兜底，markFalseAlarm / confirmRealFire / closeOrder 三个接口均无兜底且前端不传 handler，导致操作人完全丢失；前端"后续措施"复选框（复位/巡检/报修）未进入请求体。

## Notes
- 仓库 _sql/mysql/system.sql 等基线脚本不含 alarm_kind/tier/handle_status，属陈旧快照，不能据此判定线上列缺失；结论须以 AlertRecordDO + 迁移脚本 + information_schema 三者交叉验证。
- alarm_kind=5 表达的是"告警源头即误报"的类型语义，与人工"标记误报"动作无关，按报警类型=误报筛选捞不到被人工标误报的工单。
- resolveHandlerInfo 只从 details 末段解析出 handler/handleTime，不会把"标记误报"这个动作名抽成字段，VO 的 handleType/handleRemark 在该路径下不被填充。
