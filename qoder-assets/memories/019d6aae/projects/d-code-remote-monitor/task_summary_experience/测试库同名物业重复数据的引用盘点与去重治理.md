## Task description
- Core requirement: 用户问"为什么有2个广东安为安全科技有限公司"，随后要求"测试库修改一下只留166的"。
- Task background: 消防远程值守项目测试库 anwei_fire_remote_monitor（192.168.250.160）与生产库 anwei-fire-remote-monitor-prod 均通过 MySQL MCP 的 mysql_query 访问；fire_property 是物业（联网单位）主表。

## Execution process
1. 双库对比定位：测试库 fire_property 存在两条同名记录 —— id=1001（tenant_id=1、有地址、2026-04-20 建）、id=1018（tenant_id=166、无地址、2026-10-20 建）；生产库只有 id=1001 且 tenant_id=166。根因是早期把项目建在系统租户下，生产后来改了 tenant_id 而测试库未同步，之后又在 166 下重建了同名记录。
2. 引用面盘点：先用 information_schema.COLUMNS 按 column_name='property_id' 列出所有关联表（fire_alarm_order / fire_daily_statistics / fire_device_maintenance / fire_duty_schedule / fire_guard_audit / fire_hazard / fire_maintenance_contract / fire_maintenance_plan / fire_patrol_record / fire_patrol_task / fire_repair_order / fire_transmission_device + eiot_remote_operation_log），再用一条 UNION ALL COUNT 对候选表逐个统计 property_id=1018 的引用量 → 全部为 0；eiot_space 无 property_id 列（直接 WHERE 会报 Unknown column）。
3. 关键权衡：1001 挂 243 条排班（含当日 wholeday 班），不能删；1018 是空壳。故不执行"删掉 tenant 1 那条"，改为①逻辑删除 1018 ②把 1001 的 tenant_id 由 1 改为 166，结果与生产库结构一致。
4. 落库：UPDATE fire_property SET deleted = b'1' WHERE id = 1018；UPDATE fire_property SET tenant_id = 166 WHERE id = 1001（deleted 为 bit(1)，用 b'1'）。
5. 校验：SELECT 确认 1001/tenant 166/deleted=0、1018/deleted=1；按 tenant 166 聚合确认唯一物业且 duty_cnt=243 保留完整。
6. 排班表 tenant_id 不需同步：查得 fire_duty_schedule 中 property_id=1001 的记录 tenant_id 分布为 0(116)/1(1)/166(126) 三态混杂，但 FireDutyScheduleServiceImpl 走 TenantUtils.executeIgnore + getTenantPropertyIds() 按物业归属过滤，不依赖排班行自身的 tenant_id。

## Notes
- 同名实体排查判据顺序：先双库对比是否环境独有 → GROUP BY name HAVING cnt>1 找全量重复 → 逐业务表统计引用量区分"在用侧"与"空壳侧"，再决定删哪条；凭 create_time 或 tenant_id 猜哪个是新的容易删错。
- deleted 列为 bit(1) 时写 b'1'；历史行可能为 NULL，统计条件须写 (deleted = 0 OR deleted IS NULL)。
- 保留有数据的一侧并改其归属，比删除后迁移外键更安全，前提是目标租户下不存在唯一约束冲突（本库 fire_property 有 uk_tenant_id，需先确认该租户下无其他存活物业）。
