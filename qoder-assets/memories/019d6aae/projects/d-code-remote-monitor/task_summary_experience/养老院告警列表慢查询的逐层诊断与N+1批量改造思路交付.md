## 补充核实
- 【"每页少约 80 次查询"的算法口径（已用 git show 21056d3^ 旧代码 + 前端 pageSize 实测核实）】80 = 每条记录 4 次单查 × 本页 20 条。4 次构成：fillDeviceType 内 3 次（eiotDeviceInfoMapper.selectById 设备 → productMapper.getByProductKey 产品 → categoryMapper.selectById 分类）+ for 循环体内**内联**的第 4 次 tenantApi.getTenantName（→ TenantServiceImpl#getTenant → tenantMapper.selectById，无任何缓存，同租户重复 20 条也查 20 次）。易漏点：第 4 次查询不在 fillDeviceType 里而是直接写在循环体中，只数函数内的 3 个会算成 60。
- 【20 条的来源与端差异】PC 端"报警记录"页 queryParams.pageSize: 20（anwei-fire-remote-monitor-vue/src/views/eiot/firewatch/alarm-record/index.vue），故 80 这一口径绑定 PC 报警记录页；移动端告警中心 pageSize: 10，同一份代码一页约 40 次。框架 PageParam 默认 PAGE_SIZE 为 10，实际条数以各端显式传参为准。
- 【80 是上限值】fillDeviceType 存在三段提前 return（deviceId 为空 / 设备查不到 / productKey 空 / 产品查不到），命中则该条只剩 1 次租户查询；生产数据告警基本都带 deviceId，实际接近跑满，对外表述用"约 80 次"更稳。
- 【改造后口径】额外查询收敛为循环外固定 3 次 IN 批量（设备/产品/分类各一次）+ 租户 ID distinct 后 1~2 次，即 80 → 3~4 次；该数字不含 selectPage 自身的 count + list 两条 SQL。
