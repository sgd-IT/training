6. 第二轮浏览器端到端实测取证（本地环境，非生产）：
   - 视频监控并非"不出图"：4 分屏 10 路全在线，点击后首帧耗时 10–18 秒才出画面，之后正常播放；实际流地址是 `rtsp://…:9100`，经 nginx `/wsplayer-proxy` 转发，本地 HTTP 页面下不会触发混合内容拦截，7096 问题只在生产 HTTPS 下出现。首次加载偶发 `ERR_CACHE_READ_FAILURE` 导致静态资源加载失败。
   - "实时时间差太多"定位为设备 OSD：顶栏时间与系统同秒，热成像那路 OSD 慢约 20 小时，属设备端 NTP，前端改不了。
   - 排班页仍是平铺表格，无项目搜索/项目列表/整月视图入口；租户下拉无 filterable。
   - 报警统计详情弹窗 img=0 / video=0，接口 videoUrl 为 null，VO 无图片字段；移动端 alarm-detail 只渲染静态 icon——PC 与移动端的"回看图片/视频"均未实现。
   - 处置中心停留 40 秒无任何弹窗/角标/Toast，"实时刷新"只是静态标签，无 WS 无轮询。
   - 报警统计卡片总数 263 而明细 33454，抓接口发现 /statistics 返回 fireAlarms=29880 等来自全量查询、totalAlarms/handleRate 却走另一段 CASE 分组 SQL；根因是 GROUP BY 用了别名 order_status，而 eiot_alert_record 表真实存在同名 varchar 列，MySQL 优先按真实列分组，只统计到该列非空的行。
7. 第三轮生产库核对（MySQL MCP，schema anwei-fire-remote-monitor-prod）：查明大屏截图的 23/22/1 对应的是 2026-10-22 的数据（租户 166 的 19 条 + 174 的 4 条），当天 10-23 是 27 条全处置；那条"待处理"是 id=17202、handle_status=1（稍后处置）、order_status=NULL。同时查明 order_status 全表仅 286 条有值且集中在 2026-04-22~04-29，AlertRecordDO.orderStatus 全仓零引用，所有 setOrderStatus 都是 VO 计算值。

## Notes
- 盘点外部需求清单时先做与既有需求编号的重叠映射，可避免重复排查：本清单中"信息不统一/待处理0实时10/设备类型/排班/全部租户搜索"均落在上批 34/42/36/41/43 范围内。
- 检索某功能是否存在的判据要区分三种形态：完全无实现（零命中）、仅有提示文案而无解决逻辑（7096 属此类，易被误判为已处理）、有入口无功能（小程序点检属此类）。
- 硬件侧现象类需求（总线盘反馈灯与主机不一致）在软件仓库无落点，应直接归为不可由本平台修复项并向用户澄清。
- 【用户口述现象要先实测证伪】"摄像头不出图"实测是首帧 10–18 秒延迟而非失败；"实时时间不对"实测是设备 OSD 时钟。二者都不是前端缺陷，凭描述直接开工容易改错方向。
- 【派生教训】同一张表派生的多个数字出口，若某个用 CASE 表达式做 GROUP BY 且别名与真实列同名，MySQL 会按真实列分组，产出"看起来合理但只覆盖部分数据"的静默错误统计；这类 bug 只能靠对账（统计总数 vs 明细 total）发现，不会报错。
