## Task description
- Core requirement: 通过开放接口模拟热成像设备报警并验证全链路（接口→落库→实时推送→大屏弹窗→用户处置→状态回写）；后续延伸需求为给出在 IDEA 及浏览器中快速测试该接口的简单方法。
- Task background: 摄像头类报警统一由 DeviceAlertConfigServiceImpl.reportCameraAlert 处理；用户随后追问"为啥前端大屏没有推送"，需诊断推送未达原因并复测；再追问"怎么在 IDEA 快速发请求""有什么简单测试接口的方法""怎么知道 swagger 地址"。

## Execution process
1. 代码盘点确定调用契约：CameraAlertOpenController 位于 controller.app 包 → 实际路径必须带 /app-api 前缀（WebProperties 按包映射前缀）；@PermitAll 免登录鉴权；参数为表单字段 data=JSON 字符串（不是 application/json body），可选项 file 图片；eventType=2 即热成像。
2. MCP 查 eiot_device_info 选定测试设备：序列号 CE0DD7APAGA8B59 的热成像摄像头（id=17，租户166，所属产品 nk7kzc4eCTsrT67H）；devSno 必须是库里已存在的设备 dn。
3. 第一轮：Invoke-RestMethod POST http://localhost:48080/app-api/open/camera-alert/report 返回 code:0/data:true；查库基线 id=31559 → 新增 id=31560（alarm_type=2、device_id=17、read_flg=0）落库成功。
4. 用户反馈大屏无弹窗 → 读 AbstractWebSocketMessageSender/WebSocketSessionManagerImpl 确认：推送只发给处理请求的服务进程内"当前在线且租户匹配(166或1)"的会话，无匹配会话即静默丢弃、不补发；测试时浏览器无任何 WS 连接是首轮无弹窗的直接原因之一。
5. netstat 快照发现 Edge 进程保持多条 ESTABLISHED 连接到 192.168.250.144:48080，而本机 IP 是 .130 —— 坐实第二轮根因：浏览器连的是 .144 远程服务，我调的是本机 IDEA 服务，推送落在错误进程的会话表。
6. 第二轮改调 http://192.168.250.144:48080/app-api/open/camera-alert/report，返回成功；查库新增 id=31561，且与 31560 同库 —— 证实 .144 服务与本机 dev 服务共用同一数据库实例。
7. 补充大屏双到达机制说明：WS 实时秒弹 + 每10秒轮询 /recentUnprocessedAlerts?minutes=5 兜底补弹（5分钟窗口）。
8. 第三轮"再来一次"：同样参数打 .144，查库新增 id=31562（read_flg=0、handle_status=0）；同时发现 id=31561 已变为 read_flg=1、handle_status=2（处置中），证明用户在大屏点击过处置且状态成功回写，端到端链路（接口→落库→WS推送→弹窗→处置→回写）全闭环验证完成。
9. IDEA 快速发请求：盘点发现仓库已有 17 个 Controller 同名 .http 文件（团队既有习惯），但无 http-client.env.json；用 Node v22 fetch 精确模拟三种请求体格式（未编码 x-www-form-urlencoded、multipart、URL 编码 form）对 .144 实测均返回 code:0/data:true，据此新建 CameraAlertOpenController.http（URL 写死 .144，含热成像/高温/烟火/离岗/通道占用 5 种 eventType + multipart 带图示范）。
10. Swagger/Knife4j 方法：实测 doc.html 与 swagger-ui/index.html 返回真实 HTML（200）；swagger-config 与 /v3/api-docs/all 走无前缀路径可匿名访问并返回分组 ai/all/eiot/infra/system，all 分组内含 camera-alert/report 与 receiveCameraAlarm；带 /admin-api 前缀的 api-docs 被安全过滤器拦成业务 401。
11. 尝试命令行登录 admin 以验证文档页需鉴权场景，返回"登录请求令牌不能为空"（登录需验证码），故推荐用 @PermitAll 开放接口直接在文档页调试。

## Notes
- "接口返回成功"不等于"端到端成功"：必须双重验证（返回值 + 查库新记录字段符合预期）。
- 不带图片时每次调用都入库（10秒去重窗口仅在 deviceId 非空且 alertImageUrl 非空时生效）。
- PowerShell 5.1 下 curl 是 Invoke-WebRequest 别名，multipart 上传要用 curl.exe。
- 多实例环境下先确认"前端页面连的是哪个服务实例"再决定调哪个实例的接口，否则 WS 推送必然错过。
- PowerShell here-string 传 JSON 给 curl.exe 会因引号转义导致服务端 500，易被误判为"该格式服务端不支持"；跨格式验证应改用 Node fetch 精确控制原始字节。
- Invoke-WebRequest 判断接口可用性时不能只看 HTTP 状态码：本项目鉴权失败仍返回 200 而 body 是 {"code":401}，须检查响应内容。
- 本条原记载"纯测试与诊断，未修改任何代码文件"已过时：第三轮之后新建了上述两个文件，以 Related files 为准。
