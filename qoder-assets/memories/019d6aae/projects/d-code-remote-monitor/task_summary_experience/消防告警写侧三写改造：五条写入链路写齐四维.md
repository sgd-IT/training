## Notes（后续会话补充）
- 【四维关系的解释口径 2026-10 复核补充】后续被追问"这四个字段什么关系""能不能去掉一个"时，按以下已核实结论回答，勿重新推导：
  ① 维度定位：alarm_type=事件来源（0-5，无序）、alarm_kind=报警性质（1-6，无序）、level=优先级（闭集{1,2,3}，有序，1 最急）、tier=一级内部确认档位（1-4，有序，小=急）。即"三个正交维度 + 一个派生维度"。
  ② 单向派生链：所有写入链路都是 level = deriveLevel(alarm_kind)；tier 仅在 level=1 时判定（defaultTierForKind 对非 KIND_FIRE 返回 null，resolveTier 入口先判非火警直接 return null），故"tier 有值 ⇔ level=1"是硬不变量。配置表单只能选类型不能选等级的根因即在此。
  ③ 正交不可互推：kind=1 火警分不清是主机烟感还是热成像/烟火/高温；type=0 主机链路六种性质全挤在一列只有 kind 能区分。alarm_type 目前仅摄像头链路（W3）写真实 1-5，W1/W4/W5 写 0 —— 这是非视频通路的正确取值，不是缺陷。
  ④ 四档代码落点：W1 resolveTier（"manual"→Ⅰ、"composite"→Ⅱ、其余一级→Ⅳ兜底）；W3 摄像头火警类显式 Ⅲ、离岗/通道→隐患二级→NULL；W4 人工建单固定 Ⅰ；W2/W5 defaultTierForKind（火警→Ⅳ兜底、其余 NULL）。Ⅱ档 composite 属防御性预留（AEP 策略当前不产出该值）；因部件类型原料缺失，非手报的一级事件普遍落 Ⅳ。定稿"Ⅰ/Ⅱ档收到即自动确认"本期未实现，只落档位快照。
  ⑤ 存量印证正交性的实测数据：level=2 的 1,664 条中 1,597 条实为视频类（来源 1-5），真正故障仅 67 条——所以存量迁移必须按事件名称逐项映射，不能按 alarm_type 归类。
