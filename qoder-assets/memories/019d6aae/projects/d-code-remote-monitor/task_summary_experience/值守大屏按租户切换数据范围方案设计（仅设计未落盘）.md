## 任务描述
- 核心需求：需求清单中"设备状态按项目分开"标记为未实现；用户提出改为按租户划分值守大屏数据——管理员角色在左上角标题"安为智慧消防值守平台"右侧显示租户下拉框，其他角色只显示当前租户名称。
- 任务背景：duty-screen 是全屏独立页面，所有卡片数据来自单一统计接口，后端已有 TenantUtils.execute 租户隔离机制，但缺少"指定租户查看"入口。

## 执行过程
1. 定位前端真实入口：duty-screen/index.vue 的 header-left（标题区）、loadData（数据装载）、setInterval(loadData, 30000)（自动刷新）、getAdminPath（既有 super_admin/monitor_role 判断先例）。
2. 定位后端链路：FireDashboardController /dashboard/statistics → FireDashboardServiceImpl.getDashboardStatistics → executeWithTenantAware（UserTenantResolver.resolveLoginUserTenantId + TenantUtils.execute）。
3. 查清"按项目分不开"的根因：EiotDeviceInfoDO 继承 TenantBaseDO 只有 tenant_id、无 propertyId，FireDeviceMapper.selectDeviceList 靠 tenant_id JOIN fire_property，故最大可行粒度是租户。
4. 盘点大屏全部数据源并列出需同步改造的接口：statistics、realtime-alarms、property/page、property/list（地图点位独立轮询）、duty-schedule/current-duty、alert/recentUnprocessedAlerts。
5. 用户拍板两条口径：下拉仅限 super_admin 与 tenant_admin；非管理员显示的租户名由后端按登录租户 id 反查后随响应返回。
6. 核实口径可行性：RoleCodeEnum 存在 TENANT_ADMIN；tenant_admin 由创建租户时自动生成；AuthPermissionInfoRespVO.roles 是角色 code 集合；hasRole 无超管兜底适合做严格白名单；FirePropertyController /property/list-all 是"仅系统管理员跨租户"端点先例。
7. 产出可见性矩阵、后端 3 处改动（VO 加 tenantId/tenantName、接口加可选 tenantId、Service 分支限 super_admin）、前端 4 处改动（角色判断、选项双路来源、显示分支、参数组装）及联调步骤与验收清单。

## 任务概览
完成值守大屏"按租户切换数据范围"的端到端方案设计：确认了按项目粒度不可行的数据模型根因、摸清大屏全部数据消费链路与旧数据残留陷阱、把用户角色口径翻译成项目内可验证的权限判定写法，输出改动清单、联调步骤与验收清单，可直接进入实施阶段。

## 勘误（需求口径更新，以最新为准）
- 第 5 步"下拉仅限 super_admin 与 tenant_admin"作废：租户下拉框最终仅限 super_admin（权限直通、可看全部租户、可在全量/指定租户间切换）；tenant_admin 不再有下拉框，与其余角色一致只显示当前租户名称文本。第 7 步"选项双路来源"简化为仅 super_admin 一路（getTenantPage），tenant_admin 下拉分支取消。
- 普通角色需具备查询权限以获取租户名称展示：推荐随统计接口响应返回租户名（沿用已有的 eiot:firewatch:dashboard:query 权限，由菜单配置授予普通角色），不应下发 system:tenant:query（会同时解锁 /system/tenant/get 与 /system/tenant/page 全量租户列表，存在越权风险）。
- 已核实 module-eiot-biz/pom.xml 已依赖 module-system-api（RoleCodeEnum）与 spring-boot-starter-security（SecurityFrameworkService），该改动无需调整 pom。
