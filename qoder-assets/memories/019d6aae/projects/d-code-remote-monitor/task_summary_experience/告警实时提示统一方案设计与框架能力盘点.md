## Task description
- Core requirement: design a unified real-time alert notification solution for the fire remote monitoring system, covering UDP/TCP/AEP/camera AI four ingestion channels, and simultaneously inventory the framework's existing capabilities and database table structure.
- Task background: the system has inconsistent real-time capabilities across chains (only AEP has WebSocket push); user requested "先不执行方案，你先看看框架能带给我们什么便利以及已有数据库表" to inform architectural decisions; analysis revealed critical gaps (UDP/TCP silent, mobile completely silent) and framework assets (WebSocket starter with multi-sender support, Redis MQ, rule engine).

## Execution process
1. Full-stack chain analysis: traced UDP/TCP via MQ→rule engine→AlertMessageEventListener (no WS), AEP via dual-path (MQ + AlarmRecordService.pushToWebSocket), camera AI via DeviceAlertConfigServiceImpl (firewatch-alert-new). Confirmed only AEP has real-time Web push.
2. Framework capability inventory: discovered WebSocket starter supports 5 senders (local/redis/rocketmq/kafka/rabbitmq), built-in tenant filtering, bidirectional communication (JsonWebSocketMessageHandler), and session management with userType/userId/session tiers; MQ starter supports Redis Stream with pending-message auto-resend; iot-message-notify provides 6-channel external notification framework.
3. Database table analysis: eiot_alert_record has evolved with device_id/product_key/alert_image/alarm_type/handle_status columns but suffers from level dual-semantic (rules '1'-'3' vs AEP '1'-'6') and alarm_type null gap; eiot_device_alert_record exists with alert_state/recover_time modeling; push_post_ids/push_enabled fields are already implemented for role/user-level定向推送.
4. Solution decision: froze the plan at "A: only unify push layer" (not B: unify storage+push), choosing firewatch-alert-new message type for duty-screen zero-change adoption, and confirmed monitoring-center remains unchanged for now.

## Notes
- Critical finding: The framework's Redis sender mode has a consumer-side tenant context defect — RedisWebSocketMessageConsumer runs without tenant context, causing tenant filtering to degrade to broadcast; this must be fixed before multi-instance deployment.
- Key opportunity: push_post_ids and push_enabled fields are already implemented for role/user-level定向推送, providing a ready-made path for future granular alert targeting beyond tenant-level.

## Task overview
Successfully completed a comprehensive architecture audit: delivered a full-stack analysis of four alert chains, inventoried framework capabilities (WebSocket multi-sender, Redis Stream reliability, 6-channel external notification), analyzed database schema evolution and data debt (level dual-semantic, alarm_type null), and froze the unified push solution at the A scope (firewatch-alert-new message type, duty-screen zero-change adoption). All findings are production-ready and directly inform the next implementation phase.
