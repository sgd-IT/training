## Task description
- Core requirement: 审查 PC 处置中心（alarm-order/index.vue）行内"调取视频"按钮与右栏"现场视频"面板是否交互冲突，并按用户拍板的方案 A 删除弹窗单入口化；随后按用户要求把"联动预案"收紧为确认火警后才可用
- Task background: 右栏经 watch(selectedAlarm)→loadCamerasForAlarm→watch(selectedCamera)→loadCameraVideo 已自动播放第一路流，而行内按钮另开 800px el-dialog 用独立的 videoVisible/currentVideoUrl/videoLoading/videoError 四状态再 getLiveUrl 一次，形成双流、双状态源、遮挡吸顶右栏三重冲突；后端 AlertOrderStatusResolver 只有 pending/deferred/handling/handled/closed 五态，前端 getStatusText 里的 confirmed 是永不命中的死映射

## Execution process
1. 审查产出 P0~P2 九项问题清单（重复拉流挤断、cameras[0] 与 selectedCamera 不同源、弹窗遮右栏、retry 误绑 selectedAlarm、playVideo 里 alarm.deviceId||alarm.id 拿告警 id 冒充设备 id 可能播错现场、七按钮同权重等），先出报告不动代码，用户回复"A"选定最小方案
2. 方案 A 落地：删除 el-dialog 弹窗块与 playVideo 函数及四个独立视频状态；行内按钮"调取视频"改"现场视频"，@click.stop 从 playVideo(alarm) 改 selectAlarm(alarm)，播放唯一入口收敛到右栏 loadCameraVideo
3. 状态门禁落地：新增 isUnconfirmed(status)=pending/deferred，"确认火警""确认设备故障"的 v-if 从 isOpenStatus（含 handling）收紧到 isUnconfirmed；新增 canActivatePlan(alarm)=status==='handling' && alarmType!=='fault'，行内与详情弹窗 footer 两处"联动预案"按钮挂该 v-if，activatePlan 内部加 ElMessage.warning('请先确认火警，再启动联动预案') 兜底防其它入口绕过
4. 关键事实核实：确认火警走 FireAlarmOrderServiceImpl.markReadAndAppend→resolveHandleStatusByAction("确认火警")→handle_status=2→展示为 handling，故"已确认"的唯一数据表征是 status==='handling'
5. 连带修复：refreshAlarms 列表刷新后用 Object.assign(selectedAlarm.value, fresh) 原地同步选中项字段——不换引用是硬约束，替换对象会触发 watch(selectedAlarm) 使约 30 秒一次的轮询每次重拉视频流；不补这句则确认火警后详情弹窗仍停在 pending 显示"确认火警"，门禁等于白设
6. 验证：Grep 确认 playVideo/videoVisible/currentVideoUrl 零残留；GetProblems 仅剩改动前既有的 6 条未使用变量警告（isAdmin/notifyFormRef/repairOrderId 等）

## Notes
- handling 不是"确认火警"专属：后端 AlertController.handleAlertRecord（大屏"去处置"）同样写 handle_status=2，这类告警也会放开联动预案；要严格区分需后端加状态，属状态机改造未纳入本次
- 边界保留：故障类（alarmType==='fault'）确认设备故障后不放开联动预案；"标记误报"保留在整个未闭环期间（确认后仍可改判）
- 遗留未处理：P1 七按钮同权重（危险操作与查看操作并排）、点已选中行的"现场视频"无视觉反馈（可挂 refreshVideo()）
