本方案针对'小程序需要拉流视频'的需求，完成了以下工作：
1. 可行性评估：确认微信小程序video组件原生支持m3u8/HLS，后端/live/url接口已就绪，部署nginx具备反代能力；
2. 技术链路：确立video组件 + HLS流 + nginx反代的主路线，放弃WSPlayer和FLV；
3. 前端交互：设计首页'消防运行'栏目下'消控室监控'卡片入口，以及独立'视频监控'页，支持按'值班室'关键词精准筛选四路摄像头；
4. 反向代理：提供nginx.conf配置草案，明确修改位置、生效流程及验证要点。

## Notes
- 后续真机验证修正：小程序 video 组件 http 直连 HLS 在开发版真机已实测可播，且 video 的 src 属媒体资源不受小程序域名白名单校验，nginx https 反代并非主路线的必要前提，已调整为"体验版实测后再决定是否补做"（反代只解决协议可达性，不改善起播速度）。
- 起播 30-40s 的根因经实验确诊为 ICC 侧流媒体冷启动建流（上游设备→流媒体被释放后重建），与 HLS 分片时长和小程序缓冲无关；优化方向改为首页触发后端预热/保活，替代原设想中的播放链路改造。
- 拾音任务再修正（2026）："放弃 FLV"的理由不完整——FLV 并非协议上不可用，小程序 live-player 组件即可播 flv/rtmp，真正的门槛是企业主体+特定开放类目白名单审核（消防/物业类大概率不在列）；且同源 FLV 子码流的 audio tag 数为 0，换到 FLV 也拿不到音频。小程序"有无声音"的决定因素是码流选择（音轨只在 ICC 主码流），不是协议切换。本条第 2 点的主路线结论仍成立，但选型依据应改述为"避开 live-player 类目门槛 + 主码流带宽代价可控"。详见记忆"ICC 码流音频差异：主码流含 AAC 音轨、子码流纯视频"。
