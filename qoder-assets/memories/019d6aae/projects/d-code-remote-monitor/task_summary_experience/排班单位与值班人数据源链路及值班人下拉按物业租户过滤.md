## Task description
- Core requirement: investigate and explain why the current project "cannot schedule for the duty center, only for tenants"
- Task background: user sgd reported a functional gap; the investigation involved tracing the full chain from UI dropdown to database tables, verifying all intermediate layers (frontend API calls, backend service logic, tenant context handling, and actual data), and identifying the root cause in the data model design.

## Execution process
1. Frontend: traced the 'unit' dropdown in duty/index.vue to the /eiot/firewatch/property/list endpoint, confirming it loads fire_property records
2. Backend: identified that selecting a property triggers findPropertyTenantId() to extract the tenant_id, which is then passed to /system/user/simple-list?tenantId=...
3. Database: verified via MCP queries that fire_property.tenant_id maps to system_tenant.id, and that system_users is filtered by tenant_id and status=0
4. Key discovery: confirmed that the 'duty center' is system_tenant.id=1 ('Anwei Tech Duty Center'), but there is no fire_property record with name='Duty Center'; instead, it has 9 building-type properties
5. Root cause: the scheduling model is designed solely for 'tenant units' (fire_property), with no dimension for 'duty center shifts'; the propertyId field is @NotNull in FireDutyScheduleCreateReqVO, enforcing this constraint
6. Data evidence: fire_duty_schedule records are currently all under tenant_id=166, with duty users like 'Gong Yifeng, Yang Lu', indicating a workaround where duty center staff are assigned to tenant properties
7. System behavior: super_admin selecting a tenant_id=1 property triggers TenantUtils.execute(1) which, due to the 'system tenant == login tenant' condition, degrades to an unfiltered query, returning users from all tenants

## Notes
- The 'duty center' business entity is system_tenant.id=1, but its physical representation in fire_property is as buildings (e.g., 'Anwei Headquarters Building'), not as an organizational unit named 'Duty Center'
- The current workaround of assigning duty center staff to tenant properties (e.g., tenant_id=166) is semantically incorrect but operationally functional
- The system tenant degradation behavior for simple-list must be addressed during any 'duty center scheduling' implementation to prevent cross-tenant leakage

## Task overview
Successfully completed a deep analysis of the scheduling functionality's data model: confirmed the 'unit' is fire_property, the 'duty personnel' are system_users filtered by the property's tenant_id, identified the root cause as the absence of a 'duty center' scheduling dimension in the data model, and documented the current workaround and critical system behaviors. This provides a clear foundation for future feature development.
