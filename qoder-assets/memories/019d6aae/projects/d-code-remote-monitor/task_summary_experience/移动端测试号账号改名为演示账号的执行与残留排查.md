## Task description
- Core requirement: 用户要求"把测试号的移动端改为演示账号"，表述有歧义，需先定位"测试号"落点再确定改动口径。
- Task background: 系统里唯一昵称为"测试号"的账号是 system_users 中 id=104、username=test、tenant_id=1、user_type=3（Wx 小程序端）；代码库与数据库中不存在任何"演示账号"实体；移动端登录走 /system/auth/mobile-login（账号/手机号 + 密码），登录页无硬编码测试账号；server 两个 yaml 里的"测试号"仅指公众号 appid test-wx5b23ba7a5589ecbb，小程序已是正式号 wx222eb07bdf774f1d。

## Execution process
1. 盘点候选口径：数据库账号改名 / 仅改昵称 / 新建演示账号 / 微信测试号 appid 配置，四种操作互斥，向用户提问确认。
2. 用户选定"仅改昵称"：登录用户名保持 test、密码不变，移动端登录方式完全不变。
3. 经 MySQL MCP 执行 UPDATE system_users SET nickname='演示账号' WHERE id=104 AND username='test'，返回影响 1 行、变更 1 行；SELECT 复核昵称为"演示账号"、user_type 仍为 3。
4. 排查 oauth2_access_token：user_info JSON 里存有 nickname 快照，历史令牌多为已删除或已过期，末次刷新后新令牌会取新昵称，无需订正。
5. 排查业务表冗余姓名快照：一条 UNION ALL 计数 SQL 扫 8 张表，命中 fire_duty_schedule(34)、fire_patrol_task(9)、fire_patrol_record(228)，其余（handover/repair_order/alarm_order/sms/duty_log）为 0；三表记录全部关联 user_id=104。
6. 二次核查列名与状态分布：排班 33 条 absent + 1 条 scheduled（2026-05~06 历史），巡检任务 9 条全 pending，巡检记录 228 条 status 为 null；因涉及 271 行业务数据订正，再次向用户确认是否同步。

## Notes
- "演示账号""体验版"等词在整个仓库（含 logs、work-log、前端登录页）零命中，说明这类需求中的名词可能是用户口头概念而非既有实体，必须先搜证再提问，不要凭猜测动手。
- 该系统的用户姓名以"冗余快照"形式散落在排班/巡检等业务表的 name 字段中，改用户表昵称不会自动传导到这些表；判断是否需要订正存量要同时看关联 user_id 是否唯一、记录是历史还是进行中。
- information_schema.columns 按 TABLE_NAME IN (...) 批量取列名，比逐表 SHOW COLUMNS 省轮次。
