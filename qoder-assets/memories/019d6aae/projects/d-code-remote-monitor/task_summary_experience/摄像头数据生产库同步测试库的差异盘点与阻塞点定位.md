## Task description
- Core requirement: 把生产库（MCP 实例 anwei-fire-remote-monitor-prod）video_camera 表数据同步到测试库（192.168.250.160:3306 的 anwei_fire_remote_monitor）。
- Task background: 测试库与生产库各自独立维护摄像头数据，用户希望测试环境具备与生产一致的摄像头配置以便联调小程序/大屏视频功能；同步前需要先摸清两侧规模、结构、主键与租户归属差异。

## Execution process
1. 规模核对：prod video_camera 共 32 条，test 共 24 条。
2. 结构核对：通过 information_schema.COLUMNS 取 test 侧 video_camera 全部列（20 列，含 id/channel_id/device_id/channel_name/status/longitude/latitude/address/dept_id/tenant_id/remark/create_time/update_time/deleted/creator/updater/quality/pull_type/type/support_replay），确认两侧结构一致，可直接按列对齐插入。注意 MCP 的 SQL 解析器不支持 SHOW 扩展语法，探查结构必须走 information_schema。
3. 逐条比对：按 (tenant_id, device_id, channel_id) 为业务键对比全量数据，得出 prod 独有 12 条、test 独有 4 条（tenant 166 的热成像 id=29~32）、其余重叠记录字段完全一致，因此实际只需新增 12 条而非覆盖。
4. 阻塞点一（主键冲突）：prod 独有条目使用的 id 29/30/31/32 在 test 已被 tenant 166 的热成像记录占用，若原样带 id 插入会主键冲突；对策是插入时不指定 id 交给自增重新分配。
5. 阻塞点二（租户缺失）：查两侧 system_tenant，test 仅有 id=1（安为科技值守中心）、166（广东安为），而 prod 独有条目里 11 条挂在 test 不存在的租户 174（东莞南城碧桂园湾区国际）、176（粤电花园）、178（广州越秀金桥养老院）上；直接插入会成为租户隔离过滤下不可见的孤儿数据。
6. 就上述两个阻塞点向用户给出决策选项（是否一并同步 3 个租户 / 只挂现有 166；只补 12 条 / 全量对齐 32 条 / 仅补 deleted=0 的可见记录），等待确认后落盘。

## Notes
- 跨环境同步业务表前必须同时核查三件事：主键是否与目标库已有行冲突、外键性质的归属字段（tenant_id/dept_id）在目标库是否存在对应记录、以及软删除记录是否需要一并带过去；只比数据条数会漏掉"插进去也查不到"的问题。
- prod 的 video_camera 同样存在 tenant_id=0 的历史脏数据（id=14、45，均 deleted=1），不能假定 tenant_id=0 只出现在排班表。
- 新摄像头能否真正拉流还依赖 ICC/media server 侧配置，测试库 ICC 环境若无对应设备，即使数据同步到位也无法出图；本次未处理该层。
