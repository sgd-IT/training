## Task description
- Core requirement: 把移动端 /app-api 业务接口的权限"放开"，让 userType 平台位为 2（移动端）和 3（双端）的账号可访问，不再要求菜单权限点。
- Task background: 上一轮为移动端在 controller/app 包新建了 15 个 App 控制器，采用"注入 admin 控制器做薄转发"实现，权限注解照抄 admin 的 @ss.hasPermission('菜单串')。本项目全局启用 @EnableMethodSecurity，跨 Bean 委托会触发 admin 侧二次校验；且 system_users.user_type 是平台位掩码（1=PC/2=移动/3=双端），门禁此前只做在登录环节。

## Execution process
1. 框架层新增移动端准入判定：SecurityFrameworkServiceImpl 增 hasMobilePlatformAccess()，取当前账号 user_type 判移动位（null 按 PC 兜底，与 checkLoginPlatform 同口径）；SecurityFrameworkService 接口加声明；EnjoySecurityAutoConfiguration 的 ss Bean 补注入 AdminUserApi；AdminUserRespDTO 补透出 userType 字段（原 DTO 无此字段）。
2. 重写 15 个 App 控制器（controller/app/firewatch 12 个 + video/device/alert 各 1）：把 23 处 @PreAuthorize("@ss.hasPermission(...)") 全部替换为 @PreAuthorize("@ss.hasMobilePlatformAccess()")。
3. 同步把这 15 个控制器从"注入 admin 控制器转发"改为直调下层 Service，切断方法级安全下经 admin CGLIB 代理的二次权限拦截。
4. 复刻 admin 版内联逻辑与注解对齐：current-duty 租户→物业换算、statistics 日期解析、设备分页企业名批量填充（VO 转换 + 避免 N+1）、video live/url 跨租户取流、维保仪表板聚合等，并保留对应 @TenantIgnore。
5. 边界保持不动：auth 三端点仍 @PermitAll；video 两接口与 system/user/profile 维持"登录即可访问"（admin 侧本无权限注解）。
6. 验证：mvn -pl spring-boot-starter-security,module-system-api,module-system-biz,module-eiot-biz -am compile EXITCODE=0；App 包 15 个新 class 齐全；全仓复查残留 Controller 委托注入与 hasPermission 串均为 0 处。IDE 语言服务报的 "Flexible Constructor Bodies" 经 mvn 实证为误报。

## Notes
- 只改 App 侧注解放不开权限：必须同时把转发目标从 admin 控制器下沉到 Service，否则 admin 代理仍二次拦截非超管账号（详见对应陷阱记忆）。
- 每次受控请求多一次 system_users 主键查询（无缓存），本规模无感知，后续可按需加缓存。
- 维保仪表板/设备分页等聚合逻辑在 App/Admin 两侧成为两份拷贝，改统计口径时需同步（代码注释已标注）。
- 后端由 IDEA 启动不会热装新类，方法签名变更必须重启；回归应用 user_type=2 的移动端账号（如 test），PC-only 账号访问 /app-api 应收到 403。
