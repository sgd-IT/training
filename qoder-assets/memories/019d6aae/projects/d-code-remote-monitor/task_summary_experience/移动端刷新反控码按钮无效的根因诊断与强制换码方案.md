## Task description
- Core requirement: 排查并修复移动端「刷新反控码」按钮点击后无效果的问题。
- Task background: 移动端 pages/remote-control-code/index.vue 有刷新按钮绑定 fetchCode，页面另有进页/过期自动拉取；后端 RemoteControlCodeServiceImpl 从 Redis 取码，PC 端 VerifyModal.vue 由操作员输入该码后经 DeviceInstructionServiceImpl 调 verifyCode 校验。

## Execution process
1. 前端定位：确认刷新按钮 @click="fetchCode" 逻辑正常、请求封装 utils/request.js 无缓存，排除前端事件与请求层故障。
2. 后端定位根因：RemoteControlCodeServiceImpl.getRemoteControlCode() 在 CODE_TTL_MINUTES（5 分钟）有效期内直接复用 Redis 中已有码，只有 key 过期才生成新码；TTL 也只在生成时写入，刷新不会重置。因此移动端重复调用 GET /eiot/device/remote/code 拿回同一个码和同一个 expireAt，用户看到码与倒计时都不变，表现为按钮无用。
3. 交叉核对 PC 端约束：读取 VerifyModal.vue 确认反控码由人工口述输入，强制换码会使旧码失效、操作员需重新索取，属安全上期望的行为，可作为 force 语义的代价接受。
4. 确定修复方案（未落盘）：Service 接口新增带 force 的重载 → Impl 改为 if (force || code == null) 生成并覆盖写回 → AppDeviceInfoController 用 @RequestParam(value = "force", defaultValue = "false") boolean force 透传 → 移动端刷新按钮改 @click="fetchCode(true)"，fetchCode(force) 内仅手动刷新传 force，进页与过期自动拉取沿用原码。
5. 排查过程中的意外发现：同一 Java 文件 Read 工具返回 50 行版本（StringRedisTemplate、无 verifyCode），而 ripgrep 与 node 读磁盘得到 70 行版本（RedisTemplate、含 verifyCode）；PowerShell Get-Content 输出中文乱码不可用于判定，最终用 node fs.readFileSync 打印 size/mtime 作为权威依据。git status 显示 service/remote 目录两个文件均为未提交修改。
6. 任务在开始改代码前被用户中断（取消后续命令执行），修复方案未写入任何文件。

## Notes
- 「刷新按钮无用」类问题优先看服务端是否幂等复用（缓存/TTL 内返回原值），而不是先怀疑前端事件绑定；本例前端完全正常。
- 编辑类工具与检索工具对同一文件可能返回不同版本（IDE 缓冲 vs 磁盘），改动前必须用第三方通道（node 读字节）核实真实内容，否则 SearchReplace 会因原文不匹配失败。
