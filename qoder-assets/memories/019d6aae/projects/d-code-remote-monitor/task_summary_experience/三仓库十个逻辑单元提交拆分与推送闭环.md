3. 中文提交信息编码：写入 _temp\_msg_*.txt 后用 git commit -F 提交，避免 PowerShell 命令行传参乱码；写 _check_msg.cjs 用 spawnSync 取原始 Buffer 与消息文件字节比对，验证 HEAD 信息 e5918a=「告」字正确入库。
4. 推送首次失败：git push 无输出且 status 仍 ahead 9；带 GIT_CURL_VERBOSE 落日志后定位根因为沙箱拦截 spawnSync git EPERM（fetch/ls-remote 只读不受限），带 required_permissions='all' 重跑成功（5876fc9..62ddfea）。
5. PC前端远端多 1 个他人提交 cb4d456（yanglu，改 alarm/list.vue、alarm/config.vue），与本地 7 个提交无文件重叠，执行 pull --rebase origin master 无冲突后推送（cb4d456..183cdf5）；注意 rebase 后本地提交 sha 全部重写。
6. 移动端 remote 名为 anwei 而非 origin，push -u 因脚本不支持参数未建立跟踪，改用 git branch --set-upstream-to=anwei/master master 补建（e21eba6..a6c8862）。
7. 终检：逐仓库 ls-remote 对比本地 HEAD 与远端 master sha，三仓库全部一致、status -sb 无 ahead/behind。

## Notes（后续会话补充）
- 关键防呆：仓库里可能残留他人在暂存区的文件（git status 显示 A / AM / M 在索引侧）。此时 `git add <目标文件>; git commit` 会把那些无关文件一起提交。必须改用 pathspec 形式 `git commit -F <msg文件> -- <单个路径>`，它只提交指定路径的工作区内容、不触碰索引其余部分。误提交后用 `git reset --soft HEAD~1`（非破坏性，仅移动 HEAD）回退再按 pathspec 重做。
- 中文提交信息入库后的乱码判定：终端回显乱码不等于存储错误。用 node execSync({encoding:'buffer'}) 取 `git log -1 --format=%s` 原始字节并输出 hex 写入 UTF-8 文件再 Read 校验——"实"应为 e5 ae 9e、"消"应为 e6 b6 88；若见 feat锛 这类形态则是终端按 GBK 解码 UTF-8 的显示层问题，实际入库正确。
- 同次会话实测：为推送而做的 stash push → rebase origin/master → stash pop --index 中，--index 模式在"本地暂存改动与远端已提交内容完全相同"时会应用失败并保留 stash 条目，改用不带 --index 的 `git stash pop` 走三路合并即可自动去重并 drop；原 AM 状态的新文件 pop 后变为 A（内容与 stash 快照一致，可用 `git diff --stat <stash-sha>` 验证零丢失）。
- 越权风险提醒：上述 push/rebase/stash 属于独立授权动作，用户只说"提交"时不得视为推送许可。
