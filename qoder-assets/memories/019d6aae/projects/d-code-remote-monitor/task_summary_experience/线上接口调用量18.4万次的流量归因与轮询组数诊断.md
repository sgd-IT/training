## Task description
- Core requirement: 记录并归因"线上部署后才暴露"的问题——使用统计页显示 7 天接口调用 18.4 万次、活跃用户仅 6 人，怀疑异常流量；用户已知原因之一是"前端某页面快速轮询后端接口"，要求补充其余成因。
- Task background: 本地自测停留时间短、开的页面少，从未暴露该量级；需要基于 prod 访问日志做可证伪的归因，而不是凭印象下结论。

## Execution process
1. prod MCP 只读取证 infra_api_access_log（2026-10-26 起 3 天，TOP15 合计 67,842 次），按 request_url / user_agent / user_ip 聚合做流量分类。
2. 关键证据 1（机器流量）：`/admin-api/eiot/remote-console/valve/command/7` 26,318 次全部来自单一 IP 219.131.130.21，UA 为 `Mozilla/5.0 ... Chrome/65.0.3325.162 ... Hutool`（Java 客户端伪装 UA），24 小时恒定 447 次/小时 ≈ 8 秒一次；该接口 @PermitAll + tenant ignore-urls + Redis Lua 消费，是外部智能空开控制服务机器对机器拉命令，平均 0.01 秒、零 DB 压力，占 TOP15 的 39%。
3. 关键证据 2（轮询组数）：`/alert/recentUnprocessedAlerts` 按分钟聚合，10-27 03:00~03:10 连续 10 分钟每分钟精确 7 次，深夜不间断；对应 7 个页面实例各挂一条 60 秒轮询表（duty-screen / remote-console 用 useVisiblePolling 60s，monitoring-center 用裸 setInterval 60s，alarm-order 30s 等）。useVisiblePolling 只在 document.hidden 停表，KeepAlive 页面切路由时 document.hidden 仍为 false、onUnmounted 不触发，表照跑；10-27 17:00~20:00 掉到 61~133 次/小时、21:00 回到 420，是那台机器浏览器被关又开的曲线。
4. 关键证据 3（压力权重）：valve/command 26,318 次 avg 0.01 秒 vs dashboard/statistics 9,893 次但成功请求 avg 3.22 秒、单次串行十几条聚合 → 按条数排会把零压力接口顶到第一。
5. 关键证据 4（连锁放大）：dashboard/statistics 26 条 500 平均 729 秒，getDeviceWithProperty 1 条 500 耗时 7,948 秒（2.2 小时），recentUnprocessedAlerts 1 条 500 耗时 1,477 秒 → 浏览器同域 6 连接槽被 7 张轮询表挤满 → axios 30 秒超时先断 → Broken pipe → 全局兜底记假 500，与 10-27 定责同源。
6. 关键证据 5（口径/交互）：统计只按 request_url 聚合、不区分人工/页面/机器流量；且时间范围改完不点"查询"页面不重查——截图日期已选 10-26~10-28，趋势图与总量仍是 10-22~10-28 的 7 天数据（实测 3 天 67,842 次 vs 近 7 天 192,405 次），"10 万次"是被 7 天口径放大的观感。
