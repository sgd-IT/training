## Task description
- Core requirement: 用户粘贴 9 条外部需求/缺陷清单（编号 17/28/29/33/34/36/41/42/43），要求"按完成度和是否存在问题以及解决方法去看，因为用户给出的需求不一定符合修改的标准"，即逐条判定完成度 + 缺陷 + 修复方案，并对不合理需求做纠偏。
- Task background: 涉及 PC 值守大屏(duty-screen)、监控中心、火警处置中心(alarm-order)、告警记录(alarm-record)、排班(duty)四个前端页面与后端 FireDashboardServiceImpl / FireAlarmOrderServiceImpl / AlertRecordMapper / FireDutyScheduleServiceImpl 等链路；本轮为纯只读盘点，未改任何代码。

## Execution process
1. 三色管理(17)：核实 duty-screen/index.vue 已有 .level-critical/.level-major/.level-warning 三档（背景透明度仅 0.06~0.12），但 .tag-warning 无定义、.alarm-dot 恒为红色不随等级变；monitoring-center 三色完整——两屏各写死颜色无共用 token。判定：部分完成，需求措辞需纠偏为"按 level(1/2/3) 分色"，因 alarm_kind 实为六类且系统无"反馈"类型。
2. 今日值班(28)：定位三层叠加缺陷——①FireDashboardServiceImpl.buildCurrentDutyList 对普通租户按 tenant_id 过滤(selectCurrentDuty)，而 FireDutyScheduleServiceImpl.getCurrentDuty 刻意按"物业归属租户"过滤（注释说明排班常由管理员代建、tenant_id 对不上），同一份数据两套隔离口径；②system 账号走 executeIgnoreWithResult 全租户查询 orderByAsc(shiftType)+LIMIT 10，前端再 slice(0,3)，排序靠前的单位独占前三席；③DutyScheduleItemVO 只有 id/userName/shiftName/startTime/endTime/status，缺 phone/propertyName/position，卡片无法标识项目。
3. Excel 下载(29)：核实 FireAlarmOrderController 仅有 /statistics 与 /export-pdf，无 /export；alarm-record/index.vue 的 handleExportExcel 请求不存在端点→404→catch 静默 fallback exportTableToCSV()，只导当前页(pageSize=20)且格式为 CSV。判定为"伪实现"，失败无提示是主要风险。
4. 火警提示范围(33)：AlarmPopupDialog 仅挂载在 duty-screen 与 monitoring-center 两处；大屏点告警跳 /eiot/firewatch/alarm-order?id=xxx 后该页无任何新告警提醒；remote-console 有独立的按父设备子树轮询的滚动告警。历史提交 a770506/72c2108 已下线通知匣，明确不建议复活。
5. 信息不统一(34)：查出 4 个独立缺陷，其中一个是明确 bug——FireDashboardServiceImpl.convertToRespVO 第 603 行先 setOrderStatus(AlertOrderStatusResolver.resolveOrderStatus(record))，第 621 行又用 readFlg 三元表达式覆盖，导致大屏只剩 pending/closed 两态；统计侧 countTodayUnreadAlerts(handle_status<3) 与筛选侧 ORDER_STATUS_CASE_SQL='pending' 两套判据；handle_status=1(稍后处置) 被归入 pending 且前端筛选项无 deferred；alarm-order 的 pendingCount 由前端对 pageSize=10 的当前页 filter 得出。
6. 设备类型(36)：fillDeviceTypeBatch 的 device_id→product_key→category_id→name 四级映射只在 alarm-order 生效；/alert/recentUnprocessedAlerts 返回裸 AlertRecord（SQL JOIN 了设备/产品/租户但未取分类名）、WS firewatch-alert-new payload 亦无 deviceTypeName，故大屏一级报警弹窗 AlarmPopupDialog 无设备类型行。
7. 排班优化(41)：duty/index.vue 已具备筛选/新增/自动排班/日历视图/导入/导出；loadCalendarData 调 getDutyScheduleByDateRange(start,end,propertyId) 证明"整月总览"数据能力已存在，缺的是"项目列表+项目级入口"形态。指出需求歧义：现模型无"项目-值班人员池"实体，值班人即 system_users。
8. 待处理0/实时10(42)：待处理=countTodayUnreadAlerts(今日且 handle_status<3)，实时告警=selectLatestAlerts(ORDER BY alert_time DESC LIMIT 10，不限状态不限日期) + 前端 filterTodayAlarms 仅按当天过滤，badge 又取 alarmList.length，三者语义不同源，矛盾必然出现。
9. 全部租户(43)：duty-screen 的 el-select 无 filterable，选项来自 getTenantPage({pageNo:1,pageSize:100}) 并排除租户 1。判定"改为搜索按键"不合理，应加 filterable+remote。标注待确认项：工作区未找到 TenantPageReqVO，其是否支持 name 模糊查询未知。
10. 本工作区 mcps 目录仅有 browser-use/fetch/figma/genui/sequential-thinking/tgr-gz-vue，无 MySQL MCP，故所有需 DB 验证的结论均降级为"附 SQL 待用户本地核对"。

## Notes
- 判断"需求不符合修改标准"的可复用抓手：把用户口语词映射到系统真实维度（如"火警/故障/反馈"→ alarm_kind 六类 vs level 三级；"反馈"无对应类型），措辞错位时按数据模型纠偏而非照做。
- 盘点类任务的交付结构：总览表(编号|完成度|核心问题|结论) + 逐条(现状/问题/解决方法/待验证) + 迭代批次(P0 口径统一→P1 功能补齐→P2 体验形态→P3 需澄清) + 单列"不建议按原需求直接改"清单，便于用户直接转给产品。
- 易漏点：前端 catch 里的静默兜底（导出 404 退化成 CSV）会让"伪实现"长期不被发现，盘点时应专门检查兜底分支是否掩盖失败。
- 同一份数据的两套隔离口径（tenant_id vs 物业归属）是本仓库反复出现的结构性风险，遇到"只显示某单位数据"类投诉优先怀疑口径分叉而非权限配置。
