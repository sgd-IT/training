## Task description
- Core requirement: locate the mobile app's alarm center data query API endpoint and analyze its MySQL performance
- Task background: user asked for the API; we found it in the frontend (index.vue) and backend (FireAlarmOrderServiceImpl); then analyzed eiot_alert_record table indexing to address 'all status' query performance

## Execution process
1. Frontend: identified GET /eiot/firewatch/alarm-order/page call in index.vue line 139 with params (pageNo, pageSize, alarmType, orderStatus)
2. Backend: located FireAlarmOrderServiceImpl.doPageFromAlertRecord() method and confirmed MyBatis-Plus dynamic query building
3. Index analysis: discovered eiot_alert_record has only PRIMARY KEY (id), no secondary indexes
4. Query pattern analysis: 'all status' query becomes WHERE tenant_id = ? AND deleted = 0 ORDER BY alert_time DESC → full table scan + filesort
5. Optimization recommendation: proposed three composite indexes, especially idx_tenant_alert_time (tenant_id, alert_time DESC) to eliminate filesort
6. Verification method: provided EXPLAIN command examples and interpretation guide

## Notes
- 【索引现状已演进（prod 实测）】第 3 步"仅有主键、无二级索引"及第 5 步"建议新建 idx_tenant_alert_time"均已过期：生产库 SHOW INDEX 显示 idx_tenant_alert_time 已实际创建，列序为 (tenant_id, alert_time, deleted)。排查前必须先 SHOW INDEX 核对，勿再假设无索引。
- 【慢查询主因修正】列表仍慢的主因不在缺索引，而是 doPageFromAlertRecord 结果转换循环里的 N+1：每条记录经 fillDeviceType() 触发设备→产品→分类 3 次查询，再加 tenantApi.getTenantName() 1 次，每页 20 条即约 80 次额外查询。
- 【索引列序结论已被后续实测推翻】原建议改为 (tenant_id, deleted, alert_time) 已不成立：线上索引实际已是 (tenant_id, alert_time, deleted)，用户提供的 SHOW INDEX 输出与该表默认查询的 EXPLAIN 显示 type=ref 且 Extra 无 Using filesort，排序开销已由索引天然有序消掉；该表 deleted=0 占比接近全量，把 deleted 前置收益极小。结论：当前索引够用，生产库动索引有锁表风险，不应再以"优化列序"为动作项，瓶颈一律归到应用层 N+1。
- 【数据分布事实】prod 总记录 15779 条中 tenant_id=174（养老院）占 14378 条（91%），其中 pending（handle_status 为 0/NULL 或 <3）达 13535 条（94%），单租户热区导致索引区分度低。
