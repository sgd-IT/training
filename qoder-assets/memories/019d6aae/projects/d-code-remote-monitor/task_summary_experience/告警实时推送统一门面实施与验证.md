## Task description
- Core requirement: implement a unified real-time alert push facade for UDP/TCP/AEP/camera AI four ingestion channels, enabling duty-screen to receive all alerts in real time.
- Task background: the system had inconsistent real-time capabilities across chains (only AEP had WebSocket push); user requested framework capability and database table inventory first; analysis revealed critical gaps (UDP/TCP silent, mobile completely silent) and framework assets (WebSocket starter with multi-sender support, Redis MQ, rule engine).

## Execution process
1. Created AlarmRealtimeNotifyService.java: unified push facade with info-level filtering, tenant dual-send (alert tenant + system tenant), and full try-catch isolation.
2. AlertConfigService.java: changed addAlertRecord signature from void to Long return type.
3. AlertConfigServiceImpl.java: modified addAlertRecord to return recordDO.getId() after insert.
4. AlertMessageEventListener.java: added pushRealtimeAlarm method to trigger facade push after alert save; added param null-check to prevent NPE in getFormatContent.
5. AlarmRecordService.java: moved pushToWebSocket out of transaction boundary into saveAlarms loop; added firewatch-alert-new facade push alongside existing alarm-push.
6. DeviceAlertConfigServiceImpl.java: migrated camera chain to facade; replaced hard-coded level "2" with enum value; removed unused WebSocketSenderApi/TenantApi fields.
7. duty-screen/index.vue: mapped details to content.alertDetails and added subDeviceName mapping for TTS speech.
8. Verified backend compilation (mvn compile -pl module-eiot/module-eiot-biz -am -DskipTests) and frontend eslint (node node_modules/eslint/bin/eslint.js) — both passed.

## Notes
- Critical finding: RedisWebSocketMessageConsumer runs without tenant context, causing broadcast instead of per-tenant filtering; this must be fixed before multi-instance deployment.
- Key opportunity: push_post_ids and push_enabled fields are already implemented for role/user-level定向推送, providing a ready-made path for future granular alert targeting beyond tenant-level.
- Framework capability inventory: WebSocket starter supports 5 senders (local/redis/rocketmq/kafka/rabbitmq), built-in tenant filtering, bidirectional communication (JsonWebSocketMessageHandler), and session management with userType/userId/session tiers; MQ starter supports Redis Stream with pending-message auto-resend; iot-message-notify provides 6-channel external notification framework.
- Database table analysis: eiot_alert_record has evolved with device_id/product_key/alert_image/alarm_type/handle_status columns but suffers from level dual-semantic (rules '1'-'3' vs AEP '1'-'6') and alarm_type null gap; eiot_device_alert_record exists with alert_state/recover_time modeling.
