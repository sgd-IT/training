## Task description
- Core requirement: 用户按上一轮教程自行手敲实现"摄像头报警短时重复上报去重"，要求 AI 对照项目真实代码做评审复盘与复检。
- Task background: 前序诊断已确认根因是上游同一事件两次 HTTP 请求导致双入库双推送；方案选定"查库 + ±10秒时间窗"（Mapper 新增 selectRecentCameraAlert，Service 在 insert 前查重命中即 return）。AI 红线为只评审不改业务代码。

## Execution process
1. 第一轮评审（git diff --stat + git diff + Read + GetProblems 四路取证）：Mapper 的 selectRecentCameraAlert（ge/le 双向窗口、orderByDesc + LIMIT 1、风格对齐 selectActiveAlert）判定完全正确；检查位置（insert 前、tenantId 设置后）与边界判空条件正确；常量提取规范。
2. 第一轮查出三处 P0：① 常量 CAMERA_DEDUP_WINDOW_MS 写成 1000L（注释写 10 秒，实际 1 秒）；② 查询返回值被丢弃，缺"判空 + log + return"，等价于白多一次 select；③ 窗口左界方向反了，传 (alertTimeMs, alertTimeMs+窗口) 变成"只查本次之后"，用实测 918838/919787 两个时间点代入即可验出正常时序查不到。
3. 第二轮复检：三处 P0 均已改对（常量改 10 * 1000L、cameraAlertRecord 接住并判空 log.warn + return、窗口改 alertTimeMs ± 常量）；P2 未使用 import org.springframework.util.StringUtils 与格式问题清理干净；Mapper 本轮未再改动保持正确。
4. 第二轮新发现遗留 P0（尚未修复）：用户把 insert + log.info + 推送 try/catch 整块挪进守卫 if (deviceId != null && StrUtil.isNotBlank(alertImageUrl)) 内部（约 L301-L339），使"要不要查重"变成"要不要处理这条告警"的总开关——deviceId 为空（devSno 未匹配设备）或 alertImageUrl 为空（两个端点 file 参数均 required=false）时告警不落库不推送，问题性质从"重复弹窗"恶化为"漏告警"。修法：将 insert 及之后语句移出 if，回到与 if 同层级。
5. 静态检查结论：无编译错误，仅 IDE 对 ObjectUtils.isEmpty(device) 的数据流误报警告（既有代码，可忽略）；终端中文乱码属显示编码问题，须以 Read 读文件原文为准。
