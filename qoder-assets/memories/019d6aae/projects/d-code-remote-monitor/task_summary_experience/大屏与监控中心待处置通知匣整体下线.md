## Task description
- Core requirement: 删除消防值守 PC 端两处「待处置 N」告警通知匣浮层 —— 先值守大屏（duty-screen），再监控中心（monitoring-center）。
- Task background: AlarmNotice 组件（views/eiot/firewatch/alarm-notice/index.vue）被两屏各自挂载为浮动胶囊 + 展开面板，用于堆积二三级（轻）告警；一级告警走全屏弹窗 AlarmPopup/AlarmPopupDialog。用户口语"待处置"字面只命中通知匣 pill（今日警情那格叫"待处理"），存在歧义，经确认锁定为通知匣。

## Execution process
1. duty-screen/index.vue：删除模板 <AlarmNotice ref="alarmNoticeRef" :offset-right="414" :offset-top="66" show-tenant @open="onNoticeOpen" />；删除 alarmNoticeRef、alertShownIds、onNoticeOpen；import 从 `import AlarmNotice, { isLightAlarmLevel }` 改为仅 `import { isLightAlarmLevel }`。
2. duty-screen 双通道收敛：fetchRecentAlerts 轮询回调删掉「二三级 filter + push」整块，保留 alerts.some(isLightAlarmLevel) → flashPendingToast()；firewatch-alert-new WS 回调把 `if (isLightAlarmLevel) {去重 + push + Toast}` 简化为 `if (isLightAlarmLevel) { flashPendingToast() }`，一级 else 分支的 popupRef.enqueue 不变。
3. monitoring-center/index.vue：同口径删除模板 <AlarmNotice>（中栏左下 offset-left=304）、alarmNoticeRef、alertShownIds、handleNoticeOpen 及组件导入；三处推送逻辑（pushPopupAlarm、fetchRecentAlerts、firewatch-alert-new 回调）统一改为 `if (!isLightAlarmLevel(item.level)) popupRef.value?.enqueue(item)`，即只有入队全屏弹窗。
4. 保留项判定：isLightAlarmLevel 仍被两屏用于一级/二三级分流故必须继续从 alarm-notice/index.vue 导入；jumpToAlarmScene、viewAlarm、ElMessage 在别处仍有调用点，均不可随通知匣一并删除。
5. 验证：Grep 确认两文件对 alarmNoticeRef / alertShownIds / onNoticeOpen|handleNoticeOpen / AlarmNotice 零残留；用 `node .\node_modules\eslint\bin\eslint.js <file>` 逐文件校验通过（绕开 pnpm.ps1 执行策略问题）；GetProblems 仅剩既有的 -webkit-background-clip 警告与 DevelopingTag 未使用告警，非本次引入。

## Notes
- 删除 UI 组件时必须顺着 ref 反查所有"消费点"（轮询回调 + WebSocket 回调是两条独立通道，漏一条会留下对 null ref 的可选链死代码），否则只是隐藏了入口而逻辑仍在跑。
- 组件默认导出与具名工具函数混在同一文件时（export default AlarmNotice + export function isLightAlarmLevel），停用组件不能直接删文件，需先把仍被引用的函数抽到 utils 再清理，否则破坏构建。
- 用户表述"待处置/待处理"在项目里对应两个不同元素，删除类需求先用字面 grep 定位候选再向用户确认，避免误删承担 Toast 锚点的统计格。
