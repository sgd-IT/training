## Task description
- Core requirement: 对三个仓库（后端 anwei-fire-remote-monitor、PC 前端 anwei-fire-remote-monitor-vue、移动端 anwei-fire-remote-monitor-mobile）当前未提交改动做代码简洁度检查，产出带严重度分级的结构化报告。
- Task background: 后端 +597/-181（20 个 Java 文件 + 2 个 yaml）、前端 +398/-106（5 个 vue）、移动端仅 manifest.json 行尾差异；这批未提交改动是"告警未闭环口径统一 + 处置中心多维筛选 + 远程反控码新接口"的产出，其中远程反控码链路是全新代码。

## Execution process
1. 逐仓 `git status --porcelain` + `git diff HEAD --stat` 划定范围；配置文件（application*.yaml）与纯行尾差异文件（manifest.json）排除出代码检查面。
2. 大 diff 用 `git diff HEAD -- "*java" > _temp\_cc_be.diff` 落盘后分段 Read（后端 1305 行、前端 944 行），再对可疑处直读源文件与 Grep 取准确行号核实。
3. 发现严重缺陷：RemoteControlCodeServiceImpl.getRemoteControlCode() 组装完 RemoteControlCodeRespVO 后以 `return null;` 结束，方法前 16 行全部成为无效计算，App 端 `/eiot/device-info/remote/get-code` 必返 null；同时生成的 code 从未调用 `opsForValue().set(...)` 写回 Redis，注释宣称的"无或失效就重新生成并复用"语义不成立，expire 值也未真正作用到任何 TTL；TimeUnit import 未使用。判定为必须修的功能性缺陷而非单纯冗余。
4. 报告按严重/建议/可选三级列出 18 项，核心建议集中在：FireAlarmOrderServiceImpl 两处 orderStatus 过滤 switch 逐字重复、handled+closed 与 pending+deferred+handling 聚合口径在两个 Java 类加前端共 3 处各写一遍、alarm-order 页 dateShortcuts 三段样板且与 alarm-record 页重复实现、未闭环状态集在模板内联 8 次、值班条目映射 4 份近似重复、Excel 导出查询层 LIMIT 与 stream().limit() 同值双上限、公共摄像头与系统租户判定各散落两处、设备类型名解析存在 SQL JOIN 与 Java 两次跨租户查询两套实现。
5. 结尾给出净收益预估（约减 120~140 行）并按用户行为约束询问是否落地及落地范围，全程未修改任何代码。

## Notes
- 简洁度检查会顺带暴露真 bug：新增文件务必核对每条 return 路径，"方法体组装完对象却 return null"这类半成品若未被检出会直接让新接口上线即失效。
- 同一功能的两种实现路径要辨明是否可归一：WS 推送链路不能走 SQL JOIN，Java 侧 resolveDeviceTypeName 两次跨租户查询是合理补偿，不应简单判为重复而删除，只需注释标明用途边界。
- 附带发现（非简洁度范畴）：alarm-record 页导出文件名用 `new Date().toISOString().slice(0,10)` 取的是 UTC 日期，东八区 08:00 前导出会写成前一天。
- PowerShell Select-String 经 Node fallback 执行时管道输出为空不可信，改用 Grep 工具取行号。
