## Task description
- Core requirement: 解释排班页面"值班人员"下拉框在某单位下为何无数据（用户描述为"安为科技有限公司下无值班人员"）
- Task background: 上一轮已确认下拉链路为 duty/index.vue 的 userList ← loadUserList(tenantId) ← /system/user/simple-list?tenantId=xxx，tenantId 由所选 fire_property 记录的 tenant_id 反查得到；本轮需用真实数据判定空列表的原因

## Execution process
1. 用 MCP（prod / test 两个 MySQL 实例）核对 system_tenant、fire_property、system_users 三表：确认系统内不存在名为"安为科技有限公司"的单位，最接近的是"广东安为安全科技有限公司"
2. 按 fire_property.tenant_id 关联统计 system_users 中 status=0 的用户数，得出各"安为"系单位的候选人数量；唯一零用户的是"安为园区"（tenant_id=167）
3. 关键发现——同名单位的环境差异：test 库存在两条同名"广东安为安全科技有限公司"，id=1001 的 tenant_id=1（系统租户）、id=1018 的 tenant_id=166；而 prod 库同一条 id=1001 的 tenant_id=166。即该物业的租户归属在测试库被改过，属脏数据，会导致两个环境下拉出的人员集合完全不同
4. 前端定位：搜索栏"值班人"是 el-input 文本输入而非下拉，因此"无值班人员"只可能出现在新增/编辑弹窗、自动排班弹窗、换班弹窗这三处共用 userList 的 el-select
5. 后端排除项核实：UserController 类与方法均无 @PreAuthorize，FirePropertyRespVO 及 convertToRespVO 确实回填了 tenantId，AdminUserMapper.selectListByStatus 仅按 status + 租户过滤，均不会导致返回空
6. 顺带核实 fire_duty_schedule 分布：大量记录 tenant_id=0（property_id=1001/1006/1009/1016 均如此），与物业实际 tenant_id 不一致

## Notes
- loadUserList 的 catch 是静默置空（userList.value = []），接口 401/500/参数错误在页面上表现完全一致且无任何提示，这是"下拉为空"类问题最难归因的一点，排查必须先看 Network 里 simple-list 的请求参数与响应 code
- tenantId 为 null/undefined 时 loadUserList 直接返回空数组，不发起请求
- 多语句 SQL 用分号拼接传给 mysql_query 会报语法错误，必须拆成单条执行
- 判断用户连的是哪个库要看前端 .env.local/.env.dev 的后端地址与后端 application-dev.yaml 的数据源，而非只看 MCP 名称

## Task overview
调研完成但结论待用户提供环境信息后闭环：给出三条候选解释——①实际选中的是零用户的"安为园区"；②测试库选中 tenant_id=1 的那条同名脏数据单位，取到的是系统租户人员而非预期的 166 人员；③simple-list 请求失败被前端静默吞掉。已附 Network 面板验证方法（看 tenantId 参数值与响应 code/data 长度），并请用户告知环境与登录账号所属租户以便继续定位。

## 后续会话补充（2026-10-21 已闭环，以本节为准）
- 上述三条候选归因**全部被证伪**：用户实测线上环境、选择的是 tenant_id=166 那条记录，响应为 `{"code":0,"data":[],"msg":""}`（既非接口失败也非零用户单位——线上库 166 下确有 4 个启用用户 145/178/180/185）。
- 真实根因：`getSimpleUserList` 先 `TenantUtils.execute(166)` 切换上下文再查询，而数据权限规则在此上下文内计算登录人自己的角色时，`system_user_role` / `system_role` 同为租户表也被追加 `tenant_id = 166`，超管（角色关联 tenant_id=1）查不到 → roles 空 → 降级 self=true → 追加 `WHERE id = 登录人id` → 恒为 0 行。
- 修复：给该入口加 `@DataPermission(enable = false)`（编译已通过，待发版验证）。同名物业跨环境租户归属不一致这一事实本身仍成立，只是本次现象与它无关。
