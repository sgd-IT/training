## Goal
回答「某张表/某个字段为什么原本没有、什么时候被谁加上的」这类字段级历史溯源问题，产出可核对的时间线（原设计依据 → 新增动因与提交 → 口径未写全的原因 → 存量数据缺陷来源）。适用于任何需要向他人解释字段由来或判断存量数据可信度的场景。

## Steps
Step 1: Grep - 在 SQL 目录内以字段名全局检索，rationale: 一次性把「原始建表脚本」和「后续 ALTER/ADD COLUMN 迁移脚本」同时暴露出来，跳过这步直接读代码会误判字段属于原设计；输入: 字段名 + _sql 目录, 输出: 命中文件清单（基线 DDL 与迁移脚本两类）
Step 2: Grep - 在基线 DDL 中定位该表的 CREATE TABLE 段并通读列定义，rationale: 只有确认基线里没有该列，才能断言"原本没有"而非"后来删了"；同时必须检查语义相近的旧列（如拓扑角色类、类型字符串类注释），因为原设计往往用另一套抽象表达同一业务概念，这是回答"为什么原本不需要"的关键证据；输入: 表名, 输出: 基线列清单与原分类机制
Step 3: Phase check - 确认已拿到"基线无此列 + 迁移脚本有此列"两个事实；若迁移脚本文件名带日期前缀，可直接据此推断新增时间窗，无需再翻全部提交历史；若基线里其实已有该列，则问题变成"取值口径为何不全"，应改走枚举注释与实际取值的对账路径
Step 4: Bash - 对该迁移脚本做 git log --follow 取提交哈希与日期，rationale: 迁移文件的提交记录是字段引入时间与引入需求（同批还加了哪些列）的唯一权威来源，比按代码搜索猜作者意图可靠；输入: 迁移脚本相对路径, 输出: 提交号 + 日期 + 提交主题
Step 5: Bash - 分别对前端录入组件与详情组件做 git log 取近期提交，rationale: 字段存在但写入入口缺失会造成存量值为 NULL，只看后端 DDL 会漏掉这一层成因，必须把"表结构层 / 后端写入层 / 前端录入层"三层各自的时间线对齐；输入: 组件文件路径, 输出: 各层补齐时间
Step 6: 汇总 - 按"原设计依据 → 新增动因与批次 → 注释/枚举未写全 → 前端录入缺口导致存量空值"四层给出结论，rationale: 用户问"原本没有"通常混合了这三四种含义，分层作答才能一次覆盖所有可能解读

## Notes
- PowerShell 下 git log 的中文提交信息会乱码，导致误读提交主题，必须重定向为 UTF-8 文件后再读取文件内容
- 只查基线 DDL 不查迁移目录，会把"后补列"当成原设计字段，进而错误解释存量空值原因
- 项目实例：空间详细位置 position 字段的"是否纳入辅助判断"数据口径即由本流程逐层取证确定
