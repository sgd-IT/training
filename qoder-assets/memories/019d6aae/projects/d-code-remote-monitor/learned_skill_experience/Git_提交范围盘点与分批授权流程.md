## Goal
当一次"git 提交"指令面对的工作区里混有**本会话未改动**的历史遗留文件时，安全地判定归属、拆分批次并取得用户授权，避免误提交或漏提交。适用于任何多会话累积改动、工作区不干净的仓库。

## Steps
Step 1: bash - 取全量待提交清单（porcelain 形式），rationale: 必须先拿到完整改动面才能识别"预期外文件"，只按记忆里的改动清单行动会漏判, input: 仓库路径, output: 已改/新增/未跟踪文件全集
Step 2: 比对 - 将清单与本会话实际改动的文件集合求差集，rationale: 差集即归属不明的历史遗留项，是后续全部判定的对象；不先隔离就无法判断该不该提交, input: 全集 + 本会话改动集, output: 归属存疑文件列表
Step 3: bash - 对存疑文件逐项看内容级差异（stat 摘要 + 有限行数的详细 diff），rationale: 只有读实际改动才能判定它属于哪个逻辑主题，凭文件名猜测会导致错误归批, input: 存疑文件列表, output: 每个文件的真实改动语义与所属主题
Step 4: Phase check - 确认每个存疑文件都能归到一个可一句话描述的主题；若某文件改动语义不明或与任何已知主题都不匹配，则该项不进任何批次而留在工作区，并在方案中单独点名告知用户；若发现同一文件同时混装两个主题，改为按主题拆分成两批而非合批
Step 5: 拟定分批方案 - 按"一个主题一笔"列出每笔的文件清单与拟用提交信息，历史遗留项单独成批并显式标注其来源非本会话，rationale: 混入本次改动会让用户误以为都是本轮产出，独立成批便于事后单独回滚, input: 全部改动及主题归类, output: 分批次清单
Step 6: 点选确认 - 就提交范围给出候选（全部批次 / 仅本会话批次 / 仅其中一批）由用户选择，rationale: 提交会把文件从工作区剥离，错收需 reset 回退且可能夹带计划外文件，一轮澄清成本远低于返工；当指令含模糊数量词（如"那几笔""第二批"）或引用无法定位的序号时，必须先检索历史归档与工作区待办文档确认出处，三处均无则停止猜测转为向用户点选澄清, input: 分批方案, output: 用户授权的提交范围
Step 7: bash - 清空暂存区后按授权范围逐批 add+commit，每批后立即核验落库，rationale: 暂存区残留会把上一批文件卷入下一笔提交，逐批核验防止静默失败, input: 授权后的批次计划, output: 各笔提交哈希

## Notes
- 只按本会话记忆中的文件清单直接提交 causes 历史遗留改动被漏掉或被误并入无关批次，必须先用 porcelain 全集求差集把归属不明项隔离出来
- 不对存疑文件读实际 diff 仅凭文件名推断主题 causes 归错批且提交信息描述与内容不符，必须看内容级差异再定主题
- 未向用户确认就把非本会话改动一并提交 causes 用户失去对提交范围的裁剪权，必须以点选方式取得授权后再执行
- 静默扩大用户已批准的提交清单范围 causes 越权提交，额外收录的文件必须在提交前显式披露理由
- 同一物理文件混装多个需求主题时不能整文件成批，须改用 git apply --cached 局部补丁按 hunk 拆分入账
- Step 6 点选授权的具体必问项（2026-10-28 补充，随"配置不提交"规则收紧而增加）：① 本次功能必需却被默认排除的配置文件（pom.xml、application-*.yaml、nginx.conf 等）是否破例提交；② 待提交文件里混装了非本会话的其他主题改动时，是拆成独立一笔还是继续留在工作区；③ 新增的凭据类文件（htpasswd、口令哈希、密钥）是否入库——不入库则构建脚本取不到、线上鉴权失效，但入库等于把哈希写进历史。三项都必须逐条列出由用户拍板，不得以"按推荐来"代替。
