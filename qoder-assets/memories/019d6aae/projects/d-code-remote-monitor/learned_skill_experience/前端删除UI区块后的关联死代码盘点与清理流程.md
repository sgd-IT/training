## Goal
在前端单文件组件中删除一整块 UI（面板/按钮）后，安全地把仅被该块引用的处理函数、图标 import 与样式规则一并清理，且不引入新的未引用告警；适用于任何"删组件/删区块后做死代码收敛"的场景。

## Steps
Step 1: grep - 对候选标识符逐个单独检索并统计命中行，rationale: 判断"是否仅此一处引用"必须靠引用计数，而把十余个候选词合成一条长 alternation 正则会触发结果条数上限截断（显示已匹配 N 条但实际更多），导致把仍有引用的符号误判为无引用而错删；输入: 待删块内出现的函数名/组件名/图标名清单, output: 每个标识符的引用位置集合
Step 2: 阶段检查 - 确认每个标识符都已取得完整引用清单：仍被其他入口（如键盘快捷键、对话框 v-model、其他面板）复用的必须列入保留名单跳过删除；若发现某符号只在定义处命中而无消费点，才可进入删除批次
Step 3: read_file - 读取待改区域的当前原文再写入，rationale: 同文件此前检索到的行号在批量修改后整体偏移，沿用旧行号定位会替换错位置或匹配失败；输入: 目标区域, output: 可作为精确替换锚点的原文
Step 4: edit/search_replace - 按模板块 → 仅其引用的函数 → import → 样式块的顺序删除，rationale: 先删消费方再删定义方，才能在每一步都用检索验证剩余引用归零；删除变量/常量定义前必须先完成 Step 1-2 的零引用确认，否则编译报错且不指向具体删除动作；输入: Step 2 的删除名单, output: 无悬空引用的文件
Step 5: 批量替换结果逐项核对 - 一次调用提交多组替换时结果可能是"多数成功、少数失败"而非整体回滚，必须逐项比对返回的成功数与总数；失败项要重新读取该处当前实际文本再构造匹配内容（同批其他替换已改变上下文，凭改动前记忆的片段构造原文极易不匹配），不得假定全部生效继续往下走, input: 替换返回体, output: 每组替换的真实生效状态
Step 6: 连带清理二阶死引用 - 复查因上一步删除而新失去消费者的声明（如仅被已删函数使用的路由实例与其构造器 import），rationale: 一阶清理只覆盖被删块直接引用的符号，间接层不删会留下新增的未使用告警；输入: 本轮删除的函数体, output: 引用图收敛到基线
Step 7: 诊断校验 - 用问题列表/类型检查对照改动前的既有告警清单，rationale: 只有与既有告警逐条比对才能证明"未引入新问题"，语言服务首次常返回未就绪需重试一次；输入: 目标文件, output: 告警集合等于或小于基线

## Notes
- 用长 alternation 正则一次性检索多个标识符会因结果条数上限被截断，造成"以为无引用"而错删仍在使用的函数；必须拆成单标识符逐个检索计数
- 项目 lint 关闭未使用变量规则时，残留死代码不会报错也不会被工具抓到，必须靠人工引用计数判定去留，不能以"没报错"当作清理干净
- 删除几十行模板使同文件后续行号整体偏移，沿用先前检索的行号会定位错位；每次批量改动后须重新读取原文再写
- 批量替换返回部分成功时按成功计数逐项复核后再进入验证环节，遗留的未生效旧值会在后续编译或运行期才暴露
- 删除上百行代码块时把整段作为 original_text，任一字符不符即整体失败，应拆成"改调用点→删方法体→清 import"有序小批次
- 诊断校验出现新增未引用告警时，须先用全局搜索确认该标识符是否本就散落在本次改动之外的其他文件被引用，据此区分真死代码与误报，不可直接顺带删除
