## Goal
在前后端分离项目中完整闭环一个新功能（以远程反控码为样本），确保移动端查看、PC 端校验与下发、PC 端管理员查看三处均正确落点并同步生效；适用于所有需要跨端协同实现的功能开发。

## Steps
Step 1: Read - 确认各端现有结构与样式规范，rationale: 跨端功能必须遵循各端既有的 UI/UX 约定，避免风格割裂，input: 各端入口文件路径，output: 各端结构与样式事实
Step 2: SearchReplace - 修改已有文件（pages.json、VO、API 封装、Controller），rationale: 已有文件是功能接入的主干路径，必须精准修改以复用现成能力，input: 文件路径与待替换内容，output: 文件内容更新
Step 3: Write - 新建独立页面或组件，rationale: 新功能若无现成模板，需新建页面以保证职责单一与可维护性，input: 新建文件路径与内容，output: 新建文件创建成功
Step 4: Bash - 执行编译与静态校验，rationale: 多端同步落地后必须验证语法与类型正确性，避免因单端错误导致整体失效，input: 校验命令，output: 校验通过结果
Step 5: Phase check - 确认所有端均已落点且逻辑一致；某端缺失关键入口必须补全；某端校验失败必须回溯至 Step 1 重新确认结构
Step 6: Build-and-publish check - 逐端确认「源码已提交」不等于「线上已生效」，必须核对各端生产构建产物是否已重新生成并发包，rationale: 跨端功能最常见的假性缺失是各端产物目录仍是旧版本构建，源码在库但用户看不到；input: 各端构建产物目录（如 uni-app 的 unpackage/dist/build/mp-weixin、vite 的 dist-prod），output: 产物 mtime 晚于功能 commit 且含新功能标识

## Notes
- 直接修改 pages.json 而未禁用注释会导致 JSON 解析失败；必须严格遵守 pages.json 禁用注释的约束
- 移动端低频查看类操作归口「我的」页菜单，高频工作台快捷入口进首页宫格，两处必须同步更新否则可见性不一致；首页宫格新增入口时按产品口径决定是新增还是替换既有项，不可自行删除既有入口
- PC 端危险操作入口至少两处（现场页头 + 管理后台详情弹窗）共用同一二次验证逻辑，且指令下发必须两步确认：输入反控码确认后仍需 ElMessageBox.confirm 警告框 resolved 才真正 emit confirm，两次按钮文案须刻意区分
- 服务端缓存型凭证若在 TTL 内重复请求只返回旧值且不重置有效期，前端"刷新"按钮必须走 Service 侧 force 入参覆盖写回，仅重新请求必然看不到变化
- uni-app 运行时「运行」只会更新 dist/dev 目录，微信开发者工具 CLI open + 上传用的是 dist/build 目录；未走过 HBuilderX「发行」（cli.exe publish --platform mp-weixin）则 build 目录内容会停留在旧版本，真机看不到新 UI——排查此类"UI 都没有"必须先比对 build 产物 mtime 与功能 commit 时间，而不是先怀疑后端。
- PC 端 vite 生产构建输出目录由 .env.prod 的 VITE_OUT_DIR 指定（本项目为 dist-prod）；若 pnpm build:prod 被依赖脚本策略拦截（ERR_PNPM_IGNORED_BUILDS），可直接调 node ./node_modules/vite/bin/vite.js build --mode prod 绕过。
- 核验构建产物是否含某中文功能词时，terser 默认会把中文转义为 \uXXXX（且十六进制字母大写，如「反控码」→ \u53CD\u63A7\u7801），直接用 Grep 搜原文中文会得 0 命中造成误判；应改搜 ASCII 标识符（control-code/controlCode）或匹配 \uXXXX 转义序列。
