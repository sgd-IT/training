Bug class: 时间窗节流判断的减法方向写反（elapsed 计算写成 lastTime - now），叠加接线顺序/包裹层级错误导致状态写库全线冻结。

Root cause: 节流方法应为 `now - lastTime >= window` 才表示"距上次放行已过窗口"；写成 `lastTime - now` 结果恒为负数，永远小于正窗口阈值，于是首次调用后从第二次起恒定返回 false，且 put 永不执行、Map 停在最初值。缺陷若位于零调用点的死代码里会长期无现象——直到接上的那一刻全面显形：编译通过、日志正常、监控 SQL 次数反而下降（看似优化生效），属最难发现的一类回归。

**已实测复现的第二种变体（比减法反向更隐蔽）**：把节流判断接进主流程时，在外层再包一层"状态没变才进入"的 if（判据从别处"提前 return"的反向条件复制而来），内层却写"状态变了 || 到点才放行"——外层保证状态没变，内层第一个条件恒为 false，整块成死分支，设备真实上下线一次都写不进库。同时还有第一种变体：只节流了下游带前置类型判断（如仅网关设备生效）的级联方法，而目标 UPDATE 的发源调用点在节流块之外，净收益为零还引入延迟。

Fix pattern: ①对任何"两个时间点求间隔再比阈值"的判断，落地前做三值心算（首次无记录 / 窗口内 / 窗口外 → true/false/true），减法一律"较晚时刻 - 较早时刻"；②"先修逻辑 → 再接调用点"固化为顺序约束，死代码不因无调用点豁免；③接线时必须核对包裹层级：用场景推演表（每种消息类型 × 每层条件结果 × 是否写库）验证外层门卫与内层放行不互斥，且被节流的调用点下游确实产生目标 SQL；④"状态真变化"必须短路绕过节流无条件放行。

Reusable lesson: Don't 因为某段问题代码当前没有调用方就把它降级为"以后再说"并先把新调用接上去，because 接线瞬间触发全量冻结且伴随指标变好的假象，排查成本远高于现在改一个减号；instead 先用符号搜索确认调用点分布，把未接线代码的逻辑错误在接线前修完，再接入，接入后再用监控里的执行速率（次数÷窗口分钟数）作为唯一硬验收。适用于所有基于内存 Map/时间戳做频率限制或去重窗口的节流实现。不适用于纯展示型无副作用的死代码（删除即可）。
