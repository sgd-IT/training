Bug class: 前端"新老数据双读"展示层改造中的静默错误——编译通过甚至零报错，但页面运行时白屏/列空白/崩溃。

Root cause: 三类高发写法在 Vue+TS 列表页双读加工函数（decorateRow 模式：按新语义字段是否为 null 判新旧行，分别查不同映射表产出 typeText/levelText 等显示字段）中被实测踩中：
① TS 泛型参数写成大写 `Record<String, String>`——`String` 是 JS 构造函数对象不是类型，报 TS2344（这是唯一能被编译器抓到的）；
② 判空条件多敲属性链如 `row.alarmKind.id !== undefined`——旧数据该字段为 null 时运行时执行 `null.id` 抛异常导致整个列表页挂掉，且编译完全不报错；
③ 旧数据回退分支取错字段（如 `OLD_MAP[String(row.alarmKind)]`，正确应为 `String(row.level)`）——旧行的新语义字段本就是 null，取值后查表永远 miss，列静默全空白，无任何报错。另外列定义 key 与加工产出的字段名不对齐（key 留空串或漏整列）同样静默。

Fix pattern: ①类型区一律小写 string/number/boolean；②判空用 `row.x != null`（双等号一并覆盖 null 与 undefined，也杜绝手滑加属性链的动机）；③双读写完核对"三个对齐"：判据字段=新语义字段、新分支取值=新语义字段、旧分支取值=旧编码字段；④每个展示列的 key 逐一对照加工函数 return 的字段名。

Reusable lesson: Don't trust "vue-tsc passed" as proof that a dual-read transform works, because the most damaging failures (null property access, wrong fallback field, unbound column key) are runtime-only silent errors; instead after compile check must run the page against real old-format and new-format rows and inspect each column. Applies to any front-end list page doing legacy/new semantic coexistence mapping in this repo's eiot alarm views; does not apply to pages consuming backend-translated fields directly (纯透传形态无加工函数即无此类风险)。
