Bug class: 列上套函数使 LIMIT 型查询"计划看起来正常但实际扫全索引并逐行回表"，慢因被 EXPLAIN 表象掩盖。

Root cause: 两个机制叠加。①对 indexed 列写 DATE(FROM_UNIXTIME(col/1000)) = CURDATE() 这类表达式，优化器无法推出该列的键区间，只能从索引一端逐条读并对每行计算函数；此时 EXPLAIN 仍显示 key 有值、无 Using temporary、无 Using filesort，而 rows 只是 LIMIT 的估算值，不代表实际读取行数——当天匹配行为 0 时提前终止彻底失效，必须读完整个索引才能回答"空"，于是"有数据时快、没数据时最慢"。②过滤列不在该索引内（如 handle_status 不在 idx_alert_cover 中）又被 CASE / IN 等表达式包住无法下推，每扫一条索引都要回表取一次宽行，随机读才是耗时主体。本项目落点：AlertRecordMapper.TODAY_CONDITION_SQL 与 selectTodayUnclosedAlerts（eiot_alert_record）。

Fix pattern: 把时间条件改成对该列本身的左闭右开区间比较（数值毫秒列写作 col >= UNIX_TIMESTAMP(CURDATE())*1000 AND col < UNIX_TIMESTAMP(CURDATE()+INTERVAL 1 DAY)*1000，基准仍取数据库函数以免应用侧时区差一天），并把表达式过滤改成对原始列的等值集合（CASE 派生的字符串集合反推回 handle_status IS NULL OR handle_status NOT IN (3,4)，注意不可照抄另一处的 < 3 口径，出现新状态时两者会分叉）。验收看 type 是否由 index/ALL 变 range、key_len 是否只覆盖到区间列、rows 是否降到个位数，以及 Extra 是否出现 Using index condition。

Reusable lesson: Don't 因为 EXPLAIN 里 key 非空、没有 filesort、rows 等于页大小就断定这条 SQL 没问题，because rows 在带 LIMIT 时只是估算值、函数包裹的列会让索引退化为全索引顺序扫描且逐行回表；instead 先确认 WHERE 里每个被过滤的列都是"裸列比较"、且该列存在于所用索引中，再用有无数据的两种日期分别测一次。适用于本仓库 eiot_alert_record 等以 bigint 毫秒时间戳存时间、并靠 ORDER BY + LIMIT 取一页的查询；不适用于本来就按日分组聚合的统计（那里函数是必需的，问题只在驱动 WHERE 条件）。
