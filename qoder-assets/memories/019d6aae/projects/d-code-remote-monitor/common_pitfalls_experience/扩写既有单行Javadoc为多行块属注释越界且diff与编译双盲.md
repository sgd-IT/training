Bug class: "只动注释"类任务里的隐性越界——把使用者既有的单行 Javadoc 扩写成多行分段推演块，改动面自证与编译双双失效。

Root cause: FireDashboardServiceImpl 常量区与方法原本是 `/** 一句话 */` 单行形态（用户个人风格资产），agent 为"写清 why"将其改写为带 `<p>` 分段的 4-8 行块，并自行加写类注释段落。此类改动的 diff 每一行都以 `*` 或 `//` 开头，因此"逐行扫差异确认全是注释行"的自证流程判定为通过；注释不影响语法，mvn compile 必然 BUILD SUCCESS、class 时间戳正常刷新。两条验证通道对该越界同时零信号，唯一暴露方式是使用者阅读后问责"不符合我的风格"。反向同类问题是在同一轮里把行内注释写成二三十字解释句，同样超出其 15 字步骤短句口径。

Fix pattern: 改写前先把目标位置的**原有注释形态**作为约束读取并记录（单行/多行、行数、是否带标签）；只允许在原行数附近动字，需补充信息时改为新增一条行内短句而不是把单行升级成多行块；确有 must-preserve 的长结论时先征询而非直接扩写。回退判据是"与该文件既有单行样本同构"，不是"内容更完整"。同一约束已写入 code-comment-style 的 SKILL.md「用户风格硬约束」一节。

Reusable lesson: Don't 因为"要把设计依据写清楚"就把使用者已有的单行 Javadoc 扩写成多行 `<p>` 分段块，because 这种越界在 diff 层面看起来完全合规、编译也不会报错，只有使用者读后才会被问责，来回成本比初稿多写几行更高；instead 保持原行数形态只在行内动字，需要更多说明时另起一条短行内注释或先征求同意。适用于任何"只准改注释/改文案"的整理任务与有既定个人注释风格的仓库；不适用于使用者明确要求"详细说明/写清背景"的位置，也不适用于从零新建的文件（无既有形态可守）。
