Bug class: 概览卡片的聚合数字与点击进入后的列表条数不一致（静默、不报错）

Root cause: 卡片上的某个指标是多个状态值之和（例如大屏「今日警情」的 handledCount 由 AlertOrderStatusResolver.sumHandled = handled + closed 相加得出），而跳转到列表页时把该指标当成单一状态传给筛选参数（orderStatus=handled）。筛选分支只匹配其中一个值，落在另一半（closed）的记录被静默排除，于是出现"卡片显示 N 条、点进去 N-1 条甚至 0 条"。同类根因还包括时间范围不同源：卡片按当日统计而列表默认全量历史，实测点进去 262 条 vs 卡片 0 条。

Fix pattern: 跳转/筛选参数用与统计侧同源的"分组值"而非单值——后端在状态筛选 switch 里为每个聚合指标补一个 case，映射到与统计完全相同的 CASE IN (...) 集合（本项目已落 unclosed = pending+deferred+handling、finished = handled+closed），并让前端 URL 白名单常量与可见筛选下拉同步登记该分组值；时间范围同理，收敛为后端单一判据常量（todayOnly + TODAY_CONDITION_SQL）供统计侧与列表侧共用，不由前端拼日期字符串。

Reusable lesson: 不要按"指标名看起来像单个状态"就直接把它当单值传（handledCount 听起来像 handled，实际是两值之和），因为筛选集合窄于统计集合会造成用户可直接看见的数字对不上且无任何报错；必须先读统计侧实现（sumXxx / countXxx 的 CASE 或 IN 集合），再据此决定跳转参数的取值粒度，并逐出口比对判据与时间范围是否同源。适用于同一张表派生多个数字出口的链路（计数、列表、跳转目标页、顶部徽标）；不适用于指标本身就对应唯一状态值的场景，也不适用于按 id 打开详情的跳转。另需注意：未知筛选值在后端 default 分支通常只打 warn 而不抛错，会静默退化为不加筛选（列表变全量），因此新增分组分支后必须重启后端验证，不能只看编译通过。
