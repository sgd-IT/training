Bug class: 分页接口 N+1 额外查询次数测算口径失真（数字对不上或漏算）

Root cause: 三个已核实的漏算点——(1) 只统计被调用函数内部的查询（如 fillDeviceType 的 3 次），漏掉直接写在 for 循环体内的第 4 次逐条查询（tenantApi.getTenantName → TenantServiceImpl#getTenant → tenantMapper.selectById，无缓存，每次真实查库），导致算成 60 而非 80；(2) 用框架 PageParam 的默认 PAGE_SIZE（本项目为 10）当每页条数，而实际条数由各端显式传参决定（PC 报警记录页 pageSize: 20、移动端告警中心 pageSize: 10），同一份后端代码在不同端的倍数不同；(3) 把上限值当成精确值——被测函数内有提前 return 分支（deviceId 为空 / 关联记录查不到 / 业务键为空）时该条不满整链路。

Fix pattern: 按"循环体全文"而非"函数内部"逐行清点数据库会话往返（含同文件内联调用与跨模块 Api 落到 mapper 的真查库）；每页条数从对应端的请求参数实测取值而不是引用框架默认常量；结论区分上限/典型值并给出触发降级分支的数据条件。

Reusable lesson: Don't 只读被调函数就下"N 次/条"的结论，because 循环体内联的查询和跨模块 Api 内部的 selectById 同样是一次往返，漏算会让优化收益被低估、对外表述的数字被质疑；instead 把 for 循环体整段展开计数，并用 git show <commit>^:<file> 取改造前原文核对。适用：核算分页/列表接口"每页少 X 次查询"这类量化指标、复盘历史性能提交；不适用：单次详情接口（无循环）、以及走缓存或纯内存转换的字段填充。
