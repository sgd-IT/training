Bug class: 用"接口调用次数占比"给线上压力定责，导致把最该做的优化排到后面、把无效动作列为 P0；更前置的错是把调用量异常直接当成流量异常，漏了"谁在发"这一步。

Root cause: 访问日志按 request_url 聚合出的调用量只反映请求条数，不反映单请求资源开销，也不反映发起方。本项目实测：`/eiot/remote-console/valve/command/{deviceId}` 7 天 74,961 次（约 8.6 秒一次，占全站请求条数约 40%），全部来自单一出口 IP 219.131.130.21 且 User-Agent 末尾带 `Hutool`（Java HTTP 客户端的伪装 UA），是外部智能空开控制服务的机器对机器拉取，@PermitAll、单次 duration≈0.01 秒、几乎不占连接池；而 `/eiot/firewatch/dashboard/statistics` 只有 26,999 次，却每次串行执行十几条聚合查询、成功请求平均约 3 秒，才是真正吃 CPU 与连接池的一方。两者相差近 3 倍调用量，压力贡献却是反过来的。

Fix pattern: 排序前必须把调用量与耗时两列同时列出（`SELECT request_url, COUNT(*) c, ROUND(AVG(duration)/1000) avg_s, MAX(duration) FROM infra_api_access_log GROUP BY request_url ORDER BY c DESC`），以"调用量 × 平均耗时"作为压力权重；并叠加鉴权成本判断（@PermitAll / 在 platform.tenant.ignore-urls 中的接口通常开销极小）。改造优先级按权重排，不按条数排。

补充分层（2026-10-28 同一项目线上归因）：先做"流量分类"再谈异常——按 request_url + user_agent + user_ip 聚合，把流量拆成人工操作 / 页面轮询 / 机器对机器三类，判据是 UA + 来源 IP + 小时分布规整度（机器 8 秒一次 24 小时无波动，人有作息起伏）；再用"按分钟聚合"数出同时在跑的轮询表数，"每分钟精确 N 次"就是 N 张表在跑（本项目 recentUnprocessedAlerts 深夜每分钟精确 7 次 = 7 个页面实例各挂一条 60 秒表）。本次 7 天 18.4 万次调用中，机器轮询占 39%、页面轮询约 4 万次、真实人工操作不足 8%。

Reusable lesson: Don't 因为某接口调用次数最多就把它列为"投入产出比最高的优化项"并向用户推荐优先处理，because 高频轻量接口（免登录状态轮询、心跳、拉命令类）砍掉后服务器负载几乎不变，反而延误真正的高耗时聚合接口；instead 先做流量分类（谁在发）→ 数轮询组数（每分钟精确 N 次）→ 再算调用量×耗时权重排序。适用于所有依赖自建接口访问日志做容量评估与优化排序的场景。不适用边界：当高频接口本身也伴随慢查询或锁竞争（即耗时不为 0）时，条数与耗时同向，此时按条数排即可；也不适用于带宽型瓶颈（如视频流并发拉流），那类压力既不在条数也不在 CPU，须单独按出口带宽核算；"使用统计"页面若直接按 request_url 聚合展示"功能使用次数"，会把机器流量与页面轮询一起计入，不能直接当业务热度读。
