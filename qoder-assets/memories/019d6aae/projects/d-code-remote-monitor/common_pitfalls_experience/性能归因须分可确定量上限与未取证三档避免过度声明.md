Bug class: 性能归因过度声明 —— 把某个总量指标（如某张表的 SQL 执行总次数）笼统归因于单一嫌疑链路，用"很大一部分"这类无量化措辞向用户交付结论。

Root cause: 数据源本身是多来源混合计数。Druid SQL 监控里 `eiot_device_info` 的 1,284 次 SELECT 来自规则引擎每条消息的读路径、写后回查、缓存穿透等多条独立链路；只有"每次写成功后紧跟一次全字段回查"这一笔可以按 192 次写 → 192 次回查精确对齐（约 15%），缓存穿透那笔只能给出上限且取决于消息间隔。剩余 1,092 次在本链路无任何证据。嫌疑链路的代价拆解做得越细，越容易误以为它解释了全部总量。

Fix pattern: 对每个归因项标注"证据类型 + 可确定量"三态之一：①可确定量（能由已知次数一一推出，如写次数 = 回查次数，给百分比）；②上限估计（依赖时序/命中率的穿透类，明说"最多 N 次、实际不确定"）；③未取证（其余差额，显式写"来源未取证，不归入本链路"）。交付前检查结论里是否残留"大部分 / 很大比例 / 主要是"等无法回溯到数字的词。

Reusable lesson: Don't 因为某条链路被证实有写放大就把该表的全部查询量记在它头上并据此排优化优先级，because 真实占比可能只有一成多，据此定的 P0 会打在次要矛盾上，且一旦用户复核就会像本次一样被迫公开更正、损伤结论可信度；instead 先做单链路的代价拆解，再逐项标注可确定量 / 上限 / 未取证三态，余量明确留白。适用于依据 Druid / APM 聚合统计页做 SQL 压力归因与优化排序的场景。不适用于总量本身就来自单一入口（如某个定时任务独占一张表的全部读写）的情况，此时直接归因即可。
