Bug class: 代码重命名/合并后，注释里对他人的类名引用未同步，留下指向不存在符号的"权威表述"。

Root cause: anwei-fire-remote-monitor 日志清理改造中，原计划按访问日志、错误日志各建一个保留任务（AccessLogRetentionTask / ErrorLogRetentionTask），后来合并成单个 LogRetentionTask，但 AccessLogCleanJob.java:47 的注释仍写"保留天数，和 AccessLogRetentionTask 保持一致"，而同批修改的 ErrorLogCleanJob.java:47 写的是正确的 LogRetentionTask —— 即改名只在两个对称位置里落实了一个。这类注释不参与编译，mvn compile 与 IDE 诊断（GetProblems）都返回通过，对错误完全无信号；危害是后续读者按该名字全仓检索找不到类，会怀疑自己理解错或另建一个同名类，且注释的权威语气掩盖了"两处口径本应一致"这一真实约束。

Fix pattern: 凡在注释/Javadoc 里点名了某个类或方法（"和 X 保持一致""参见 X""由 X 触发"），改动落地的同一轮就用 `git grep -n <X名>`（含 --untracked）核对该符号是否仍存在，0 命中即说明注释失实，按当前实际类名在原行内改字，不扩写。批量提交前把本轮新增的所有"跨文件点名"注释集中列一遍逐一核验。

Reusable lesson: Don't 依赖编译通过和语言服务无报错来判定注释里的跨文件引用仍然成立，because 注释符号不参与符号解析，指向已消失的类名照样 BUILD SUCCESS，误导只发生在人读阶段；instead 每次重命名或合并类后立刻用 git grep 反查注释中出现的旧名。适用于任何修改了条件、阈值、类名或方法名的 Java/Vue 文件（本项目 firewatch、infra job 等模块尤其密集，历史上同类问题已出现于 DeviceStateCheckHandler 的失实"始终更新 DB"注释）；不适用于纯描述行为、不含具体符号名的注释，那类只需按新行为改写措辞。
