Bug class: 把用户粘贴的监控统计数字默认归属到某一套环境，据此输出面向生产的结论与行动建议，被用户纠正后整段定性需返工。

Root cause: 同一项目的测试库与生产库往往存在结构相同但数据量、版本、索引状态都不同的两套实例，而 Druid / APM 的 SQL 统计页本身不带环境标识，只有贴出来的上下文才知道来源。凭"我正在处理线上问题"的惯性推断来源，就会把测试环境的耗时当成生产证据；同时该类统计是累积型——ExecuteCount 只增不减、MaxTimespan 取历史最大值，索引或改写生效后历史值不会自动下降，因此它既不能证明当前仍慢，也不能用来判断修复是否生效。

Fix pattern: 拿到外部统计数字先明确归属环境再展开结论，并把证据按来源分类列出（应用侧统计 vs 直连实测 vs 变更后复测）。判读时记住累积特性：要验证修复效果必须先重置该条统计（或重启应用使计数清零），再触发一次真实请求看新的 MaxTimespan 与 ExecuteCount；判定修复是否生效一律以执行计划（type/key/rows/Extra）为准，毫秒数只作量级佐证。需要确认"改动是否落在应用真正使用的库上"时，用 information_schema.PROCESSLIST 按 client_host 聚合连接数核对，而不是假定库名一致即同一副本。

Reusable lesson: Don't 未确认环境归属就把监控统计当生产现状交付结论并据此排生产动作优先级，because 结论对象错领会让用户以为线上已修好或线上仍有故障，且历史最大值会让人误判"加了索引没用"；instead 先问清/查清统计来源环境，再按"历史累积值 ≠ 当前状态"处理，验收改走执行计划与重置后的新数字。适用于本仓库消防远程值守这套测试（LAN 5.7）与生产（CDB 5.6）双库并存、后端接 Druid 监控的场景；不适用于只有一套环境或统计自带环境标签的情况。
