Bug class: 代码改动后未同步的注释仍保持权威语气，误导后续读者并掩盖新引入的设计取舍。

Root cause: DeviceStateCheckHandler.handle() 中"对于显式 state 类型消息…始终更新 DB，避免缓存与 DB 不一致导致状态丢失"这段注释写于加节流之前；随后在同一方法引入按设备的时间窗节流（状态没变则等窗口），state 消息也会被拦，"始终"不再成立。原句被删掉一半还会留下残缺表述（如只剩"// 当"两字）。危害有两层：一是读者据此认为该分支无条件写库，看不出这里实际存在"最长一个窗口的状态不一致"这一真实代价；二是残缺注释比无注释更费解。编译与 IDE 诊断（GetProblems 返回 No errors）对这类问题完全无信号。

Fix pattern: 每次修改条件、阈值或短路分支时，同轮检查该方法内描述该分支行为的注释是否仍成立，把绝对化措辞（"始终""一定""所有情况""永久"）改写为分情况说明；同时清理只说了一半的残句。已完成的 TODO 施工说明压缩为纯坑位预警（并发容器选型、装箱 NPE、容量上限这类不可省略的判断），删掉现场话术。

Reusable lesson: Don't 只改代码不改描述该代码行为的注释，because 越权威的旧注释越会让接手人照它做设计判断并看不到新引入的取舍；instead 改动落地的同一轮就把相关注释一起核对到当前行为。适用于任何修改了既有分支条件／时间窗／短路逻辑的 Java 方法；不适用于用户手敲训练产出的代码——那里的注释是学习痕迹，须先征得同意再改写。
