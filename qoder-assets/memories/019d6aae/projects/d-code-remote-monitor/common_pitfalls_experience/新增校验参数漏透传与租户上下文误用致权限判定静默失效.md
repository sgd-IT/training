Bug class（两类同源失败）：A. 新增横切校验参数在部分调用路径上未透传，形成静默失效的"半接线"状态；B. 跨层透传的过滤/覆盖租户参数成为"死参数"，且在切换后的租户上下文里做登录人身份判定得到错误口径。

Root cause A：UdpComponent 中为源IP增加 senderAddr 校验（isAutoRegisterAllowed / allowedCidrs）时只接了主上报入口，而 reportRawData() 内部改调 processData 时没有把作用域内的 senderAddr 继续传下去，恒以 null 进入白名单判定；协议注册帧（CMD=0x00）恰好走这条被漏掉的路径，于是 autoRegisterCidrs 一旦配置非空，白名单校验反而把所有新设备挡在门外——安全目标反向变成可用性故障。此类缺陷编译与单测均不暴露，只在特定配置值下才触发。

Root cause B（四种已核实机制）：① 目标租户 id 一路加到 Controller→Service→私有 build 方法，但中间用只认"登录租户"的旧包装器 executeWithTenantAware(Supplier) 执行，且 build 方法体从未引用该参数——SQL 过滤条件仍来自 ThreadLocal，参数被完全丢弃；非超管场景"忽略参数"恰是期望行为，只有超管切换视角时暴露粒度不一致。② TenantUtils.execute(tenantId, () -> {}) 传空 lambda：该方法只是"保存旧上下文→设新→回调→finally还原"，真正查询写在块外时上下文早已还原。③ 在 execute 块内调用 TenantContextHolder.getTenantId() 取到的是被切换后的目标租户而非登录用户租户，据此判身份会把企业账号误判成管理员或反之；该值还来自 HTTP tenant-id header（TenantSecurityWebFilter 写入），可被篡改。④（2026-10-21实测确证）在 TenantUtils.execute(目标租户) 回调内触发数据权限规则计算：规则要查登录人自己的 system_user_role/system_role（同为租户表），这些SQL同样被追加 tenant_id=目标租户 → 超管在自己租户1下的角色关联查不到 → roles为空 → 降级 self=true → WHERE id=登录人id 叠加 tenant_id=目标租户 必然0行，接口返回 code:0 + data:[]（恒定空集而非报错）。凡"切换租户上下文+未关闭数据权限"组合均适用此判据。

Fix pattern：给方法新增参与权限/白名单/限流判定的参数后，用 Grep 枚举该方法全部调用点逐一确认已透传（而非只看主入口），并对"参数为空即拒绝"分支补一次带该配置开启态的端到端验证。未被使用的参数一律从签名删除，宁可少一层透传也不留装饰品。把"角色白名单判定+上下文选择"收敛成一个共用包装（形如 executeWithTenantAware(supplier, overrideTenantId)，内部先判 override 非空且有超管角色才用 override，否则回退登录租户），所有入口各一行调用，规则只存在一处。登录人真实租户统一用 UserTenantResolver.resolveLoginUserTenantId()（从 system_users.tenant_id 解析，与 header 无关）在进入 TenantUtils.execute 之前取好并作为变量传入，禁止 TenantContextHolder.getTenantId()；角色白名单用 SecurityFrameworkService.hasRole(code)。对"按指定租户取下拉候选项"类接口，正确做法是在入口方法加 @DataPermission(enable = false) 彻底不参与权限计算（注解由 DataPermissionAnnotationAdvisor 在任意 bean 方法上生效，import com.enjoyiot.framework.datapermission.core.annotation.DataPermission），而不是试图"先算权限再切上下文"。历史同类坑：DeviceInfoServiceImpl / FirePropertyServiceImpl 曾以 getTenantId()==1L 作超管判据，配合 mapper 的 eqIfPresent(tenantId) 形成双层过滤导致可见范围不符预期。

Reusable lesson：Don't 只给主调用链接线新参数就认为功能完成，也不要假定"切了租户上下文最坏是数据不全"，因为旁路会以 null/默认值进入校验使整条特性静默失效，且切换上下文会反噬登录人自身角色查询使结果直接变空集；instead 每加一个过滤类参数就从入口追到底自问"值进来了吗、在哪生效、没生效是漏了还是设计"，并额外检查"在这个上下文里框架还要不要查登录人自己的租户表"，改完跑全量编译并用超管/普通两种身份各验一遍数据粒度。适用于本仓库多租户 TenantUtils/TenantContextHolder 体系下的任何"指定租户查看""按维度覆盖过滤""跨租户下拉取数"改造及访问控制类参数重构；不适用于纯展示层或参数在方法体内被真实用于SQL条件的常规查询。
