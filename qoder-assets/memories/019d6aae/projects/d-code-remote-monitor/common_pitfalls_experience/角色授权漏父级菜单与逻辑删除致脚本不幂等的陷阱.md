Bug class: RBAC 角色授权改库后"权限看起来没生效 / 页面进不去"，以及授权迁移脚本重复执行产生脏关联行。

Root cause: 两个已实测的机制。(1) system_menu 是 type=1 目录 → type=2 页面（有 path/component）→ type=3 按钮 三层结构，前端菜单树按父链构建：只勾按钮不给其 type=2 页面与 type=1 目录，入口根本不出现；且按钮所在页面若是隐藏路由菜单（如 deviceDetail/:id 这类 visible=0 的 type=2 行），不授权该菜单点列表进详情直接 404；设备控制类按钮还依赖同页面的查询权限点，否则列表为空选不到目标。(2) system_role_menu 收回权限走的是逻辑删除（deleted=b'1'），而幂等 INSERT 里的 NOT EXISTS 若写成 rm.deleted = 0，就检测不到这些已存在的删除行，再执行一次会插入同一 (role_id, menu_id) 的第二行，造成后续按 deleted=0 统计与实际判定不一致。

Fix pattern: 授权集合必须"父目录 + 页面 + 隐藏路由 + 依赖查询权限 + 目标按钮"整链一起给；迁移脚本按"先 UPDATE 恢复 deleted=b'1' 的目标行，再对完全无行的菜单 INSERT"两段式编写，NOT EXISTS 去掉 deleted 过滤条件改为覆盖任意状态行；落库后用 COUNT(*) 与 COUNT(DISTINCT menu_id) 双查确认无重复。

Reusable lesson: Don't 只按 permission 字符串清单授权或只写一段 INSERT ... NOT EXISTS 就认为脚本安全幂等，因为缺父级与隐藏路由会让功能静默不可用、逻辑删除行会让重复执行产生脏数据；instead 每次授权前先列出按钮对应的 parent 链并检查是否存在 visible=0 的路由菜单，收回统一走逻辑删除且脚本含恢复段。适用于本项目 system_role_menu 直改库授权与迁移 SQL 编写；不适用于后台"角色-菜单勾选"界面操作（它整体重建关联表，不受此约束）。
