Bug class: 自写结构对账脚本产出"全量误报/漏报"，结论看似精确实则失真

Root cause: 两类机制在本轮各造成一次假结论。① 用 mysql -N -B 导出结果后按 '\n' 切行，Windows 下行尾为 \r\n，导致**每行最后一个字段**残留 '\r'；当 SELECT 只取两列（TABLE_NAME, COLUMN_NAME）时 COLUMN_NAME 正是末列，于是所有列名比对全部不匹配，误报"每张表缺所有列（含 id）"。② 解析 Java DO 时用"字段声明前固定 N 字符窗口"判断该字段是否带 @TableField(exist = false)，连续字段场景下上一字段的注解落进下一字段的窗口，把不该排除的字段一并排除或反之，误报 eiot_virtual_device 缺三列。另有一类非脚本成因的失真：@TableField("`trigger`") 的反引号转义使解析出的列名带反引号而与库中真实 trigger 不等。

Fix pattern: 行切分统一用 split(/\r?\n/)（或对每行末尾做 trim 掉 \r）；注解归属判定改为记录上一个字段匹配的结束位置 lastEnd，把 before 窗口限定在 [max(lastEnd, pos-N), pos) 内并在推进后更新 lastEnd；解析出的列名先剥反引号再比对。任何"批量比对结果为空/全命中"的输出，先抽 1~2 个已知应相等的样本打印原始字节（hex）确认解析层无误，再采信整体结论。

Reusable lesson: Don't 直接采信一次性批量比对脚本的全量结论 because 一个不可见字符差异就能把结论翻转成"什么都不存在"，进而据此向用户报告错误的缺失面；必须先用已知必然成立的样本（如主键 id 列）做阳性对照，阳性对照失败即说明是解析 bug 而非数据缺失。适用于自写脚本比对 information_schema / 配置文件 / AST 式文本解析的场景；不适用于直接用 SQL JOIN 在服务端完成比对的情况（无行尾与窗口问题）。边界补充：控制台显示乱码不代表数据错误，判定中文内容须以 hex 或 Buffer 相等比对为准。
