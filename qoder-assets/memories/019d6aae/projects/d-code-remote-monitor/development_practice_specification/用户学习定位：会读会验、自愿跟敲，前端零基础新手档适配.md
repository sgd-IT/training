用户在项目中的角色是"看懂改动 + 自主验收 + 提需求"。关于手敲训练（2026-10-08 两次实测修正）：早期用户自述不会手敲前端并质疑必要性，一度定为"不要求以默写/手敲作为训练手段"；但后续用户主动要求"你给代码我跟着敲"并完整手敲了告警消息列表的双读改造——**跟敲是用户自愿采用的理解手段，正确口径是"不强制、但用户要求时按跟敲模式组织教材"**。

对应约定：
- 讲改动按"三问"组织：①数据是裸的还是转过的；②双读是哪种形态（选表加工出显示字段/使用处 if 判空/纯透传补字段）；③边界怎么处理（null 与 undefined 都判、旧数据缺新值显示什么）。
- 跟敲模式组织方法：先讲数据流全景 → 拆成若干块（每块 5-20 行）→ 给验证命令与自查清单 → 用户贴回后逐行评审。
- 评审重点排序：编译器抓不到的静默错误（判据多敲属性、旧分支取错字段、列 key 未绑定加工字段）价值高于编译能抓的错误；修复练习代码时保留其命名与排版，只修错误处。
- 其他检验方式：三连问复述、真实小改动跑完整验证（造数据→看页面→F12 对请求→查库对字段）、找茬题。出题练习优先用真实待办项。
- "检查一下，给点思路"类请求：结构固定为「已完成清单→还开着的问题→决策表/心智模型替换→下一个待办的自检问法→面板状态同步」，零实现代码；当错误源于把两种结局揉进同一个 else 时，给"每种结局×各自动作"的决策表比逐条纠错更有效；每项缺陷按语义而非语法判状态。

注意：本条约束教学强度，不降低交付质量——改动仍须自行完成并给验证结论。

2026-10-16 画像：前端几乎零基础（HTML/CSS/JS 不熟，Vue3 语法、组件插槽、调试联调、CSS 布局四处易卡），要求教程"再详细上手"；后端能看懂、自己写需参考。

【更正 2026-10-28】上文"跟敲模式升级：每块给可直接抄改的完整小块 + 逐行说明 + 锚点定位"**仅适用于前端**。后端无论跟敲还是出题，都只给方法签名 + 步骤描述 + 坑位，不给完整方法体或可直接粘贴的 if/return 块；该口径已写入 SKILL.md 红线2、模式选择表与 5.4 第②项，学员因我按前端口径给后端成品代码而明确问责过。
