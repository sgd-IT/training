Bug class: 批量文本替换在 Windows 工程目录下静默失效（零命中却无任何报错）

Root cause: 本机存在按进程白名单工作的透明加密驱动。白名单进程（git、IDE 内置 Read/Grep 工具）写出到工作区的文件在磁盘上是密文；非白名单进程（PowerShell、robocopy、tar）读这些文件得到的是乱码字节，于是 .Contains('明文密钥') / Select-String 恒为 False，所有 Replace 分支都不触发，文件被原样写回，流程看似"执行成功"但内容完全没改。反向也成立：非白名单进程写出的文件对 git 是明文，git add/commit/diff 能读到正确文本，所以写回路径可用。

Fix pattern: 需要以明文批量处理工作区文件时，先用"权威读取通道"取证定性——用 IDE 的 Read 工具与 [IO.File]::ReadAllBytes($path) 对比同一路径：若 Read 显示正常文本而 PowerShell 读出二进制头（如 head=136,125,28...），即确认命中加密态。随后改为在白名单外产出明文：git archive --format=tar HEAD 经 .NET Process 的 StandardOutput.BaseStream 写入 TEMP（注意 git archive -o 直接落盘只生成 4096 字节空包，不可用），或 git checkout-index 导出后必须立刻校验可读性；在 TEMP 目录完成文本处理后，再用 robocopy /MIR 写回工作区并交给 git 提交。TEMP 目录不在加密范围内，可作为安全的中转区。

Reusable lesson: Don't rely on PowerShell Select-String / [IO.File]::ReadAllText returning plain text for files under an encrypted workspace, because it silently yields ciphertext and every replace becomes a no-op; must first cross-check with the IDE Read tool or byte header, then route all text processing through TEMP plaintext exported by git archive piped via BaseStream. Applies when batch-editing or masking text inside a source-controlled working copy on this machine (e.g. push-remote/backend 的 deploy、_sql、application-*.yaml); does not apply to single-file edits done through IDE edit tools, nor to pure git metadata operations (log/status/diff/push), which read plaintext correctly on their own.
