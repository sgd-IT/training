代码注释采用自然口语风格，核心原则是注释写给"人"看而非机器：用跟同事口头解释的语气，不堆术语、不复述代码。六条具体做法：
1. 解释"为什么"而不是"是什么"，代码本身能看出的信息不复述（反例：`// 获取用户列表` 配 `userMapper.selectAll()`；正例：`// 这里必须全量查，因为下游推送需要比对增量，不能漏人`）。
2. 长逻辑在方法开头用一句话剧透整体流程（如"校验 → 扣库存 → 发通知"）。
3. 历史遗留或临时方案的坑位直接带情绪标注（如"别动""等上游修复"），比冷冰冰的 WARNING 更有效。
4. 复杂公式或多步链式调用在上方用自然语言分步拆解每一步算什么。
5. TODO 必须具体可追溯：写明改什么、为什么没改、什么时候改，禁止只写"TODO: 优化"。
6. 控制密度：只在"不看注释容易误解"的地方写，不是每行都注。
