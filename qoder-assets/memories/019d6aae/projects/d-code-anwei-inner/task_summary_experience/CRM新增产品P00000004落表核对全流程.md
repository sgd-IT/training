## Task description
- Core requirement: 用户质疑此前新增的产品「智慧消防远程值守服务 / P00000004」是否写错了表，需要给出确定性结论。
- Task background: anwei-inner（anwei-office 库）并存两套互不同步的产品主档 erp_product 与 crm_product，另有 crm_contract_product、crm_business_product 两张明细快照表；CRM 报价/合同的产品下拉与保存校验只认 crm_product，因此"加错表"是真实存在的风险点。

## Execution process
1. 用 SELECT TABLE_NAME FROM information_schema.TABLES WHERE TABLE_NAME LIKE '%product%' 盘点出 8 张候选表（crm_product、crm_product_category、crm_business_product、crm_contract_product、erp_product、erp_product_category、erp_product_module、erp_product_unit）。
2. 试错发现两表列名不同：crm_product 的编码列是 no（varchar），用 code 过滤直接报 Unknown column；erp_product 才有 code 列。据此分别按 name / code 查询，结果只在 crm_product 命中 id=4，erp_product 返回空集。
3. 逐字段做取值语义校验：unit=13 对应字典 crm_product_unit 的「套」；status=1 对应字典 crm_product_status 的「上架」（0=下架）；category_id=3 在 crm_product_category 中 name=「其他」；owner_user_id=159 在 system_users 中 username=huyixuan、nickname=胡艺璇；price=45000.00、no=P00000004、tenant_id=1、creator=159、deleted=0。
4. 横向对比同表既有记录：id=3「应急 / P00000003」同为 creator=159，编号连续，证明 P00000004 是该页面正常写入序列的下一个。
5. 反向排除候选表：erp_product 无负责人字段且 code 查不到；crm_contract_product / crm_business_product 是合同与商机的产品明细快照表，不是产品档案表。
6. 正向验证链路：src/views/crm/product/ProductForm.vue（字段 name/no/unit/price/categoryId/status/description/ownerUserId）→ @/api/crm/product 的 createProduct → POST /crm/product/create → 后端 CrmProductDO 的 @TableName("crm_product")。

## Notes
- 字典类 int 列（unit/status）在库里存数字而非中文标签，是设计如此，页面靠 dict 翻译回显，不能当作脏数据或写错表的证据。
- crm_product_category 没有 status 列、system_users 没有 name 列，按猜测列名查询会报 Unknown column，应先查 information_schema.COLUMNS 再写过滤条件。
- 判定"是否加错表"最有说服力的组合是：全库同名前缀表盘点 → 各表结构差异（如是否有 owner_user_id）→ 字典/外键三方交叉校验 → 前端表单到 @TableName 的链路闭环。
