## Task description
- Core requirement: 在 anwei-office 库中新增一条报价数据，使前端「销售管理 → 报价列表」某行出现「新建合同」按钮（用户指定样例：BJ20261010000022 / 广州金桥养老院智慧消防远程值守项目 / 已冻结 / 有效期 2026-10-29 / ¥45,000 / 负责人 胡艺璇）。
- Task background: 报价列表页 src/views/crm/quote/QuotePage.vue 第 63 行的按钮条件为 frozen(row) && !expired(row)，其中 frozen = status ∈ ['已冻结','已完成']，expired = validUntil 非空且早于今天；库中原有 2 条已冻结报价的 valid_until 均为 9 月（已过期），故按钮全部不显示。用户此前明确要求数据库操作走 MCP（anwei-inner-office 服务已启用后本轮全程用 mysql_query）。

## Execution process
1. QuotePage.vue：确认按钮显示条件由 status + valid_until 两个字段驱动，与前端其它逻辑无关，造数只需满足这两项。
2. 通过 MCP 盘点 crm_project_quote / crm_customer / crm_project / crm_project_quote_item 的列结构、tenant_id（统一为 1）、既有数据样式，以及 information_schema.TABLES 的 AUTO_INCREMENT：客户=103、项目=8、报价=22、明细=50。
3. 关键推断并被实际验证：报价编号规则为 "BJ" + yyyyMMdd + 6 位补零 id（CrmQuoteManagementController / CrmProjectQuoteController 里 LocalDate.now().toString().replace + String.format），项目编号同理为 "PJ" 前缀；因此自增 id=22 恰好生成用户样例中的 BJ20261010000022，id=8 生成 PJ20261010000008 —— 说明用户贴的那条正是按系统规则预期的目标形态，不是查询已有数据。
4. 依次 INSERT 四条（全部走 MCP mysql_query，中文以 JSON 传参无损）：客户 103（industry_id=4 即「智慧消防（远程值守）」、owner_user_id=159 胡艺璇）、项目 8、报价 22（status='已冻结'、valid_until='2026-10-29'、amount=45000、completed_time 填值）、报价明细 50（product_id 留空，用快照名称方式）。
5. 用与前端完全一致的条件（status IN ('已冻结','已完成') AND (valid_until IS NULL OR valid_until >= CURDATE())）回归查询：造数前 0 条命中，造数后恰好命中 id=22 一条，确认按钮会出现。
6. 顺带排查用户上一张截图的「产品不存在」报错：文案不在前端源码里，来自后端 ErrorCodeConstants.PRODUCT_NOT_EXISTS；调用链为 CrmSalesContractController(/crm/sales-contract/save-with-plans) → CrmContractServiceImpl.createContract → validateContractProducts → CrmProductServiceImpl.validProductList，校验对象是 crm_product 表，而该表当前为空；CollectionUtils.convertSet 只 filter(Objects::nonNull)、不过滤 0，故保存合同时产品 id 校验必然失败。已在回复中作为遗留风险告知用户，未擅自补产品主档数据。

## Notes
- 教训一：用户贴出一段具体业务数据并说「按这个新建」时，应先判断这是**目标样例**还是**已有记录**；本轮先花多轮去库里查证该记录是否存在（结论是不存在），属于方向性跑偏，用户随后明确纠正"不是让你查询"。正确做法是先确认意图或直接按样例造数，同时用编号生成规则等旁证反推样例是否自洽。
- 教训二：本机环境把 .sql 文件落盘后内容会变成乱码/密文，mysql CLI source 执行报 "ASCII '\0' appeared in the statement"；含中文的 SQL 一律走 MCP mysql_query，不要再用文件+CLI 兜底。
- 教训三：造跨表演示数据前先查 AUTO_INCREMENT，可以让生成的业务编号自然对齐系统规则（BJ/PJ + 日期 + 6 位 id），避免手工拼号撞车或格式不符。
- 教训四：yudao 系 MySQL 表的 deleted 是 bit(1)、tenant_id 必须与既有数据一致（本项目为 1），否则数据会插入成功但列表因多租户过滤而看不到。
