## Task description
- Core requirement: 定位山东企业（company_code=3708319579）大华闸机"人闸车闸方向对不上"以及"刚测试人闸后云端无数据"的根因，并确认问题所属代码分支。
- Task background: 采集端在 fireworks-dhsdk-local 分支（netsdk EventHandler 订阅设备事件并 HTTP 上报），平台后端在 prod 分支（DaHuaService 保存人员/车辆出入记录并关联设备管理表 em_gate_device_info）。用户无 prod 修改权限，只能改 dhsdk。

## Execution process
1. 盘点 prod 分支结构：git ls-tree/grep 定位 modules/third/qt/DeviceRecordController.java 与 modules/third/service/DaHuaService.java（DaHuaService 是实现 PersonAndCarStrategy 的具体类，非接口），导出到 temp 阅读。
2. 读通后端逻辑：人闸 savePersonInoutRecord 用上报 devSno 与 em_gate_device_info 按 companyCode + devSno.contains(deviceCode) 匹配，取 deviceType(1进/2出) 作 inOutState；车闸 saveCarInoutRecord 先按设备管理设方向，但随后被 setInOutState(recordVo.getStatus()) 无条件覆盖为采集端上报值。
3. 查生产库验证登记：MCP 服务(anwei_fire_remote_monitor_test)中途不可用，改用本机 mysql.exe 直连生产库 anwei_mon_fireworks（连接参数取自本地已有配置，须带 --ssl-mode=DISABLED），HEX() 逐字符确认 id444-447 四台设备 device_code 均为正确数字0版、入口device_type=1/出口=2，登记无误。
4. 发现采集端全局配置 carInOrOut=1 使两台车闸都上报"进"，是车闸方向对不上的直接原因。
5. 对照实验定位"无数据"：POST /record/upload/dh/personInout 空 data 返回 code 500"数据不能为空"证明接口存活；发送 eventDate=当前+8小时 → API 返回 OK 但库中无记录（被静默丢弃）；发送 eventDate=当前时间 → 成功入库且 in_out_state=1；随后 DELETE 清理测试行恢复原状。
6. 确认后端硬校验：eventDate.after(new Date()) 时直接 return 丢弃但仍返回 OK；采集端 handlerEvent_ivs_access_ctl 是唯一仍启用 +8 偏移的 handler（其余 handler 的 +8 已注释），设备为北京时区时 +8 即未来时间被丢。
7. 分支归属验证：git ls-tree 各分支确认 EventHandler.java(+8) 仅存在于 fireworks-dhsdk-local；setInOutState(recordVo.getStatus()) 覆盖行同时存在于 prod/fireworks-local/odlTest-fireworks 三个后端分支。

## Notes
- HttpUtils.post 无论 HTTP 成败均返回 true，导致上报失败被当作成功，故障隐蔽。
- 生产接口对照实验采用"未来时间探测→正常时间验证→立即DELETE清理"的方式，无副作用；personId 会被后端截断为11位存储（TESTAA20261013→TESTAA20261），按完整值查询会误判为未入库。
- 修复方案定为只改 fireworks-dhsdk-local：人闸 +8 改为自适应写法（offset.before(now)?offset:date）；车闸方向可将 carInOrOut 改为按设备分别配置（入口1/出口2）。
- 上述"自适应写法（offset.before(now)?offset:date）"部署后被现场证伪：设备钟比采集机快 30~48 秒时加 8 被判为未来 → 不加 8 → 上报 UTC 值 → 云端显示早 8 小时（17 点测试显示 8 点）。最终有效写法为"时差比对"：Math.abs(now-eventDate) > 4 小时则 +8 还原北京时间，否则直接用，末尾再加"结果晚于当前时间则取当前时间"的防未来兜底。
- 补充事实：设备 Web 管理页确认其时区为 UTC+8 且时钟正确，但大华 SDK 上报的时间字段仍是 UTC 化的，故原始无条件 +8 本身正确；人闸进出方向由后端设备管理表判定（实测入口 .11→in_out_state=1、出口 .12→in_out_state=2 均正确），方向可靠性不受采集端影响。
- 车闸方向的落地形态已再次演进（2026-10-29 新企业 3708324436 接入时发现）：上一版实现是 EventHandler 里静态 CAR_IN_OUT_MAP 按设备SN硬编码方向 + 全局 dh.carInOrOut 兜底，每接一家新企业都要往代码里补两条 SN，导致新企业车闸未登记时全部回退"进"。现已删除该硬编码映射，DhConfig 新增 per-device `carInOrOut` 字段，getCarInOut(deviceId) 改为遍历 dh.configs[] 按 deviceCode 匹配取值、未配置才回退全局；切换后所有已上线企业的现场 application-prod.yml 必须给每台车闸补 carInOrOut，否则方向退化。排查车闸方向异常时应先看现场 yml 是否配了该字段，而不是找代码里的映射表。
- 人闸方向依赖的设备管理登记存在脏数据风险：em_gate_device_info 里 device_code 可能被填成中文名称（如"人脸识别进"），此时 devSno.contains(device_code) 永不命中，该设备的人闸记录 in_out_state 恒为 NULL（新企业 3708324436 的 id=299 实测如此）；排障时除查代码还要核对该表 device_code 是否为真实SN。

## Task overview
已完成根因定位与分支归属：人闸无数据 = 采集端 fireworks-dhsdk-local 分支人闸 handler 残留 +8 小时偏移，上报为未来时间被 prod 后端静默丢弃；车闸方向对不上 = 后端三分支统一存在 setInOutState(recordVo.getStatus()) 覆盖 + 采集端全局 carInOrOut=1。结论：无需 prod 权限，仅改 dhsdk 即可闭环；具体代码修改待用户确认后执行（尚未落地）。
