## Task description
- Core requirement: 定位"气体检测/气体分析"功能在 APP 端与 Web 端的确切位置，确认需求 32（气体检测数据可多次记录和修改）的实现落点，并在测试库构造一条"未开始"与一条"进行中"的可测数据。
- Task background: 项目并存两套气体数据体系（在用 base_work_sensor / 遗留 base_ticket_analysis），用户按"气体分析"字面在移动端找不到入口；需同时厘清 PC 端是否具备前端页面。

## Execution process
1. 代码检索确认在用体系链路：录入页 ActivityYasAnalysis、查看 Fragment FragmentJobSlipGas、后端 ApiSpecialController 的 addWorkSensor/updateWorkSensor，数据表 base_work_sensor（workId 挂作业票 outerId）。
2. 追溯移动端入口：读取 activity_hot_work.xml 发现该 tab 实际文案为"取样分析"且 visibility="gone"；读 ActivityHotWork.java 的 setRight() 确认仅 sourceType 为 "1"(动火)/"2"(受限空间)/"6"(临时用电) 时才置 VISIBLE，其余票型永远看不到该 tab。
3. 核查需求 32 实现与状态：FragmentJobSlipGas 提供连续添加按钮、点击记录携带 canEdit 进编辑页、isEditable() 按作业状态控制；ActivityYasAnalysis 按 outerId 是否为空分流新增/更新接口并支持只读态。git status 复核 ApiSpecialController.java、BaseWorkSensorServiceImpl.java、BaseWorkSensorMapper.xml 仍为已修改未提交，other1/ 整仓未纳入 git。
4. 造数前侦查：验证 MCP hc-standard-test 连 WINDOWS-3D9R3V5（160 测试库）、tgr-gz-vue 连 anwei1-0001（220 正式库，保持只读）；用 information_schema 取表结构（MCP 解析器不支持 SHOW FULL COLUMNS）；查明列表接口仅按 ticketsType + deleteMark=0 过滤、详情接口有权限掩码与 area_id 校验。
5. 以模板票 f3bca37a284e4fdbbd33b80262c3d791 克隆入库：base_work_special 两张（workStatus=0 / =2）+ base_work_approve 各 6 行 + base_work_step 各 16 行 + base_work_video 各 1 行 + base_work_sensor 各 2 行（不同检测时间），主键用 REPLACE(UUID(),'-','') 生成，curOperatorId=1、createBy=admin。
6. 回查验证：两张票 sensors=2/approves=6/steps=16/videos=1、areaExists=1 全部通过。
7. Web 端核实：ruoyi-ui 全量检索 sensor/workSensor 零匹配（仅 indexShow.vue 的遗留"取样分析"卡片与 notice 文案无关）；sys_menu 搜气体/取样/分析/sensor 返回 0 条菜单；BaseWorkSensorController 六个 CRUD 接口齐备但无前端无权限挂载。
