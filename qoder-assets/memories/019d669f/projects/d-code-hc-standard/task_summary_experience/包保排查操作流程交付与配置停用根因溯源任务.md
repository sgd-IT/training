## Task description
- Core requirement：用户在"让 862 开展包保排查"方案基础上连续追问四件事——①要"操作流程"（从修复到日常运转的具体步骤）；②纠正"途径 A 目录不对"；③确认"只改排查任务的检查人员就行了吧"；④追问"为什么会停用"，并补充线索"他们删除的记录号码的"。
- Task background：hc-standard（RuoYi）包保排查由 base_risk_task 配置 + base_risk_task_record 记录承载；袁志明账号 697→858→862 删除重建后配置漏迁移；220 线上三类负责人包保配置共 28 条全部处于停用状态。

## Execution process
1. Grep ruoyi-ui/src/views/base/riskTask/index.vue 确认"检查人员"（prop=checkUserId）为 el-select 多选、选项来自 userList，界面可直接逐条改；查 sys_menu 确认页面 component 落点。
2. 递归 CTE 在 160 报 ERROR 1064（版本不支持 WITH RECURSIVE），改用普通查询取祖先链，核实顶级菜单为"风险管理"(menu_id=2327, path=risk, parent_id=0)，其下含风险对象2605/风险单元2472/停机记录2633/风险事件2478/风险管控2484/排查任务2490/排查记录2496/四色图管理2611；系统内不存在"双控"目录名。
3. 回答"只改检查人员够不够"：读 TaskHandleMapper.xml 的 selectRiskTaskList，确认生成条件为 deleted=0 AND status=0 AND task_next_time<=NOW()；再查 220 base_risk_task 得 9 条配置 status=1（停用）、task_next_time=2027-01-28、update_by=system1、update_time=2026-01-29 15:15~15:16。
4. 用 sys_dict_data(dict_type='sys_normal_disable') 实锤 0=正常/1=停用；GROUP BY work_type,check_user_id,status 查明三类负责人配置全部停用（697×9、696×9、835×10）。
5. 停用原因取证：比对 riskTask 操作日志月度分布（2026-01~09 持续有操作），逐条读 oper_param 的 status 字段——1-29(6278) 与 2-07(6511) 提交时均为 status="0"，7-30(7106)、9-16(7239) 均为改检查人员而非停用；结合 28 条配置无对应界面日志也无 update_time 痕迹，判定停用发生在 7-28 之后且为直接改库。
6. 用户线索坐实：查 sys_user 得 697 del_flag=2/update_time=2026-01-29 15:14:23、858 建后 46 秒删、862 建于 15:15:10；查 business_type=3 的删除日志得 697 于 2025-04-11、2026-01-29 15:11:02、15:14:23 三次被删（日志 4547/6264/6276），紧随其后 6277 新增 862、6278-6287 编辑 9 条配置但 param 仍 checkUserId="697"。
7. 结论交付：根因是 1-29"删旧号建新号漏迁配置"→ 7-28 第二批任务派给已删账号 → 三类包保配置被统一停用止血并搁置；修复动作=改检查人员+启用状态+迁 9 条待检记录。

## Notes
- 交付的操作流程中曾把菜单路径写成"双控目录"，被用户当场纠正——行业叫法不等于系统内菜单名，给界面路径前必须查 sys_menu 逐级祖先核实。
- 160 实例不支持 WITH RECURSIVE（MySQL 5.x），递归查菜单祖先链会直接 1064 报错；同一语句在 220 可正常执行，跨库复用 SQL 需先考虑版本差异。
- 判断"配置状态是何时被谁改的"若界面日志缺失，可用 sys_oper_log.oper_param 里携带的 status/workType 快照做时间切片比对，配合 update_by/update_time 是否留痕来区分"界面操作"与"直接改库"。
- 用户口语线索（"他们删除的记录号码的"）值得顺着查 sys_user.update_time + business_type=3 删除日志，往往能直接定位事故起点。

## Notes
- "迁 9 条待检记录"这一步的范围描述需要限定：它解决的是"待检 tab 有无事可做"，不代表历史记录归属已全部理顺。APP 列表按 getType 分互斥 tab（0→check_status=0 待检、1→in(1,2,3) 已检、4→=4 已逾期），已检与逾期记录同样受 check_user_id 过滤约束，若也要在新账号下完整呈现历史履职，须按 check_status 全量迁移而非仅限待检；反之只要不影响未来派发与当下可排，仅迁待检即够用。
- 上述第 5、7 步关于"停用系绕过界面的直接改库止血"的结论已被后续会话实测推翻：真实原因是"液氯气化仓库"风险单元登记了停机（base_risk_unit_log 两轮检修：7-26 起计划 9-15 恢复、9-22 起计划 10-05 恢复），BaseRiskUnitLogServiceImpl 与 BaseRiskUnitServiceImpl.updateStatus 调用 BaseRiskTaskMapper.updateStatusByUnitId 按 risk_unit_id 级联批量停用其下全部排查任务；痕迹在 /base/riskunitlog 的操作日志里，故当时按 riskTask 接口路径过滤必然查不到。相应地，第 7 步的修复动作不再包含"手动启用配置"——正规恢复路径是在 PC 风险单元页把该装置"工作状态"切"开"（自动启用任务并把 task_start_time/task_next_time 重置为当天，次日 00:10 定时任务生成新批次），手动单独启用会绕过"停机不排查"规则而在检修期误派任务。另外 check_user_id 迁移至 862 已在后续会话完成，7 月批挂 697 的 9 条待检经确认无需迁移。
