## Execution process
1. 交付 6 条证据链 SQL（上半年完成记录 / sys_user 三账号时间线 / sys_oper_log business_type=3 删除日志 / base_risk_task 挂 697 配置 / base_risk_task_record 挂 697 待检 / 862 待检对照），均标注在 220 执行、加 --default-character-set=gbk。
2. 复查 base_risk_task 发现重大变化：check_user_id='697' 已为 0 条，9 条主要负责人配置已迁至 862（GROUP BY check_user_id,status 得 862：停用 10 条 + 启用 1 条），base_risk_task_record 仍有 9 条待检挂在 697 → 纠正用户"862 没有任何排查任务配置"的说法为"配置已迁、记录未迁"。
3. 查代码确认新增配置的生成时机：BaseRiskTaskServiceImpl.insertBaseRiskTask 自动 setTaskStartTime(getTimeOfBeforeDawn(3,1))，BaseRiskTaskMapper.xml insert 同时把 task_next_time 写成同值；updateBaseRiskTask 更新列含 task_start_time 但不含 task_next_time；sys_job 104 "根据风险排查任务生成记录" TaskList.addRiskTaskRecord cron=0 10 0 * * ? → 结论：保存配置后次日凌晨 00:10 才生成，非即时可见。
4. 追查"为什么会停用"：Grep updateStatusByUnitId 命中 BaseRiskUnitServiceImpl.updateStatus 与 BaseRiskUnitLogServiceImpl，发现该 SQL 按 risk_unit_id 批量改其下全部排查任务，status=0 分支额外把 task_start_time/task_next_time 置 CURDATE() —— 即"风险单元停机"功能的级联效果。
5. 数据取证坐实：base_risk_unit 中液氯气化仓库（334b8aa6…）status=1、update_by=system1、update_time=2026-09-23 10:41；base_risk_unit_log 三条停机记录（1-28 停 6 分钟、7-26 起计划 9-15 恢复、9-22 起计划 10-05 恢复）；sys_oper_log /base/riskunitlog 对应新增日志（business_type=1，hazardCode=420510077002）。
6. 定位恢复入口：riskUnit/index.vue "工作状态"列 el-switch（active-value=0 开/inactive-value=1 停）→ api changeStatus → PUT /base/riskUnit/changeStatus → Controller 调 baseRiskUnitService.updateStatus → 级联启用 + 重置生成时间 + 写实际恢复时间。
7. 交付最终流程与目录：风险管理→风险单元→液氯气化仓库切"开"（一步到位，自动级联）；明确警告不要手动去"排查任务"页单独启用那 9 条（绕过停机不排查规则会在检修期误派任务）；7 月批 9 条待检无需迁移。同步修正两条既有记忆的错误结论。
