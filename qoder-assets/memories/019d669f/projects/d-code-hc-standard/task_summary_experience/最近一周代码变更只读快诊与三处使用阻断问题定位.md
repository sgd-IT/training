## Task description
- Core requirement：用户要求对最近一星期的代码变更做一次快速 debug，只看是否影响实际使用，风格/性能/理论性问题一律忽略，须快速过完。
- Task background：hc-standard（RuoYi 多模块）近期迭代密集，涉及园区对接推送、作业票视频同步、企业证书审核、服务记录同步状态等链路；用户未给具体报错或复现症状，因此只能按变更范围与风险定位核心路径做静态诊断，不做全库穷举。

## Execution process
1. 以 git log 核定"最近一周"的实际提交窗口，得到 43 次提交、102 个变更文件作为检查范围；同时查看 git status 确认工作区未提交业务变更边界。
2. 按"是否影响使用"筛选主链路（查询/保存/审批/同步/权限/WebSocket），逐条交叉核对新增代码与其调用的下游实现，而不是孤立看单个文件。
3. 定位到缺陷①：ruoyi-system/src/main/java/com/ruoyi/board/service/impl/ApiLocationWebSocket.java 第 26 行附近——断线重连线程被创建但从未调用 start()，且重连逻辑只存在于线程体内，调用方仅在首次连接与发送心跳处介入，缺少补充重连入口，故一次断线后定位报警可能永久收不到。
4. 定位到缺陷②：ruoyi-admin/src/main/java/com/ruoyi/web/controller/base/BaseContractorCertController.java 第 79 行附近——管理员校验只挂在修改入口；ruoyi-system/src/main/resources/mapper/base/BaseContractorCertMapper.xml 第 50、63 行把请求中的 status 原样写入，新增服务直接交给 Mapper 无字段清洗，导致具备新增权限的非管理员可携带 status=3 直接新增"审核通过"的证书，绕过审核。
5. 定位到缺陷③：ruoyi-system/src/main/java/com/ruoyi/base/service/impl/BaseServiceRecordServiceImpl.java 第 176 行附近——修改已同步记录时附件处理会抛异常，而外层 autoSync() 在 208~213 行仅记日志、不回写失败状态，结果上报失败仍显示"已同步"，本地与平台状态不一致且易漏报。
6. 顺带跑了一个本地表单校验探针（缺字段失败、绑定字段通过），据此判定报备校验相关现象已修正，未列为缺陷。
7. 输出按"路径+准确行号 / 触发条件 / 用户影响 / 验证证据 / 最小修复建议"组织，并显式标注三项均为 Strong Hypothesis（静态高置信）、未运行复现。

## Notes
- 全程严格只读：未修改文件、未执行 git commit、未运行完整构建、未连接任何数据库实例、未调用外部业务接口，符合"正式库不可写 + 提交前须确认"的用户规范。
- 用户没有给出复现症状时，禁止伪称已复现；静态推断与运行证据必须在结论里分层标注，否则容易被当成已验证缺陷直接修。
- 这类"对称性缺失"型缺陷最有效：新增入口有校验而修改入口才有、重连线程建了没 start、异常被 catch 成日志而不回写状态——都是同一功能在两个平行分支上只做了一半，快诊时应优先比对成对分支。
- 快扫不等于回归通过，结论必须带上未覆盖限制（未启动业务、未覆盖全部执行分支与未跟踪产物）。
