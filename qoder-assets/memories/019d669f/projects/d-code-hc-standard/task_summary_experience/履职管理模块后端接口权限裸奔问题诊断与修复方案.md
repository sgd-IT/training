## Task description
- Core requirement: diagnose and fix the backend interface permission isolation issue in the '履职管理' (platement) module
- Task background: The platement module contains 12 controllers (e.g., PlatementImplementTaskController, PlatementBaogaoController) covering all aspects of major hazard source management. The frontend uses v-hasPermi permissions, but the backend has almost no @PreAuthorize checks — only one exists on PlatementEnterprisePlanController.remove(). This creates a critical security vulnerability where any authenticated user can access, modify, or delete all platement data.

## Execution process
1. Searched for '履职管理' and 'PlatementImplement' across the codebase to locate relevant files.
2. Read PlatementImplementTaskController.java, PlatementImplementTaskMapper.xml, and PlatementImplementTaskServiceImpl.java to confirm the absence of @PreAuthorize and data scope filtering.
3. Compared with BaseContractorController.java to establish the project's standard permission pattern (e.g., @PreAuthorize("@ss.hasPermi('base:contractor:list')")).
4. Listed all 12 platement controllers and their URL mappings by grepping @RequestMapping.
5. Mapped each controller to its corresponding frontend v-hasPermi permission prefix (e.g., platement:implementtask:*).
6. Identified two key points requiring confirmation: (a) the existence of corresponding entries in the sys_menu perms table for these permissions, and (b) a potential frontend typo in enterpriseInfo/index.vue using 'platement:implementperson:add' instead of 'platement:enterpriseInfo:add'.

## Task overview
Successfully diagnosed the root cause: 12 platement controllers have zero functional permission isolation. A complete, minimal-fix solution was formulated: add @PreAuthorize annotations to every method in all 12 controllers using the exact permission strings already used by the frontend's v-hasPermi directives.
