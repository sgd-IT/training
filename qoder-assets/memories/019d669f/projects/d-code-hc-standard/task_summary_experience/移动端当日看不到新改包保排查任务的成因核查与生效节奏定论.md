## Task description
- Core requirement：用户连续追问"修改（排查任务）后移动端能否看到""我只管后续新增的和移动端是否可见""为什么手机端还是没有呢，今天修改完的人""你今天修改的检查人员是不是需要明天才能看到排查任务"，要求定位"当天改完检查人员、APP 仍看不到包保排查任务"的原因。
- Task background：hc-standard（RuoYi）包保履职由 base_risk_task（配置）+ base_risk_task_record（记录）承载，液氯气化仓库（risk_unit_id=334b8aa659464ade8d5bda20c68fc8af）28 条负责人任务已启用且 task_next_time=2026-09-28。目标库为线上 220.203.23.144（anwei1-0001），按口径全程只读；命令行 mysql 加 --default-character-set=gbk 使中文列可读。

## Execution process
1. 查 base_risk_task 按 work_type/check_user_id/status/task_next_time 分组 + 统计当天新增记录数（结果：当天生成 26 条，最早 00:00:00、最晚 16:00:00）+ 三账号名下待检数，确认配置层无异常。
2. 查 sys_oper_log WHERE oper_url LIKE '%riskTask%' AND oper_time>=当天，取到 system1（IP 122.191.197.215）多条操作，最后一条 14:23:56，证明当天确有界面修改动作。
3. 用 update_time>=当天 反筛被改配置，精确定位改动范围：仅 work_type=1（主要负责人）9 条、check_user_id=862（袁志明）、最晚修改 14:23:57；work_type=2（696/朱文浩，最后修改 2026-02-07）与 work_type=3（835/夏翔飞，2026-06-10）当天未被改动。
4. 对当天新增的 26 条记录按 is_defend/check_user_id 分组排除干扰：全部 is_defend=0（日常巡检），归属瞿彬/彭亨清 5 条、佘艳信 1 条、李家洲/张丛海 2 条、文茂华/全正华/冯中卫 18 条——无任何液氯负责人（包保）记录。
5. 交叉推导生成机制：sys_job 104（TaskList.addRiskTaskRecord，cron=0 10 0 * * ?）每天凌晨 00:10 跑一轮，当天批次在 00:10 已执行完毕，白天 14:23 的修改无法回头触发；updateBaseRiskTask 不含 task_next_time 列故不提前生成时间，但下次生成时读取的是最新 check_user_id。
6. 交付结论与验证计划：改动生效节奏 = T 日改 → T+1 日 00:10 生成 → T+1 日可见；明晨预期生成 862×9 / 696×9 / 835×10；同时说明历史遗留（旧号 697 名下 9 条待检）按 check_user_id 过滤不会出现在 862 的 APP 列表，可不处理。

## Notes
- "今天库里新增了记录"极易被误读为"我的修改已生效"：必须按 is_defend 与 check_user_id 分组核实这批记录属于谁的哪类任务，否则会把别人的日常巡检当成自己的包保任务已生成。
- 判断"某人今天改没改配置"不要依赖操作日志做时间推断，直接按 update_time>=当日 反筛 base_risk_task 更准确（updateBaseRiskTask 会写 update_time=now）。
- 按 oper_url LIKE '%riskTask%' 过滤日志只能看到本模块入口的操作，跨模块级联写入不在此列（此教训已由既有记忆固化）。
- 面向客户的沟通应把机制讲成一句可复述的规律（"次日凌晨生成、次日可见"），避免逐条解释表结构。
