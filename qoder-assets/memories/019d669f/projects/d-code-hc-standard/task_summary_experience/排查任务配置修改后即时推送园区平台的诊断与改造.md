## Task description
- Core requirement：用户先问"那修改和新增都推送吗"（排查任务配置 base_risk_task 是否新增/修改都会推园区平台），得到结论后下达指令"修改完直接落库后推送"，要求把修改链路改成保存落库后立即推送。
- Task background：园区接口 5.4.6.6 /openapi/checkTask/saveOrUpdateBatch 是按 outerId 的 upsert（同 id 覆盖），文档标题为"新增或修改排查任务配置"；本地侧 Controller 的 add/edit 只落库，推送能力集中在同类 sync(String[] ids) 方法上，另有 quartz DataSyncTask.syncRiskTask 定时补推与 PC 手动同步按钮。

## Execution process
1. 读 BaseRiskTaskController.java 确认 add/edit 无任何平台调用，同步是独立入口 GET /base/riskTask/sync/{ids}。
2. 读 riskTask/index.vue 与 riskMeasure/taskIndex.vue 的 handleUpdate/submitForm：两处均为 this.form = response.data 整条回填后原样提交，域对象 BaseRiskTask 的 syncStatus/syncResult 无 @JsonIgnore，因此修改会把已有的 '1' 写回。
3. 用 MCP 查 information_schema 实测列默认值：base_risk_task.sync_status 与 work_day_type 均 DEFAULT '0'（char(1)，可空），故新增记录天然落在定时扫描集合内。
4. 结论口径：新增=不实时推但会被 quartz（每天 6:00/23:30，扫 sync_status is null or in ('0','2')）补推；修改=既不实时推也不会被补推（sync_status 保持 1 被扫描条件排除），只能靠手动同步按钮或 PushDataController 按日期补推——即"修改→自动同步"未闭环。
5. 代码改动（仅一处）：BaseRiskTaskServiceImpl.updateBaseRiskTask 在 mapper 更新返回 rows>0 后调用同类 sync(new String[]{id})，推送复用 selectBaseRiskTaskListByIds 现查最新值；网络级异常 try/catch 记 log.error 并调 updateSyncStatus(msg, "2", ids) 标记失败，不向上抛错以免阻断本地保存。
6. 编译验证：JAVA_HOME 指向 D:\Tool\jdk\jdk1.8 执行 mvn -q -o -pl ruoyi-system -am compile -DskipTests 通过，并以 target/classes 下 BaseRiskTaskServiceImpl.class 的时间戳/大小确认确实重新编译。
7. 同步更新既有机制记忆《排查任务推送报文与触发机制》，追加"修改落库后立即推送、异常标记 2 由定时任务重试"的新行为。

## Notes
- 上述第 4 步"修改既不实时推也不会被补推"是改造前的旧现状，现已被第 5 步的改动取代：当前代码里 updateBaseRiskTask 落库成功后会立即推送园区平台，即在测试期编辑任何一条排查任务配置都会产生真实外呼，评估改动面前须按此新行为判断。
- 关于配置生成时机的补充实测：insertBaseRiskTask 会强制 setTaskStartTime(getTimeOfBeforeDawn(3,1)) 覆盖前端填写的开始时间，且 insert SQL 把 task_next_time 写成同值，故新建配置要到次日凌晨 sys_job 104（TaskList.addRiskTaskRecord，cron 0 10 0 * * ?）跑过才生成待检记录；updateBaseRiskTask 的更新列含 task_start_time 但不含 task_next_time，即修改配置不会提前或推后下一批生成时间。
