## Task description
- Core requirement: verify whether the current implementation of the "5.4.6.6 新增或修改排查任务配置" interface (POST /openapi/checkTask/saveOrUpdateBatch) matches its official documentation, and identify any differences.
- Task background: The user provided the API documentation and asked "有区别吗"; the task required comparing the doc against the actual codebase (entities, mappers, service logic), verifying field-by-field mapping, checking database schema and data, and confirming the real-world behavior.

## Execution process
1. Searched for all related code files (RiskTaskSaveEntity.java, CheckTaskEntity.java, BaseRiskTaskMapper.xml, PlatementRiskCheckUnitApi.java, DataSyncTask.java) to locate the implementation path.
2. Compared each documented field (id/outerId, riskMeasureId, troubleshootContent, checkCycle, checkCycleUnit, checkCycleStart/End, checkStartTime, workDayType, workType, taskNum, createTime/updateTime) against the actual code and SQL mapper to determine if it is sent and how it is mapped.
3. Verified that `workDayType` is the only difference: it is present in the local DB (`base_risk_task.work_day_type`) and entity but not included in the push payload (selectBaseRiskTaskListByIds does not select it).
4. Used MCP to query both test (160) and prod (220) databases and confirmed that `work_day_type` is uniformly `'0'` across all records, meaning the omission has no functional impact as the platform defaults to `0`.
5. Confirmed that the frontend UI (riskTask/index.vue, riskMeasure/taskIndex.vue) does not expose a form field for `workDayType`, so users cannot configure it anyway.
6. Documented the full comparison table, real-world impact assessment, and future considerations for adding `workDayType` support.
