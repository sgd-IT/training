Bug class: 两类同源错误——把相邻模块的同步约定当成通用规则跨实体套用，以及把本地状态枚举原样直传给平台而忽略两侧数值同义不同。

Root cause: hc-standard 园区对接各模块的上报能力与实现位置都不对称。从业人员（practitioners）等实体有 deleted 标记软删上报路径（setDeleted("1") + saveOrUpdate 复用），而重大危险源包保责任人（PlatementImplementPerson）对应的 OpenAPI 只提供 POST /openapi/implementPerson/saveOrUpdateBatch（批量新增/变更），平台侧不存在删除上报语义；按"同类模块都有删除同步"推测就给包保补 deleted 字段与删除上报，等于向平台推它不接收的语义——该口径早已被记录为 IMMUTABLE 记忆却未检索确认，导致白做一轮并用 git checkout 整体还原。另一侧，双控排查记录的两条同步 SQL 曾把本地 check_status 原样直传，结果 31333 条本地"正常"在园区侧被标成"存在隐患"，真正的异常记录一条未传。

Fix pattern: 改动任何"是否要上报园区平台""上报什么值"的逻辑前，先核对该实体在已封装 OpenAPI 中的接口清单（只有 saveOrUpdateBatch 即无删除上报能力），并把平台约定以 Javadoc 就地写回方法注释（如"批量删除包保责任人（平台约定：删除无需上报园区平台，仅本地删除）"）防止后人再当成遗漏补一遍；动手前先检索该实体是否已有权威口径记忆。改上报范围/字段时先定位该实体的外呼集中点（可能在 ServiceImpl，也可能在 mapper SQL，多处查询须同改），凡涉及状态类字段必须核对本地字典（sys_dict_data）与平台文档枚举是否同义，不同义则在 SQL 里用 CASE 做值映射而非直传。

Reusable lesson: Don't 按相邻模块的同步实现或数值相同的枚举推断本实体可照搬，因为平台可能既无该接口又用不同枚举，结果是引入错误外呼或把数据报错语义并需整体回滚；instead 先查该实体的 OpenAPI 接口清单、外呼集中点与两侧枚举定义，并检索既有口径记忆再决定改法。适用于 ruoyi-common/platement 域对象、ruoyi-system/base/service/impl 下 Platement*ServiceImpl 以及 base mapper 中带园区语义的同步查询改造；不适用于纯本地 CRUD（无园区对接语义）的功能。
