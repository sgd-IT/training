Bug class: 后台"删除用户"操作被业务数据静默拦截，误判为权限或缓存问题
Root cause: hc-standard 的 SysUserServiceImpl.deleteUserByIds() 在删 sys_user 前会调 baseWorkSpecialMapper.selectCheckUserIdCount(userId)（SQL 口径：base_work_special 中 deleteMark = 0 AND curOperatorId = #{userId}）以及 baseRiskTaskMapper 同类计数，任一 >0 就抛 ServiceException。curOperatorId 存的是 sys_user.user_id 数值而非手机号；由于作业票列表页也按 deleteMark 过滤，票在界面上可能已看不见但 deleteMark 仍为 0，导致"看不到票却删不掉人"。
Fix pattern: 遇到该提示先用 user_name='<手机号>' 查 sys_user 取 user_id（本项目 sys_user 无 phonenumber 列，写 phonenumber 会报 Unknown column），再按 curOperatorId=<user_id> AND deleteMark=0 定位主票 outerId，以 workId=outerId 逐张核对子表（base_work_approve / base_work_step / base_work_video / base_work_certificate / base_work_sensor）；解除拦截只需把主票置 deleteMark=1（与系统自身删除语义一致），无需物理删除。若确要物理删，顺序为先子表后主表最后 sys_user，并用一条 COUNT 汇总做残留验证。
Reusable lesson: Don't 通过清角色/岗位关联或重启服务来绕过"该用户存在作业票，不允许删除"，因为拦截只来自业务表计数，绕不过去；instead 直接处理主表 deleteMark 标记。同时必须先读 sync_status/sync_result 判断该票是否已成功上报园区平台——sync_status='2'（上报失败）说明平台侧无此数据可放心清理，反之需先考虑平台侧一致性。适用于 hc-standard 后台删除 APP 账号被拦截、或按账号批量清理特殊作业票数据的场景；不适用于 ticket/ticketSbb 等废弃页面所用的 base_ticket_* 系列表（其关联键是 uniqueKey，不是 workId）。
