Bug class: 状态字段被"跨模块级联"改写，按本模块操作日志溯源查不到痕迹，误判为绕过界面的直接改库。
Root cause: hc-standard 中 base_risk_task.status（排查任务启用/停用）除自身页面的 changeStatus 入口外，还被风险单元停机功能按 risk_unit_id 批量改写——BaseRiskUnitLogServiceImpl（登记停机）与 BaseRiskUnitServiceImpl.updateStatus（恢复启停）都调用 BaseRiskTaskMapper.updateStatusByUnitId(unitId,status)，其 status=0 分支同时把 task_start_time/task_next_time 重置为 CURDATE()。因此排查任务的停用痕迹只出现在 /base/riskunitlog 的操作日志里，用 oper_url LIKE '%riskTask%' 过滤必然为空，遂得出"无日志、疑似改库止血"的错误归因。
Fix pattern: 溯源某列何时被谁改成什么值时，先在代码层全仓检索该列名与其 mapper 方法名（如 updateStatusByUnitId），列出所有会写它的 Service 与各自的入口 URL/菜单，再按这些 URL 去操作审计表取日志；找到候选写入点后，用主数据侧的状态表（本例 base_risk_unit.status + base_risk_unit_log 停机记录）交叉验证时间线是否吻合。
Reusable lesson: Don't 仅按目标实体自己的模块接口路径过滤操作日志就断定"没人改过、是直接改库"，因为另一个模块的级联写入不会留下本模块日志，会把根因归错方向并给出错误的修复建议（本例曾建议手动启用配置，实际正确做法是恢复风险单元工作状态开关）；instead 先全仓 grep 该状态列/mapper 方法找出全部写入方再定日志检索范围。适用于任何带操作审计表且存在跨实体级联更新的管理系统状态溯源；不适用于确认无任何其他 SQL 写过该列的场景（须以全仓检索结果为前提）。
