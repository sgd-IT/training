Bug class：多实例同名库场景下的"环境定性误判"，导致向生产库执行写操作（本仓已实际发生：把正式库当测试库执行了菜单 UPDATE）。

Root cause：环境的"测试/正式"性质不会出现在任何机器可读信号里。三类常被误用的代理信号全部不可靠——① 连接名/MCP serverName/文件名里的 test、prod、dev 字样（命名习惯与实况可以完全相反）；② 库名（同一项目多个实例常共用同一个 schema 名，无法区分）；③ 运行时活动信号（如"该库今天有测试人员在操作""这是当前生效数据源所以一定是开发库"——正式库同样每天有业务写入）。真正唯一的锚点是配置文件中生效数据源与被注释备用数据源的 IP 地址，以及用户对每个地址性质的明示。

Fix pattern：写操作前做"地址→库别"单向核对：从 datasource 配置读出目标 IP，与该项目的权威环境映射比对得到库别；只要判定结果不是"可自由读写的测试库"，就降级为只读并把变更登记到待上正式库清单等用户执行。禁止用连接名、文件命名、当日活跃度反推库别；这些信号只能作为触发向用户求证的线索。

Reusable lesson：Don't 凭连接名/库名/当天有无测试活动来判定某实例是测试库然后直接写入，因为同名多实例下这类推断可以整体反向，一旦命中正式库就是不可逆的生产写入；instead 先按 IP 比对权威环境映射，非测试库一律只读+登记清单+等确认。适用于同一项目存在两个及以上同名 schema 实例、或配置文件同时保留生效与备用数据源的任何仓库；不适用于只有一个实例、或用户已明确授权对该地址可直接写的场景（此时仍应在执行前一句话复述目标 IP）。
