结论：作业报备（base_ticket_bb）同步园区平台时不引入任何本地判重列或同步状态列——外呼全部集中在 BaseTicketBbServiceImpl 的 reportPlatform → PlatementPrepareApi.save，且实现为"先上报成功再写本地库"，上报失败直接抛异常不落库。

理由（权衡）：正因为该时序不变量，库里根本不会存在"已落库但待推送"的中间态记录，所以既不需要 synced 类标记列区分新增/修改，前端也不需要同步状态列与重试按钮；若改为"先落库后上报"，则必须同时补同步状态字段与重试载体，改动面会扩到表结构、前端与定时任务三处。

适用/失效条件：仅适用于采用"先推后落"时序的实体（当前即 base_ticket_bb 一处）。对比参照：第三方单位服务记录 base_service_record 因采用"先落后推 + 失败回写状态"，才需要 synced 标记列区分平台的 save/update 两个接口；而包保责任人等平台侧只暴露 saveOrUpdateBatch 批量 upsert 接口的模块，两类判重列都不需要。

已实例化的反例（2026-09-23 实测）：排查任务配置 base_risk_task 走的正是"先落库后推送"分支，因此它确实同时具备 sync_status/sync_result 两列（列默认值 '0'）、PC 列表同步状态列、手动同步按钮与 quartz 定时重试扫描，完全印证上述"改时序需补同步状态列与重试载体"的改动面判断；同一实体上"修改后是否会自动重推"取决于 update 是否重置 sync_status，具体触发路径见「排查任务推送报文与触发机制」。
