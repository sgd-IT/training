hc-standard 园区对接在"页面上报/同步状态/人工补推"层面的三条已验证口径（实体级外呼点见各实体专条，不在本条范围）：

1. 无自动补推兜底：测试期为停用外呼而临时注释某实体的推送代码后，期间新增或修改产生的数据在恢复注释后**不会被自动补推**——项目不存在待推队列或重试定时任务承载。需要把这段窗口期的数据送到平台时，必须手工走按主键的批量接口或对应实体的补推入口触发。

2. 同步状态列失去回写来源：注释掉推送后，该实体列表页的"同步状态"列不再有写入方，会长期显示"未同步"，属预期现象而非缺陷；排查时不要据此判定链路故障。同时被注释处引用的 api 字段与相关 import（如 ServiceException、JSONObject）成为死引用，Java 侧只告警不报错，恢复时可直接复用而不必重写。

3. 补推运维接口调用约定：ruoyi-admin/src/main/java/com/ruoyi/web/controller/push/PushDataController.java（全文 155 行实测）共 6 个 POST 接口 /push/workSpecial、/push/workVideo、/push/riskObj、/push/riskTask、/push/hiddenTrouble、/push/contractor，挂在测试服务器 http://192.168.250.130:28080 下。共同特征：均需登录 token（请求头 Authorization: Bearer <token>，token 从 PC 登录后浏览器 Cookie 的 Admin-Token 复制）、参数走 @RequestParam（URL query 或 form 均可）、无前端页面入口、非定时任务，调用即真实外呼园区平台。各接口的必填参数、onlyUnsynced 语义与逐实体推送顺序见《PushDataController六个补推接口参数与推送顺序约定》。关键风险：这些接口是绕过同步状态的人工出口，即使某实体常规上报已被注释停用（如气体分析传感器），走整票补推 /push/workSpecial 仍会把该实体的子数据推给平台，执行前必须确认当日是否允许真实外呼。

## Notes
- 第 2 条仅适用于"推送代码被主动注释停用"的场景，不可推广为"同步状态显示异常一律属预期"。服务记录（base_service_record）的真实缺陷分支已被实测证伪并修复：BaseServiceRecordServiceImpl.sync 的业务异常原先被外层 autoSync() 只记日志不回写，导致上报失败仍显示"已同步"；现已改为异常分支先回写 sync_status='2' 再抛出。因此若看到"显示已同步但平台无数据"，应先按缺陷排查而非当作预期现象。
