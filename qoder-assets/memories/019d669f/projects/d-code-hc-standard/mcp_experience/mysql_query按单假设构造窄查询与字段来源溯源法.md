## Usage Scenario
用 mysql_query 验证功能实现状态、数据同步健康度、诊断数据相关问题；尤其是用户声称某 DDL/SQL 已执行但运行时表现仍像没执行时。

## Usage Method
一次只验证一个假设：优先写直接检验核心论断的窄查询（"这批记录是否已同步""失败原因是什么""最新一条数据是什么"），而不是宽查询。追踪某业务字段的权威来源时，先读若干现有行学习取值格式（长度/模式），再用同一字面值去兄弟表检索，从而定位主数据表及其引用链。核对跨环境的列定义差异时，按精确属性逐项比对（序号位置、类型、可空性、注释文本的 HEX），不要靠肉眼看输出。

## Notes
- 不带假设地跑 SELECT * FROM table 会返回海量数据且浪费时间，必须收敛到单个聚焦问题。
- 中文列注释经终端输出比对会因编码产生假不一致，须改比 HEX 值。
- 同一个库内表的列命名风格并不统一（老表用 camelCase、新表用 snake_case），凭实体字段名猜列风格会报 Unknown column 并白跑轮次，写列表前必须先从该表的 mapper resultMap 或一条窄探测查询确认真实列名。
- SHOW TABLES LIKE 带引号通配符会被本 MCP 的 SQL 解析器拒绝，表/列元数据一律走 information_schema。
- 在某一个实例上重复执行同一条元数据查询不会带来新信息；需要区分环境时必须换到候选实例上分别执行（见「MCP数据库查询须先验证连接实例再做跨环境结论」）。
