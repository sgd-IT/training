## Goal
诊断"外部平台侧展示/统计结果与本地业务含义不符"这类隐蔽缺陷，或在放开上报范围、修改状态类字段前确认取值口径是否安全。适用于任何本地字典与外部系统枚举可能只是数字相同、语义不同的对接链路核查，也适用于"同步状态显示全部成功但对方说数据不对"的场景。

## Steps
Step 1: read_file - 读取上报字段的拼装位置（实体类与同步查询语句），rationale: 状态值可能在 Java 侧组装、也可能直接写在 mapper XML 的 select 列里，只看 ServiceImpl 会漏掉真正决定取值的落点，导致改了不该改的地方；若该实体有定时同步与手工补推两条链路，两处查询必须同时纳入清单，input: 承载数据的表名或接口路径, output: 每个上报字段的实际来源表达式与其过滤条件
Step 2: bash - 对状态列与同步状态列做双维交叉分组统计，rationale: 单维统计会出现"两组总数相等"的巧合组合而推不出结论，只有落到每个"状态×同步状态"单元格才能钉死哪些数据从未上传；input: 表名 + 两个状态列, output: 各组合的行数分布
Step 3: bash - 查本地字典表中该状态列的 label/value 定义，rationale: 字典是本地语义的唯一权威来源，凭数值猜语义是这类缺陷的成因本身；input: 字典类型名, output: 本地各数值的业务含义
Step 4: grep_code - 检索写入端与展示端对该字段的使用（客户端提交逻辑、页面渲染所用字典），rationale: 字典可能被改过或与真实写入不一致，只有"字典 + 写入端赋值 + 展示端渲染"三方一致才算把语义钉死，缺一方便结论可被质疑返工；input: 字段名, output: 各端对该数值的实际解释
Step 5: Phase check - 确认已同时持有"字段来源表达式 + 状态×同步交叉分布 + 本地字典释义 + 写入端与展示端印证"四类证据，且已与外部文档枚举逐项对齐；若发现两侧枚举数值同义不同，则本次改动必须包含值映射而不能只放开过滤条件；若发现某状态值在本地存在但不在对方枚举内，须先向业务方确认归属再动手；若字段来源分布在多条查询里，后续修改须覆盖全部查询
Step 6: bash - 把映射表达式作为纯查询在真实数据上跑一遍分组验证，rationale: 映射写进语句文件前先在数据上看清每个原值流向哪个目标值，能立刻暴露漏项与错向，避免改完编译通过却仍报错值；input: 映射表达式, output: 各原值到目标值的流向与行数
Step 7: 修改后用 XML 语法校验加全量编译做回归，并用编译产物时间戳坐实：静默模式的构建命令无输出即成功，但需二次确认退出码或产物更新时间，否则无法区分"成功"与"根本没执行"

## Notes
- 只按"本地有该状态记录"就断言对方会显示同样的含义，会把错误数值持续推给外部系统且本地看不出异常（同步状态一直是成功），必须先比对两侧枚举定义再决定是否映射。
- 用两条单维分组查询的数字相等来论证"某类数据全部未上传"逻辑上不严密，必须做双维交叉分组到单元格级别。
- 语言服务未就绪时基于 IDE 诊断的回归手段不可用，涉及编译期引用的改动必须回落到真实构建命令验证，不能仅凭无报错判定通过。
