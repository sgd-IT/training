## Goal
在一批未提交变更中系统性定位重复实现、重造轮子与无调用方代码，并给出可量化的删减收益；适用于提交前代码审查、模块批量新增后的冗余治理、重构范围评估等场景。

## Steps
Step 1: bash - 按功能主题分组取全量 diff，rationale: 先建立变更全景与文件归属，否则后续比对会漏掉跨目录的同构文件，输入: 工作区状态，输出: 按主题聚类的文件清单
Step 2: read_file - 成对读取疑似同构文件（同类 Service / 同类 Api / 同类页面）做逐行比对，rationale: 重复实现只有并排读才能判定是"仅标识符不同"还是"实质差异"，只看文件名或行数会误判，输入: Step 1 聚类结果，输出: 重复组与其行数规模
Step 3: grep_code - 用公共能力符号反查所有调用点，rationale: 判断某段手写逻辑是否属于重造轮子，必须确认同一批次引入的公共封装已被哪些位置复用、哪些位置绕开了它，输入: 公共方法名集合，输出: 复用与绕开的分布
Step 4: Phase check - 确认每个重复组都已找到"应被复用而未复用"的既有实现作为替代依据；若某组只有单一实现且无第二个使用方，则不按重复处理而按 YAGNI 单独判定，避免为一次性代码引入抽象
Step 5: grep_code - 对疑似无调用方的方法与被注释入口的导出符号反查引用，rationale: 只有反查零命中才能称其为无调用方代码，凭直觉标注会产生假阳性并误删恢复锚点，输入: 方法名与导出名，输出: 调用方存在性结论
Step 6: Phase check - 区分"计划内暂停"与"真死代码"：若该调用方是被有意整段注释以等待外部依赖就绪，则单列为可选项并注明保留代价，不计入净删减收益；否则并入删减项
Step 7: 汇总输出 - 逐条给出位置、判定类型、收敛手法与预估削减行数，末尾给合计值，rationale: 不带量化收益的审查结论无法支撑"改还是不改"的决策

## Notes
- 用 shell 统计由编辑器写入的源码文件行数会得到明显偏小的错误值（透明加密下读到密文），导致重复度与规模判断整体失真，必须改用文件读取工具取真实内容后再比对
- 只按文件路径相似就断言重复 causes 把字段名不同的合理差异说成可合并，must 必须实际并排读取两个文件确认差异面
- 把联调期被注释入口残留的方法当死代码删除 causes 丢失最简恢复锚点，must 先确认其停用意图再决定是否计入删减
- 语言服务不可用时以符号定义逐个核对加最小范围真实编译加产物时间戳验证正确性，quiet 构建无输出须二次确认退出码或产物更新时间，否则易把"根本没执行"当成通过
- 对已确认可复用的改动模式做批量套用前须先取参考模块实际改动的文件全集逐层复制，完成后按相关 API 名与定时任务全仓反查确认无隐藏出口，否则会在测试期触发意外对外推送
