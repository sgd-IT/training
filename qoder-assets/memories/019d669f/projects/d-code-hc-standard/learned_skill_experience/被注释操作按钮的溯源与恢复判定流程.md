## Goal
对"页面上被注释/隐藏的操作按钮（或任何疑似被禁用的功能点）"做完整审计：确定它是谁在何时为何关掉的、页面现在是否还在用、该不该恢复，并把结论沉淀到代码注释里；适用于功能恢复类需求核查、废弃模块清理、遗留禁用项盘点。

## Steps
Step 1: grep - 按注释模式批量扫描目标视图目录列出全部命中文件与行号，rationale: 先拿到全量清单再逐处判定，漏扫会直接导致需求覆盖不全, input: 注释特征正则+目录范围, output: 待核查位置清单
 Step 2: git blame - 对每处起始行取提交哈希与作者日期，rationale: 不溯源就无法区分"有意长期禁用"与"临时注释忘了还原"，恢复决策完全依赖这一步, input: 文件+行号, output: 每处的引入提交
 Step 3: 数据库查询（元数据表如菜单/权限表）- 查每个宿主页面的启用状态（可见性、启停、名称中的废弃标记），rationale: 页面若已废弃或未启用，其注释按钮属"无需恢复"，跳过此步会把废弃功能误恢复成在用功能；废弃形态有两类都要覆盖——菜单名带"废"字后缀的，以及菜单处于隐藏加停用状态的, input: 页面路由/组件标识, output: 页面存活判定
 Step 4: Phase check - 确认清单每处都同时具备"引入提交 + 页面存活状态"两项证据；若某页面既无菜单入口又无引用，归为无需恢复并在结论中注明；若发现同类禁用是本轮任务自己临时加的（如为停止外呼而注释），必须从恢复清单中剔除并单独说明, input: 步骤2/3产出, output: 两类分组（无需恢复 / 恢复前需业务确认）
 Step 5: edit_file - 在每处注释块上方就地写入备注（溯源结论+当前状态+恢复前确认点），rationale: 结论只写在回复里会随会话丢失，写回代码才能让下一个改动者不再重复考古, input: 分组结论, output: 带原因说明的注释块
 Step 6: 编译或构建校验 - 对改动的模板文件做一次构建/lint 校验，rationale: 注释块插入易破坏标签闭合与缩进，需即时回归, input: 改动文件集, output: 构建通过或定位到的具体行

## Notes
- 只看代码里有注释按钮就一律恢复，会把废弃页面的死功能重新暴露给用户造成新缺陷，必须先以元数据表判定页面存活状态
- 用整行文本作为编辑工具的匹配锚点常因不可见空白或行尾差异失败，应改用短且唯一的子串锚定，并在批量插入后统一复查缩进漂移
