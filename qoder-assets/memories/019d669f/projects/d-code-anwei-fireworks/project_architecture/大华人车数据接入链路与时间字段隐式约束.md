大华（DaHua）人车数据接入 prod 的链路与隐式约束（任务中经代码与数据库双向核实）：
- 接收入口在 monkey-monitor-api 的 DeviceRecordController，路由为 /record/upload/dh/personInout 与 /record/upload/dh/carInout；业务落库逻辑集中在 monkey-monitor 模块的 DaHuaService，入参 DTO 为 PersonInOutRecordDh / CarInOutRecordDh；采集端代码不在独立仓库，而是同一仓库 D:\code\anwei-fireworks 的分支 fireworks-dhsdk-local（路径 src/main/java/com/netsdk/...，含 module/handler/EventHandler.java 与 util/HttpUtils.java）。
- 隐式不变量：DaHuaService 对人员进出事件做"事件时间晚于当前服务器时间即丢弃"的校验，且丢弃后接口仍返回成功——任何采集端对 eventDate 做时区/偏移处理都会静默丢数，排查"无报错但无记录"必须优先核对时间字段。
- 设备匹配依赖 devSno + companyCode 双条件（表 em_gate_device_info，device_code 存设备序列号，如 CB0415CPAJ356DB）；车辆记录的 status 字段在采集端语义是"成功/失败"，prod 侧按"进出方向"解析，两端语义不一致会造成方向全部判为进入。
- 车牌由定长字节数组转换而来，尾部 NUL 未清理会写入 em_car_in_out_info.license_plate_number（表现为 byte 长度大于 char 长度），影响后续车牌匹配与省平台推送。
- 山东方向推送是另一条独立链路（platform/push/sd/PushingSDDataService、SetSDUploadInfo），与"设备→采集→prod 入库"问题不要混为一因。
