## Task description
- Core requirement: 确认火警处置页（views/eiot/firewatch/alarm-order/index.vue）在前端项目里到底被哪些位置引用，验证用户"应该只有大屏右侧实时告警点击那一处"的假设。
- Task background: 该页面是误报确认/处置留档功能的主改动点，回归测试必须先弄清真实入口有哪些；项目里有 large-screen、duty-screen、alarm-screen、monitoring-center、dashboard 五个含告警列表的大屏类页面，容易混淆。

## Execution process
1. 全 src 扫描组件 import：仅 src/router/modules/remaining.ts 一处静态注册隐藏路由 /eiot/firewatch/alarm-order（name FireWatchAlarmOrder, hidden: true），注释写明供大屏/值守大屏跳转，静态注册故直接输 URL 也可进入。
2. 用带引号的路径字符串 '/eiot/firewatch/alarm-order' 精确搜跳转点，实际 router.push 只有 4 处、分布在 3 个页面：monitoring-center 快捷操作「火警处置」；alarm-screen 左侧待办任务卡片"更多 >"；dashboard 的实时告警项点击（带 ?id=）与快捷操作两处。
3. 发现 dashboard 自身的路由注册块在 remaining.ts 已被整块注释，代码内也无其它引用，判定为大概率不可达的遗留页面（是否仍在后端菜单表需查库确认）。
4. 逐个核实各大屏右侧实时告警点击的真实行为，均不跳该页面：duty-screen 点击开弹窗，弹窗"去处置"跳 /remote-console 或 /video-surveillance；monitoring-center 点击开详情对话框；large-screen 实时告警卡片在左侧面板且纯展示无点击；alarm-screen 顶部"详情 »"跳报警记录页。
5. 区分噪音：firewatch.api.ts 的 13 个接口路径常量、页面自身与 alarm-record、large-screen 的接口调用字符串都是后端路径而非页面引用。
6. 顺带核实两个后端缺失接口：large-screen 调用的 /alarm-order/list 与 alarm-record 调用的 /alarm-order/export 在 FireAlarmOrderController 中不存在（只有 /export-pdf）；前者走静默请求长期无声失败，后者有前端 CSV 兜底。

## Notes
- 判断"某页面被谁引用"必须分三层：组件 import（路由注册）、带引号的运行时路径字符串（真实跳转点）、同名字符串的接口路径常量（噪音）；只看第一层会漏掉全部入口，只看字符串会把 API 常量误当跳转。
- 存在跳转代码不等于可达：目标页自身路由若被注释，残留跳转是死链，需回查路由注册状态。
