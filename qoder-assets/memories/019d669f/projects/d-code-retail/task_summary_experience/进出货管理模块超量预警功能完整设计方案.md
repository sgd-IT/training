## Task description
- Core requirement: design a complete solution for the '进出货管理模块超量预警' feature, covering how alerts are generated, notified, disposed of, and closed.
- Task background: The system already has `OverStorageDetectionService.checkAndAlert()` which creates `AlarmRecord` on inventory overage, but currently lacks notifications, has no synchronous `RiskWarningRecord` generation, and relies on an unimplemented scheduled task for risk escalation. The goal is to define a robust, production-ready workflow.

## Execution process
1. Diagnosed current state: confirmed `checkAndAlert()` calculates overage deterministically and inserts `AlarmRecord`, but does not trigger any notifications or create `RiskWarningRecord`.
2. Identified existing infrastructure: `ruoyi-common-push` (WebSocket/SSE), `ruoyi-common-sms`, `VoiceBroadcastService`, and `retail_config` table with push-enabled switches are all available and ready to use.
3. Defined notification strategy: prioritize voice broadcast (in-store) first, then station-wide SSE/WebSocket push; SMS only if configured and paid for.
4. Defined sync/async boundary: keep detection + alarm insertion synchronous within the transaction, but move all notifications to async execution via `@TransactionalEventListener(AFTER_COMMIT)` and `@Async` to prevent blocking the core business flow.
5. Defined disposition and closure logic: human disposition workflow is already in place (start处置 → submit feedback); automatic closure (`autoCloseResolvedAlarms`) exists but has three critical gaps: it can override ongoing human disposition, doesn't upgrade alarm levels on worsening conditions, and doesn't prevent duplicate alarms during active disposal.
6. Proposed resolution for gaps: a) allow parallel alarms for escalating severity, b) add level-upgrade logic on subsequent overage detections, c) restrict automatic closure to only alarms with `disposalStatus=0` (not yet started).
7. Highlighted critical missing piece: `RiskWarningRecord` table has no write source — requires either synchronous creation in `checkAndAlert()` or a new scheduled task.

## Corrections（2026-08-28 最终实施，以下条目 cover 上文旧建议）
- 通知渠道最终决定：仅 Web 站内推送（SSE）。语音播报不接（无设备测试）、短信不做。移动端仅以 payload.data 结构预留（notificationType/alarmNo/retailId/currentWeight/approvedWeight/ratio）。
- 落库+推送一体：用 `MessageService.publishMessage(userIds, payload)`（SysMessageServiceImpl 实现）替代裸 PushHelper——自动落库 sys_message + SSE 弹窗 + 铃铛(#icon-message)可见 + 点击跳转 /alarm。
- 收件人：sys_user.retail_id 字段（用户已加列）→ 新增 UserService.selectUserIdsByRetailId。无关联用户时跳过不广播（用户拍板"不兜底"）。
- 异步实现：弃用 @TransactionalEventListener+@Async，改用 TransactionSynchronizationManager.registerSynchronization(afterCommit) 内联 lambda（更少文件、同等效果）。
- 防重复：只看 alarmStatus=0（处置中不新增报警，但每次进出货仍超量会再推一次通知=策略B"操作即提醒"）。
- 等级恶化升级、RiskWarningRecord 同步生成：均不做（用户拍板）。fireworks_risk_warning_record 保持死表。
- 阈值 over_storage_level1/2/3 默认值(1.00/1.50/2.00)与代码百分比语义不符：用户拍板"阈值目前只做展示作用"，不修。
- 前端改动：push.ts 弹窗 type 读 payload.data?.notificationType（warning 橙/success 绿）。
