# 并发与锁

> 跨项目技术专题。定位：先判"要互斥 / 要降频扩容 / 要绝对不重复"三件事，再选手段，不要一见并发就上分布式锁。

## 本地锁 vs 分布式锁 · 2026-10-27
> 项目：跨项目专题（起因：消防远程值守大屏 Broken pipe 排查后的并发认知梳理）
### 【一句话区分】
本地锁锁的是"本 JVM 里的线程"，分布式锁锁的是"连到同一个协调中心的所有实例"；前者没有网络开销，后者没有进程边界。
### 【对比】
| 维度 | 本地锁 | 分布式锁 |
|---|---|---|
| 实现 | synchronized / ReentrantLock / Semaphore / StampedLock | Redis `SET NX EX`、Redisson、ZooKeeper 临时顺序节点、MySQL 唯一索引或行锁 |
| 生效范围 | 单个 JVM 进程内的线程 | 所有连到同一协调中心的实例，跨机器、可跨语言 |
| 典型用途 | 缓存击穿时只放一个线程回源、线程间防脏写、内存态去重窗口 | 多实例抢同一资源、防止多实例同时消费同一条 MQ 消息、多机同时缓存击穿只放一个实例回源、抢票抢券类活动 |
| 优点 | 零依赖、无网络开销、开销纳秒级 | 跨实例、跨语言 |
| 缺点 | 多实例部署即失效（每个实例各锁各的） | 强依赖中间件、一次加锁多跳网络、代码复杂度高（续期 / 误删 / 可重入 / 降级） |
| 失败代价 | 锁不住 → 并发重复执行，通常靠 DB 兜底 | 协调中心不可用 → 全链路阻塞，必须预先设计降级 |
### 【分布式锁四个必备条件】
1. 互斥：`SET key value NX PX ttl` 一条命令原子完成，不要 `SETNX` 之后再 `EXPIRE`；
2. 防死锁：必须带 TTL；业务耗时不可预估时要续期（Redisson 看门狗默认 30 秒、每 1/3 周期续一次）；
3. 锁归属：value 写唯一标识（UUID + 线程 ID），释放时先比对是不是自己的；
4. 原子释放：比对 + 删除必须 Lua 一次执行，否则"查完发现是自己的 → 期间锁过期被抢走 → 删掉别人的锁"。
### 【坑】
- `SETNX` 后再 `EXPIRE`：两条命令之间宕机 → key 永不过期 → 死锁。
- 直接 `DEL` 释放：锁已超时被他人获取 → 误删别人的锁 → 两个线程同时进入临界区。
- 业务耗时 > 锁 TTL：A 的锁过期、B 拿到锁，A 算完若无条件写库 → 照样并发写。锁只买来互斥窗口，落库还得幂等兜底（唯一索引 / 条件更新 / 版本号）。
- Redis 主从异步复制：主节点加锁成功、未同步即宕机 → 从库升主后锁丢失，同一把锁被两人持有。RedLock 本身有争议，工程上的正解是业务层兜底，而不是把锁做到绝对可靠。
- 本地锁用在集群：`synchronized` 在 3 个实例上等于 3 把锁，防不住重复执行；服务从单实例扩到多实例前，必须回头把每一处本地锁重新判断一遍。
### 【什么时候不该上分布式锁】
- DB 条件更新能解决：`UPDATE ... WHERE status = 0` 命中 1 行才算抢到，天然原子且少一次网络往返；
- 唯一索引能解决：让 DB 报冲突，比"先查 + 加锁 + 再插"简单；
- 幂等 + 重试能解决：MQ 消费端天生可能重复投递，做幂等（消息 ID / 状态机）比做互斥更贴合语义；
- 单实例的缓存击穿：本地锁 + 双重检查就够，上分布式锁只是多付一次 RTT。
### 【项目实例对照】
- 告警去重内存窗口：本地 `putIfAbsent` + CAS 刷新，单实例够用；跨实例正确性交给 DB 唯一索引（见 03-踩坑手册"告警去重"条）。
- 编号生成 Redis INCR：不是锁问题，是"自增基线放在缓存"的持久化问题，重启归零得靠落库 MAX+1 或启动预热（见 03-踩坑手册"缓存自增编号"条）。
- 反控码 Redis TTL：刻意不加锁——同租户两端读同一个 key、过期才换，语义是"有人看着给码"，加锁只会让生成变慢（见 01-项目/消防远程值守系统.md 2026-10-23 条）。
- 大屏 Broken pipe：多块大屏同时轮询属于"排队与容量"问题，不是互斥问题，加本地锁或分布式锁只会让请求等更久；解法是降轮询频率、按浏览器 6 个同域连接核算轮询组数（见 01-项目/消防远程值守系统.md 2026-10-27 条）。
### 【面试追问】
- 为什么不用 ReentrantLock 而用 synchronized？→ 只要互斥、不需要可中断 / 超时 / 公平策略时，synchronized 更轻且不用手工释放；
- Redisson 看门狗怎么知道业务有没有结束？→ 它不知道，锁持有期间定时续期，业务线程正常结束才停；所以必须在 finally 里停续期，否则锁永不释放；
- 分布式锁能保证消息不被重复消费吗？→ 只能保证"同一时刻一个消费者"，消费成功锁就释放，重复投递仍会再消费一次，幂等才是根本解。
