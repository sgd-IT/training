# 踩坑手册

> 纯结论，按技术栈分区。每条四行：问题 → 根因 → 触发条件 → 做法；只记会再犯的坑。

## 后端（Java / Spring）

### 新旧语义切换（level → alarm_kind）

- 问题：定稿写"删除 info 回退分支"，执行时发现删不得。
- 根因：旧回退出口 mapLevel 对 '4'/'5' 产 'info'，是 31,563 条存量数据的唯一解释通道。
- 触发条件：改等级/类型代码时看到"旧字段回退分支"，或按类型字段做数据分布统计 = 先怀疑语义漂移。
- 做法：删回退分支前逐处核实数据源形态；切换用"行级判据（新字段 IS NULL = 旧）+ 读侧先于写侧原子切换 + 消费点清单每步对账"分层推进。

### MQTT 客户端（Paho v3）

- 问题：断线重连后订阅丢失收不到消息；回调里做业务偶发断线；多线程 publish 死锁。
- 根因：自动重连不恢复业务订阅；回调线程内异常/阻塞被 paho 判为连接故障；并发 publish 无同步保护。
- 触发条件：设备显示在线但收不到指令、重连后消息丢失、回调里偶发断连 = 先查订阅是不是放在 connectComplete。
- 做法：订阅动作放 connectComplete 回调（勿放 @Bean 初始化）；业务处理下沉 Spring Bean + 全量 try-catch（非 Bean 回调类用静态容器取 Bean）；publish 加 synchronized + waitForCompletion 超时；messageArrived 的 topic 已被 broker 展开，来源识别需自实现通配符匹配。

### 告警去重（内存窗口）

- 问题：持续告警在 5 分钟窗口边界判重失准，同一告警反复入库。
- 根因：get 判断与 put 刷新是两步操作，中间有竞态；三参 replace 的返回值未校验，两个线程同时通过窗口检查时都会落库。
- 触发条件：同一告警反复入库、恰好卡在窗口边界、并发量上来后判重失效 = 先查是不是先 get 后 put，以及 CAS 返回值有没有处理。
- 做法：putIfAbsent 原子占位 + 非重复时才 CAS 刷新；CAS 失败按重复处理（`if (!replace(...)) return null`）；强一致场景用 DB 唯一索引或分布式锁兜底，内存缓存只做第一层。

### 设备在线状态判定

- 问题：UDP 组件 60 秒无上报就判离线，大华终端 1 小时一报，设备长期显示离线。
- 根因：超时阈值与设备上报周期不匹配；组件内存会话表与统一检查任务形成双份状态源。
- 触发条件：设备"长期离线"但日志有上报、离线率异常偏高、协议组件里出现超时清理定时器 = 先核对上报周期与阈值。
- 做法：阈值 = 上报周期 × 2（留一轮容错）；协议组件只记活跃时间，判定交给 DeviceStateCheckTask；删掉组件内的内存会话表与周期清理。

### 状态口径 Java / SQL 双实现

- 问题：告警列表按 orderStatus 筛选的数量与统计数字对不上。
- 根因：Java 解析与 SQL CASE 各写一套、更新不同步；文本细节匹配用了全文 contains，早期处置记录误命中。
- 触发条件：列表筛选数量和统计卡片对不上、同一单不同页面状态不一致 = 先查 Java 与 SQL 是不是两套口径。
- 做法：SQL CASE 片段作为常量放在解析器里，Java 与 SQL 同源修改；文本推断只取末段（lastIndexOf('[')）；优先级固定为权威字段 > 兼容字段 > 兜底。

### 第三方 OpenAPI 契约对接（严格 schema）

- 问题：上报字段"看起来都在"，平台仍返回 500 或参数错误。
- 根因：实体直接序列化会把前端展示字段、审计字段、子表对象一并带上，平台按严格 schema 校验，多字段即拒绝；部分枚举字段按票型区分取值（如 level 仅动火/盲板/高处/吊装四类合法）。
- 触发条件：首次联调第三方接口报 500、同一实体既要给前端又要给平台、实体加字段后老接口突然报错 = 先看报文有没有多余字段。
- 做法：对接层按平台文档白名单重建报文（逐字段 set 或统一清理非平台字段），实体只做内部承载；枚举字段先查文档再决定传不传；HTTP 200 必须再判业务 code。

### 无幂等键的外部接口重试

- 问题：请求超时后重试，平台出现两条相同数据。
- 根因：把"结果不明"当成"确定失败"处理，重试前没有确认对方是否已落库。
- 触发条件：外部接口无幂等键、失败提示是超时/连接中断/SocketTimeout = 一律按"结果不明"处理，不能自动重试。
- 做法：同步状态分成功/失败/结果不明三态；调用前置"不确定"标记，只有平台明确返回失败才降级为失败；结果不明只能人工对账；入口用条件更新占位（UPDATE 命中 1 行才继续）防并发提交。

### 缓存自增编号（Redis INCR）

- 问题：服务重启后当日编号从 0001 重新开始，出现重号。
- 根因：自增基线在缓存不在库，Redis 重启或 key 过期都会让序号归零。
- 触发条件：编号规则是"前缀 + 日期 + 序号"、序号来自 Redis INCR、重启后当天出现重复单号 = 就是这个坑。
- 做法：编号落库 MAX+1 并加锁，或启动时用库内当日最大序号预热 key；无论选哪种，代码里都要留兜底注释写明切换方案。

### 时间字段双重语义

- 问题：改任务派送时间，逾期统计跟着变坏。
- 根因：一个时间字段同时承担"何时下发"和"何时算逾期"两个语义。
- 触发条件：改派送/提醒时间后报表逾期数异常、同一个时间字段在两处被不同方式计算 = 先查语义是否被复用。
- 做法：派送时刻与逾期基准拆成两个字段/两个口径；同一业务动作的多个时间语义分别命名，不共用一列。

### 含外部调用的定时任务整体提频

- 问题：为提升实时性把同步任务改成每分钟执行，平台接口压力与失败面成倍放大。
- 根因：本地状态校正与外部推送耦在同一个 @Scheduled 方法里，提频连带放大了远端调用。
- 触发条件：想靠调 cron 提升实时性时 = 先看这个方法里有没有调外部 API。
- 做法：按"是否调外部"拆任务，只提本地任务频率；外部推送保持原节奏 + 未同步扫描补偿；状态联动顺序固定为"先下游任务、再主体状态"，中断后下一轮可自愈。

### AOP 注解依赖代理调用（自调用 / @Scheduled / @Async）

- 问题：定时任务方法标了 @TenantIgnore 想跑全量数据，实际仍按租户过滤，任务线程报“租户 ID 不能为空”或统计恒为空；同一个类里 this.xxx() 调用带注解方法、@Async 方法被自调用时，注解同样静默失效，编译与启动都不报错。
- 根因：@TenantIgnore / @Transactional / @Async 都靠 AOP 代理生效，前提是这次调用经过代理对象；this 自调用不经过代理，@Scheduled 的调用目标是 Bean 后处理阶段拿到的那个对象（可能是代理，也可能不是原始目标对象）——官方 issue SPR-13914 记录了这一长期不确定性（2026-10 关闭为 invalid，未认定为缺陷）。已逐版比对 Spring 6.0.23 / 6.1.0 / 6.2.1 的 ScheduledAnnotationBeanPostProcessor，同一段逻辑三版一致，不存在“6.1 起才绕过代理”的版本分界，别按版本号下结论。
- 触发条件：定时任务/异步线程里要跨租户取数、日志出现“租户 ID 不能为空”或统计数字恒为 0；或看到同一个类里 this.xxx() 调用了带注解的方法 = 先确认这次调用有没有经过代理。
- 做法：定时任务一律用编程式上下文——全量用 TenantUtils.executeIgnoreWithResult(...)，指定租户用 TenantUtils.execute(tenantId, ...)，并把“为什么不用 @TenantIgnore”写进行内注释（参考 LogRetentionTask）；需要事务或异步时，把定时触发与业务逻辑拆到不同 Bean，由容器注入的依赖发起调用，让调用真正跨过代理；结论要下准就自己比对对应版本源码，别引用二手说法。

### 循环插入复用同一实体

- 问题：批量插入从第二条开始报主键冲突，或后一条覆盖前一条。
- 根因：MyBatis 插入后会回填生成的主键，同一实体对象在循环里反复用，第二轮带着上一轮的 ID 去 insert。
- 触发条件：一个实体在 for 循环里反复 insert、第一条成功第二条失败 = 先看有没有 setId(null)。
- 做法：每轮新建对象，或显式 `setId(null)` 再赋业务字段；能批量插入就不要循环单条插。

### 多套编码体系按序号推断

- 问题：内部类型 11-18 与第三方类型 1-8 映射错位，票型串票。
- 根因：两套编码顺序并不对应（12→4、14→2、18→3），按"11→1、12→2"的直觉写映射或加减偏移。
- 触发条件：对接方枚举也是数字、本地映射表看着"跳号" = 必须逐条对着文档核，不能算。
- 做法：用单个枚举承载全部维度（内部码、外部码、前缀、模板、名称），转换只走枚举方法，禁止在业务代码里做算术。

### 状态机校验读错对象

- 问题：状态流转的前置校验永远通过或永远不通过，重复操作拦不住。
- 根因：校验读的是方法内 new 出来的空对象字段，而不是查库得到的记录。
- 触发条件：校验分支写了但线上从不生效、重复提交没被拦 = 先看变量来自 new 还是 select。
- 做法：所有前置校验统一读查库对象；new 对象只用来承载待更新字段，不要拿它做判断。

### poi-tl 列表只渲染第一行

- 问题：Word 模板里表格的循环数据只输出一行。
- 根因：模板变量没有绑定行循环策略，poi-tl 按普通变量渲染，只取集合第一个元素。
- 触发条件：渲染结果行数比数据少、只有首行有值 = 先看 Configure 里有没有 bind。
- 做法：列表变量显式 `bind("变量名", new LoopRowTableRenderPolicy())`；图片用 `Pictures.ofUrl().size()` 指定尺寸，避免撑破版式。

### 循环内逐次查库（伪批量）

- 问题：列表/树接口慢，翻代码发现注释写着“避免 N+1”，实际还是循环里逐个查库。
- 根因：把租户/设备 ID 先 distinct 再在循环里单查，只是把“按行查”降成“按去重后的行查”，查询次数仍是 O(去重后条数)；单租户数据下表现正常，跨租户一页就白跑十几次。
- 触发条件：循环体内出现 getXxx / selectById / selectCount、接口耗时随页内租户数或设备数增长、同一段回填代码在多个 Controller 里重复 = 先数循环里有几次数据库往返。
- 做法：循环外收集 ID 集合，一次批量查（selectBatchIds / selectList(字段, 集合) / 项目已有的 getTenantMap），再在内存里 Map 回填；跨租户包 TenantUtils.executeIgnore*；验收只看调用次数是否 N→1。

### 逐条查询改批量收集（Collectors.toMap）

- 问题：把循环内单条查询改成 Map 批量收集，接口在某些账号下直接 500。
- 根因：Collectors.toMap 默认禁止重复 key（抛 IllegalStateException）且禁止 null value（NPE）；一页记录常是同一租户（重复 key），下游取值异常时 catch 返回 null。
- 触发条件：改批量收集后"个别账号 500、列表页打不开"= 先看收集前有没有 distinct、value 是否可能为 null。
- 做法：key 先 distinct；value 可能为 null 时不用 toMap，改 HashMap 手动 put；业务键不唯一时给 merge function `(a, b) -> a` 兜底。

### MyBatis-Plus 批量方法选错（selectBatchIds 只认主键）

- 问题：按业务键批量查产品，传 productKey 字符串给 selectBatchIds，不报错但一条都查不出来，页面关联列全部空白。
- 根因：selectBatchIds 拼的是 WHERE id IN (...)，字符串业务键被 MySQL 隐式转成 0，静默查空；方法名里的"Ids"只指主键。
- 触发条件：批量改造后"关联字段整列变空、不报错不抛异常"= 先核对批量方法按主键还是按业务键。
- 做法：按主键批量用 selectByIds / selectBatchIds；按业务字段批量用 BaseMapperX.selectList(SFunction, Collection)（即 WHERE 字段 IN）；批量改造验收看"调用次数是否 N→1"，不看方法名是否带 Batch。

### 缓存“读不到就生成”漏写回

- 问题：同一个接口每次调用返回不同的码，且过期时间恒等于当前时刻、倒计时永远是 0。
- 根因：生成分支只把新值赋给局部变量，没有 `set(key, value, ttl)` 写回；key 一直不存在，`getExpire` 返回 -2，按“当前时间 + 0 秒”算过期时刻。
- 触发条件：代码里出现 `if (cached == null) 生成` 的写法，且改完后没有连续请求两次比对返回值 = 先看生成分支后面有没有写回。
- 做法：生成后立即写回并设 TTL；验收标准是有效期内连续两次返回同一个值、TTL 递减。

### 增量编译的 BUILD SUCCESS 不可当验证结论

- 问题：接口新增抽象方法，实现类没实现，`mvn compile` 仍报 BUILD SUCCESS，直到运行时调用才抛 AbstractMethodError。
- 根因：实现类文件未变更，增量编译跳过它，javac 不会拿旧 class 去校验新接口；构建日志里没有 Compiling 行、耗时异常短。
- 触发条件：改了接口签名/新增方法后构建秒过 = 先确认目标类是否真的重编，而不是看 BUILD SUCCESS。
- 做法：比对 `target/classes` 的 class 时间戳是否晚于源码，或用 `javap -p` 确认新方法存在；拿不准就 clean 重编。

### 写响应阶段 Broken pipe 被计成假 500

- 问题：大屏接口红条报加载失败，错误日志里全是 `AsyncRequestNotUsableException: ServletOutputStream failed to write: Broken pipe`，同一接口另一些客户端却一切正常。
- 根因：客户端在响应写完前就断开（前端超时或连接被排队），后端业务已算完、写响应时才发现连接没了；GlobalExceptionHandler 对 Exception.class 兜底又会 log.error + 落错误日志 + 再写一次响应，把写失败记成假 500。
- 触发条件：堆栈有 writeWithMessageConverters 帧但没有业务帧、失败集中在单一出口 IP、duration 长到几百秒 = 先按 user_ip 横向对比，别急着改 SQL。
- 做法：按 result_code + user_ip 聚合访问日志定位单点；给全局异常处理器加 AsyncRequestNotUsableException / ClientAbortException 前置分支降噪；量化 SQL 只能取服务端慢日志或 APM（duration 含网络写出时间，不能反推 SQL）；同出口多终端轮询要按“浏览器 6 个同域连接”核算轮询组数。

### Semaphore 抢失败也 release 会让闸门失效

- 问题：限并发防击穿写了 tryAcquire + finally release，看上去没错，但开 3 个标签页同刷仍出现 3 个线程一起重建。
- 根因：`release()` 不校验调用方是否真持有许可（javadoc 明确 “There is no requirement that a thread that releases a permit must have acquired that permit”），抢失败的分支也执行 release 就会让可用许可越还越多，闸门形同虚设。
- 触发条件：用 Semaphore/信号量做并发上限时，并发数看起来没受控、或跑久了限流越来越弱 = 先查 release 是否被无条件调用。
- 做法：先声明 `boolean acquired = false`，tryAcquire 结果存进去，finally 里只有 `if (acquired)` 才 release；同理抢不到要用 tryAcquire 而不是 acquire，后者的阻塞排队会占满 Tomcat 工作线程。

### fastjson 整体反序列化缓存信封会静默丢字段

- 问题：缓存读出来字段全是 null，而时间戳字段却总是“刚刚”，新鲜度判断恒为 true，缓存过期了还在返旧数据，且全程不报错。
- 根因：把信封 `{"data":{业务对象},"buildAt":毫秒数}` 整体当成业务 VO 反序列化，业务字段名对不上全变 null；而 VO 里恰好有个同名 `buildAt`（LocalDateTime）与顶层毫秒数类型兼容，fastjson 直接把它当时间戳填成当前时间。
- 触发条件：缓存/消息体是“元信息 + 业务数据”两层结构时，直接 `parseObject(json, VO.class)` = 必查。
- 做法：分两步解——先 `JSONObject.parseObject(json)` 拿信封，再 `wrapper.getObject("data", VO.class)` 取业务对象、`wrapper.getLong("buildAt")` 取时间戳；写侧对称地 `put("data", 对象)` 不存字符串，避免双重序列化。

### 时间窗节流：减法方向与装配层级

- 问题：给设备状态写库加 5 分钟节流，上线后设备上下线状态再也不更新，而 Druid 里 UPDATE 次数断崖下降，看起来像优化大成功。
- 根因：三层叠在一起。① 时间差写成 `lastTime - now`，恒为负、永远小于正窗口，第二次起恒返回 false；② 外层又包了一层“状态没变才进”的 if（从别处“提前 return”的反向判据复制而来），内层却是“状态变了才写”，外层保证状态没变 → 内层第一个条件恒为 false，整块死分支；③ 删外层时把“状态变了”的豁免条件一起删掉，变成一律等 5 分钟，设备失联最多延迟一个窗口。
- 触发条件：监控里 SQL 执行数大幅下降但业务状态“冻住”、或某类操作看着成功却没效果 = 先做三值心算（首次无记录 / 窗口内 / 窗口外）和“消息类型 × 每层条件”推演表。
- 做法：减法一律“较晚时刻 - 较早时刻”；“状态真变化”必须用 `||` 短路绕过节流，不能只靠窗口；`put` 只能放放行分支（放开头等于每次重置计时）；节流必须包在真正产生目标 SQL 的调用点上（下游带 `NODE_TYPE_GATEWAY` 这类前置判断的方法会空转）；先修逻辑再接调用点，死代码里的缺陷不因无调用点而豁免。

### 保存成功 ≠ 异步生效（配置类接口）

- 问题：管理后台改组件配置，提示“修改成功”，实际组件根本没起来，只有服务端日志每 5 秒刷一条解析失败。
- 根因：接口只做了 validateExists + updateById 就返回 true；真正加载配置的是另一个 5 秒轮询的定时任务，解析失败只有一行 log.error，没有任何回传通道。
- 触发条件：配置/参数类保存接口的消费方是定时任务、MQ 消费者或其他异步链路 = 这个 true 只代表“写进库了”。
- 做法：能同步判断的（JSON 合法性、字段必填）前移到保存时校验并抛业务错误码；不能同步判断的（端口占用、连通性）把提示语改成“已保存，将在 N 秒内生效”，别写成“修改成功”；同一接口被两种意图复用时（改配置 / 切开关），新增校验必须对另一种意图放行——线上就有 config 为 NULL 的行，直接判 `isJson(null)` 会把“只想启停”的操作拦死。

## 前端（Vue / UniApp）

### RuoYi 前后端权限标识不一致

- 问题：功能开发完了，按钮不显示或点击 403。
- 根因：前端 v-hasPermi 与后端 @PreAuthorize 的权限串不一致；新菜单未在 sys_menu 授权给角色。
- 触发条件：按钮消失、接口 403、换账号就正常 = 先比对两处权限串与角色菜单授权。
- 做法：权限串以 sys_menu.perms 为准，前后端逐字复制；新增菜单同步授权给所有启用角色，不要只授给 admin。

### 轮询加载态闪烁（Loading Flicker / Spinner Flash）

- 问题：处置中心列表固定在 30 秒间隔整块蒙层闪一下；监控大屏的统计数字周期性先跳回假值再变回真值。
- 根因：定时器回调复用了用户动作的加载函数，把绑定 v-loading / 按钮 loading 的状态置 true；另一处是轮询每轮先铺 mock 兜底再回填接口数据。
- 触发条件：白色蒙层 / 骨架屏 / 刷新按钮转圈按固定周期重复出现，或数字“先旧后新”地跳一下 = 先查 setTimeout/setInterval 回调里有没有切 loading、有没有重置兜底数据。
- 做法：轮询只做静默刷新（加载函数加 silent 参数：不切 loading、失败不弹 toast，如 refreshAlarms(notify, silent)）；加载态只留给首屏、手动刷新和筛选翻页；mock 兜底只在首次铺；弹窗打开时暂停轮询。业界把这类现象叫 Loading Flicker（也叫 Spinner Flash、轮询闪烁），修复模式叫静默刷新 / stale-while-revalidate。

### 轮询只判 document.hidden 挡不住页面常驻与多表叠加

- 问题：值守大屏、监控中心开着过夜后，未处置告警接口每分钟固定 7 次，凌晨 3 点也不停，3 天累积 2 万多次。
- 根因：useVisiblePolling 只在 document.hidden 时清表；同一标签页内切路由（KeepAlive 缓存）时 document.hidden 仍为 false、组件的 onUnmounted 不触发，表照跑；而且每个页面各建各的表，页面开得越多表越多，多张表还会互相挤占浏览器同域的 6 个连接槽。
- 触发条件：同一接口每分钟出现整数倍的稳定次数、凌晨仍有固定频率调用、同时开着多个大屏/控制台标签页。
- 做法：按分钟聚合接口调用次数，“每分钟精确 N 次”直接对应 N 张轮询表，据此合并调度或降频；停表条件要覆盖路由离开（onDeactivated）与长时间无交互，不止 document.hidden。

## 数据库（MySQL / Redis）

### 存量数据迁移（alarm_kind 语义迁移）

- 问题：按 alarm_type 估算的迁移分布严重失真（估 29,797/92/1,674，实测 31,150/295/118）。
- 根因：同一事件存在两条写入链路两种编码（热成像 type=2/level="1" 29,347 条 + type=0/level="2" 922 条），摄像头类 level 为历史硬编码，类型字段不能代表真实语义。
- 做法：存量分布必须按原始业务名称逐项映射核验，禁止按类型字段批量分类。

### MyBatis 列别名与显式映射不一致

- 问题：库里查得出值，接口返回的对象属性却是 null，且不报错。
- 根因：resultMap 显式映射的 column 与 SQL 别名大小写/下划线不一致，MyBatis 静默跳过赋值。
- 触发条件：字段"明明有值"但接口返回 null、换个查询方法就正常 = 先对 resultMap 的 column 和 SQL 别名。
- 做法：别名与 resultMap 逐字对齐；要么全走 mapUnderscoreToCamelCase，要么全显式映射，不要两套混用。

### 缓存新鲜期与 Redis TTL 用同一个值，旧值兜底是死代码

- 问题：缓存实现了“过期用旧值兜底”，但上线后旧值分支一次都没走到，日志里只有命中与重建两种结局。
- 根因：数据新鲜期（比如 70 秒）和 Redis key 存活期（TTL）用了同一个常量，key 到点就被 Redis 自身删掉，“已过期但 key 还在”这个状态物理上不可能存在，stale 变量永远是 null。
- 触发条件：写 stale-while-revalidate / 旧值兜底 / 单飞重建这类缓存时，只要新鲜期与 TTL 同步 = 兜底分支必是死代码。
- 做法：拆两个常量——新鲜期决定“多久算旧”（对齐调用方轮询间隔），key 存活期必须严格大于新鲜期，多出来的那段才是旧值兜底窗口（如新鲜期 70 秒、TTL 300 秒）。

## 基础设施 / 部署

### Druid 过滤器参数配在 druid 下而非 dynamic.druid 下，不生效也不报错

- 问题：生产配了 `log-slow-sql: true`，但慢 SQL 日志从未输出，导致“单条 SQL 耗时”无法量化，线上排查只能拿访问日志 duration 推算。
- 根因：用的是 dynamic-datasource，真实数据源由 `DruidDataSourceCreator` 创建，它只在 `getFilters()` 非空时才挂 stat filter、参数取自 `getStat()`；而配置写在了 `spring.datasource.druid.filter.stat` 下，那是独立 Druid 自动配置的路径，多数据源不读。
- 触发条件：用 dynamic-datasource 且配了 Druid 慢 SQL / wall / 连接池参数，但数据源监控页有连接数却没慢 SQL 记录 = 先看参数挂在哪个前缀下。
- 做法：过滤器与连接池参数都写到 `spring.datasource.dynamic.druid` 下，并显式声明 `filters: stat`；wall 慎挂——它的 `multi-statement-allow` 等开关也要同步配在 dynamic.druid 下，否则可能拦掉现有多语句 SQL。另 `max-wait` 不要用默认的 600000（10 分钟）量级，连接池打满时请求会干等十分钟才失败。

### 接口调用量暴涨先分类流量来源再谈异常

- 问题：使用统计显示 7 天 18.4 万次接口调用、活跃用户只有 6 人，被当成“流量异常/被人刷接口”。
- 根因：统计口径只按 request_url 聚合，不区分人工操作、页面轮询、机器对机器轮询；排行榜 Top1 的 39% 是外部 Java 服务（Hutool UA、固定 IP、8 秒一次、24 小时曲线无波动）拉取命令，平均 0.01 秒、零 DB 压力。
- 触发条件：看到“调用次数远大于用户数”、排行榜被某个接口霸占第一、同一 URL 的小时分布毫无作息起伏。
- 做法：先按 request_url + user_agent + user_ip 聚合把流量分成人/机/页面三类；再按分钟聚合数轮询表数；最后按“调用量 × 平均耗时”排优先级，条数高但耗时≈0 的接口砍了负载几乎不变。

## 其他

### 精确替换连续失配多半是缩进失真

- 问题：用编辑器工具精确替换源码片段连续报“未匹配”，原文在带行号的读取输出里“看起来”完全一致；改用不含行首空白的子串才匹配上，替换后缩进还多了一层。
- 根因：带行号的读取输出会吃掉或压缩行首制表符，方法体实际是两个制表符时可能显示成零个或一个；拿显示结果当原文必然失配。另外当原文片段不含行首空白时，工具会保留原有前导空白再叠加新文本的空白，缩进直接翻倍。
- 触发条件：编辑以制表符缩进的源码、精确替换反复失配、或替换后代码缩进异常 = 先怀疑显示结果与真实字节不一致，别反复改文案重试。
- 做法：先用只读脚本按字节打印目标区域（node 读文件后 JSON.stringify 每行，制表符会显示成 \t），确认真实缩进与换行符后再写原文；原文必须自带完整行首制表符，不要只截行内子串；一次调用里把“修正缩进”和“插入新方法”拆成互不重叠的替换项，改完回读验证。

### Windows 终端读 UTF-8 源码中文乱码

- 问题：PowerShell 的 Get-Content 读 Java 源码，中文全是乱码；改用 node 打印同样乱码，一度以为文件内容被写坏。
- 根因：控制台代码页是 GBK/GB2312，与文件内容的 UTF-8 不匹配，是显示层问题不是文件问题；乱码只在终端回显时出现。
- 触发条件：用 Get-Content / cat 看中文源码，或在终端里打印中文内容时。
- 做法：判断文件是否损坏不要看终端回显，改用 IDE 的读取工具；确需终端核对，先设 [Console]::OutputEncoding=[Text.Encoding]::UTF8 再输出。

### better-harness 的 observed=0 是数据缺失，不是真没用

- 问题：harness checkup 报 37 个 skill 全部 unobserved、cleanupEligible=false，看起来像"这些资产全白建了"。
- 根因：Qoder 会话归档在 2026-09-11 后不再落本地（transcripts 最新只到 9/11，globalStorage/aicoding-agent 下只有空 schedule 目录），会话源 eligibleSessions=0 < minimumSessions=5，observed 恒为 0。
- 触发条件：想用 better-harness 判断"哪些 skill/MCP 该删"、或看到 unobserved 要下结论时。
- 做法：unobserved 只当"无证据"，不当"未使用"；要对账得先显式授权读被禁的 cache-project-session / global-project-jsonl 源，或改用 memory 侧证 + transcript 扫描这种土办法。

### better-harness 重跑时 --canvas-out 指向已存在文件会废掉 lead lane

- 问题：第二次带同一个 --canvas-out 跑 evidence-bundle，bundle.status=failed，lead 报 CANVAS_OUTPUT_EXISTS。
- 根因：canvas.json 已存在时 lead-analyzer 拒绝覆盖，整条 lead lane 直接不可用，连带 normal 模式判定失败。
- 触发条件：同一 run-dir 下重复采证、或上一轮中断留下 canvas.json。
- 做法：每次采证用新的 run-dir；重跑前先删旧 canvas.json；projectHarness lane unavailable 时按 skill 规则停手，别硬凑报告。

### PowerShell 5.1 的 > 重定向写 UTF-16LE+BOM

- 问题：`node xxx.mjs > out.json` 之后 JSON.parse 报 Unexpected token '锟'。
- 根因：Windows PowerShell 5.1 的 > 默认 UTF-16LE 带 BOM，非 UTF-8。
- 触发条件：把 CLI 的 JSON 输出重定向到文件再解析时。
- 做法：先接进变量，再用 `[IO.File]::WriteAllText(path, ($out -join "`n"), (New-Object System.Text.UTF8Encoding($false)))` 落盘。
