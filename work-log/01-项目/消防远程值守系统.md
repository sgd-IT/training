## AOP 代理边界与定时任务的租户上下文 · 2026-10-30
> 项目：消防远程值守系统
### 【类型】
技术债 / 架构
### 【背景】
做大屏统计缓存预热时踩到一类坑的通用形态：定时任务方法上挂 @TenantIgnore 想跑全量数据，实际仍按租户过滤，任务线程报“租户 ID 不能为空”或统计恒为空。顺着这条线回查，意识到它不是“一个注解写错”，而是一整类根因：@TenantIgnore / @Transactional / @Async 全都靠 AOP 代理生效，前提是这次调用经过代理对象。项目里这三种误用同时存在——FirewatchScheduledTask 在 @Scheduled 方法上同时挂了 @TenantIgnore 与 @Transactional；AepCallbackServiceImpl、CallRecordPushServiceImpl、TenantEventListener 在 @Async 方法上挂 @TenantIgnore；DeviceInfoServiceImpl#getUnbindPage 用 this.getDeviceInfoPage(...) 自调用。
### 【方案】
把结论从“某个注解不生效”升级为“代理边界”这条通用规则，并用源码核实而非二手结论定事实：
1. 核实 @Scheduled 的调用目标。逐版比对 Spring 6.0.23 / 6.1.0 / 6.2.1 的 ScheduledAnnotationBeanPostProcessor 源码，postProcessAfterInitialization 三个版本完全一致：都用 AopProxyUtils.ultimateTargetClass 取目标类做注解扫描，但真正被调用的 bean 是 Bean 后处理阶段拿到的那个对象（可能是代理，也可能不是原始目标对象），官方 issue SPR-13914 记录了这一长期不确定性（2026-10 关闭为 invalid，未认定为缺陷）。项目实际版本是 Spring Boot 3.4.1 / Spring Framework 6.2.1。
2. 修正一处错误版本断言。原踩坑条目写的是“Spring 6.1+ 的 @Scheduled 直接在目标对象上调用、绕过代理”，源码比对证明 6.0.23 与 6.1.0、6.2.1 该段逻辑一致，并不存在 6.1 的行为分界，这个版本号结论必须改掉——按版本号下结论本身就是这类问题最常见的传播方式。
3. 落成两条稳妥做法：定时触发与业务逻辑拆到不同 Bean（定时方法只负责触发，业务方法放到被注入的依赖 Bean 上，保证调用从外部进入、跨过代理）；或在定时任务里用编程式上下文显式开关租户状态——全量走 TenantUtils.executeIgnoreWithResult(...)，指定租户走 TenantUtils.execute(tenantId, ...)，后者内部做的是“保存旧值 → 置位 → 执行 → finally 还原”，等价于手写 TenantContextHolder.setIgnore 的安全版。
4. 选定项目口径：以编程式上下文为准（LogRetentionTask 已有先例，注释里写明了“为什么不用 @TenantIgnore”）；注解只保留在由 Controller / 事件监听等外部入口触发的路径上。
### 【我的角色】
独立负责：根因抽象、跨版本源码核实、错误版本断言的修正、项目口径收敛
### 【结果】
把一条具体踩坑升级为一条可复用的通用规则（注解生效前提 = 调用经过代理对象），并在三个版本源码上验证、修正了一处错误版本断言。盘点出项目内 3 类同源用法（定时任务上的 @TenantIgnore + @Transactional、@Async 方法上的 @TenantIgnore、this 自调用），逐条给出改造方向。代码侧未改动，本条为规则沉淀与事实校正。
### 【踩坑 & 根因】
① 错误版本断言：“Spring 6.1+ 绕过代理”是二手结论，比对 6.0.23 / 6.1.0 / 6.2.1 源码后证伪——真正的不确定性在于调用拿到的是不是代理对象，与版本号无关；② 把“注解不生效”当成单点 bug 修，只改了 @TenantIgnore 却放过同样依赖代理的 @Transactional 与 @Async；③ 只记“加注解就行”而不说清调用路径，跨 Bean 注入调用与 this 自调用的差别才是判据。
### 【可复用结论】
AOP 注解（@TenantIgnore / @Transactional / @Async）生效的前提是“经过代理对象调用”——外部注入的依赖调用可以，this 自调用与 @Scheduled 触发都不保证；定时任务里凡涉及租户或登录态，一律用编程式上下文显式开关，不依赖方法上的注解；需要事务或异步时，把触发与业务逻辑拆到不同 Bean；给这类结论定版本事实时必须自己比对对应版本源码，别引用二手说法。

## 大屏统计缓存预热与活跃租户判定 · 2026-10-30
> 项目：消防远程值守系统
### 【类型】
性能优化 / 架构
### 【背景】
防击穿改造上线后仍有反馈：从管理后台回到大屏要等一段时间，且“在后台待 5 分钟以上”才明显。排查发现两个事实叠在一起：① 前端轮询走 useVisiblePolling，页面切后台或跳走路由就停表，缓存失去唯一的续期来源；② key 存活期正好 300 秒，到点被 Redis 删除，而 staleData 是请求内的局部变量、不是持久兜底，此刻为 null，旧值兜底彻底失效，返回时必须同步跑十几条聚合。结论：上一轮只做了防击穿，没做保活。
### 【方案】
1. 活跃租户用 Redis ZSet 判定：成员是缓存 key 的视角后缀（租户 id 或 all），分值是最后访问的毫秒时间戳；请求侧每次访问写一次，预热侧只读不写。选 ZSet 是因为要按“最近 N 分钟”取集合并定期清理窗口外成员——Set 无成员级 TTL，String 得自己维护过期表。
2. 活跃窗口取 30 分钟而不是 5 分钟：痛点是“离开超过 5 分钟”，窗口若等于 key 存活期会与原问题完全重合，等于白做。
3. 拆 loadStatisticsCached：把“解析登录租户”与“重建 + 写缓存”解耦，抽出 getOrRebuildStatistics(生效租户)，请求侧与预热侧共用同一段缓存逻辑，租户 id 由调用方给定。
4. 预热任务用 @Scheduled(fixedDelay = 60s)：fixedDelay 而非 fixedRate，避免预热超时任务堆积；周期必须小于新鲜期 70 秒。
5. 预热入口按租户分支建上下文：null（全量视角）走 TenantUtils.executeIgnoreWithResult，非 null 走 TenantUtils.execute(租户, buildStatistics)，两条路都显式建上下文、不依赖注解。
### 【我的角色】
独立负责：根因定位（缓存空窗与前端停表的时间线对齐）、判定方案选型、缓存逻辑拆分、定时任务实现与多轮编译评审
### 【结果】
生产库实测支撑选型：system_tenant 共 9 个租户（全部正常），近 2 天该接口只有 4 个租户在调（平台租户 7,053 次 / 均值 4.7s，租户 178 共 61 次 / 646ms），据此判定“按活跃预热”优于“全部租户预热”。完成活跃集合 key、缓存逻辑拆分、接口预热入口、@Scheduled 任务四处改造，module-eiot-biz 全量重编 585 文件通过。当前状态：最后一轮改动把日志放到 try 块外引用块内变量，编译未过，尚未联调与提交。
### 【踩坑 & 根因】
① @TenantIgnore 标在 @Scheduled 方法上不生效——它靠 @Around 切面，而 Spring 6.1+ 的定时任务在目标对象上直接调用、绕过代理；② 预热路径复用请求侧的 executeWithTenantAware 会丢租户——该方法先取登录租户，登录租户为 null 时直接返回 null、根本走不到 override 分支，于是任务线程算成全量并写进某个租户 key，形成串租户；③ 预热周期 ≥ 新鲜期会让预热空转（60s 周期 + 70s 新鲜期 = 实际两轮才重建一次，刷新节奏变 120 秒）；④ 预热侧若回写活跃时间会自我续命，窗口永远滑动、租户永不退出；⑤ 活跃集合与统计缓存是两个 key 形态（ZSet 单 key 存 member vs String 拼后缀），混用会留下 active-tenants:{id} 脏 key 且按前缀扫会撞 WRONGTYPE。
### 【可复用结论】
缓存 TTL 要按“用户离开时长”设计，不能只按“数据新鲜度”：TTL 与业务停顿时长对齐时，返回即冷启动；旧值兜底若只是方法内局部变量，key 一消失就无值可兜。定时任务里凡涉及租户/登录态，一律用编程式上下文，不依赖方法上的 AOP 注解。预热周期必须小于缓存新鲜期，否则预热与请求的过期判定互相打架。

## 设备状态写库节流与失联通知耦合 · 2026-10-29
> 项目：消防远程值守系统
### 【类型】
性能优化 / 并发
### 【背景】
Druid 监控显示 `UPDATE eiot_device_info SET state, online_time` 在 15 小时窗口跑 1,862 次（2.0 次/分）、最慢 391ms、并发 3。逐层拆开发现单次“状态刷新”不是一次 UPDATE，而是 1 写 + 最多 2 查：updateDeviceState 先 UPDATE，紧接着 getDeviceInfo 回查整台设备（该方法无 @Cacheable，必回库）只为取 productKey/dn 清缓存；方法上 @CacheEvict 又清掉 Redis 设备缓存，使下一条消息的 getDeviceInfoFromCache 必然穿透回库。设备每 30 秒一条心跳，等于每 30 秒付 3 笔 DB 访问，其中真正有信息量的不到 10%。
### 【方案】
按设备做时间窗节流，窗口 5 分钟，用 `ConcurrentHashMap<deviceId, 上次放行时间戳>` 记账；判断式为 `状态真变了 || 已过窗口`。
1. 只节流冗余写，不节流状态变化。判据复用已有的 `device.isOnline() != state.isOnline()`（缓存记的 vs 报文说的），左边成立直接短路，不问窗口。
2. put 只能放在放行分支。提到方法开头等于每次调用都重置计时，节流永不生效且不报错。
3. 选 ConcurrentHashMap 不选 HashMap：多个 messageHandler 线程并发写；不加过期清理，键上限就是设备表行数（5,092 台不到 250KB）。
### 【我的角色】
独立负责：链路拆解、节流方案设计、多轮代码评审与缺陷定位
### 【结果】
UPDATE 预期 2.0 次/分 → 0.2 次/分，连带省掉 90% 的回查 SELECT 与缓存穿透。代码已通过编译与逐场景推演，未上线，待用“执行次数 ÷ 窗口分钟数”做硬验收。
### 【踩坑 & 根因】
这一条改造过程中连续踩了四种形变，全部编译通过、日志正常：① 减法方向写反（`lastTime - now` 恒为负，第二次起恒返回 false）—— 接线上线即设备状态全线冻结，而 Druid 里 UPDATE 次数断崖下降，看起来像优化大成功；② 外层多包一层“状态没变”的 if（从别处“提前 return”的反向判据复制而来），内层却是“状态变了才写”，外层保证状态没变 → 内层第一个条件恒为 false，整块死分支；③ 节流装到 updateSubDeviceState 上，而该方法首行判 `NODE_TYPE_GATEWAY`，非网关设备空转，目标 UPDATE 发源点在节流块外 → 净收益为零还引入子设备延迟；④ 删外层 if 时把“状态变了”的豁免条件一起删了，变成“不管变没变一律等 5 分钟” → 设备失联最多延迟一个窗口。最后查明：设备失联通知走的是同一条写库路径——DeviceStateCheckTask 判超时后组一条 `type=state, identifier=offline` 的消息投 MQ，被同一个 handle() 接收，所以作用在这个写库点上的任何节流条件都直接决定界面离线显示的延迟，不只是心跳的冗余写。
### 【可复用结论】
时间差判断一律写“较晚时刻 - 较早时刻”，落地前做三值心算（首次无记录 / 窗口内 / 窗口外 → true/false/true）；双层嵌套条件要做语义一致性检查，外层门卫与内层放行互为取反时整块是死分支，只能靠“每种消息类型 × 每层结果”的推演表发现；节流收口前必须确认被包住的调用点下游真的产生目标 SQL；先修逻辑再接调用点，死代码里的缺陷不因无调用点而豁免；验收看执行速率而不是最慢耗时。

## 组件配置保存的校验与提示闭环 · 2026-10-29
> 项目：消防远程值守系统
### 【类型】
功能开发 / 技术债
### 【背景】
管理后台“组件配置”页面保存后提示“修改成功”，但后端 updateComponent 只做 validateExists + updateById 就返回 true——它做不到判断组件能不能用这份配置跑起来。组件是 5 秒后异步轮询才 parseObject + stopServer + startServer，解析失败只有一行 log.error，界面完全无感：用户以为改好了，实际组件没起来，还会每 5 秒刷一条错误日志。
### 【方案】
按“能同步判断的保存时就拦，不能同步判断的提示语别撒谎”分两层：
1. 后端保存前用 JsonUtils.isJson 校验 JSON 合法性，不合法抛新增的 COMPONENT_CONFIG_INVALID（2_007_002_001），文案“组件配置不是合法的 JSON 格式，请检查括号与引号”。
2. 前端成功提示由“修改成功”改为“配置已保存，组件将在几秒内重新加载”；状态开关那处保持“修改成功”，因为启停是立即生效的动作。
3. 明确不做：端口占用、字段名写错这类“JSON 合法但语义错”拦不住，一个请求里拿不到启动结果，要补得上“组件加载结果回写”，成本高一个量级，单独排期。
### 【我的角色】
独立负责：问题定位、校验方案与提示语设计、前后端落地与编译验证
### 【结果】
非法 JSON 在保存时即被拦下、库不会被写坏；失败文案可读并能指导下一步动作。后端 `mvn -pl module-eiot/module-eiot-biz -am compile` BUILD SUCCESS。
### 【踩坑 & 根因】
状态开关（handleStatusChange 传整行）走的是同一个 /eiot/component/update 接口，线上 type='udp' 那条的 config 是 NULL。如果直接判 `JsonUtils.isJson(null)` 返回 false → 用户只想启停组件却被提示“配置格式不对”，且再也启不起来。所以必须先 `StrUtil.isNotEmpty` 判空再判 JSON，顺序不能反。
### 【可复用结论】
保存类接口返回 true 只代表“写进库了”，不代表“上下游已生效”；能同步判断的校验必须前移到保存时，不能等异步消费方发现；同一个接口被两种意图（改配置 / 切开关）复用时，新增校验必须对另一种意图放行。

## 大屏统计缓存防击穿与配置排错 · 2026-10-28
> 项目：消防远程值守系统
### 【类型】
性能优化 / 架构 / 故障排查
### 【背景】
dashboard/statistics 单次串行跑十几条聚合 SQL，平均 3.22 秒。前端 30 秒轮询、多块大屏同时开着，缓存过期那一瞬间多个请求同时重建，把 Druid 连接池（max-active 20）打满；同时 Broken pipe 被全局兜底记成假 500 污染错误日志；想量化单条 SQL 耗时，才发现慢 SQL 日志从来没生效过。
### 【方案】
围绕三个目标：缓存要真命中、重建要限并发、失败要能兜底。

1. 双时间窗拆两个常量。新鲜期 70 秒（前端 30 秒轮询，能盖住 30/60 两个轮询点）；Redis key 存活期 300 秒（旧值兜底窗口）。原实现两者共用同一个 70 秒常量——key 到点被 Redis 自己删掉，"过期但 key 还在"这个状态物理上不可能存在，旧值兜底写了等于没写。
2. 并发闸门用 JVM 内 Semaphore(2) + tryAcquire 非阻塞。抢不到立刻返回旧值，不用 acquire 排队（排队线程一直占着 Tomcat 工作线程，几个大屏同刷就能把线程池占满，连告警处置接口一起进不来）。finally 里按 `isWinner` 标志位才 release——Semaphore javadoc 明确 release 不校验调用方是否真持有，抢失败也还会让 permits 虚增。
3. 缓存信封结构 `{"data":{业务对象},"buildAt":毫秒时间戳}`，data 直接放对象不先转 JSON 字符串（放字符串会双重序列化，读的时候要反着解两层）。
4. 重建与写缓存拆成两个 try-catch：重建失败返回旧值（没算出来只能给老的）；写缓存失败照样返回新数据（统计已经算对了，只是没存住）。原实现共用一个 catch，写缓存失败也掉进去返旧值，白扔刚算出来的数据。
5. Broken pipe 降噪：GlobalExceptionHandler 加 `isClientDisconnect` 前置分支，识别 `AsyncRequestNotUsableException` 与 Broken pipe / Connection reset 根因；命中后只记 info，不写 infra_api_error_log、不再写响应（写了必然再抛一次）。
6. Druid 慢 SQL 配置排错：反编译 `DruidDataSourceCreator` 确认 `initFilters` 只在 `getFilters()` 非空时才挂 stat filter，stat 参数取自 `getStat()`。而生产把 `log-slow-sql` 配在 `spring.datasource.druid.filter.stat` 下——那是独立 Druid 自动配置，真实数据源由 dynamic-datasource 创建，这段配置从未生效。改为挂在 `spring.datasource.dynamic.druid` 下 + 显式 `filters: stat`。只挂 stat 不挂 wall：wall 会拦 SQL，而它的 `multi-statement-allow` 没配在 dynamic.druid 下，挂上去可能拦掉现有多语句 SQL，属于引入回归。
7. `max-wait` 600000（10 分钟）→ 30000。连接池打满时请求干等十分钟才失败，是线上最长 8034 秒的机制来源之一。
8. 分段耗时打点 `timed()`：统计的 12 个分段各自计时，超 500ms 单独 warn。因为访问日志 duration 含响应写出时间，反推不出 SQL 耗时，只能自己埋点。
9. 前端红条自愈 + 统计接口独立 12 秒超时。原红条只增不减（`loadErrors` 只 push 不清除），一次抖动就永久挂着；缩短该接口超时是为了早失败早释放浏览器同域 6 个连接槽。
### 【我的角色】
独立负责：缓存方案设计与实现、并发闸门选型、Druid 配置排错取证、前端降级策略
### 【结果】
缓存命中后不再打 DB；缓存过期瞬间最多 2 个线程重建，其余请求毫秒级拿旧值返回，不再打穿连接池。Broken pipe 不再产生假 500 与错误日志污染。修正一个从未生效的配置——慢 SQL 日志此前从未输出，导致"单条 SQL 耗时"无法量化（此前只能用访问日志 duration 猜测，而那含响应写出时间）。`max-wait` 从 10 分钟降到 30 秒，连接池打满时快速失败走降级而非干等。
### 【踩坑 & 根因】
① 新鲜期与 Redis TTL 用同一个常量 → key 到点被删，"过期但 key 还在"不存在，旧值兜底永远不触发；② Semaphore 抢失败也 release → permits 虚增、闸门形同虚设；③ 整个 json 当 VO 反序列化 → fastjson 不报错，业务字段全 null，而顶层 buildAt 因类型兼容被当毫秒时间戳自动填成当前时间，于是"永远判定新鲜"，缓存过期照样返旧数据；④ 重建直接调 `buildStatistics()` 不走 `executeWithTenantAware` → 丢租户上下文，企业租户可能看到全部租户数据；⑤ Druid 过滤器配置位置错 → dynamic-datasource 不读 `spring.datasource.druid.filter.stat`。
### 【可复用结论】
数据新鲜度和 key 存活期是两个概念，必须拆两个常量，否则旧值兜底是死代码；限流器的 release 不校验持有关系，必须用标志位严格控制；缓存信封与业务对象要分层解析，整体反序列化在 fastjson 下会静默出错（比抛异常更难查）；用 dynamic-datasource 时，Druid 过滤器与连接池参数都得配在 `spring.datasource.dynamic.druid` 下；写缓存失败不能和重建失败共用一个 catch，前者该返新数据。

## 线上接口调用量异常的流量归因 · 2026-10-28
> 项目：消防远程值守系统
### 【类型】
故障排查 / 性能优化 / 技术债
### 【背景】
线上"使用统计"页面显示近 7 天接口调用总量 184,163 次、日均 26,309 次，而活跃用户只有 6 人——"4 个用户 10 万次调用"看着像异常流量。本地自测时页面停留时间短、开的页面少，从未暴露过这个量级。目标是查清这 10 万次由谁发起、值不值得治、该先治哪个。
### 【方案】
分三层归因：先按"谁在发"给流量分类，再用"定时器签名"数出同时在跑几张轮询表，最后用"条数 × 耗时"重排优化优先级。

1. 流量分类（人 / 机 / 页面轮询）。按 request_url + user_agent + user_ip 聚合 prod 库 infra_api_access_log（2026-10-26 起 3 天，TOP15 合计 67,842 次）。`/eiot/remote-console/valve/command/7` 26,318 次全部来自单一 IP 219.131.130.21，UA 为 `Mozilla/5.0 ... 2. 定时器签名：数出同时在跑几张轮询表。`/alert/recentUnprocessedAlerts` 按分钟聚合，10-27 03:00~03:10 连续 10 分钟每分钟精确 7 次，深夜不间断。7 = 7 个页面实例各挂一条 60 秒轮询表（duty-screen / remote-console 用 useVisiblePolling 60s、monitoring-center 用裸 setInterval 60s、alarm-order 30s 等），各页面各建各的表，没有全局共享调度。已有 useVisiblePolling 只在 document.hidden 时停表——同一标签页内切路由（KeepAlive 缓存）时 document.hidden 仍为 false、组件 onUnmounted 不触发，表照跑；页面开着过夜就是 24 小时不停。10-27 17:00~20:00 掉到 61~133 次/小时、21:00 又回到 420 次/小时，是那台机器的浏览器被关掉又重开的曲线。
3. 压力权重：条数 ≠ 压力。valve/command 26,318 次、平均 0.01 秒、零 DB 压力；dashboard/statistics 仅 9,893 次，但成功请求平均 3.22 秒，单次串行跑十几条聚合查询。按条数排序优化，第一名砍掉服务器负载几乎不变，真正的痛点排第三。
4. 慢 → 堆积 → 假 500 的连锁。dashboard/statistics 26 条 500 平均 729 秒，getDeviceWithProperty 1 条 500 耗时 7,948 秒（2.2 小时），recentUnprocessedAlerts 1 条 500 耗时 1,477 秒。浏览器 HTTP/1.1 同域只有 6 个连接槽，7 张轮询表 + 慢接口互相排队 → 前端 axios 30 秒超时先断 → Broken pipe → 全局异常兜底记成假 500，与 10-27 的定责结论同源。
5. 口径与交互层：数字本身还有两处放大器。一是口径，统计的是"接口调用次数"，不区分人工操作、页面轮询、机器轮询，机器流量挂在同一出口 IP 下还会被算进某个账号；二是交互，时间范围改完不点"查询"页面不会重查，截图里日期已选 10-26~10-28，而趋势图与总量仍是 10-22~10-28 的 7 天数据（实测 3 天 67,842 次 vs 近 7 天 192,405 次），"10 万次"是被 7 天口径放大出来的观感。
### 【我的角色】
独立负责：prod 库只读取证 + 三层归因方法设计 + 优化优先级重排
### 【结果】
把"10 万次调用"拆成三类流量并各自定性：机器轮询 26,318 次（占 TOP15 的 39%，平均 0.01 秒、零压力）、页面轮询约 4 万次（7 张表 × 60 秒，深夜不间断）、真实人工操作不足 8%。拿到可量化的诊断指标——"每分钟精确 7 次"就是同时在跑的轮询表数量，可直接作为降频与压测基线。纠正了优化排序：按条数排会把零压力的 valve/command 顶到第一，按"条数 × 耗时"排才是 dashboard/statistics 优先。同时定位"10 万次"观感的两处放大器：统计口径不分类 + 时间筛选需手动点查询。
### 【踩坑 & 根因】
① 把接口调用量当"功能使用热度"→ 机器轮询与页面轮询全被计入，"4 人 10 万次"看着像流量异常；② 归因只看条数不看发出方 → 把 @PermitAll 的外部服务轮询当成前端问题；③ 只查单个接口不数并发表数 → 以为是"某个页面轮询太频繁"，实际是 7 张表叠加；④ 拿访问日志 duration 当压力 → duration 覆盖整个请求生命周期（含响应写出与排队），max 2.2 小时不是 SQL 耗时。
### 【可复用结论】
"接口调用次数"要拆成人工操作 / 页面轮询 / 机器对机器三类再谈异常，判据是 UA + 来源 IP + 小时分布的规整度；数轮询组数最快的办法是按分钟聚合，"每分钟精确 N 次"就是 N 张表在跑；定时器只判 document.hidden 不够，同标签页内切路由（KeepAlive）和页面开着过夜都会让它一直跑；给线上压力定责要用"调用量 × 平均耗时"，高频轻量接口砍了负载几乎不变。

## 值守大屏接口 Broken pipe 定责 · 2026-10-27
> 项目：消防远程值守系统
### 【类型】
故障排查
### 【背景】
值守大屏顶部红条持续报"接口加载失败: /eiot/firewatch/dashboard/statistics"。现场是多块大屏同时开启、一起轮询同一套后端服务，错误日志里刷的是 `AsyncRequestNotUsableException: ServletOutputStream failed to write: Broken pipe`，直觉容易判成后端 bug 或慢 SQL。
### 【方案】
分四步定责，先不动 SQL：
1. 按 result_code + user_ip 聚合 infra_api_access_log：近 7 天成功 27393 次（均 3 秒），失败 51 次（均 261 秒、最长 8034 秒），失败集中单一出口 IP 219.131.130.21，同接口其他 20+ IP 均值仅 1 秒。
2. 按 exception_name 分类 infra_api_error_log：全部是 Broken pipe，无 SQLSyntaxErrorException → 排除缺表缺列与权限成因。
3. 读堆栈分帧：栈顶是 writeWithMessageConverters → Jackson flush → ServletOutputStream.write，全链无 Controller/Service/Mapper 帧 → 业务已算完，断在写响应这一步。
4. 统计同一 IP 各接口调用量：valve/command 74962 次（约 8.6 秒一次）、recentUnprocessedAlerts 58342 次（10 秒）、dashboard/statistics 26999 次（26 秒）等共 5 组独立轮询；浏览器 HTTP/1.1 同域只有 6 个并发连接，排队超过前端 axios 30 秒超时即被掐断。
结论：多块大屏同时开启 → 5 组轮询挤占同一个出口的 6 个连接槽 → 请求排队超时 → 客户端先断、后端再写 → Broken pipe。服务端 buildStatistics 串行十几条聚合是放大耗时的真实隐患，但不是本次主因。
### 【我的角色】
独立负责：线上日志取证 + 堆栈解读 + 根因分层 + 定责顺序设计
### 【结果】
把"慢 SQL / 缺索引"的错误定性纠正为"客户端并发排队为主因、链路集中于单一出口 IP"；撤回改 SQL + 建索引的无收益动作；明确唯一有日志证据支撑的改动是给 GlobalExceptionHandler 增加 AsyncRequestNotUsableException / ClientAbortException 前置分支，消除假 500 与错误日志污染。
### 【踩坑 & 根因】
① 拿访问日志 duration 当 SQL 耗时 → duration 覆盖整个请求生命周期（业务处理 + 响应体写出 + 网络阻塞），客户端慢时全部计入，最长 8034 秒其实与 SQL 无关；② GlobalExceptionHandler 对 Exception.class 兜底会 log.error + 落错误日志 + 再返回一次响应（必然再失败）→ 写失败被记成假 500，污染错误日志；③ 想用 `SET GLOBAL long_query_time=1` 降阈值取慢 SQL 被拒（ERROR 1227 需 SUPER），且 log_output=FILE 时 mysql.slow_log 恒 0 行、performance_schema 摘要表为空，阈值只能走云控制台参数设置。
### 【可复用结论】
线上"接口慢/报错"先按来源 IP 横向对比，失败集中于单一出口时优先怀疑那处的并发与链路，而不是服务端全局缺陷；访问日志 duration 不能当 SQL 耗时，量化单条 SQL 只能取服务端慢日志或 APM；同一出口多终端跑多组轮询时，浏览器 6 个同域连接会被互相排队，轮询组数与频率本身就是容量项。并发问题先分清"要互斥"还是"要降频扩容"——本地锁/分布式锁只解决互斥，排队型问题加锁只会让等待更长。
### 【关联】
只读取证：prod MCP 查 infra_api_access_log / infra_api_error_log；code：FireDashboardServiceImpl#buildStatistics、framework GlobalExceptionHandler#defaultExceptionHandler、vue alarm-screen/index.vue（axios timeout 30 秒）

## 列表接口租户名回填的 N+1 体检 · 2026-10-20
> 项目：消防远程值守系统
### 【类型】
性能优化 / 技术债
### 【背景】
上一轮修完告警列表的 N+1 后回扫同类写法，发现设备、空间、摄像头、远程控制台四条列表链路都在做同一件事：把租户 ID 去重后，循环里逐个 `tenantService.getTenant(id)` 取企业名。注释都写着“避免 N+1 查询”，实际只是把“按行查”降成了“按租户查”——页内企业不重复时一页仍是十几次单表查询；摄像头树与远程控制台是把全量数据按企业分组，企业越多查得越多。
### 【方案】
1. 模式识别：判断标准不是“有没有循环”，而是“循环体内有没有数据库往返”；去重只压低了系数，查询次数仍是 O(去重后条数)。
2. 用现成能力收敛：TenantService 已有 `getTenantMap(Collection<Long>)`（内部 selectBatchIds，一条 IN 查询），同仓 UserController 的分页与导出早就在用；四条链路统一改成“收集 tenantIds → 一次 getTenantMap → 内存回填”。
3. 租户上下文：跨租户取名要包 `TenantUtils.executeIgnoreWithResult`，与原来的 executeIgnore 语义一致，否则系统租户查不到企业数据。
4. 容错取舍：原来的 try-catch 是逐条吞异常；改批量后不再吞——租户名只是展示字段，但批量查询走的是同一个库，真出异常时主列表本来也查不出来，继续吞只会把问题藏起来。
### 【我的角色】
参与：同类模式全仓体检 + 定位 5 处同构实现 + 给出统一改法并落地
### 【结果】

## 自动排班锚点轮换 · 2026-10-19
> 项目：消防远程值守系统
### 【类型】
逻辑设计 / 功能开发
### 【背景】
24 小时值班制要求每天 1 条全天班（08:00 → 次日 08:00），值班人员按名单轮换。原实现用"当月第几天"对人数取模，31 天月份的次月 1 号会连排同一人（31 % 2 = 1，1 % 2 = 1）；同时每天一次 selectCount 判断是否已有排班，重复执行会重复生成。
### 【方案】
- 轮换基准改为绝对天数 epochDay，与月份天数解耦；
- 锚点轮换：取该单位"日期最大的一条全天班"（含未来月份）作为锚点，`floorMod(anchorIndex + (date - anchorDate), size)` 全局推算，先排哪个月结果都一致；
- 锚点人已不在本次名单（调岗、导入没填用户 ID）时锚点作废，从名单第 1 位重新起头；
- 名单 `distinct` 保序去重：重复 ID 会让轮换序列错位，同一人被连排；
- 已有排班按日期区间一次查出 Set，循环内跳过，替代原来的每日一次 count 查询；
- 只排明天及以后（今天和过去不生成），排未来月份时从月初开始。
### 【我的角色】
独立负责：规则设计 + 实现 + 边界验证
### 【结果】
单条改动 +66/-36；月边界连排消除；重复执行幂等（已有日期不重复生成）；排班查询从 N 次（每天一次 count）降为 2 次（锚点 + 已有日期）；2 人隔日交替、3 人上 1 休 2 均验证通过。
### 【踩坑 & 根因】
① 取模基准用"当月第几天"→ 每月天数不同，跨月必然错位 → 周期性轮换的基准必须是绝对时间；② 锚点不能取"最后插入的一条"→ 先排未来月份再排当月时，锚点会指向未来，导致序列回跳 → 必须取"日期最大"；③ 名单不去重 → 重复 ID 占两个位置，轮换序列整体偏移。
### 【可复用结论】
周期性轮换的取模基准要用绝对时间（epochDay），不要用"当期第几个"；需要"先算哪一段结果都一致"时，用持久化锚点 + 日期差取模，而不是每次从起点重数；批量生成前先把"已存在的日期"一次查成 Set，避免循环内查库。

## 告警去重时间戳竞态 · 2026-10-14
> 项目：消防远程值守系统
### 【类型】
故障排查 / 技术债
### 【背景】
告警统一落库前按 dedupKey（deviceId:alarmType:sourceType）做 5 分钟窗口去重。持续告警（设备反复上报同一事件）在窗口边界出现时间戳被刷新、判重失准的问题；同时代码里并存两套判断：putIfAbsent 组合和基于 get + remove 的 isDuplicate 方法。
### 【方案】
- 用 `ConcurrentHashMap.putIfAbsent(key, now)` 原子占位：同 key 并发只有一个线程拿到 null（首次）；
- 把时间戳刷新收敛进"判定为非重复"分支，用三参 `replace(key, old, now)` 做 CAS 刷新；
- 删除基于 get + remove 的 `isDuplicate` 方法，判定只保留一套。
### 【我的角色】
独立负责：根因定位 + 修复 + 并发边界复核
### 【结果】
单文件 +2/-18；判定逻辑从两套收敛为一套；窗口内重复告警不再入库。
### 【踩坑 & 根因】
① `get` 判断再 `put` 是两步操作，中间存在竞态，必须用 putIfAbsent 原子占位；② `replace` 的返回值没校验——两个线程同时读到过期时间戳时都会通过窗口检查，CAS 只有一个成功，另一个仍会继续落库，当前去重是"尽力而为"而非强一致；③ 同一件事留两套判断，后改的一处迟早与另一处打架。
### 【可复用结论】
缓存去重要"原子占位 + CAS 刷新"一体，不要先 get 再判断；CAS 失败要当重复处理（`if (!replace(...)) return null`），否则窗口边界会漏；内存缓存只做第一层，强一致要 DB 唯一索引或分布式锁兜底。
### 【关联】
code：AlarmRecordService#saveAlarm、buildDedupKey；git：f3dfa8e
