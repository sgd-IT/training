## AOP 代理边界：注解生效的前提是“经过代理对象调用” · 2026-10-30
> 项目：消防远程值守系统｜角色：独立负责
- **技术维度**：后端深度（框架原理 / 多租户上下文）
- **场景与规模**：多租户框架（Spring Boot 3.4.1 / Spring Framework 6.2.1）的 @TenantIgnore 走 AOP 切面；项目内同时存在 3 类同源用法——定时任务方法上挂 @TenantIgnore + @Transactional、@Async 方法上挂 @TenantIgnore、this 自调用
- **我做了什么**：把一条具体踩坑（定时任务想跑全量数据却仍被租户过滤、报“租户 ID 不能为空”）升级为一条通用规则：@TenantIgnore / @Transactional / @Async 都靠 AOP 代理生效，前提是这次调用经过代理对象；据此给出两条稳妥做法——定时触发与业务逻辑拆到不同 Bean，或在定时任务里用编程式上下文显式开关租户状态（全量走 TenantUtils.executeIgnoreWithResult，指定租户走 TenantUtils.execute，内部即“保存旧值→置位→执行→finally 还原”）
- **难点与解决**：原结论写的是“Spring 6.1+ 的 @Scheduled 绕过代理”，我逐版比对 Spring 6.0.23 / 6.1.0 / 6.2.1 的 ScheduledAnnotationBeanPostProcessor 源码，三版 postProcessAfterInitialization 完全一致（都用 AopProxyUtils.ultimateTargetClass 扫注解，被调用的是 Bean 后处理阶段拿到的那个对象），并不存在 6.1 的行为分界 → 推翻自己的版本号结论，改为“不确定的是调用拿到的是不是代理，与版本无关”（官方 issue SPR-13914 记录了该长期不确定性，2026-10 关闭为 invalid）
- **结果**：一条具体坑升级为可复用的通用规则 + 一处错误版本断言被证伪并修正；盘点出 3 类同源用法并逐条给出改造方向。代码侧未改动，属规则沉淀与事实校正
- **追问与答案**：① 为什么 @Scheduled 上的 @TenantIgnore 不生效？→ 注解由 AOP 切面实现，@Scheduled 触发时的调用目标是 Bean 后处理阶段拿到的对象，未必是代理，所以切面可能压根不参与；② 那为什么不干脆把 @Scheduled 方法改成非代理类？→ 定时任务本质是反射调用目标对象，代理与否取决于容器组装顺序，不该由业务代码赌这一点；③ 为什么不用 AopContext.currentProxy() 强行拿代理？→ 它只能救“类内自调用”场景，且会把隐式依赖变成显式耦合；定时任务场景直接用编程式上下文更直白；④ 你怎么确定“Spring 6.1+ 绕过代理”是错的？→ 拉三个版本的 ScheduledAnnotationBeanPostProcessor 源码对比 postProcessAfterInitialization，完全一致，没有 6.1 分界；这类结论不比对源码不敢上简历；⑤ 这条规则怎么迁移到事务上？→ 同理：@Transactional 挂在 this 自调用的方法上同样不生效，判定标准都是“这次调用有没有跨过代理”
- **技能**：Java / Spring AOP / Spring Boot / 多租户上下文 / 源码溯源

## 设备状态写库节流与失联通知耦合 · 2026-10-29
> 项目：消防远程值守系统｜角色：独立负责
- **技术维度**：后端深度（并发限流 / 线上排查）
- **场景与规模**：5,092 台设备、每 30 秒一条心跳；单条 UPDATE 背后是 1 写 + 2 查（回查无 @Cacheable + 清缓存致下一条穿透）；15 小时窗口 1,862 次 UPDATE、2.0 次/分、最慢 391ms
- **我做了什么**：按设备做 5 分钟时间窗节流（ConcurrentHashMap 记账），判断式写成“状态真变了 || 已过窗口”，让状态变化用 `||` 短路绕过节流、只有冗余心跳才排队
- **难点与解决**：改造中连续出现四种“编译通过、日志正常”的形变——减法方向写反（恒返回 false）、外层包了“状态没变”的 if 形成死分支、节流装到对非网关设备空转的下游方法上、删外层时把状态变化豁免一起删了；最后查明设备失联通知与心跳共用同一个写库点（定时任务组 offline 消息投 MQ → 同一个人 handle），所以节流条件直接决定离线显示延迟
- **结果**：UPDATE 预期 2.0 → 0.2 次/分，连带省 90% 回查 SELECT 与缓存穿透；代码已编译通过、逐场景推演过，尚未上线
- **追问与答案**：① 为什么不直接跳过“状态没变”的写库，而要节流？→ online_time 被消控室协助面板当“数据时间”展示，完全不写会让面板时间停住，值班员以为设备失联；② 为什么状态变化不能用节流？→ 设备掉线靠定时任务组 offline 消息、走同一个写库点，节流会把“失联 5 分钟后才变红”引入消防场景；③ 怎么验收这次没写坏？→ 用“执行次数 ÷ 窗口分钟数”（2.0→0.2）而不是最慢耗时，后者只证明单次快慢、证明不了没写坏；功能侧还得实测断电后多久变离线
- **技能**：Java / 并发控制 / 时间窗节流 / 线上监控排查

## 大屏统计缓存防击穿与 Druid 配置排错 · 2026-10-28
> 项目：消防远程值守系统｜角色：独立负责
- **技术维度**：后端深度（并发限流 / 缓存设计 / 配置排错）
- **场景与规模**：dashboard/statistics 单次串行十几条聚合 SQL、均 3.22 秒；前端 30 秒轮询，多块大屏同时开启；Druid max-active 20、max-wait 原本 600000（10 分钟）
- **我做了什么**：设计“双时间窗 + 非阻塞信号量 + 旧值兜底”三层缓存：新鲜期与 key 存活期拆成两个常量，Semaphore(2) + tryAcquire 限制重建并发、抢不到立即返旧值，重建与写缓存拆成两个 try-catch；同步排查 Druid 配置为何不生效
- **难点与解决**：缓存的旧值兜底分支一直不触发 → 新鲜期与 Redis TTL 共用同一个 70 秒常量，key 到点被 Redis 自己删掉，“已过期但 key 还在”物理上不可能存在；另发现慢 SQL 日志从未生效 → 反编译 `DruidDataSourceCreator` 确认 `initFilters` 只在 `getFilters()` 非空时才挂 stat，而配置写在了独立 Druid 自动配置的 `spring.datasource.druid` 路径下，dynamic-datasource 不读
- **结果**：缓存过期瞬间最多 2 个线程重建，其余请求毫秒级拿旧值返回，不再打穿连接池；Broken pipe 不再产生假 500 污染错误日志；修正一个从未生效的慢 SQL 日志配置（此前只能用含网络写出时间的 duration 猜测 SQL 耗时）；`max-wait` 从 10 分钟降到 30 秒，连接池打满时快速失败而非干等
- **追问与答案**：① 为什么不用项目已有的 Redisson 分布式锁？→ 实测生产是单实例（docker-compose 单 server 容器 + nginx 单 upstream），JVM 内信号量已能覆盖全部流量，分布式锁在这个场景是过度设计且多一条网络失败路径；扩容多副本后必须重评；② 为什么不用 acquire？→ acquire 拿不到会阻塞排队并一直占着 Tomcat 工作线程，几个大屏同刷就能把线程池占满、连告警处置接口一起进不来；tryAcquire 拿不到立刻降级，毫秒级返回；③ 为什么写缓存失败要返新数据而不是旧值？→ 重建失败是“没算出来”只能给旧的；写缓存失败时统计已经算对了、只是没存住，返旧值等于白扔刚算出的数据；④ 信号量为什么要用标志位控制 release？→ `release()` 不校验调用方是否真持有许可，抢失败也 release 会让 permits 虚增，闸门越跑越松
- **技能**：Java / Spring Boot / Redis 缓存设计 / 信号量并发控制 / Druid / 线上配置排错

## 线上接口调用量异常的流量归因 · 2026-10-28
> 项目：消防远程值守系统｜角色：独立负责
- **技术维度**：后端深度（线上排查 / 容量评估）
- **场景与规模**：线上“使用统计”显示 7 天接口调用 18.4 万次、活跃用户仅 6 人，实际只有 4 个真实用户、20+ 接口；单个请求最长耗时 2.2 小时；同一出口 IP 上跑着多块大屏
- **我做了什么**：按“流量分类 → 定时器签名 → 压力权重”三层归因：按 request_url + user_agent + user_ip 把流量拆成人/机/页面三类，按分钟聚合数出同时在跑的轮询表数量，再按“调用量 × 平均耗时”重排优化优先级
- **难点与解决**：Top1 的 26,318 次（占 39%）全部来自单一 IP + `Hutool` UA 的外部 Java 服务，8 秒一次、24 小时恒定、平均 0.01 秒 → 是机器对机器拉命令，不是人也不是浏览器；而真正的痛点 dashboard/statistics 只有 9,893 次，成功请求平均 3.22 秒、单次串行十几条聚合 → 按条数排会把该砍的第一名砍成零收益，真正该优化的排第三
- **结果**：10 万次调用拆成三类流量并各自定性（机器轮询 39%、页面轮询约 4 万次、人工操作不足 8%）；拿到“每分钟精确 7 次”这个可量化指标作为轮询组数基线；纠正优化排序，并定位“10 万次”观感的两处放大器（统计口径不分类机器流量 + 时间筛选需手动点查询导致 7 天数字被看成 3 天）
- **追问与答案**：① 怎么区分机器流量和真人操作？→ UA + 来源 IP + 小时分布规整度三重判据，外部服务 8 秒一次且 24 小时无波动，浏览器轮询会有人的作息起伏；② 怎么知道同时跑了几张轮询表？→ 按分钟聚合接口调用次数，“每分钟精确 N 次”就是 N 张表，深夜不间断更是页面常驻未关的证据；③ duration 2.2 小时能当 SQL 耗时吗？→ 不能，duration 覆盖业务处理 + 响应写出 + 排队，量化单条 SQL 只能查服务端慢日志或 APM；④ 为什么不直接扩连接池或加机器？→ 瓶颈不在吞吐而在重复发起，先合并调度降频、把慢接口的串行聚合改批量与缓存，扩容只会把同样多的无效请求放大
- **技能**：Java / Spring Boot / MySQL / 访问日志分析 / 容量评估 / Vue3

## 大屏接口 Broken pipe 定责与服务端假 500 降噪 · 2026-10-27
> 项目：消防远程值守系统｜角色：独立负责
- **技术维度**：后端深度（线上排查 / 并发）
- **场景与规模**：值守大屏 dashboard/statistics 偶发加载失败（红条）；近 7 天成功 27393 次（均 3 秒）、失败 51 次（均 261 秒、最长 8034 秒），涉及 20+ 来源 IP；本端多块大屏同时开启轮询同一套后端
- **我做了什么**：按“错误日志分类 → 堆栈分帧 → 访问日志按 IP 横向对比 → 同 IP 接口调用量分布”四步定责，把 AsyncRequestNotUsableException + Broken pipe 从“后端 bug / 慢 SQL”修正为客户端并发排队
- **难点与解决**：失败请求 duration 高达 8034 秒，看上去像慢 SQL → 但 duration 覆盖整个请求生命周期含响应写出与网络阻塞、同一接口其他 IP 均值仅 1 秒 → 定性为单出口 IP 上 5 组轮询挤占浏览器 6 个同域连接、排队超 30 秒被 axios timeout 掐断
- **结果**：51 次失败 100% 收敛到单一出口 IP；撤回无收益的改 SQL / 建索引动作；明确唯一有证据的改动是全局异常处理器增加 Broken pipe / ClientAbort 前置分支，杜绝假 500 污染错误日志
- **追问与答案**：① 怎么排除 SQL 慢？→ 错误日志无 SQLSyntaxErrorException、堆栈无 Mapper 帧、同接口其他 IP 均值 1 秒，三条独立证据；② duration 为什么不能当 SQL 耗时？→ 它覆盖业务处理 + 响应写出 + 网络阻塞，客户端慢时全部计入，要量化 SQL 只能查服务端慢日志或 APM；③ 为什么不用分布式锁或限流解决？→ 这是排队与容量问题，加锁只增加等待；正确方向是降轮询频率、按连接数核算轮询组数，或把串行聚合改批量与缓存
- **技能**：Java / Spring MVC / MySQL / 线上排查 / 日志分析

## 租户级动态反控码与 PC 二次验证 · 2026-10-23
> 项目：消防远程值守系统｜角色：独立负责
- **技术维度**：后端深度（安全设计 / 缓存一致性）+ 前端交付
- **场景与规模**：PC 端远程控制主机（消音/复位/启停），原二次确认密码为设备级静态明文、配一次长期有效；需改为动态码，由移动端查看、PC 端输入，覆盖移动端、远程控制台、管理后台三条取码/用码路径
- **我做了什么**：用 Redis 单 key + 5 分钟 TTL 承载租户级 6 位随机码，按登录用户租户而非上下文租户定位（避开跨租户切换改写）；下发前校验、校验失败不重新生成；PC 管理端查看要求重输登录密码，BCrypt 比对当前用户并兼容三方登录无本地密码；移动端接口用 user_type 平台位准入
- **难点与解决**：PC 端登录态可被借用，直接在控制台展示反控码等于没有二次验证 → 在取码接口再加一层“重新输入登录密码”，密码只走请求体、不落前端存储；两端读同一个 key 保证码一致
- **结果**：反控码从设备级长期静态改为租户级 5 分钟动态；PC-only token 无法调移动端接口取码；后端编译、移动端脚本、PC 端 vue-tsc 三层校验通过
- **追问与答案**：① 为什么不用 TOTP？→ TOTP 依赖两端时钟对齐，现场手机时间偏差会让码对不上；服务端存码 + TTL 更简单，授权语义是“有人看着给码”而非“算法对齐”；② 为什么按登录用户租户而不是设备租户？→ 反控码是操作方组织的授权凭证，跨租户监控设备时仍用自己租户的码，避免去对方租户取码；③ 二次验证为什么不用 authenticate？→ 那套会写登录日志、累加失败次数、触发锁定，语义是登录；这里只确认本人，用密码比对更轻，代价是没有失败限流
- **技能**：Java / Redis / Spring Security / 权限设计 / UniApp

## 告警列表慢查询诊断与 N+1 批量改造 · 2026-10-20
> 项目：消防远程值守系统｜角色：独立负责
- **技术维度**：后端深度（排查 / 性能）
- **场景与规模**：移动端告警中心列表加载慢；单租户（养老院）告警 1.4 万条占全表 15,779 条的 91%，其中 94% 待处理；接口 GET /eiot/firewatch/alarm-order/page
- **我做了什么**：按"前端接口 → 后端方法 → 线上索引/数据分布取证 → EXPLAIN → 组装段审查"五步定位；确认 SQL 命中索引且无 filesort 后，把主因修正到组装循环内的 N+1（每条 4 次单查、每页约 80 次），设计三级串行批量改造（deviceId→设备 Map→productKey→产品 Map→categoryId→分类 Map→内存回填）
- **难点与解决**：首轮判断"索引列序不优"被实测推翻 → deleted 全为 0 时列序收益趋零、生产 DDL 纯风险 → 撤回索引变更只改应用层；评审时拦下三处静默故障：toMap 重复 key 抛异常、null value 抛 NPE、selectBatchIds 传业务键按主键查空导致类型列全空
- **结果**：主因定性从数据库层修正到应用层；批量方案每页查询约 80 次降到 3~4 次（用户实施中，未跑通验证）；避免一次无收益的生产索引 DDL
- **追问与答案**：① 为什么一开始怀疑索引？→ 1.4 万条 + 单租户集中 + 历史上建议过加索引，先验证最便宜的假设；② EXPLAIN 里看什么判断不用改索引？→ type=ref 说明命中、Extra 无 Using filesort 说明排序由索引承担，rows 偏大是数据倾斜不是列序问题；③ 为什么 selectBatchIds 传 productKey 不报错？→ MP 拼 WHERE id IN ('业务键')，MySQL 隐式转 0，静默查空，页面表现为类型列全空
- **技能**：Java / MySQL / EXPLAIN 执行计划 / 性能优化 / MyBatis-Plus

## 园区监管平台 OpenAPI 对接层 · 2026-10-20
> 项目：hc-standard｜角色：独立负责
- **技术维度**：设计模式 / 逻辑设计
- **场景与规模**：本地安全生产平台作为被监管方，需按园区 20+ 类上报资源（作业票、风险单元、承包商、值班值守）对接；OpenAPI 客户端 24 个、platement 包 91 个类、8 类特殊作业票型
- **我做了什么**：拆两层——基类管传输与判定（HMAC-SHA256 签名、requireSuccess 业务码判定、createdId 兼容 data 两种形态、批量 10 条分批且任一批失败即返回），子类只管白名单报文（非平台字段清理、按票型移除非法 level、operatorInfo 分隔符转换、子表按文档字段重建）
