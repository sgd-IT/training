## 主题：`Collectors` 的**机制**，以及「什么时候不该用流」

### 一、★ groupingBy = 分类 + 「下游收集器」

| 写法 | 结果 |
|---|---|
| `groupingBy(分类函数)` | `Map<K, List<T>>`（默认每个桶是 `List`） |
| `groupingBy(分类函数, counting())` | `Map<K, Long>`（**Long，不是 Integer**） |
| `groupingBy(分类函数, mapping(f, toList()))` | 桶里放 `f` 的结果 |
| `groupingBy(分类函数, TreeMap::new, toList())` | 换掉 Map 实现 → 才有顺序 |

第二个参数叫**下游收集器**：它决定「一个桶里的东西怎么收」。

### 二、★★ partitioningBy 与 groupingBy 不是一回事

| | 空输入时的结果 |
|---|---|
| `partitioningBy(条件)` | `{false=[], true=[]}` —— **两个 key 永远都在** |
| `groupingBy(条件)` | `{}` —— 只出现实际存在的 key |

所以「按 true/false 分两堆」正确的是 `partitioningBy`。这一条是今天的主陷阱。

### 三、★★ toMap 的两个坑

1. **key 重复** → `IllegalStateException: Duplicate key`（要合并就传第三参数 `(a, b) -> b`）
2. **value 为 null** → `NullPointerException`（内部 `requireNonNull`，null 装不进）

`toMap` 是**一对一**的，撞了就当你代码有 bug，直接抛；不像 `groupingBy` 会塞进同一个桶。

### 四、★ Map 的类型与顺序

`groupingBy` 默认给 **`HashMap`**，遍历顺序不保证。要顺序只有两条路：

```java
groupingBy(f, TreeMap::new, toList())   // 归集时指定
new TreeMap<>(result)                   // 收完再转
```

### 五、★ 什么时候**不该**用流

| | 流 | 循环 |
|---|---|---|
| 可读性 | 「做什么」一眼看得出 | 「怎么做」要读细节 |
| 性能 | 有装箱 / 管道开销 | 基本类型循环最快 |
| 提前退出 / 改外部状态 | 别扭 | 自然（`break` / 累加） |

**简单累加、需要 `break`、要改循环外变量 → 用循环；筛选、转换、分组 → 用流。**

| # | 题 | 首答 | 结果 |
|---|---|---|---|
| ① | 为什么只有 `partitioningBy` 保证两个 key 都在？ | ✅「partitioningBy 固定用 boolean 做 key，桶的数量固定；groupingBy 是拿 key 找桶、没有就建」 | ✅ **一次过，自己组织的语言** |
