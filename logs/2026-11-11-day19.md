## 主题：读一遍就够的东西（面试真会问的 3 个点）

### 一、三种协议，同一套骨架

```
RESP（Redis）   *3\r\n$3\r\nSET\r\n$1\r\nk\r\n$1\r\nv\r\n    ← 文本，长度前缀是 ASCII 数字
MQTT            固定头(1) + 变长整数 + 负载                   ← 二进制
AMQP 帧         type(1) + channel(2) + size(4) + payload + 0xCE ← 二进制
```

共性只有三件事：**长度前缀、大端序、变长整数。**
（真实项目一律用客户端库：Lettuce / Jedis、RabbitMQ 客户端、MQTT 客户端 —— 这些字节细节你不需要自己写。）

### 二、★ 大端序（网络字节序）

```
0x12345678  →  12 34 56 78   高位字节先走（网络协议几乎全是大端）
0x12345678  →  78 56 34 12   小端序（x86 内存里就是这么放的）
```

### 三、★ `byte` 有符号 → `& 0xFF` 是唯一出路

```java
(byte) 0xFF          → -1
(int) (byte) 0xFF    → -1        // 符号扩展：高位全补 1
0xFF & 0xFF          → 255       // 先零扩到 int 再与
```

**这是今天唯一"值得带走"的知识点**，因为它在协议之外的场景反复出现：

| 场景 | 踩的坑 |
|---|---|
| MD5 / HMAC 转十六进制 | 不 mask 就出 `-1`，生成 hex 少一位 / 拼成 `ffffff…` |
| AES 加解密 | 密文 `byte[]` 里有 ≥ 0x80 的字节，直接转字符串变乱码 |
| 文件 / 图片读写 | `InputStream.read()` 返回 `int`，用之前要 `& 0xFF` |
| 拆包粘包 | 长度字段解析错，后面的全错位 |

### 四、★ 长度前缀算的是**字节数**，不是字符数

```java
"中".length()                 → 1     // 1 个 char
"中".getBytes(UTF_8).length   → 3     // 3 个字节
```

长度写 1、实际给 3 个字节 → 对端解析直接错位。

### 五、`>>` 与 `>>>` 对负数不同

```java
-1 >> 8    → -1           // 算术右移：左边补 1
-1 >>> 8   → 0x00FFFFFF   // 无符号右移：左边补 0
```

大端序写正数两者一样，写负数必须想清楚用哪个。

### 六、什么叫「变长整数」（只需读懂，不用写）

MQTT 用 1~4 字节表示长度（上限 268435455）：

```
每个字节：低 7 位是数据，bit7 = 「后面还有没有下一个字节」
127  → [0x7F]                塞得进 7 位，1 字节
128  → [0x80, 0x01]          低 7 位是 0 → 第一字节 0x80（续位=1）；剩下 1 → 0x01
```

## 练习过程

**2026-11-12 16:34** 学员口述 3 题（本日无代码）。

**① 大端序 vs 小端序**

学员答：「大端的高位字节先传输…小端的低位字节先传输…统一的原因是一开始就是用的大端序吧」

- 「谁先走」✅ 答对
- 「为什么统一」🟡 **循环论证** —— 真正的原因是：**跨平台互通必须有一个约定**（RFC 1700 定的 network byte order），
  而且大端在**十六进制 dump / 抓包里人眼可读**（数值书写顺序 = 字节顺序）。「一开始就是这么定的」是事实，不是理由。

**② `& 0xFF`**

学员答：「就是得到无符号的数」

- 只说了**结果**，没说**机制**：`byte` 是有符号的，转 `int` 会**符号扩展**（高位补 1），`& 0xFF` 把高 24 位清零。
- 🔴 **并且没给「协议之外的场景」** —— 这是题目里明确要求的，他跳过了。

教练实测（可直接拿去讲）：

```
byte b = (byte) 0xF3;                    // = -13
Integer.toHexString(b)          → fffffff3     ← 不 mask，摘要转 hex 直接爆长度
Integer.toHexString(b & 0xFF)   → f3           ← mask 之后才是 243
```

**③ `"中"` 的长度前缀**

学员答：「不清楚」❌

正解：`"中".length()` 是 **1**（一个 char），UTF-8 下占 **3 个字节**；
协议里的长度前缀一律是**字节数**，所以写 3。写 1 而实际给 3 个字节，对端会从错误的位置继续读 → **整体错位**。
