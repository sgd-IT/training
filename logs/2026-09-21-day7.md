## 今日考点
1. `Object` 给每个类白送的三个方法：`toString` / `equals` / `hashCode`
2. 默认行为：`toString` 返回 `类名@hashCode`；`equals` **比地址**；`hashCode` 由地址派生
3. 重写 `toString()` → 人能读懂 + 字符串拼接自动调用
4. 重写 `equals(Object o)`：四步（**自反 → null → 类型 → 强转后比字段**）
5. **🔴 今日最大陷阱**：`equals(Point o)` 是**重载**不是**重写**
   —— 代码看起来对，但 `obj1.equals(obj2)` 在声明类型为 `Object` 时永远走不到它
   —— 解法：**一律加 `@Override`**，让编译器抓笔误
6. 重写 `hashCode()` 的唯一规则：**equals 相等 → hashCode 必须相等**（反之不要求，叫哈希冲突）
7. **必须成对重写**：只写一个等于没写
8. `java.util.Objects`：`Objects.equals`（null 安全比较）、`Objects.hash`（组合哈希）、`String.valueOf`（null → "null"）
9. `HashSet` / `HashMap` 的工作方式：**hashCode 找桶 → equals 确认**
10. **`Object` vs `Objects`**：前者是所有类的父类（`equals`/`hashCode`/`toString` 从它继承来重写）；
    后者是 JDK 7 的工具类（`Objects.equals` / `Objects.hash` 静态调用）。**差一个 `s`，两个类。**
11. **字符串常量池**：字面量 `"abc"` 全程序只有一个对象 → `==` 会碰巧返回 `true`
    （`new String("abc")` 才是真正的两个对象）→ 这是 `==` 比 String 最毒之处
12. **NPE 的唯一触发条件**：在 `null` 上"点"（`.`）。**参数是 `null` 不会报错**，
    报不报错看方法内部怎么用它 —— 这正是 `Objects.equals` 只挡左边的理由

### 第 5 问的实测取证（探针 `_probe/Probe3.java`）
```
a=null,  a.equals(b)          -> java.lang.NullPointerException
d=null,  c.equals(d)          -> false
Objects.equals(null, "abc")   -> false
Objects.equals("abc", null)   -> false
```
**正确结论**：
> **NPE 只有一个触发条件 —— 在 `null` 上"点"（`.`）：调方法、取字段。**
> `null` 当**参数**传进来本身不报错，报不报错看方法内部怎么用它。
> `"abc".equals(null)` → `String.equals` 内部先 `instanceof` 判类型 → `false`，**不报错**。

**这也解释了 `Objects.equals` 为什么写成 `a == b || (a != null && a.equals(b))`** ——
它**只需要挡左边**（右边 `a.equals(null)` 本来就不炸）。
> 回看学员的 bug：`Objects.equals(this, o)` 的左边是 `this`，**永远不为 null** →
> 这道防线**形同虚设** → 直接放行到 `this.equals(o)` → 回到方法自己 → ♾️ 2560 帧。
> **防线挡错了一边，等于没有防线。**

## 追问记录

### 追问 A —— `Object` 与 `Objects` 混用
学员自述"这一次主要是使用 **object 类**的使用方法"。**差一个 `s`，是两个不同的类：**

| | `java.lang.Object` | `java.util.Objects` |
|---|---|---|
| 是什么 | **所有类的父类** | **JDK 7 的工具类** |
| 有什么 | `equals` / `hashCode` / `toString` / `getClass` | `equals` / `hash` / `hashCode` / `requireNonNull` |
| 怎么用 | `@Override` **继承来重写** | `Objects.xxx()` **静态调用** |

→ **Day 7 实际练的是两件事：① 重写 `Object` 的三个方法（继承+多态）；② 调用 `Objects` 的工具方法（静态工具类）。**
口诀：**`Object` 是爹，`Objects` 是工具箱。**

### 追问 B —— 「假绿」实证：`==` 比 String 也能全绿（教练自己踩出来的洞）
学员写 `Book.equals` 第 2 版时用了 `book.author == author`。
教练做探针（`_probe/Probe2.java`）验证：**该版本在原有 7 个测试下全 PASS。**

```
--- A) String 字段用 == 比，跑原有测试 ---
  PASS  equalsComparesValues
  PASS  notEqualsDifferentValues / 年份
  PASS  notEqualsDifferentValues / 作者
  PASS  equalsHandlesNullFields
  ^^ 全 PASS：== 的 bug 完全没被抓住

--- B) 同一个 == 版本，换成 new String 构造 ---
  FAIL  new String 版
```

**原因（`_probe/Probe.java` 实测）**：
```
literal   "LCX" == "LCX"                -> true      ← 字符串常量池
new       new String("LCX") == new ...  -> false     ← 真相
equals    c.equals(d)                   -> true
intern    c.intern() == a               -> true
```
**字符串字面量进常量池 → 同一个字面量全程序只有一个对象 → `==` 碰巧返回 true。**
**这就是 `==` 比 String 最毒的地方：在最普通的写法下它看起来完全正确。**

**处置（教练责任）**：`ValueUtilsTest` 早已用 `new String(...)` 刻意规避（注释："避免字符串常量池干扰"），
而 `BookTest` 漏了 —— **是我建测试时的漏洞**。已补第 8 个测试
`equalsHandlesEqualButDistinctStringInstances`，用 `new String(...)` 强制破池。146 → **147**。
