## 主题：Agent 调模型就是这个动作

### 一、JSON 就是「对象 ⇄ 字符串」

调 OpenAI / 通义 / 任何模型：请求体是 JSON，响应体也是 JSON。Java 侧标准工具是 **Jackson**（Spring Boot 内置）。

```
ObjectMapper              「翻译机」，线程安全，可复用
JsonProcessingException   受检异常 —— 解析失败必须处理（Day 15 的知识点复现）
```

### 二、★ record 天生能被 Jackson 处理（2.12+）

```java
record Point(int x, int y) {}
// 序列化 → {"x":1,"y":2}   组件名就是字段名，不需要 getter
```

能这样是因为 record 的访问器和构造器都带名字信息 —— Day 14 的东西直接用上。

### 三、★★ 未知字段默认**抛异常**（坑 1）

```java
record Point(int x, int y)
对方返回 {"x":1,"y":2,"z":3}
→ UnrecognizedPropertyException（JsonProcessingException 子类）
```

由 `DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES` 控制，**默认 true**。
线上真实事故形状：对方接口加了个字段，你的服务直接 500。

### 四、★★ 泛型擦除在这里复发（坑 2，今天最重要）

```java
mapper.readValue(json, List.class)                          → List<LinkedHashMap>   // 错
mapper.readValue(json, new TypeReference<List<Point>>(){})   → List<Point>           // 对
```

`List.class` 是擦除后的 Class 对象，里面没有 `Point`。
`TypeReference` 的原理是**匿名子类**：泛型信息写在子类签名里，运行期反射还能读到 —— 和 Day 14 的 `checkcast` 同一套机制。

### 五、★ HTTP：JDK 自带 HttpClient

```java
HttpClient client = HttpClient.newHttpClient();
HttpRequest request = HttpRequest.newBuilder(URI.create(url)).GET().build();
HttpResponse<String> resp = client.send(request,
        HttpResponse.BodyHandlers.ofString(StandardCharsets.UTF_8));
```

两个要点：
1. `send` 抛 `IOException` + `InterruptedException`（都是受检的）
2. 读 body **必须显式指定 UTF-8** —— `ofString()` 不带参数用默认编码

另外 JDK 21 起 `HttpClient` 实现了 `AutoCloseable`，可以 try-with-resources。

## 复盘问答（3 题，2 轮）

| # | 题 | 首答 | 补问 | 结果 |
|---|---|---|---|---|
| ① | `TypeReference` 凭什么拿得到 `Point`，`List.class` 为什么拿不到？ | ❌ **把两个坑合并**：「用了 list 那存入的 point 类型会擦除，抛出未知字段异常」—— `List.class` 根本不抛异常 | ❌ 补问「`List.class` 读出来的元素是什么类」答成 `TypeReference<List<Point>>`（答的是**怎么办**，不是**会变成什么**） | ❌ **未过 → 进 Day 21 闸门第 2 题** |
| ② | 未知字段异常的开关名；关掉有什么风险？ | ❌ 名称写成 `JsonProcessingException`（那是异常类）；且**方向反了**：「关掉的话多一个字段就会报错」 | ✅ 补问「默认是开着还是关着」答 **「开着」** | ✅ |
| ③ | `send` 抛哪两个受检异常？`InterruptedException` 为什么不能吞？ | 🟡 两个名字对（`IOException` / `InterruptedException`），「不清楚」为什么不能吞 | 讲解 | 🟡 |

**教练给的标准答案（题干用）**：

- **`List.class` 的后果**：不抛异常，元素全部退化成 `LinkedHashMap`；直到 `(Point) list.get(0)` 才在运行期 `ClassCastException`。
- **那对 `{}`**：创建**匿名子类**，`TypeReference<List<Point>>` 的泛型实参写进子类的 **`Signature` 属性**，运行期 `getClass().getGenericSuperclass()` 读得到；`List.class` 只有一个裸 Class 对象，签名里没有 `Point` —— Day 14 的擦除原封不动。
- **开关**：`DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES`，**默认 true**；关掉之后未知字段被**静默忽略**（比报错更难查）。
- **中断**：`interrupt()` 抛 `InterruptedException` 时**中断标志被清除**；吞掉等于把别人的中断请求吃掉，优雅停机/超时取消全部失效。规矩：往外抛，或 `Thread.currentThread().interrupt()` 恢复标志后转业务异常。

## 教练点评

1. **Q4 的错误形状值得记住**：三个方法同构，第四个就照抄 —— **按形状写代码，不按题意写代码**。这是 AI 辅助编码最常见的后遗症。
2. **「答案就在你自己文件的注释里」第三次复发**（Day 13、Day 19③、Day 20 Q4）。修 Q4 时他读了，说明**不是读不懂，是没形成习惯** → 已要求：动笔前先读完整个类注释。
3. **② 的错法是「方向反」**：默认开着（会抛）说成关掉（会抛）。这与「自相矛盾」同源 —— 结论和前提没对齐。
4. **① 的错法是「两个坑合并」**：他脑子里「泛型擦除 = 抛异常」是一件事，实际是两个完全不同的后果（一个抛、一个静默变形）。
5. **预测第 3 条答 `null`** 说明「擦除」在他那里还是「什么都没有」，没意识到**会退化成 Map 顶上**。
