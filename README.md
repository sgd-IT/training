## 三、三条铁律

### 铁律 1 —— 只改 TODO
> 只允许修改 `// TODO:` 标注的方法体。**测试文件、其他代码一律不许动。**
> 测试是"需求说明书"，改了测试就等于改题目。

### 铁律 2 —— 练习期间不问 AI
> 卡住时按顺序走：**先读测试 → 再读报错（至少 5 分钟）→ 仍卡住才允许求助。**
> **查 API 之后必须手抄重打一遍，不许复制粘贴。**
> （这条是整套训练的核心目的，其他都是为它服务的。）

#### ⚠️ "查 API" 的边界（2026-09-24 补充 · Day 8 实证）

> **✅ 允许**：你知道有这个方法、也用过，只是**想不起签名/参数顺序** → 查，然后手抄重打。
> **❌ 禁止**：你**根本不知道它存在**，搜索出来直接抄上去 → 这叫**学习**，不叫查 API。

**判据一句话：你是在「找回」一个会的东西，还是在「绕过」一个不会的东西？**

**实证（Day 8）**：学员在 `ShapeBook` 里写了 `mapToDouble` / 方法引用 `Shape::area` /
`Collectors.joining(", ")` —— 这些是 **Day 17–18** 的内容，**从没学过**，不属于"忘记"。
**而受害者是学员自己**：

| | `describeAll` 的分隔符问题 | 结果 |
|---|---|---|
| **Day 6** | 自己想出来的（`Zoo.describeAll`） | 改了 **4 遍** → 痛，**但学到了** |
| **Day 8** | 搜出 `Collectors.joining(", ")` 直接抄 | 一次就绿 → 不痛，**什么也没学到** |

> **搜索 / AI 的机制，就是让你绕过那个"痛"的环节 —— 而痛正是学习发生的地方。**
> 这也是"每个中间件都配手写底层练习"（§七）的同一个逻辑：
> **没有"能跑就算对"这回事。**

### 铁律 3 —— 伪代码先行
> 每题**先在文件顶部写 3–5 行注释版伪代码**，再动手写实现。
>
> **2026-09-17 修订（不阻塞版）**：伪代码写在文件里即可，**不必等教练确认就能动手**。
> 教练在检查时一并看。
> 原因：原规则"贴给教练、确认后再写"会卡住节奏，与"不断更、保手感"冲突；
> 而规则的目的（先想再打）不依赖往返确认。

## 四、每日 1 小时流程

| 时间 | 环节 | 内容 |
|---|---|---|
| 0–5 min | **复盘** | 回顾上次的错题与追问结论 |
| 5–40 min | **主练习** | 手敲。卡住也别跳，先自己撞 |
| 40–50 min | **卡点求助** | 把"卡在哪、试过什么"说清楚再问 |
| 50–60 min | **审阅 + 追问** | 跑测试 + 教练点评 + 概念追问 |
| 收尾 | **提交** | **教练把本次所有改动 `git commit`** —— 见下方硬规矩 |

> ### 🔴 硬规矩：**有修改就提交**（2026-09-17 学员要求）
>
> **任何一次文件新增/修改之后，立刻 `git commit`。不攒批量，不等"告一段落"。**
>
> - 教练负责执行：每写完日志 / 脚手架 / README 更新，**当次就提交**
> - 学员在 IDEA 里也可随时提交（`Ctrl+K`）
> - **双保险**：git 保历史，IDEA Local History 保"未提交时的临时改动"
>
> **为什么定这条**：2026-09-17 教练误判文件损坏并删除原 `README.md`，
> 当时仓库刚建、**尚无提交**，导致原文件无从恢复（详见第十二节）。
> **有提交，就有后悔药；没有提交，一次误判就是永久损失。**

## 七、贯穿全课的主线：**每个中间件都配一个"手写底层"练习**

中间件本质是"**用库**"——直接学必然退化成抄代码。所以每个专题都配上手写练习：

| 专题 | 手写什么 | 练到什么 | AI 能帮吗 |
|---|---|---|---|
| 线程池 | **手写迷你线程池** | core/max/队列/拒绝策略的真实语义 | ❌ 帮不了 |
| 并发/异步 | 手写 `Future` 回调链 | 异步的本质 | ❌ 帮不了 |
| **Spring** | **手写迷你 IOC 容器 + 手写动态代理切面** | 反射、注解、Bean 生命周期、AOP 的本质 | ❌ 帮不了 |
| 集合 | **手写迷你 `ArrayList`**（Day 9） | 扩容、`size` vs `capacity`、迭代器 `modCount` | ❌ 帮不了 |
| **协议**（Day 19，**三合一** 🆕） | **手写 RESP + AMQP 帧 + MQTT 报文** | 帧结构、长度前缀、**大端序**、**变长整数**、`byte` 有符号与 `& 0xFF` | ❌ 帮不了 |
| **AI Agent** 🆕 | **手写余弦相似度 + 暴力 top-k 检索**、**手写 Tool 路由表 / ReAct 循环**、**手写 SSE 分帧** | 向量检索的**机制**、工具调用的分发与结果回填、流式分帧 | ❌ 帮不了 |
| **前端** 🆕 | **手写 Axios 封装 + 请求/响应拦截器** | 请求生命周期、错误与令牌的统一处理 | ❌ 帮不了 |

> **2026-10-09 学员决定**：RESP / AMQP 帧 / MQTT 报文原本各占一天，
> **合并为 1 天（Day 19）** —— 三者共性大于差异（都是"帧 / 长度前缀 + 大端序 + 变长整数"），
> 一起学反而更容易看出套路，同时省下 2 天。
> MQTT 的**客户端实验台**仍单独占 1 天（Day 50，用现成库真跑起来，不手写报文）。

**共同点：没有"能跑就算对"这回事**——只有一个 `byte[]`（或一个线程池状态）和一个期望值。
抄来的代码错了，你看不出来。**这是反 AI 依赖的核心手段。**

#### 📌 Phase 3「线程池配置清单」（2026-09-17 新增）

**必须刻进脑子的一条 —— 任务提交后的执行顺序：**
```
① 核心线程没满 → 新建核心线程
② 核心满了    → 进队列排队
③ 队列满了    → 新建非核心线程（直到 maximumPoolSize）
④ 最大也满了  → 触发拒绝策略
```
> ⚠️ **经典坑**：用 `LinkedBlockingQueue`（默认无界）时，**队列永远填不满**，
> 于是 `maximumPoolSize` **形同虚设**，非核心线程根本不会创建。

**七参数**：`corePoolSize` / `maximumPoolSize` / `keepAliveTime` / `unit` /
`workQueue` / `threadFactory` / `handler`

**队列选型**：`ArrayBlockingQueue`（有界）/ `LinkedBlockingQueue`（可无界 ⚠️）/
`SynchronousQueue`（不排队）/ `PriorityBlockingQueue`

**四种拒绝策略**：`AbortPolicy`（默认，抛异常）/ `CallerRunsPolicy`（调用方执行，天然降速）/
`DiscardPolicy`（静默丢弃 ⚠️）/ `DiscardOldestPolicy`

**怎么配**：CPU 密集 vs IO 密集；为什么要自定义 `threadFactory`（给线程起名，方便排查）
**为什么阿里规范禁用 `Executors.newFixedThreadPool`**（无界队列 → OOM）
**监控**：`getActiveCount` / `getQueue().size()` / 活跃度告警

#### 📌 Phase 3「异步专题」要点

- `CompletableFuture`：`supplyAsync` / `thenApply` / `thenCompose` / `allOf` / `exceptionally`
- **默认 `ForkJoinPool.commonPool()` 的坑** → 业务异步必须传自定义线程池
- `@Async` + 自定义 `ThreadPoolTaskExecutor`（企业里最常见的用法）
- **异步里抛的异常会"消失"**（经典坑）
- 异步 + `@Transactional` 的坑（异步方法里事务不生效）

**为什么三合一反而更好**：三个协议看着毫不相干，**字节层是同一套东西**——

| 共性 | RESP | AMQP 0-9-1 | MQTT |
|---|---|---|---|
| **前缀标明长度 / 类型** | `$5\r\n` | `type(1)+channel(2)+size(4)` | 固定头 + Remaining Length |
| **大端序** | 少 | 有 | 全部多字节整数 |
| **变长整数** | 少 | 有（字段表） | Remaining Length（每字节低 7 位 + 续接位） |
| **结束标记** | `\r\n` | `frame-end = 0xCE` | —— |

放一起练，**套路一眼就出来**，比分开三次各学一遍更省力。

**要练到的硬骨头：**
- **位运算**：`>>`、`&`、`|` —— 拆字节、拼字节
- **`byte` 是有符号的**：`0xFF` 实际是 `-1`，转 `int` 必须 `& 0xFF`（经典坑）
- **可变长度整数**：每字节低 7 位存数据，最高位当"还有后续"标志
  - `64` → `0x40`；`128` → `0x80 0x01`；`321` → `0xC1 0x02`
- **大端序**：网络字节序
- `byte[]` ↔ `String` 的 UTF-8 编解码

### ⚠️ 读取路径陷阱（2026-09-17 踩坑，务必牢记）

> **本环境下，PowerShell 的 .NET 文件读取不可信。**

| 读取方式 | 可信度 | 说明 |
|---|---|---|
| **DSH `read` / `grep` 工具** | ✅ 可信 | 首选 |
| **`cmd /c type` / `cmd /c dir`** | ✅ 可信 | 独立进程，绕过被 hook 的 .NET API |
| **`git hash-object` / `git diff`** | ✅ 可信 | 内容级比对，判定"文件是否真被改动"的**权威手段** |
| `[System.IO.File]::ReadAllBytes()` | ❌ **不可信** | 对某些文件返回乱码 + 约 10 倍大小 |
| `Get-Content` / `Get-Item.Length` | ❌ **不可信** | 同上，会报出错误的大小与乱码内容 |

**踩坑经过**：2026-09-17，教练用 `.NET ReadAllBytes` 检查 `README.md`，
得到乱码与异常大小，遂判定"文件损坏不可恢复"，**删除并重建**。
事后核验发现：**同目录下其它文件用同样方法读也全是乱码，但实际全部完好**
（`git hash-object` 逐文件比对，62 个文件中仅 `README.md` 有差异，且那正是本次合法编辑）。

### 📌 由此确立的三条硬规矩

1. **判定"文件是否损坏"，只认 `git hash-object` / `git diff`**，绝不凭 PowerShell 的 .NET 读取下结论。
2. **疑似损坏时，先用 `cmd /c type` 复核**，再动手；**永远先备份，不要先删**。
3. **重大文件必须先进 git**——本次侥幸未造成实质损失，靠的正是当天刚做的首次提交
   （`git fsck` 干净、HEAD 内容完好，随时可恢复）。
   **"先提交再动手"从此是硬规矩。**

### 📌 第 4 条硬规矩：有修改就提交（2026-09-17 学员要求）

> **任何一次文件新增/修改之后，立刻 `git commit`。不攒批量，不等"告一段落"。**

**执行细则**：

| 场景 | 动作 |
|---|---|
| 写完当日训练日志 | 立即提交 |
| 搭好新一天脚手架（新 stub + 测试） | 立即提交 |
| 更新 README / 排期 | 立即提交 |
| 学员做完练习、教练改动了任何文件 | 立即提交 |
| 学员在 IDEA 里改了自己的代码 | 学员自行 `Ctrl+K` 提交（教练也会在下次检查时补提交） |

**提交信息规范**：一句话说清"改了什么、为什么"，中文即可。

**双保险**：
- **git** —— 保全部历史，跨机器可恢复
- **IDEA Local History**（`右键 → Local History → Show History`）—— 保"还没提交时的临时改动"，**与 git 无关，独立生效**

**立此规矩的原因**：2026-09-17 教练误判文件损坏并删除原 `README.md`；
当时仓库刚建、**尚无任何提交**，原文件无从恢复。
**有提交，就有后悔药；没有提交，一次误判就是永久损失。**

### 📌 第 5 条硬规矩：先预测，再跑（2026-09-23 学员选定制）

> **写完一个方法，先在它上方写 1 行预测，然后跑测试。预测错了必须停下来问"为什么"，不许直接改代码重跑。**

```java
// 预测：内容相同的两个 Book → true ；b.equals(null) → false ；b.equals("x") → false
public boolean equals(Object o) { ... }
```

| 跑完 | 动作 |
|---|---|
| 预测 ✅ | 过 |
| 预测 ❌ | **停下找原因**（读报错 / 读栈帧 / 查 JDK 源码），**严禁"改一版再跑跑看"** |

**成本**：约 10 秒/方法。

**这条规矩的由来（演进过程，记录在案）**：

| 日期 | 规则 | 结果 |
|---|---|---|
| 2026-09-17 | 伪代码先行（贴给教练确认后才动手） | 连续 4 次未执行 → 改为不阻塞版 |
| 2026-09-17 | 伪代码先行（不阻塞版，写在文件里） | 仍流于形式 |
| 2026-09-21 | **两轮推演**（每个方法 4 条完整推演写进注释） | 学员判定"太浪费时间"，写成了"代码翻译"（复述代码意图），未执行 |
| **2026-09-23** | **先预测，再跑**（1 行/方法） | 教练砍掉 3/4 成本，学员选定制 —— 现行 |

**为什么必须是"预测"而不是"读一遍"**：Day 7 已用学员自己的 bug 实证 ——
`Objects.equals(this, o)` 这一行，配上一句"比较 this 和 o 是否是同一个对象"的注释，
**读一百遍都挑不出毛病**，而它炸了 2560 个栈帧。
**"代码翻译"复述的是意图，"读一遍"检查的也是意图 —— 两者在原理上都不可能发现"实现 ≠ 意图"。**
只有**把具体值代进去跑**（人脑推演 或 先写预测再跑测试）才能暴露。

### 📌 第 6 条硬规矩：交付前自己先跑绿（2026-09-28 立）
